# Numeric types

## INT / INTEGER

**Use:** whole numbers (counts, IDs when range fits).
32-bit signed integer (range: -2,147,483,648 to 2,147,483,647 in most systems).

**Example:**

```sql
CREATE TABLE users_int (
  id INT PRIMARY KEY,
  age INT
);
INSERT INTO users_int VALUES (1, 29);
```

**Notes:** Use `SMALLINT` (smaller range) or `BIGINT` (larger range) depending on expected max value.

## SMALLINT, TINYINT, BIGINT

**Use:** conserve space (`TINYINT` in MySQL for 0–255 or -128–127, `BIGINT` for very large counts).

**Example:**

```sql
CREATE TABLE counters (
  tiny TINYINT,     -- MySQL
  small SMALLINT,
  big BIGINT
);
INSERT INTO counters VALUES (255, 32000, 9223372036854775807);
```

## DECIMAL(p,s) / NUMERIC(p,s)

**Use:** exact fixed-point decimals (money, financial calculations). `p` = precision, `s` = scale.

**Example:**

```sql
CREATE TABLE invoice (
  id INT,
  total DECIMAL(12,2)   -- up to 9999999999.99
);
INSERT INTO invoice VALUES (1, 1999.95);
```

**Notes:** Use for currency where rounding errors from floats are unacceptable.

- In SQL Server, PostgreSQL, and MySQL, `DECIMAL` and `NUMERIC` are functionally identical — they are synonyms.

> **Note:**
> Precision in a decimal data type refers to the total number of digits that can be stored, both to the left and right
> of the decimal point. Scale refers to the number of digits allowed to the right of the decimal point.

For example, a decimal defined as `DECIMAL(10,2)` has:

- **Precision = 10:** up to 10 total digits.
- **Scale = 2:** up to 2 digits after the decimal point.

## FLOAT / REAL / DOUBLE PRECISION

**Use:** approximate floating-point numbers (scientific calculations, measurements).

**Example:**

```sql
CREATE TABLE measurements (
  temp REAL,
  lat DOUBLE PRECISION
);
INSERT INTO measurements VALUES (36.6, 12.3456789);
```

**Caution:** Not suitable for currency due to rounding/precision issues.

### 1️⃣ REAL (SQL)

- 4 bytes (32-bit)
- ~ 7 decimal digits precision
- Approximate type

Equivalent to: `FLOAT(24)` in SQL Server

**Example (SQL Server)**

```sql
CREATE TABLE TestReal (
    Value REAL
);

INSERT INTO TestReal VALUES (123.456789);
```

### 2️⃣ FLOAT (SQL Server)

In SQL Server, `FLOAT` supports precision:

```sql
FLOAT(n)
```

Where:

- `n` = number of bits of precision
- 1–24 → 4 bytes (like `REAL`)
- 25–53 → 8 bytes (like `DOUBLE`)

**Examples**

```sql
FLOAT(24)   -- 4 bytes
FLOAT(53)   -- 8 bytes (default)
FLOAT       -- same as FLOAT(53)
```

### 3️⃣ DOUBLE PRECISION

This depends on the database system.

✅ **MySQL / PostgreSQL**

```sql
DOUBLE PRECISION
```

- 8 bytes
- ~15–16 digits precision

❌ **SQL Server**

SQL Server does not support `DOUBLE PRECISION`.

Instead, use:

```sql
FLOAT(53)
```

# Character / Text types

## CHAR(n) (fixed-length)

**Use:** short codes of fixed length (country codes, status codes).

## VARCHAR(n) (variable-length)

**Use:** typical strings such as names, emails.

**Example:**

```sql
CREATE TABLE employees (
  id INT,
  code CHAR(2) PRIMARY KEY, -- 'IN', 'US'
  email VARCHAR(255)
);
INSERT INTO employees VALUES (1,'Aman Kumar','aman@example.com');
```

- `CHAR(2)` always stores exactly 2 bytes/characters (padded).
- If no max is needed, some DBs support `VARCHAR` without length or `TEXT`.

## TEXT / CLOB

**Use:** very large text (articles, logs).

**Example:**

```sql
CREATE TABLE posts (
  id SERIAL PRIMARY KEY,
  body TEXT
);
INSERT INTO posts (body) VALUES ('Very long article...');
```

**Notes:** In some DBs `TEXT` has no length limit; performance and indexing differ by engine.

# Binary / Blob types

## BINARY / VARBINARY / BLOB

**Use:** images, files, encrypted blobs.

**Example:**

```sql
CREATE TABLE files (
  id INT,
  data BLOB,
  filename VARCHAR(255)
);
-- Insert: use parameterized driver APIs to send binary content
```

**Tip:** Often better to store files in object storage and keep URLs in DB.

# Boolean

## BOOLEAN / BOOL

**Use:** true/false flags (`is_active`, `is_verified`).

**Example:**

```sql
CREATE TABLE tokens (
  id INT,
  active BOOLEAN
);
INSERT INTO tokens VALUES (1, TRUE);
```

SQL Server historically used `BIT` (0/1).

# Date & Time types

## DATE

**Use:** calendar dates (birthdate, event date).

**Example:**

```sql
CREATE TABLE events (
  id INT,
  event_date DATE
);
INSERT INTO events VALUES (1, '2026-02-17');
```

## TIME and TIME WITH TIME ZONE

**Use:** time-of-day values.

**Example:**

```sql
CREATE TABLE shifts (start_time TIME);
INSERT INTO shifts VALUES ('09:00:00');
```

## TIMESTAMP / TIMESTAMP WITH TIME ZONE

**Use:** precise moments in time (`created_at`, `updated_at`). Use timezone-aware type for global apps.

**Example:**

```sql
CREATE TABLE audit (
  id SERIAL PRIMARY KEY,
  created_at TIMESTAMP WITH TIME ZONE DEFAULT now()
);
INSERT INTO audit DEFAULT VALUES;
```

**Notes:** PostgreSQL `TIMESTAMPTZ` stores timezone; MySQL `TIMESTAMP` has its own semantics.

## INTERVAL (Postgres)

**Use:** durations (e.g., "2 hours 30 minutes").

**Example:**

```sql
SELECT now() + INTERVAL '2 hours';
```

**Example 1 – Adding interval**

```sql
SELECT NOW() + INTERVAL '5 days';
```

**Example 2 – Subtracting interval**

```sql
SELECT NOW() - INTERVAL '2 hours';
```

**Example 3 – Column with INTERVAL type**

```sql
CREATE TABLE tasks (
    task_name TEXT,
    duration INTERVAL
);
```

- In Microsoft SQL Server, `INTERVAL` does NOT exist.

Instead use:

**Add time**

```sql
SELECT DATEADD(DAY, 5, GETDATE());
```

- In Oracle Corporation MySQL, `INTERVAL` is not a data type, but used in date functions.

**Example – Add interval**

```sql
SELECT DATE_ADD(NOW(), INTERVAL 5 DAY);
```

## DATETIME2

In SQL Server, `DATETIME2` is the modern, recommended data type for storing date and time values. Here's why it's preferred:

**Key Features:**

- **Range:** 0001-01-01 through 9999-12-31 (much wider than `DATETIME`, which starts at 1753).
- **Precision:** Up to 7 fractional seconds (100 nanoseconds). You can choose precision from 0 to 7.
- **Storage:** Between 6 and 8 bytes depending on precision (often smaller than `DATETIME`, which always uses 8 bytes).
- **Standard compliance:** Aligns better with the SQL standard for date/time types.

**Example:**

```sql
CREATE TABLE Orders (
    OrderID INT PRIMARY KEY,
    OrderDate DATETIME2(3) -- precision to milliseconds
);
```

- `DATETIME2(0)` → stores only seconds.
- `DATETIME2(3)` → milliseconds precision.
- `DATETIME2(7)` → full precision (100 ns).

# UUID / GUID

## UUID (Postgres) / UNIQUEIDENTIFIER (SQL Server)

**Use:** globally unique identifiers (distributed systems).

**Example:**

```sql
CREATE TABLE orders (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  total DECIMAL(10,2)
);
INSERT INTO orders (total) VALUES (49.99);
```

**Notes:** Use when you need uniqueness across systems; index size is larger than `INT`.

### Declaring UNIQUEIDENTIFIER

```sql
CREATE TABLE Users (
    Id UNIQUEIDENTIFIER PRIMARY KEY,
    Name NVARCHAR(100)
);
```

### Generating GUIDs in SQL Server

#### 1️⃣ NEWID()

Generates random GUID.

```sql
SELECT NEWID();
```

Insert example:

```sql
INSERT INTO Users (Id, Name)
VALUES (NEWID(), 'Aman');
```

#### 2️⃣ NEWSEQUENTIALID()

Generates sequential GUID (better for indexing performance).

```sql
CREATE TABLE Orders (
    Id UNIQUEIDENTIFIER DEFAULT NEWSEQUENTIALID(),
    OrderName NVARCHAR(100)
);
```

> ⚠️ Can only be used as `DEFAULT` constraint.

# JSON / Semi-structured

## JSON, JSONB (Postgres)

**Use:** flexible document storage, event payloads, metadata.

**Example:**

```sql
CREATE TABLE products (
  id SERIAL PRIMARY KEY,
  attrs JSONB   -- searchable & indexable in Postgres
);
INSERT INTO products (attrs) VALUES ('{"color":"red","size":"M"}');
```

**Notes:** `JSONB` is binary, indexable, faster for querying in Postgres. MySQL supports JSON with functions; SQL Server
has JSON functions but not a native JSON type (stored as `NVARCHAR`).

# ENUM (dialect-specific)

## ENUM (MySQL / Postgres via check/type)

**Use:** constrained set of values (status: `'open'`, `'closed'`, `'pending'`).

**Example (MySQL):**

```sql
CREATE TABLE tickets (
  id INT,
  status ENUM('open','pending','closed')
);
INSERT INTO tickets VALUES (1, 'open');
```

### Postgres alternative

`CREATE TYPE status AS ENUM (...)` or use `VARCHAR` + `CHECK` constraints.

### In Microsoft SQL Server, ENUM does not exist

Instead, use one of these approaches:

✅ **Option 1 – CHECK Constraint (Simple & Common)**

```sql
CREATE TABLE Users (
    Id INT PRIMARY KEY IDENTITY,
    Name NVARCHAR(100),
    Status NVARCHAR(20)
        CHECK (Status IN ('Active', 'Inactive', 'Pending'))
);
```

- ✔ Simple
- ✔ Good for small fixed lists

# Arrays

## Arrays

An array stores multiple values in a single column.

> ⚠️ **Important:** Not all SQL databases support arrays directly.

## In PostgreSQL Global Development Group PostgreSQL, arrays are fully supported

📌 **Declaring an Array Column**

```sql
CREATE TABLE students (
    id SERIAL PRIMARY KEY,
    name TEXT,
    marks INT[]
);
```

## Arrays in SQL Server

In Microsoft SQL Server, arrays are NOT supported.

❌ **Wrong Way (Don't do this)**

```sql
Marks NVARCHAR(100)  -- storing "85,90,78"
```

This breaks normalization.

✅ **Correct Way (Relational Model)**

Instead of array, create a related table.

```sql
CREATE TABLE Students (
    Id INT PRIMARY KEY IDENTITY,
    Name NVARCHAR(100)
);

CREATE TABLE StudentMarks (
    StudentId INT FOREIGN KEY REFERENCES Students(Id),
    Mark INT
);
```

Insert:

```sql
INSERT INTO Students (Name) VALUES ('Aman');

INSERT INTO StudentMarks VALUES (1, 85);
INSERT INTO StudentMarks VALUES (1, 90);
INSERT INTO StudentMarks VALUES (1, 78);
```

- ✔ Scalable
- ✔ Query friendly
- ✔ Follows normalization

# Auto-Increment / Sequence in SQL

Used to generate unique incremental numbers automatically, typically for primary keys.

## IDENTITY & SEQUENCE

In Microsoft SQL Server, you have two main options:

### 🔹 A) IDENTITY (Most Common)

Automatically increments when inserting.

```sql
CREATE TABLE Users (
    Id INT IDENTITY(1,1) PRIMARY KEY,
    Name NVARCHAR(100)
);
```

🔎 **Meaning of IDENTITY(1,1)**

```text
IDENTITY(seed, increment)
IDENTITY(1,1) → start at 1, increment by 1
```

Insert:

```sql
INSERT INTO Users (Name) VALUES ('Aman');
```

SQL automatically generates:

```text
Id = 1
```

⚠️ **Important Behavior**

- Cannot manually reuse deleted IDs
- Gaps may occur (rollback, server restart)
- Bound to one table only

### 🔹 B) SEQUENCE (More Flexible)

Introduced in SQL Server 2012.

```sql
CREATE SEQUENCE UserSeq
    START WITH 1
    INCREMENT BY 1;
```

Use it:

```sql
INSERT INTO Users (Id, Name)
VALUES (NEXT VALUE FOR UserSeq, 'Rahul');
```

✅ **Why SEQUENCE is Powerful**

- Can be shared across multiple tables
- Can control increment, min, max, cycle
- Better for advanced systems

## MySQL — AUTO_INCREMENT

In Oracle Corporation MySQL:

```sql
CREATE TABLE Users (
    Id INT AUTO_INCREMENT PRIMARY KEY,
    Name VARCHAR(100)
);
```

Auto increments automatically.

## PostgreSQL — SERIAL & SEQUENCE

In PostgreSQL Global Development Group PostgreSQL:

**SERIAL (Shortcut)**

```sql
CREATE TABLE Users (
    Id SERIAL PRIMARY KEY,
    Name TEXT
);
```

`SERIAL` automatically creates a sequence behind the scenes.

## 🎯 Production Advice (Important for You)

Since you're aiming for production-ready backend systems:

✅ **Use IDENTITY when:**

- Simple primary keys
- Single-table auto increment
- Standard CRUD app

✅ **Use SEQUENCE when:**

- Need shared numbering (InvoiceNo, OrderNo)
- Custom increment logic
- High-performance systems

# Deprecated Types (Avoid in new systems)

- `TEXT`
- `NTEXT`
- `IMAGE`
- `TIMESTAMP` (Use `ROWVERSION`)
- `DATETIME` (Prefer `DATETIME2`)

# TIMESTAMP vs ROWVERSION

- `TIMESTAMP` in SQL Server is misleadingly named — it does not store date/time values.
- Instead, it stores a binary counter that changes whenever a row is updated.
- Because of the confusion, Microsoft renamed it to `ROWVERSION` (they are functionally identical).

**Why prefer ROWVERSION?**

- The name clearly reflects its purpose: tracking row changes.
- Avoids confusion with actual date/time data types.
- `TIMESTAMP` is deprecated, so `ROWVERSION` is the future-proof choice.

# NULL vs empty vs 0

Let's clearly separate:

```text
NULL ≠ '' (empty string) ≠ 0
```

They mean completely different things.

## 1️⃣ NULL

### 🔹 Meaning

No value / Unknown / Not applicable

- It does NOT mean zero.
- It does NOT mean empty.
- It means value is missing or not provided.

**Example**

```sql
CREATE TABLE Users (
    Id INT,
    MiddleName NVARCHAR(50) NULL
);

INSERT INTO Users VALUES (1, NULL);
```

### Important Behavior

```sql
SELECT * FROM Users WHERE MiddleName = NULL;   -- ❌ Wrong
SELECT * FROM Users WHERE MiddleName IS NULL;  -- ✅ Correct
```

### Key Points

- `NULL` is not equal to anything (even `NULL`)
- Arithmetic with `NULL` returns `NULL`

```sql
SELECT 10 + NULL;  -- NULL
```

## 2️⃣ Empty String ('')

### 🔹 Meaning

Value exists but contains no characters

```sql
INSERT INTO Users VALUES (2, '');
```

This means:

- The column has a value
- That value is an empty string
- It is NOT missing

### Check for Empty

```sql
SELECT * FROM Users WHERE MiddleName = '';
```

## 3️⃣ Zero (0)

### 🔹 Meaning

Actual numeric value

```sql
CREATE TABLE Orders (
    Quantity INT
);

INSERT INTO Orders VALUES (0);
```

This means:

- Quantity is explicitly zero
- It is NOT missing

# VARCHAR vs NVARCHAR

- **VARCHAR:** Stores non-Unicode character data, typically using the ASCII character set. It's suitable for languages that don't require special characters, like English.
- **NVARCHAR:** Stores Unicode character data (using UTF-16), enabling support for virtually all written languages, including Chinese, Japanese, Korean, and special symbols or emojis.

## Storage Size

- **VARCHAR:** Uses 1 byte per character.
- **NVARCHAR:** Uses 2 bytes per character (or more for certain Unicode ranges), consuming approximately double the storage space for the same text.

## Maximum Length

- **VARCHAR:** Can store up to 8,000 characters (or `VARCHAR(MAX)` for larger data).
- **NVARCHAR:** Can store up to 4,000 characters (or `NVARCHAR(MAX)` for larger data).
