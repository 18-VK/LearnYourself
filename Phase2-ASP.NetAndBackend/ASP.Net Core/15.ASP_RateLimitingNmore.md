# Rate Limiting

Rate limiting controls how many requests a client can make to a service within a given time window. It protects APIs from abuse, prevents overload, and ensures fair usage across clients.

Watch this: https://youtu.be/mQCJJqUfn9Y

## Common Algorithms

### Fixed Window

Count requests in fixed time blocks (for example, per minute). The counter resets at each interval boundary. This is simple, but bursts near window edges can allow up to 2x the limit through (for example, 100 requests at 0:59 and 100 more at 1:00).

Pros:

- Very simple to implement and understand
- Low memory footprint (just a counter and timestamp per client)
- Cheap to compute; good for high-throughput systems

Cons:

- Edge burst problem — up to 2x the limit can slip through at window boundaries
- Not truly fair over time — traffic is not smoothed

### Sliding Window

Tracks requests over a rolling time period instead of fixed blocks, smoothing out the edge-burst problem.

Pros:

- Fixes the boundary-burst issue and provides smoother enforcement
- Fairer distribution of allowed requests over time
- Still relatively simple, especially with sliding window counters

Cons:

- More memory and compute than fixed window
- Slightly more complex to implement, especially in a distributed system

### Token Bucket

A bucket holds tokens (capacity = burst limit). Tokens refill at a fixed rate. Each request consumes a token; if the bucket is empty, the request is rejected or delayed.

This allows short bursts while enforcing a long-term average rate. It is very common in production APIs; AWS and Stripe use variants of it.

Pros:

- Allows controlled bursts while still enforcing a long-term average rate
- Flexible — you can tune bucket size and refill rate independently
- Industry-proven; a good default choice for most APIs

Cons:

- Slightly more complex to reason about than fixed window
- Bursts, though bounded, can still stress downstream systems briefly
- Requires careful tuning to avoid letting too much or too little through

### Leaky Bucket

Requests queue up and are processed at a constant outflow rate regardless of burst size, smoothing traffic instead of allowing bursts.

Pros:

- Produces a constant, predictable outflow rate
- Great for protecting downstream systems that cannot handle spiky traffic
- Smooths bursts completely rather than only bounding them

Cons:

- No burst tolerance — legitimate momentary spikes get queued or delayed
- Requests can pile up under sustained load, increasing latency
- Queue management adds complexity

### Rule of Thumb

Token bucket is the most commonly used pattern in production APIs because it balances flexibility and burst tolerance. Use leaky bucket when you need strict constant throughput to protect a fragile downstream system. Use sliding window when precision matters more than raw performance. Fixed window is fine for simple or internal use cases where perfect accuracy is not critical.

# Implementing Rate Limiting in .NET

ASP.NET Core has built-in rate limiting since .NET 7 via `Microsoft.AspNetCore.RateLimiting`. For single-instance apps, no third-party package is required.

## 1. Basic Setup

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddRateLimiter(options =>
{
    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;

    options.OnRejected = async (context, token) =>
    {
        context.HttpContext.Response.Headers["Retry-After"] = "60";
        await context.HttpContext.Response.WriteAsync(
            "Too many requests. Please try again later.", token);
    };
});

var app = builder.Build();
app.UseRateLimiter();
app.Run();
```

## 2. All Four Limiter Types

```csharp
builder.Services.AddRateLimiter(options =>
{
    // Fixed Window
    options.AddFixedWindowLimiter("fixed", opt =>
    {
        opt.PermitLimit = 10;
        opt.Window = TimeSpan.FromSeconds(60);
        opt.QueueProcessingOrder = QueueProcessingOrder.OldestFirst;
        opt.QueueLimit = 2;
    });

    // Sliding Window
    options.AddSlidingWindowLimiter("sliding", opt =>
    {
        opt.PermitLimit = 10;
        opt.Window = TimeSpan.FromSeconds(60);
        opt.SegmentsPerWindow = 4;   // divides window into 4 sub-segments
        opt.QueueLimit = 2;
    });

    // Token Bucket
    options.AddTokenBucketLimiter("token", opt =>
    {
        opt.TokenLimit = 20;
        opt.TokensPerPeriod = 5;
        opt.ReplenishmentPeriod = TimeSpan.FromSeconds(10);
        opt.AutoReplenishment = true;
        opt.QueueLimit = 2;
    });

    // Concurrency Limiter (not rate over time, but limits parallel requests)
    options.AddConcurrencyLimiter("concurrency", opt =>
    {
        opt.PermitLimit = 5;
        opt.QueueLimit = 10;
    });
});
```

## 3. Per-User / Per-IP Limiting (Partitioned)

This is the version you will usually want in real APIs: limit per client, not globally.

```csharp
builder.Services.AddRateLimiter(options =>
{
    options.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(context =>
    {
        var key = context.User.Identity?.IsAuthenticated == true
            ? context.User.Identity.Name!
            : context.Connection.RemoteIpAddress?.ToString() ?? "anonymous";

        return RateLimitPartition.GetTokenBucketLimiter(key, _ => new TokenBucketRateLimiterOptions
        {
            TokenLimit = 20,
            TokensPerPeriod = 5,
            ReplenishmentPeriod = TimeSpan.FromSeconds(10),
            AutoReplenishment = true,
            QueueLimit = 0
        });
    });
});
```

Now each user or IP gets their own bucket instead of sharing one global limit.

Let's break this down piece by piece. This is the global, per-client partitioned limiter pattern, and there is a lot packed into these few lines.

1. `options.GlobalLimiter = ...`

Unlike named policies such as `AddTokenBucketLimiter("token", ...)`, which only apply when you explicitly attach them via `.RequireRateLimiting("token")` or `[EnableRateLimiting]`, `GlobalLimiter` runs automatically on every request that hits the app. It is checked by the middleware unconditionally, in addition to any named policy that the endpoint might also have.

2. `PartitionedRateLimiter.Create<HttpContext, string>(...)`

```csharp
PartitionedRateLimiter.Create<HttpContext, string>(context => { ... })
```

This is a factory that produces a separate, independent rate limiter per partition key instead of one global counter shared by everyone.

- `<HttpContext, string>` — generic type parameters. `HttpContext` is the input type (what gets inspected per request), and `string` is the partition key type (what distinguishes one client from another).
- The lambda you pass in is called once per incoming request. Its job is only to extract or compute the key. It does not do the rate limiting itself.

Think of it as: "here is how to figure out which bucket this request belongs to." The actual limiting logic is defined separately in step 4.

3. The key-extraction lambda

```csharp
var key = context.User.Identity?.IsAuthenticated == true
    ? context.User.Identity.Name!
    : context.Connection.RemoteIpAddress?.ToString() ?? "anonymous";
```

This decides who counts as one client:

- If the request is authenticated, use the username as the key.
- If not authenticated, fall back to the IP address as the key.
- If even the IP is null, fall back to the literal string `"anonymous"`.

The `!` after `context.User.Identity.Name` is the null-forgiving operator. It tells the compiler to trust that the value is not null because we already checked `IsAuthenticated == true`. It suppresses a nullable-reference warning and does not add a runtime null-check.

4. `RateLimitPartition.GetTokenBucketLimiter(key, factory)`

```csharp
return RateLimitPartition.GetTokenBucketLimiter(key, _ => new TokenBucketRateLimiterOptions { ... });
```

This is where the actual limiter for that key gets created or reused. Two arguments are involved:

- `key` — the partition key you computed (the username or IP)
- The second argument `_ => new TokenBucketRateLimiterOptions { ... }` — a factory function, not the options directly

The `_` parameter is discarded/unused, but it represents the key itself and can be used if you want to vary options per key.

Critical behavior: this factory is only invoked the first time a given key is seen. Internally, `PartitionedRateLimiter` maintains a dictionary keyed by your partition key and lazily creates a new `TokenBucketRateLimiter` the first time each unique key appears. After that, it reuses the same instance for every subsequent request from that same key. That is what makes it per-client.

5. The bucket options themselves

```csharp
new TokenBucketRateLimiterOptions
{
    TokenLimit = 20,
    TokensPerPeriod = 5,
    ReplenishmentPeriod = TimeSpan.FromSeconds(10),
    AutoReplenishment = true,
    QueueLimit = 0
}
```

This uses the same token bucket semantics as before, just applied per partition. Each client can burst up to 20 requests and refill at 5 tokens every 10 seconds, which is roughly 0.5 requests per second sustained. `QueueLimit = 0` means no queuing at all. If the bucket is empty, the request is rejected immediately.

### Putting It Together — End-to-End Flow for One Request

1. A request arrives and the middleware calls the global limiter.
2. The lambda runs and checks `context.User.Identity` to choose a username or IP as the key.
3. `PartitionedRateLimiter` looks up whether it already has a `TokenBucketRateLimiter` for that key.
   - First time seeing the key → factory runs and creates a fresh bucket.
   - Seen before → reuses the same bucket instance and its remaining tokens.
4. `AcquireAsync` is called on that specific bucket instance.
5. If the lease is acquired, the request proceeds. If not, and `QueueLimit = 0`, the request fails immediately with `429`.

### Why This Pattern Matters

This solves the fairness problem: a single global counter would let one noisy client exhaust the shared limit and block everyone else. Partitioning gives every client their own quota, so one bad actor only throttles themselves.

The catch is that this dictionary of limiter instances lives in memory and can grow unboundedly as new unique keys appear. This is especially important for anonymous requests from many IPs. In multi-instance deployments, each app instance keeps its own in-memory dictionary unless you move the limiter state to Redis or another shared backend.

## 4. Distributed Rate Limiting (Redis)

Built-in limiter state is in-memory, so it does not sync across multiple instances behind a load balancer. For multi-instance deployments, use Redis-backed rate limiting or implement it manually with `StackExchange.Redis`.

```bash
dotnet add package RedisRateLimiting
```

```csharp
using RedisRateLimiting;
using RedisRateLimiting.AspNetCore;

var redis = ConnectionMultiplexer.Connect("localhost:6379");

builder.Services.AddRateLimiter(options =>
{
    options.AddRedisTokenBucketLimiter("redis-token", opt =>
    {
        opt.ConnectionMultiplexerFactory = () => redis;
        opt.TokenLimit = 20;
        opt.TokensPerPeriod = 5;
        opt.ReplenishmentPeriod = TimeSpan.FromSeconds(10);
    });
});
```

This uses Redis as shared state, so all instances see the same counters.

## 5. Using It on Controllers

```csharp
using Microsoft.AspNetCore.RateLimiting;

[ApiController]
[Route("api/[controller]")]
public class OrdersController : ControllerBase
{

    [HttpPost("webhook-callback")]
    [DisableRateLimiting]
    public IActionResult WebhookCallback() => Ok();
}
```

```csharp
// in minimal API

```

# Rate Limiter Parameters Explained

## Fixed Window Limiter

```csharp
options.AddFixedWindowLimiter("fixed", opt =>
{
    opt.PermitLimit = 10;
    opt.Window = TimeSpan.FromSeconds(60);
    opt.QueueProcessingOrder = QueueProcessingOrder.OldestFirst;
    opt.QueueLimit = 2;
});
```

| Parameter | Meaning |
| --- | --- |
| `PermitLimit` | Maximum number of requests allowed within one window. `10` means 10 requests per window. |
| `Window` | Duration of each fixed window. `60s` means the counter resets every 60 seconds. |
| `QueueProcessingOrder` | When requests exceed the limit and queuing is enabled, this decides which queued request gets processed first. `OldestFirst` is FIFO; `NewestFirst` is LIFO. |
| `QueueLimit` | Number of excess requests allowed to wait in the queue instead of being rejected immediately. `2` means two requests can queue; the third excess request gets `429` immediately. |

---

## Sliding Window Limiter

```csharp
options.AddSlidingWindowLimiter("sliding", opt =>
{
    opt.PermitLimit = 10;
    opt.Window = TimeSpan.FromSeconds(60);
    opt.SegmentsPerWindow = 4;
    opt.QueueLimit = 2;
});
```

| Parameter | Meaning |
| --- | --- |
| `PermitLimit` | Maximum number of requests allowed across the whole sliding window. |
| `Window` | Total duration of the sliding window, such as 60 seconds. |
| `SegmentsPerWindow` | Divides the window into N sub-buckets that expire independently. `4` segments over 60 seconds means each segment is 15 seconds. As the oldest segment ages out, its request count is subtracted. |
| `QueueLimit` | Number of excess requests allowed to wait rather than reject immediately. |

Why segments matter: instead of storing every timestamp, the sliding window approximates smoothness by tracking counts per segment and rolling old segments off as time passes.

---

## Token Bucket Limiter

```csharp
options.AddTokenBucketLimiter("token", opt =>
{
    opt.TokenLimit = 20;
    opt.TokensPerPeriod = 5;
    opt.ReplenishmentPeriod = TimeSpan.FromSeconds(10);
    opt.AutoReplenishment = true;
    opt.QueueLimit = 2;
});
```

| Parameter | Meaning |
| --- | --- |
| `TokenLimit` | Maximum bucket capacity; this is the maximum burst size. `20` means a client can fire up to 20 requests instantly if the bucket is full. |
| `TokensPerPeriod` | How many tokens are added back each replenishment cycle. `5` means 5 tokens refill per period. |
| `ReplenishmentPeriod` | How often refilling happens. `10s` means every 10 seconds, `TokensPerPeriod` tokens are added up to the `TokenLimit` maximum. |
| `AutoReplenishment` | If `true`, the runtime automatically refills tokens in the background. If `false`, you must call `.TryReplenish()` manually. |
| `QueueLimit` | Requests allowed to wait for the next token instead of being rejected immediately. |

Mental model: the bucket starts full with 20 tokens. Each request costs 1 token. When the bucket is empty, requests are rejected or queued. Every 10 seconds, 5 tokens are added back up to the maximum of 20.


---

## Concurrency Limiter

```csharp
options.AddConcurrencyLimiter("concurrency", opt =>
{
    opt.PermitLimit = 5;
    opt.QueueLimit = 10;
});
```

| Parameter | Meaning |
| --- | --- |
| `PermitLimit` | Max number of requests allowed to execute **at the same time** (not per time window — this is about parallelism). `5` = only 5 requests can be "in flight" concurrently. |
| `QueueLimit` | How many additional requests can wait for a free slot before being rejected. |

**Key difference from the others:** this isn't rate-over-time — it's about limiting simultaneous in-progress work (e.g., protecting a resource-heavy endpoint like report generation from being hit by too many parallel calls). A permit is released when the request finishes, not on a timer.

---

## Global Limiter (Partitioned by user/IP)

```csharp
options.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(context =>
{
    var key = ...;
    return RateLimitPartition.GetTokenBucketLimiter(key, _ => new TokenBucketRateLimiterOptions { ... });
});
```

| Parameter | Meaning |
| --- | --- |
| `PartitionedRateLimiter.Create<HttpContext, string>` | Creates a limiter that's keyed per-partition instead of global. `HttpContext` is the input type, `string` is the partition key type. |
| The lambda (`context => ...`) | Extracts a **partition key** from each request — e.g., user ID or IP. Each unique key gets its *own independent* limiter instance/state. |
| `RateLimitPartition.GetTokenBucketLimiter(key, factory)` | Returns (or creates, if new) the token bucket limiter for that specific key. The factory function defines the options for a fresh partition the first time that key is seen. |
| `QueueLimit = 0` | No queuing — reject immediately once tokens run out for that partition (common for global/security-type limiters where you don't want requests piling up). |

---

## Redis Token Bucket (Distributed)

```csharp
options.AddRedisTokenBucketLimiter("redis-token", opt =>
{
    opt.ConnectionMultiplexerFactory = () => redis;
    opt.TokenLimit = 20;
    opt.TokensPerPeriod = 5;
    opt.ReplenishmentPeriod = TimeSpan.FromSeconds(10);
});
```

| Parameter | Meaning |
| --- | --- |
| `ConnectionMultiplexerFactory` | Function returning the shared `IConnectionMultiplexer` (Redis connection). Using a factory (not a direct instance) lets the library manage connection lifecycle/reuse properly. |
| `TokenLimit`, `TokensPerPeriod`, `ReplenishmentPeriod` | Same meaning as the in-memory token bucket, but the bucket **state itself lives in Redis** (via atomic Lua scripts) instead of app memory — so all instances behind your load balancer share the same count. |

## Global Rejection Handling

```csharp
options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;

options.OnRejected = async (context, token) =>
{
    context.HttpContext.Response.Headers["Retry-After"] = "60";
    await context.HttpContext.Response.WriteAsync("Too many requests...", token);
};
```

| Parameter | Meaning |
| --- | --- |
| `RejectionStatusCode` | HTTP status returned when a request is rejected (default is `503`; almost everyone overrides to `429`). |
| `OnRejected` | Callback invoked on rejection — lets you customize the response body, add headers like `Retry-After`, log the rejection, etc. `context` gives you `HttpContext` + which limiter/lease rejected it; `token` is a `CancellationToken` for the write operation. |

---

**Quick tuning intuition:**

- **Fixed/Sliding Window** → tune `PermitLimit` + `Window` for "X requests per Y time."
- **Token Bucket** → tune `TokenLimit` (burst allowance) separately from `TokensPerPeriod`/`ReplenishmentPeriod` (sustained rate).
- **Concurrency** → tune `PermitLimit` based on how many parallel operations your resource (DB, CPU, external API) can actually handle.

# AddSlidingWindowLimiter does it use slidingwindow log or sliding window counter?

Answer: It's a Sliding Window Counter (segmented), not a Sliding Window Log

ASP.NET Core's built-in AddSlidingWindowLimiter uses the segmented counter approach — it does not store a timestamp per individual request like a true sliding window log would.

How it actually works

The window is divided into SegmentsPerWindow fixed-size sub-buckets, each tracking just a request count — the sliding window algorithm is similar to the fixed window algorithm but with the addition of segments, where a segment is part of a window (e.g. a 2-hour window split into 4 segments of 30 minutes each).
Microsoft

There's a pointer to the current segment, and requests during a period go into the current segment; every segment-duration the window slides by one segment, and if there were requests during the segment the window slides past, those get refreshed and the available limit increases by that amount.
Microsoft

In plain terms:

- Each segment = a counter (an integer), not a list of timestamps
- As each segment expires, its request count is released and a new segment begins — preventing a client from exploiting the boundary between two fixed windows to send two rapid bursts

Concrete example — PermitLimit = 10, 4 segments currently holding counts [3, 2, 4, 0] (segment 4 is the live/current one):

- Existing total = 3+2+4+0 = 9
- Request #10 arrives asking for 1 permit → 9+1 = 10 ≤ 10 → accepted, segment 4 becomes 1
- Request #11 arrives right after → 10+1 = 11 > 10 → rejected (or queued)

There's no separate "per-segment limit" — segments are just the bookkeeping unit for expiring old counts. The rejection rule only ever cares about the grand total across all live segments vs. PermitLimit, checked at the exact moment AcquireAsync runs for that request.

# Approach should follow 

For an ASP.NET Core API, I'd layer it: coarse limits at the edge, fine-grained limits in the app.

**1. Edge layer (CDN, WAF, API gateway, or nginx)**
Block floods and obvious abuse by IP before they reach your servers. This protects capacity but can't understand users, plans, or endpoint cost.

**2. Application layer (per user or API key)**
Use the built-in `Microsoft.AspNetCore.RateLimiting` middleware (.NET 7+). Limit by authenticated identity, falling back to IP for anonymous traffic.

```csharp
builder.Services.AddRateLimiter(o =>
{
    o.RejectionStatusCode = StatusCodes.Status429TooManyRequests;

    // Global: per user/API key, fall back to IP
    o.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(ctx =>
    {
        var key = ctx.User.Identity?.IsAuthenticated == true
            ? ctx.User.FindFirst("sub")!.Value
            : ctx.Connection.RemoteIpAddress?.ToString() ?? "anon";

        return RateLimitPartition.GetTokenBucketLimiter(key, _ => new TokenBucketRateLimiterOptions
        {
            TokenLimit = 100,
            TokensPerPeriod = 50,
            ReplenishmentPeriod = TimeSpan.FromSeconds(10),
            QueueLimit = 0
        });
    });

    // Stricter policy for sensitive endpoints (login, OTP, exports)
    o.AddPolicy("strict", ctx => RateLimitPartition.GetSlidingWindowLimiter(
        ctx.Connection.RemoteIpAddress?.ToString() ?? "anon",
        _ => new SlidingWindowRateLimiterOptions
        {
            PermitLimit = 5, Window = TimeSpan.FromMinutes(1), SegmentsPerWindow = 6
        }));

    o.OnRejected = async (ctx, ct) =>
    {
        if (ctx.Lease.TryGetMetadata(MetadataName.RetryAfter, out var retry))
            ctx.HttpContext.Response.Headers.RetryAfter = ((int)retry.TotalSeconds).ToString();
        await ctx.HttpContext.Response.WriteAsJsonAsync(
            new { title = "Too many requests" }, ct);
    };
});

app.UseForwardedHeaders();   // before auth/limiter, or every client looks like your load balancer
app.UseRateLimiter();
```

Apply the strict policy with `.RequireRateLimiting("strict")` or `[EnableRateLimiting("strict")]`.

**Key decisions**

- **Algorithm:** Token bucket is the best default because it allows short bursts while enforcing an average rate. Use sliding window for strict limits like login attempts. Avoid plain fixed window, since a client can double-burst at the boundary. Use a concurrency limiter for expensive endpoints (reports, exports).
- **Multiple instances:** The built-in limiter keeps state in memory per instance. With N replicas, a client effectively gets N times the limit and the count resets on restart. Fixes: enforce at the gateway, or use a shared Redis store with atomic counters (Lua script or a package like `RedisRateLimiting`). Per-instance limits are fine as a rough safety net, but not for quotas or billing.
- **Redis failure:** Decide up front whether to fail open (availability) or fail closed (protection). Fail open for general traffic and closed for auth endpoints is a common split.
- **Client identity:** Prefer API key or user ID over IP, since many users share NAT. Never trust `X-Forwarded-For` unless it comes from your known proxy (configure `KnownProxies`).
- **Response contract:** Return 429 with `Retry-After`, and ideally `RateLimit-Limit` and `RateLimit-Remaining` headers, so well-behaved clients can back off.
- **Tiers:** Different limits per plan or endpoint cost. Cheap reads can be generous, while writes, search, and auth should be tighter.

**Rollout**

1. Ship in log-only mode first, recording who would have been limited.
2. Set limits from real p95/p99 per-client traffic, not guesses.
3. Enforce, with a per-client allowlist or override for internal services.
4. Alert on 429 rate, top limited keys, and limiter latency.

For one or two instances, the built-in middleware is enough. Once you scale out horizontally or need real quotas, move enforcement to the gateway or Redis.

## Extension to this approach 

Yes, use both, but they do different jobs, so don't think of them as two versions of the same thing.

- **Per-user (or per-key) limit:** fairness and abuse protection. It stops one client from consuming more than their share.
- **Global limit:** protecting the server. It's a safety valve for total load, so the API sheds traffic instead of falling over.

If you only have a global limit, one noisy client can use up the whole budget and everyone else gets 429s. If you only have per-user limits, 10,000 well-behaved users can still overload you together. You need both.

In my earlier snippet, the property named `GlobalLimiter` was actually partitioned per user. In ASP.NET Core, "global" just means "applies to every endpoint". It doesn't mean "one shared bucket". For a true shared cap, use a single constant partition key, and combine the two with `CreateChained`:

```csharp
builder.Services.AddRateLimiter(o =>
{
    o.RejectionStatusCode = StatusCodes.Status429TooManyRequests;

    o.GlobalLimiter = PartitionedRateLimiter.CreateChained(
        // 1. Per-user / per-key (fairness)
        PartitionedRateLimiter.Create<HttpContext, string>(ctx =>
        {
            var key = ctx.User.Identity?.IsAuthenticated == true
                ? ctx.User.FindFirst("sub")!.Value
                : ctx.Connection.RemoteIpAddress?.ToString() ?? "anon";

            return RateLimitPartition.GetTokenBucketLimiter(key, _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = 100,
                TokensPerPeriod = 50,
                ReplenishmentPeriod = TimeSpan.FromSeconds(10),
                QueueLimit = 0
            });
        }),

        // 2. Server-wide cap (capacity protection)
        PartitionedRateLimiter.Create<HttpContext, string>(_ =>
            RateLimitPartition.GetConcurrencyLimiter("global", _ => new ConcurrencyLimiterOptions
            {
                PermitLimit = 200,   // tune from load tests
                QueueLimit = 0
            })));
});
```

A request has to pass both limiters. If either rejects it, it gets a 429.

**Recommendations**

- **Use a concurrency limiter for the global cap.** What actually overloads a server is requests in flight, not requests per minute. A cap on concurrent requests tracks real capacity and adapts when downstream calls slow down. Set it from load testing, at roughly 70-80% of what the instance handles before latency degrades.
- **Set the global limit well above normal peak.** It should only trigger in a real overload. If it fires during ordinary traffic, you're degrading everyone instead of just the heavy users.
- **Add a third layer for sensitive endpoints.** A strict per-IP policy on login, OTP and password reset, like the `"strict"` policy from before, since these need much tighter limits than the general per-user one.
- **Keep the global limiter per instance.** For a concurrency cap, per-instance is correct, because each instance has its own CPU and connection limits. You only need Redis or a gateway for the per-user quotas, where a client's count must be shared across replicas.
- **Make the two limits distinguishable.** Return different error messages or headers for "you're over your quota" vs "the server is busy". Clients should retry the second one with backoff, while the first means they should slow down.

So the setup is: per-user limit (shared via Redis or the gateway if you run multiple replicas), per-instance concurrency cap as a safety valve, and strict per-IP limits on auth endpoints.

# Throttling 

In practice: rate limiting is a policy ("you get X requests per minute, period"). Throttling is a mechanism for controlling the rate of processing — which can be used to enforce a rate limit softly (delay instead of reject), or independently, to protect a resource regardless of any client-facing quota.

They actually overlap a lot in real systems — the leaky bucket and token bucket algorithms we discussed are, technically, throttling mechanisms (smoothing traffic flow); using them to reject with 429 at the API boundary is what turns that mechanism into a rate limiting policy. The queue-with-QueueLimit > 0 behavior in ASP.NET Core's rate limiter (delaying rather than immediately rejecting) is throttling behavior layered on top of a rate limit.

## Where throttling shows up in .NET specifically

### 1. SemaphoreSlim — concurrency throttling
This is the classic hand-rolled throttle: limit how many operations run in parallel, regardless of time window.

```csharp
private static readonly SemaphoreSlim _throttle = new SemaphoreSlim(5); // max 5 concurrent

public async Task<IActionResult> CallExternalApiAsync()
{
    await _throttle.WaitAsync(); // blocks/queues here if 5 are already running
    try
    {
        return Ok(await _httpClient.GetAsync("https://slow-downstream-api.com"));
    }
    finally
    {
        _throttle.Release();
    }
}
```

This is functionally identical to the ConcurrencyLimiter we covered earlier — that's actually ASP.NET Core's built-in version of the same pattern, just wrapped as middleware instead of manual semaphore code.

### 2. System.Threading.RateLimiting with QueueLimit > 0 — delay instead of reject

```csharp
options.AddTokenBucketLimiter("throttled", opt =>
{
    opt.TokenLimit = 10;
    opt.TokensPerPeriod = 2;
    opt.ReplenishmentPeriod = TimeSpan.FromSeconds(5);
    opt.QueueLimit = 20; // <-- this is what makes it throttling, not just limiting
    opt.QueueProcessingOrder = QueueProcessingOrder.OldestFirst;
});
```

With QueueLimit = 0, excess requests are rejected — that's pure rate limiting. With QueueLimit = 20, excess requests wait for a token instead of failing — that's throttling behavior, using the rate limiter as the mechanism.

## When to use which

### Use rate limiting (reject) when:

You're protecting a public-facing API and need a hard, predictable contract with clients (e.g., "Free tier: 100 req/hour")
You need to defend against abuse or DoS — you want bad actors to get an immediate, cheap-to-produce rejection, not consume server resources waiting in a queue
The client is expected to handle the rejection (retry with backoff, upgrade their plan, etc.) — this is a client-visible contract

### Use throttling (delay/smooth) when:

You're calling your own downstream dependency (a database, a third-party API with its own limits, a legacy system that can't handle bursts) — you want to smooth your own outgoing traffic, not tell your caller "no"
You have background/batch processing where there's no "client" to reject — the work just needs to happen at a sustainable pace
You want to protect a shared resource's capacity (DB connection pool, thread pool, memory) from being overwhelmed by legitimate concurrent load, where slowing down is fine but rejecting would break functionality
Quality of service under load — e.g., video streaming reducing bitrate rather than cutting the stream
