# Approach 1 — Fully custom, build-it-yourself (what we've been building)

You write `IdentityService`, `TokenService`, RS256 signing, refresh rotation — everything — using ASP.NET Core Identity as the user store, but rolling your own
token issuance logic.

**When this fits:** Single API, single frontend, you fully control both. No need for multiple client apps, no SSO across products, no third-party developers
consuming your auth.

**Tradeoffs:** Full control over every claim, every flow, every edge case — nothing hidden behind a framework's opinions. But you own every security decision
yourself: token revocation edge cases, replay detection, key rotation, rate limiting — all of it is your bug to find. This is exactly what your Task
Management API auth module is right now, and it's the right call for that scope.

# Things to know for building it

## ASP.NET Core Identity

ASP.NET Core Identity is a membership system — it manages users, passwords, roles, claims, and external logins. It is not a JWT library, not an OAuth server,
and not a session manager by itself.

Identity only handles the "who is this user and is their password correct" part.

**What Identity gives you out of the box:**

- User and role storage (via EF Core, by default)
- Password hashing (PBKDF2)
- Account lockout after failed attempts
- Email/phone confirmation tokens
- Two-factor authentication support
- External login linking (Google, Microsoft, etc.)

**What it does NOT give you:**

- JWT generation (you write this — as you already have)
- OAuth2/OIDC flows (that's OpenIddict/Duende's job)
- Authorization policies beyond basic role/claim checks (you still write handlers for resource-based checks)

### The core building blocks

### IdentityUser&lt;TKey&gt; — the user model

`IdentityUser<TKey>` is the generic base class ASP.NET Core Identity gives you for the "user" entity, letting you control the type of the primary key instead of
being stuck with `string` (GUID).

**The class hierarchy:**

```text
IdentityUser<TKey> : where TKey : IEquatable<TKey>
    ↑
IdentityUser : IdentityUser<string>   // the non-generic shorthand, Id is a GUID string
```

So when you write `IdentityUser`, you're actually using `IdentityUser<string>` under the hood — Identity generates a GUID string for `Id`.

**What's inside IdentityUser&lt;TKey&gt;**

```csharp
public class IdentityUser<TKey> where TKey : IEquatable<TKey>
{
    public TKey Id { get; set; }
    public string UserName { get; set; }
    public string NormalizedUserName { get; set; }
    public string Email { get; set; }
    public string NormalizedEmail { get; set; }
    public bool EmailConfirmed { get; set; }
    public string PasswordHash { get; set; }
    public string SecurityStamp { get; set; }     // invalidates tokens when user data changes
    public string ConcurrencyStamp { get; set; }   // optimistic concurrency (RowVersion-like)
    public string PhoneNumber { get; set; }
    public bool PhoneNumberConfirmed { get; set; }
    public bool TwoFactorEnabled { get; set; }
    public DateTimeOffset? LockoutEnd { get; set; }
    public bool LockoutEnabled { get; set; }
    public int AccessFailedCount { get; set; }
}
```

| Property                                          | Purpose                                                           |
| ------------------------------------------------- | ----------------------------------------------------------------- |
| **Id**                                            | Primary key (Guid here, string by default)                        |
| **UserName, NormalizedUserName**                  | Login identifier + case-insensitive lookup copy                   |
| **Email, NormalizedEmail**                        | Same pattern for email                                            |
| **PasswordHash**                                  | PBKDF2 hash — never plaintext                                     |
| **SecurityStamp**                                 | Changes on password/security changes — invalidates stale sessions |
| **ConcurrencyStamp**                              | Optimistic concurrency token for the user row itself              |
| **LockoutEnd, LockoutEnabled, AccessFailedCount** | Brute-force protection                                            |
| **EmailConfirmed, PhoneNumberConfirmed**          | Confirmation gates                                                |
| **TwoFactorEnabled**                              | 2FA toggle                                                        |

**Custom class for extra fields**

```csharp
public class ApplicationUser : IdentityUser<Guid>
{
    public string FirstName { get; set; } = string.Empty;
    public string LastName { get; set; } = string.Empty;
    public DateTime CreatedAtUtc { get; set; } = DateTime.UtcNow;
    public bool IsActive { get; set; } = true;
}
```

Inherit from `IdentityUser<Guid>`.

#### IdentityRole&lt;TKey&gt;

`IdentityRole<TKey>` is the generic counterpart for roles — same idea as `IdentityUser<TKey>`, letting you control the key type instead of being locked into `string`.

**Class hierarchy:**

```text
IdentityRole<TKey> : where TKey : IEquatable<TKey>
    ↑
IdentityRole : IdentityRole<string>   // shorthand, Id is a GUID string
```

**What's inside IdentityRole&lt;TKey&gt;**

```csharp
public class IdentityRole<TKey> where TKey : IEquatable<TKey>
{
    public TKey Id { get; set; }
    public string Name { get; set; }
    public string NormalizedName { get; set; }
    public string ConcurrencyStamp { get; set; }  // optimistic concurrency, same as IdentityUser
}
```

That's it — much leaner than `IdentityUser<TKey>` since a role is really just a name plus an id.

#### IdentityDbContext

`IdentityDbContext` is the base `DbContext` that wires up all the Identity entities (users, roles, claims, logins, tokens) into EF Core — it's what turns "just
some C# classes" into actual database tables with the relationships between them configured.

**Class hierarchy (overloads, simplest to most flexible)**

```csharp
// 1. Simplest — string keys, default IdentityUser, no roles table
IdentityDbContext : IdentityDbContext<IdentityUser>

// 2. Custom user, string key
IdentityDbContext<TUser> : IdentityDbContext<TUser, IdentityRole, string>
    where TUser : IdentityUser

// 3. Custom user + custom role, custom key
IdentityDbContext<TUser, TRole, TKey>
    where TUser : IdentityUser<TKey>
    where TRole : IdentityRole<TKey>
    where TKey : IEquatable<TKey>
```

**What it does that a plain DbContext doesn't**

`IdentityDbContext` inherits from `DbContext`, but its `OnModelCreating` pre-configures:

- Table names (`AspNetUsers`, `AspNetRoles`, `AspNetUserRoles`, etc.)
- Primary keys and indexes (unique index on `NormalizedUserName`, `NormalizedEmail`)
- Foreign key relationships between user ↔ role ↔ claims ↔ logins ↔ tokens
- Max lengths on key columns (so `NormalizedUserName` etc. can be indexed properly across DB providers)

**Full example tying it together**

```csharp
public class ApplicationUser : IdentityUser<int>
{
    public string FullName { get; set; }
    public int? DepartmentId { get; set; }
    public Department Department { get; set; }
}

public class ApplicationRole : IdentityRole<int>
{
    public string Description { get; set; }
}

public class Department
{
    public int Id { get; set; }
    public string Name { get; set; }
}

public class AppDbContext : IdentityDbContext<ApplicationUser, ApplicationRole, int>
{
    public AppDbContext(DbContextOptions<AppDbContext> options) : base(options) { }

    public DbSet<Department> Departments { get; set; }

    // Your own app tables, unrelated to Identity, live here too
    public DbSet<TaskItem> Tasks { get; set; }

    protected override void OnModelCreating(ModelBuilder builder)
    {
        base.OnModelCreating(builder); // MUST come first — configures all Identity tables

        // Rename Identity's default table names if you don't like AspNet* prefix
        builder.Entity<ApplicationUser>().ToTable("Users");
        builder.Entity<ApplicationRole>().ToTable("Roles");
        builder.Entity<IdentityUserRole<int>>().ToTable("UserRoles");
        builder.Entity<IdentityUserClaim<int>>().ToTable("UserClaims");
        builder.Entity<IdentityRoleClaim<int>>().ToTable("RoleClaims");
        builder.Entity<IdentityUserLogin<int>>().ToTable("UserLogins");
        builder.Entity<IdentityUserToken<int>>().ToTable("UserTokens");

        // Your own relationships
        builder.Entity<ApplicationUser>()
            .HasOne(u => u.Department)
            .WithMany()
            .HasForeignKey(u => u.DepartmentId)
            .OnDelete(DeleteBehavior.SetNull);
    }
}
```

```csharp
// Program.cs
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("DefaultConnection")));

builder.Services.AddIdentity<ApplicationUser, ApplicationRole>(options =>
{
    options.Password.RequiredLength = 8;
    options.User.RequireUniqueEmail = true;
})
.AddEntityFrameworkStores<AppDbContext>()
.AddDefaultTokenProviders();
```

**A gotcha worth knowing**

If you switch `TKey` away from `string`, every place that references `IdentityUser`, `IdentityRole`, `IdentityUserClaim`, `IdentityUserRole`, etc. needs the same `TKey` — EF
Core's Identity model builder wires these together via generics, so a mismatch (e.g., `ApplicationUser : IdentityUser<int>` but `AppDbContext :
IdentityDbContext<ApplicationUser>` without specifying `int`) won't compile.

## UserManager&lt;TUser&gt;

`UserManager<TUser>` is the central service class in ASP.NET Core Identity for all user-related operations — creating users, hashing/verifying passwords, managing
roles, claims, lockout, 2FA, email/phone confirmation, and external logins. It sits between your controllers/services and the underlying `IUserStore<TUser>`
(which talks to the database via EF Core).

### Definition & registration

```csharp
public class UserManager<TUser> : IDisposable where TUser : class
```

It's registered automatically when you call `AddIdentity` / `AddIdentityCore`:

```csharp
builder.Services.AddIdentity<ApplicationUser, ApplicationRole>(options =>
{
    options.Password.RequiredLength = 8;
    options.Password.RequireNonAlphanumeric = false;
    options.Lockout.MaxFailedAccessAttempts = 5;
    options.User.RequireUniqueEmail = true;
})
.AddEntityFrameworkStores<AppDbContext>()
.AddDefaultTokenProviders();
```

Then inject it anywhere via DI:

```csharp
public class AccountController : ControllerBase
{
    private readonly UserManager<ApplicationUser> _userManager;

    public AccountController(UserManager<ApplicationUser> userManager)
    {
        _userManager = userManager;
    }
}
```

Internally it never calls `SaveChanges` on its own `DbContext` directly — it goes through the configured `IUserStore<TUser>`, which is why
`AddEntityFrameworkStores<AppDbContext>()` is required; that's what wires `UserManager` to your actual database.

### Creating & deleting users

```csharp
// CreateAsync(user) — no password, e.g. external-login-only account
var user = new ApplicationUser { UserName = "aman", Email = "aman@example.com" };
IdentityResult result = await _userManager.CreateAsync(user);

// CreateAsync(user, password) — hashes password automatically
IdentityResult result = await _userManager.CreateAsync(user, "P@ssw0rd123");

if (!result.Succeeded)
{
    foreach (var error in result.Errors)
        Console.WriteLine($"{error.Code}: {error.Description}");
    // e.g. "PasswordTooShort: Passwords must be at least 8 characters."
}

// DeleteAsync(user)
await _userManager.DeleteAsync(user);

// UpdateAsync(user) — after modifying properties directly
user.FullName = "Aman Kumar";
await _userManager.UpdateAsync(user);
```

### Finding users

```csharp
var byId    = await _userManager.FindByIdAsync("5");
var byName  = await _userManager.FindByNameAsync("aman");
var byEmail = await _userManager.FindByEmailAsync("aman@example.com");

// FindByLoginAsync — external login lookup
var byLogin = await _userManager.FindByLoginAsync("Google", "108234982374982374");

// GetUserAsync — from the current ClaimsPrincipal (in a controller)
var currentUser = await _userManager.GetUserAsync(User);   // User = HttpContext.User

// Users — IQueryable<TUser> for custom LINQ queries
var admins = _userManager.Users.Where(u => u.DepartmentId == 3).ToList();
```

### Password management

```csharp
// CheckPasswordAsync — verify without signing in
bool valid = await _userManager.CheckPasswordAsync(user, "P@ssw0rd123");

// ChangePasswordAsync — requires knowing the current password
var result = await _userManager.ChangePasswordAsync(user, "OldP@ss1", "NewP@ss2");

// AddPasswordAsync — for users created without one (e.g. external-login-only)
await _userManager.AddPasswordAsync(user, "NewP@ss123");

// RemovePasswordAsync
await _userManager.RemovePasswordAsync(user);

// Reset password flow (forgot password)
string token = await _userManager.GeneratePasswordResetTokenAsync(user);
// ... email this token to the user as part of a reset link ...
var result = await _userManager.ResetPasswordAsync(user, token, "NewP@ss123");

// HasPasswordAsync
bool hasPassword = await _userManager.HasPasswordAsync(user);
```

`GeneratePasswordResetTokenAsync` uses the `DataProtectorTokenProvider` by default — time-limited, tied to the user's `SecurityStamp`, so it auto-invalidates
once used or once the password changes.

#### GeneratePasswordResetTokenAsync

**What it does**

```csharp
Task<string> GeneratePasswordResetTokenAsync(TUser user);
```

It generates a time-limited, single-purpose token tied to that specific user, without storing the token anywhere in the database. Instead, it's cryptographically
derived and later re-verified — this is the key thing people get wrong, thinking it's like a session ID stored in a table.

**How it works internally (step by step)**

**Step 1 — Token provider selection**

By default, Identity uses `DataProtectorTokenProvider<TUser>` (registered via `AddDefaultTokenProviders()` in your `Program.cs`). This provider uses ASP.NET Core's Data Protection API — the same encryption system used for auth cookies.

**Step 2 — What goes into the token**

```csharp
// Conceptually, the provider builds a payload like this internally:
var payload = new
{
    UserId = user.Id,
    Purpose = "ResetPassword",             // the "purpose" string
    SecurityStamp = user.SecurityStamp,    // <- the important part
    Expiry = DateTimeOffset.UtcNow.Add(options.TokenLifespan)  // default 24 hours
};
```

That payload is then encrypted (not just encoded) using the Data Protection API's `IDataProtector`, keyed to the specific purpose string `"ResetPassword"`. The result is what you get back as the token string — an opaque, encrypted blob.

**Step 3 — Why SecurityStamp matters**

This is the real security mechanism. `SecurityStamp` is a random GUID stored on `IdentityUser` that gets regenerated whenever something sensitive changes on the
account — password change, 2FA setup, email change, etc.

So if a token is generated, then the password changes for any reason (including using that very token), the `SecurityStamp` baked into the token no longer matches the user's current `SecurityStamp` in the database — meaning the token auto-invalidates itself without needing a "used tokens" table.

**Step 4 — Verification (ResetPasswordAsync)**

```csharp
Task<IdentityResult> ResetPasswordAsync(TUser user, string token, string newPassword);
```

This decrypts the token, checks:

- Does the `Purpose` match `"ResetPassword"`?
- Does the embedded `SecurityStamp` match the user's current `SecurityStamp`?
- Has the token expired (based on `TokenLifespan`)?

If all three pass, it resets the password — and resetting the password itself regenerates `SecurityStamp`, so the same token can't be replayed even within its 24-hour window.

**Working example — full forgot-password flow**

```csharp
// 1. User requests a password reset
[HttpPost("forgot-password")]
public async Task<IActionResult> ForgotPassword(ForgotPasswordDto dto)
{
    var user = await _userManager.FindByEmailAsync(dto.Email);

    // Always return OK even if user is null — don't leak whether an email exists
    if (user == null || !await _userManager.IsEmailConfirmedAsync(user))
        return Ok(new { message = "If that email exists, a reset link has been sent." });

    string token = await _userManager.GeneratePasswordResetTokenAsync(user);

    // Token contains characters that break URLs (+, /, =) — must URL-encode
    string encodedToken = WebUtility.UrlEncode(token);

    string resetLink = $"https://yourapp.com/reset-password?email={user.Email}&token={encodedToken}";

    await _emailSender.SendEmailAsync(user.Email, "Reset your password",
        $"Click here to reset your password: {resetLink}");

    return Ok(new { message = "If that email exists, a reset link has been sent." });
}

// 2. User clicks the link, submits new password + token
[HttpPost("reset-password")]
public async Task<IActionResult> ResetPassword(ResetPasswordDto dto)
{
    var user = await _userManager.FindByEmailAsync(dto.Email);
    if (user == null)
        return BadRequest("Invalid request.");   // don't reveal which part failed

    // dto.Token arrives URL-decoded automatically if bound from query string properly,
    // but if you manually decode: WebUtility.UrlDecode(dto.Token)

    var result = await _userManager.ResetPasswordAsync(user, dto.Token, dto.NewPassword);

    if (!result.Succeeded)
    {
        foreach (var error in result.Errors)
            Console.WriteLine($"{error.Code}: {error.Description}");
        // Common failure: "InvalidToken" — happens if token expired, was already
        // used (SecurityStamp changed), or was tampered with
        return BadRequest(result.Errors);
    }

    return Ok(new { message = "Password reset successful." });
}
```

> Good catch to dig into — there's a gap here: the reset link is a frontend page URL (GET, query string), but `ResetPassword` action is a POST API endpoint
> expecting a JSON body (`ResetPasswordDto dto`). These are two different requests, connected through a frontend page in between. Let me walk through the full flow.

**The two-step flow**

```text
Step 1: Email link → GET → opens a frontend page (Angular/React/whatever)
                            https://yourapp.com/reset-password?email=...&token=...

Step 2: Frontend page → reads query params → user enters new password →
                         POST (JSON body) → https://yourapi.com/api/account/reset-password
```

**Configuring the token lifespan**

Default is 24 hours if not set:

```csharp
// Program.cs
builder.Services.Configure<DataProtectionTokenProviderOptions>(options =>
{
    options.TokenLifespan = TimeSpan.FromHours(1);  // e.g., tighten to 1 hour
});
```

#### Email confirmation — yes, same pattern as password reset

Identical shape: generate token → embed in URL → frontend page reads query string → POST to confirm.

```csharp
// 1. Generate + send link (e.g. right after registration)
string token = await _userManager.GenerateEmailConfirmationTokenAsync(user);
string encodedToken = WebUtility.UrlEncode(token);
string confirmLink = $"https://yourapp.com/confirm-email?userId={user.Id}&token={encodedToken}";

await _emailSender.SendEmailAsync(user.Email, "Confirm your email",
    $"Click here to confirm: {confirmLink}");

// 2. Frontend/client send request to API with required details (including Token that it got in step 1)

// 3. API side : client will pass token sent by server shown above to API 
public class ConfirmEmailDto
{
    public string UserId { get; set; }
    public string Token { get; set; }
}

[HttpPost("confirm-email")]
public async Task<IActionResult> ConfirmEmail(ConfirmEmailDto dto)
{
    var user = await _userManager.FindByIdAsync(dto.UserId);
    if (user == null) return BadRequest("Invalid request.");

    var result = await _userManager.ConfirmEmailAsync(user, dto.Token);
    return result.Succeeded ? Ok() : BadRequest(result.Errors);
}
```

> **Note:** Same `SecurityStamp`-based self-invalidation, same URL-encoding gotcha, same "frontend page in between" requirement. Nothing changes conceptually — it's
> the identical mechanism, just a different token purpose string internally (`"EmailConfirmation"` instead of `"ResetPassword"`).

#### OTP — completely different pattern, no link involved

OTP (One-Time Password / verification code) is designed for the user to manually type a short code — usually sent via SMS or email as plain text, not as a
clickable link. There's no query string, no frontend routing, no URL encoding concern.

```csharp
// 1. Generate a short numeric/alphanumeric code (NOT the long encrypted Identity token)
string otp = await _userManager.GenerateTwoFactorTokenAsync(user, TokenOptions.DefaultEmailProvider);
// This still uses Identity's token machinery under the hood, but the
// DefaultEmailProvider produces a short numeric code (6 digits), not a
// long encrypted blob like GeneratePasswordResetTokenAsync does

await _emailSender.SendEmailAsync(user.Email, "Your verification code",
    $"Your code is: {otp}");   // e.g. "482913" — sent as plain text, no link

// 2. Frontend/client send request to API with required details (including OTP)

// 3. API side
public class VerifyOtpDto
{
    public string Email { get; set; }
    public string Code { get; set; }
}

[HttpPost("verify-otp")]
public async Task<IActionResult> VerifyOtp(VerifyOtpDto dto)
{
    var user = await _userManager.FindByEmailAsync(dto.Email);
    if (user == null) return BadRequest("Invalid request.");

    bool isValid = await _userManager.VerifyTwoFactorTokenAsync(
        user, TokenOptions.DefaultEmailProvider, dto.Code);

    if (!isValid) return BadRequest("Invalid or expired code.");

    // e.g. mark 2FA step passed, issue JWT, etc.
    return Ok();
}
```

#### Set Token lifespan

Good instinct to separate these — by default, `Configure<DataProtectionTokenProviderOptions>` applies globally to every token generated by
`DataProtectorTokenProvider` (which covers both password reset AND email confirmation), so if you just set one `TokenLifespan`, it affects both identically. To get
truly independent lifespans, you need separate named token providers, each with its own options.

**The problem with the naive approach**

```csharp
// This sets ONE lifespan for EVERYTHING using DataProtectorTokenProvider —
// password reset AND email confirmation both get 2 hours, no way to differ them
builder.Services.Configure<DataProtectionTokenProviderOptions>(options =>
{
    options.TokenLifespan = TimeSpan.FromHours(2);
});
```

You can't set password reset to 1 hour and email confirmation to 24 hours this way — they share the same provider and same options class.

#### Solution: register custom named providers, each with its own lifespan

**Step 1 — Create a distinct provider class per purpose**

`TUser` is your `IdentityUser<T>` class, that is `ApplicationUser` in our context.

```csharp
// A thin subclass just to get a distinct DI registration + distinct options binding
public class PasswordResetTokenProvider<TUser> : DataProtectorTokenProvider<TUser>
    where TUser : class
{
    public PasswordResetTokenProvider(
        IDataProtectionProvider dataProtectionProvider,
        IOptions<PasswordResetTokenProviderOptions> options,
        ILogger<DataProtectorTokenProvider<TUser>> logger)
        : base(dataProtectionProvider, options, logger) { }
}

public class PasswordResetTokenProviderOptions : DataProtectionTokenProviderOptions
{
    public PasswordResetTokenProviderOptions()
    {
        Name = "PasswordReset";
        TokenLifespan = TimeSpan.FromHours(1);   // 1 hour default
    }
}

public class EmailConfirmationTokenProvider<TUser> : DataProtectorTokenProvider<TUser>
    where TUser : class
{
    public EmailConfirmationTokenProvider(
        IDataProtectionProvider dataProtectionProvider,
        IOptions<EmailConfirmationTokenProviderOptions> options,
        ILogger<DataProtectorTokenProvider<TUser>> logger)
        : base(dataProtectionProvider, options, logger) { }
}

public class EmailConfirmationTokenProviderOptions : DataProtectionTokenProviderOptions
{
    public EmailConfirmationTokenProviderOptions()
    {
        Name = "EmailConfirmation";
        TokenLifespan = TimeSpan.FromDays(1);    // 24 hours default
    }
}
```

For OTP, Identity already ships a purpose-built provider for exactly this — `EmailTokenProvider<TUser>` (short numeric codes) — you don't need a custom class,
just its own options.

**`DataProtectorTokenProvider<TUser>`:**

```csharp
public class PasswordResetTokenProvider<TUser> : DataProtectorTokenProvider<TUser> { ... }
public class EmailConfirmationTokenProvider<TUser> : DataProtectorTokenProvider<TUser> { ... }
```

**Why?** Because `DataProtectorTokenProvider<TUser>` only has one options type it binds to (`DataProtectionTokenProviderOptions`). If you register it twice under two
different names but both read from the same options class, they'd both pick up the same `TokenLifespan` — DI can't tell them apart. So the workaround is: make two
subclasses, give each its own dedicated options class, and now each can have an independent lifespan.

`EmailTokenProvider<TUser>` doesn't have this problem — it's a completely different, separate class already built into Identity, with its own dedicated options
class already provided by the framework: `EmailTokenProviderOptions`. So you don't need to write a subclass at all — the framework already did that separation for
you.

```csharp
public class OtpTokenProviderOptions : DataProtectionTokenProviderOptions
{
    public OtpTokenProviderOptions()
    {
        Name = "EmailOtp";
        TokenLifespan = TimeSpan.FromMinutes(5);  // 5 minutes
    }
}
```

**Step 2 — Register everything in Program.cs**

```csharp
builder.Services.AddIdentity<ApplicationUser, ApplicationRole>(options =>
{
    options.Password.RequiredLength = 8;
})
.AddEntityFrameworkStores<AppDbContext>()
.AddDefaultTokenProviders()   // still keep this — provides Authenticator, some defaults
.AddTokenProvider<PasswordResetTokenProvider<ApplicationUser>>("PasswordReset")
.AddTokenProvider<EmailConfirmationTokenProvider<ApplicationUser>>("EmailConfirmation")
.AddTokenProvider<EmailTokenProvider<ApplicationUser>>("EmailOtp");

// Bind each options class independently — this is what makes lifespans independent
builder.Services.Configure<PasswordResetTokenProviderOptions>(options =>
{
    options.TokenLifespan = TimeSpan.FromHours(1);
});

builder.Services.Configure<EmailConfirmationTokenProviderOptions>(options =>
{
    options.TokenLifespan = TimeSpan.FromDays(1);
});

builder.Services.Configure<OtpTokenProviderOptions>(options =>
{
    options.TokenLifespan = TimeSpan.FromMinutes(5);
});
```

**Step 3 — Use the named providers explicitly when generating/verifying**

`GeneratePasswordResetTokenAsync()` and `GenerateEmailConfirmationTokenAsync()` use hardcoded internal purpose names by default — to actually route through your
named providers, you call the generic token methods and pass the provider name explicitly:

```csharp
// Password reset — 1 hour lifespan
string resetToken = await _userManager.GenerateUserTokenAsync(
    user, "PasswordReset", "ResetPassword");

bool resetValid = await _userManager.VerifyUserTokenAsync(
    user, "PasswordReset", "ResetPassword", resetToken);

if (resetValid)
{
    // manually reset password since you're bypassing ResetPasswordAsync's own token check
    await _userManager.RemovePasswordAsync(user);
    await _userManager.AddPasswordAsync(user, newPassword);
}

// Email confirmation — 24 hour lifespan
string confirmToken = await _userManager.GenerateUserTokenAsync(
    user, "EmailConfirmation", "EmailConfirmation");

bool confirmValid = await _userManager.VerifyUserTokenAsync(
    user, "EmailConfirmation", "EmailConfirmation", confirmToken);

if (confirmValid)
{
    user.EmailConfirmed = true;
    await _userManager.UpdateAsync(user);
}

// OTP — 5 minute lifespan
string otp = await _userManager.GenerateUserTokenAsync(
    user, "EmailOtp", "OtpLogin");

bool otpValid = await _userManager.VerifyUserTokenAsync(
    user, "EmailOtp", "OtpLogin", otp);
```

> **Note:** once you go this route, `ResetPasswordAsync(user, token, newPassword)` and `ConfirmEmailAsync(user, token)` won't recognize tokens generated by your
> custom-named providers — those built-in methods are hardcoded to look for tokens from the default provider under specific internal purpose strings. So you
> either commit to the manual `GenerateUserTokenAsync`/`VerifyUserTokenAsync` + manual action (as shown above), or you accept a shared lifespan and skip this whole
> setup.

### Lockout

```csharp
bool lockoutEnabled = await _userManager.GetLockoutEnabledAsync(user);
await _userManager.SetLockoutEnabledAsync(user, true);

// Lock a user until a specific time (or DateTimeOffset.MaxValue for "forever")
await _userManager.SetLockoutEndDateAsync(user, DateTimeOffset.UtcNow.AddMinutes(15));

DateTimeOffset? lockoutEnd = await _userManager.GetLockoutEndDateAsync(user);
bool isLockedOut = await _userManager.IsLockedOutAsync(user);

// Failed access count tracking (used internally by SignInManager on bad password attempts)
await _userManager.AccessFailedAsync(user);      // increments count, auto-locks if threshold hit
await _userManager.ResetAccessFailedCountAsync(user);   // reset on successful login
```

**Explain**

Lockout is Identity's built-in brute-force protection — instead of you tracking failed login attempts yourself, `UserManager`/`SignInManager` do it automatically
and temporarily lock the account after too many bad password attempts. Let me walk through every piece.

**The mental model**

Two things control whether a user can be locked out:

1. **LockoutEnabled** (per-user flag) — is lockout even possible for this user?
2. **LockoutEnd** (per-user timestamp) — is the user currently locked out (i.e., is this timestamp in the future)?

And one counter drives it:

3. **AccessFailedCount** — how many consecutive bad password attempts has this user racked up? Once it hits the configured max, Identity locks them out
   automatically.

All of this maps directly to columns already on `IdentityUser<TKey>` you saw earlier — `LockoutEnd`, `LockoutEnabled`, `AccessFailedCount` are real database columns,
not something `UserManager` computes on the fly.

**Global configuration first:**

```csharp
builder.Services.AddIdentity<ApplicationUser, ApplicationRole>(options =>
{
    options.Lockout.AllowedForNewUsers = true;              // new users are lockout-eligible by default
    options.Lockout.MaxFailedAccessAttempts = 5;             // lock after 5 bad attempts
    options.Lockout.DefaultLockoutTimeSpan = TimeSpan.FromMinutes(15);  // how long a lockout lasts
})
.AddEntityFrameworkStores<AppDbContext>();
```

`DefaultLockoutTimeSpan` is what gets used when Identity locks someone out automatically (via `AccessFailedAsync` hitting the threshold) — it's the default
duration, not something you set per-lockout-event unless you override it manually.

**GetLockoutEnabledAsync / SetLockoutEnabledAsync — is lockout possible for this user?**

```csharp
bool lockoutEnabled = await _userManager.GetLockoutEnabledAsync(user);
await _userManager.SetLockoutEnabledAsync(user, true);
```

This is a per-user override, not global. Why would you ever turn it off for a specific user? Two common cases:

```csharp
// Case 1: Service/system accounts that should never be lockable
var systemUser = await _userManager.FindByNameAsync("system-integration-account");
await _userManager.SetLockoutEnabledAsync(systemUser, false);

// Case 2: A trusted admin account you don't want accidentally locked
// during, say, automated testing that hammers the login endpoint
```

If `LockoutEnabled` is false for a user, `AccessFailedAsync` still increments the counter, but Identity's `SignInManager` won't actually enforce a lockout —
`IsLockedOutAsync` stays false regardless of the failed count.

**SetLockoutEndDateAsync / GetLockoutEndDateAsync — the actual lock**

```csharp
await _userManager.SetLockoutEndDateAsync(user, DateTimeOffset.UtcNow.AddMinutes(15));

DateTimeOffset? lockoutEnd = await _userManager.GetLockoutEndDateAsync(user);
```

This just writes/reads a `DateTimeOffset?` to the `LockoutEnd` column. The logic is simple: if this timestamp is in the future (relative to `UtcNow`), the user is
locked out. Nothing more sophisticated than a stored expiry.

```csharp
// Manually lock someone out for 15 minutes (e.g. you detect suspicious activity)
await _userManager.SetLockoutEndDateAsync(user, DateTimeOffset.UtcNow.AddMinutes(15));

// Lock someone out indefinitely (e.g. admin suspends an account)
await _userManager.SetLockoutEndDateAsync(user, DateTimeOffset.MaxValue);

// Unlock someone immediately (clear the lockout early)
await _userManager.SetLockoutEndDateAsync(user, null);
// or equivalently, set it to a time in the past:
await _userManager.SetLockoutEndDateAsync(user, DateTimeOffset.UtcNow.AddMinutes(-1));
```

> **Note:** `LockoutEnabled` must also be true for this to actually take effect during sign-in checks — setting `LockoutEnd` on a user with `LockoutEnabled = false` has no
> practical effect.

**AccessFailedAsync / ResetAccessFailedCountAsync — the auto-lockout trigger**

This is the piece that ties failed logins to automatic lockout, and it's normally called for you by `SignInManager`, not something you call directly in most apps.

```csharp
await _userManager.AccessFailedAsync(user);
await _userManager.ResetAccessFailedCountAsync(user);
```

`AccessFailedAsync` does two things:

- Increments `AccessFailedCount` by 1 and saves it.
  If the new count >= `MaxFailedAccessAttempts` (5, from your config) and `LockoutEnabled == true`, it automatically calls `SetLockoutEndDateAsync(user, UtcNow.Add(DefaultLockoutTimeSpan))` for you — locking the account for 15 minutes without you writing that logic yourself.

- `ResetAccessFailedCountAsync` just zeroes the counter back to 0 — called after a successful login so a user's occasional typo doesn't accumulate toward lockout
  indefinitely.

### External logins

External logins let a user sign in via a third-party provider (Google, Microsoft, GitHub, Facebook) instead of — or in addition to — a local password.
Identity's job here isn't to talk to Google itself (that's OAuth middleware's job); Identity's job is just to remember the link between "this external account"
and "this local user record" once the OAuth handshake succeeds.

```csharp
var info = new UserLoginInfo("Google", "108234982374982374", "Google");
await _userManager.AddLoginAsync(user, info);
await _userManager.RemoveLoginAsync(user, "Google", "108234982374982374");
IList<UserLoginInfo> logins = await _userManager.GetLoginsAsync(user);
```

**Here's the same flow simplified into numbered steps — easier to follow than the ASCII art:**

**Step-by-step**

**Step 1 — User clicks "Sign in with Google"**

Frontend (Angular) triggers a redirect.

**Step 2 — Frontend redirects browser to Google**

Browser navigates away to `accounts.google.com` with your `client_id`, `redirect_uri`, and requested scopes.

**Step 3 — Google shows login + consent screen**

User enters Google credentials (or is already signed in) and approves access. This all happens on Google's page — your app has no visibility here.

**Step 4 — Google redirects back with a token**

Browser is sent back to your app's redirect URI with an `id_token` attached.

**Step 5 — Frontend sends the token to your API**

```http
POST /api/auth/google
{ "idToken": "eyJhbGciOi..." }
```

**Step 6 — API validates the token**

Checks signature, issuer, audience — then extracts `sub` (providerKey), `email`, `name`.

**Step 7 — API checks the database**

```text
FindByLoginAsync("Google", sub)
Found → user already linked, skip to Step 9
Not found → check FindByEmailAsync(email) → link or create a new user
```

**Step 8 — API creates/links user (only if new)**

```text
CreateAsync(newUser)
AddLoginAsync(newUser, googleLoginInfo)
```

**Step 9 — API generates a JWT**

Your own access token, not Google's.

**Step 10 — API responds to frontend**

```http
200 OK { "token": "..." }
```

**Step 11 — Frontend stores token, user is logged in**

Redirect to dashboard.

**The mental model**

Two systems work together, and it's important not to conflate them:

- **OAuth middleware** (`AddGoogle`, `AddMicrosoftAccount`, etc.) — handles the actual redirect-to-Google, user-logs-in-on-Google's-site,
  Google-redirects-back-with-a-code flow. This is not part of `UserManager` at all.
- **UserManager's external login methods** — once step 1 succeeds and you have the provider's identifier for that user, these methods store/retrieve/remove the link
  between that external identity and your local `ApplicationUser` row.

The three methods you posted are step 2 — pure bookkeeping on the `IdentityUserLogin<TKey>` table from earlier.

**UserLoginInfo — what identifies an external account**

```csharp
public UserLoginInfo(string loginProvider, string providerKey, string displayName)
```

**The critical detail:**

`providerKey` should be the provider's stable subject identifier (the `sub` claim in OpenID Connect), never the email address — a user can change their Google
email, but their Google account ID never changes.

**AddLoginAsync — linking an external account to a local user**

```csharp
var info = new UserLoginInfo("Google", "108234982374982374", "Google");
await _userManager.AddLoginAsync(user, info);
```

This writes a row into `AspNetUserLogins`:

| LoginProvider | ProviderKey        | ProviderDisplayName | UserId |
| ------------- | ------------------ | ------------------- | ------ |
| Google        | 108234982374982374 | Google              | 5      |

**Scenario A — brand-new user, signing up via Google (no local account exists yet)**

```csharp
[HttpGet("signin-google-callback")]
public async Task<IActionResult> GoogleCallback()
{
    // ASP.NET Core's OAuth middleware already validated the Google response
    // and authenticated an external "temporary" principal at this point
    var authResult = await HttpContext.AuthenticateAsync(IdentityConstants.ExternalScheme);
    if (!authResult.Succeeded)
        return BadRequest("External authentication failed.");

    var externalPrincipal = authResult.Principal;
    string providerKey = externalPrincipal.FindFirstValue(ClaimTypes.NameIdentifier); // Google's sub
    string email = externalPrincipal.FindFirstValue(ClaimTypes.Email);
    string name = externalPrincipal.FindFirstValue(ClaimTypes.Name);

    var info = new UserLoginInfo("Google", providerKey, "Google");

    // Try to find an existing link first (see GetLoginsAsync section below for the reverse lookup)
    var existingUser = await _userManager.FindByLoginAsync("Google", providerKey);

    if (existingUser != null)
    {
        // Already linked — just issue a JWT, no need to create anything
        return Ok(new { token = GenerateJwt(existingUser) });
    }

    // No link exists — check if a local account with this email already exists
    var userByEmail = await _userManager.FindByEmailAsync(email);

    if (userByEmail != null)
    {
        // Local account exists (e.g. they signed up with password originally) —
        // link Google to it so they can use either method going forward
        await _userManager.AddLoginAsync(userByEmail, info);
        return Ok(new { token = GenerateJwt(userByEmail) });
    }

    // Truly new user — create local account AND link Google in one go
    var newUser = new ApplicationUser { UserName = email, Email = email, FullName = name, EmailConfirmed = true };
    var createResult = await _userManager.CreateAsync(newUser);   // no password set
    if (!createResult.Succeeded)
        return BadRequest(createResult.Errors);

    await _userManager.AddLoginAsync(newUser, info);

    return Ok(new { token = GenerateJwt(newUser) });
}
```

**Scenario B — existing logged-in user wants to link a second provider (e.g. "Connect your Microsoft account" in account settings)**

```csharp
[HttpPost("link-microsoft")]
[Authorize]
public async Task<IActionResult> LinkMicrosoft([FromBody] ExternalLoginCallbackDto dto)
{
    var user = await _userManager.GetUserAsync(User);   // currently logged-in user

    var info = new UserLoginInfo("Microsoft", dto.ProviderKey, "Microsoft");

    var result = await _userManager.AddLoginAsync(user, info);

    if (!result.Succeeded)
    {
        // Common failure: "LoginAlreadyAssociated" — this Microsoft account
        // is already linked to a DIFFERENT local user
        return BadRequest(result.Errors);
    }

    return Ok(new { message = "Microsoft account linked successfully." });
}
```

**RemoveLoginAsync — unlinking**

```csharp
await _userManager.RemoveLoginAsync(user, "Google", "108234982374982374");
```

Deletes that specific row from `AspNetUserLogins`. Needs both `loginProvider` and `providerKey` because a user could theoretically have multiple entries under the same provider in edge cases (rare, but the composite key requires both to identify one exact row).

```csharp
[HttpPost("unlink-provider")]
[Authorize]
public async Task<IActionResult> UnlinkProvider(string provider, string providerKey)
{
    var user = await _userManager.GetUserAsync(User);

    // Guard rail worth adding yourself: don't let a user unlink their
    // ONLY sign-in method if they have no password set either
    bool hasPassword = await _userManager.HasPasswordAsync(user);
    var logins = await _userManager.GetLoginsAsync(user);

    if (!hasPassword && logins.Count == 1)
        return BadRequest("Cannot remove your only sign-in method. Set a password first.");

    var result = await _userManager.RemoveLoginAsync(user, provider, providerKey);

    return result.Succeeded ? Ok() : BadRequest(result.Errors);
}
```

### Two-factor authentication (2FA)

```csharp
await _userManager.SetTwoFactorEnabledAsync(user, true);
bool enabled = await _userManager.GetTwoFactorEnabledAsync(user);

// Authenticator app (TOTP) setup
string authenticatorKey = await _userManager.GetAuthenticatorKeyAsync(user);
if (authenticatorKey == null)
{
    await _userManager.ResetAuthenticatorKeyAsync(user);
    authenticatorKey = await _userManager.GetAuthenticatorKeyAsync(user);
}
// ... show authenticatorKey as a QR code for the user to scan ...

bool codeValid = await _userManager.VerifyTwoFactorTokenAsync(
    user, TokenOptions.DefaultAuthenticatorProvider, "123456");

// Recovery codes
IEnumerable<string> recoveryCodes = await _userManager.GenerateNewTwoFactorRecoveryCodesAsync(user, 10);
int remaining = await _userManager.CountRecoveryCodesAsync(user);
```

**Is it one secret per user? — Yes**

Each user gets their own independent, randomly generated secret, stored against their specific `UserId` in the `AspNetUserTokens` table:

```text
UserId | LoginProvider     | Name             | Value
  5    | [AspNetUserStore] | AuthenticatorKey | JBSWY3DPEHPK3PXP
  12   | [AspNetUserStore] | AuthenticatorKey | QX7MZKLP2VNRWTBS
  47   | [AspNetUserStore] | AuthenticatorKey | HYRTL9DKAXFPQZ4E
```

This has to be true — if every user shared the same secret, anyone's authenticator app would generate valid codes for everyone's account. The whole security
model depends on the secret being unique per user, since it's the only thing distinguishing "this specific person's phone" from anyone else's.

**Is it one-time? — Depends what you mean by "one-time"**

Here it's worth separating two different things: the secret itself vs the codes it generates.

The secret is long-lived, not one-time. Once generated, it stays the same indefinitely — that's exactly why it works. If the secret changed every time, the
phone and server would immediately go out of sync and no code would ever match, since both sides need to be computing against the same secret to land on the
same 6-digit result.

**What's actually inside the QR code**

The QR code is just a visual encoding of this URI:

```text
otpauth://totp/TaskManagementApp:aman@example.com?secret=JBSWY3DPEHPK3PXP&issuer=TaskManagementApp&digits=6
```

Everything except `secret` is just display metadata. The secret is the entire mechanism.

**Why this needs a QR code instead of just typing it**

It doesn't, strictly — most authenticator apps also let you manually type the secret (`JBSWY3DPEHPK3PXP`) instead of scanning. The QR code just exists because
typing a 16+ character random base32 string correctly is annoying and error-prone; scanning is a UX shortcut, not a security requirement.

**What the phone actually does with it**

Once scanned, the authenticator app stores that raw secret locally on the phone — nothing else is ever transmitted between your server and the phone again.
From that point on, both sides compute the code completely independently.

**If the phone is lost — this is exactly why re-setup is needed**

Since the secret only ever lived in two places (your DB and that one physical phone), losing the phone means that copy is gone. There's no way to "recover" it
remotely — which is precisely why:

- Recovery codes exist as the backup plan, and
- Re-enabling 2FA on a new phone requires generating a brand new secret via `ResetAuthenticatorKeyAsync` and scanning a new QR code — you can't transfer the old
  secret to a new phone, because neither the user nor your server has any way to read it back out of the lost device.

**How it works**

```text
Server (stores secret) ────┐
                            ├──> Current time (30 second window)
Phone app (stores same secret) ──┘

Server        → computes → 482913
Phone app     → computes → 482913

Same secret + same time, computed independently, always matches
```

> **Note:** two devices storing the same secret generate the same code.

## Cookie

A cookie is a small piece of data that a server tells the browser to store, which the browser then automatically sends back with every future request to that
same site. It's the mechanism traditional (non-JWT) web apps use to remember "this browser belongs to a logged-in user" between page loads.

**The basic mechanic**

1. Browser sends a request → Server
2. Server responds with a `Set-Cookie` header
3. Browser stores that cookie
4. Every subsequent request to that domain automatically includes the cookie
5. Server reads the cookie on each request to know who's asking

**A raw HTTP example**

First request — login succeeds, server sets a cookie:

```http
POST /login HTTP/1.1
Host: yourapp.com
Content-Type: application/json

{ "email": "aman@example.com", "password": "P@ssw0rd" }
```

Server response:

```http
HTTP/1.1 200 OK
Set-Cookie: .AspNetCore.Identity.Application=CfDJ8NrA9XyZ...; HttpOnly; Secure; SameSite=Lax; Expires=Wed, 25 Jul 2026 18:00:00 GMT
```

Every request after that, the browser attaches it automatically:

```http
GET /api/tasks HTTP/1.1
Host: yourapp.com
Cookie: .AspNetCore.Identity.Application=CfDJ8NrA9XyZ...
```

You never wrote any JavaScript to attach that cookie — the browser does it automatically for every request to `yourapp.com`, until it expires or is cleared.

## SignInManager

`UserManager<TUser>` and `SignInManager<TUser>` sit at different layers — `UserManager` owns the user record itself (data), `SignInManager` owns the act of signing in
(session/cookie/authentication state). They're used together, not as alternatives to each other.

`SignInManager` is actually built on top of `UserManager` — it calls into `UserManager` internally for password checks, lockout checks, etc., then adds the
cookie-writing behavior on top.

**Where this matters for your setup specifically**

Since you're doing JWT-based auth (not cookie-based), this is the key thing to understand: `SignInManager`'s main job — setting an auth cookie — is largely
irrelevant to you. You mostly work directly with `UserManager` and skip `SignInManager` almost entirely, or use only specific pieces of it.

**Example — the traditional cookie-based flow (SignInManager-driven)**

This is the "textbook" ASP.NET Core MVC/Razor Pages pattern:

```csharp
public class AccountController : Controller
{
    private readonly UserManager<ApplicationUser> _userManager;
    private readonly SignInManager<ApplicationUser> _signInManager;

    public AccountController(
        UserManager<ApplicationUser> userManager,
        SignInManager<ApplicationUser> signInManager)
    {
        _userManager = userManager;
        _signInManager = signInManager;
    }

    [HttpPost("login")]
    public async Task<IActionResult> Login(string email, string password)
    {
        // SignInManager handles EVERYTHING: password check, lockout check,
        // 2FA check, AND sets the auth cookie on success
        var result = await _signInManager.PasswordSignInAsync(
            email, password, isPersistent: false, lockoutOnFailure: true);

        if (result.RequiresTwoFactor)
            return RedirectToPage("/Account/LoginWith2fa");

        if (result.IsLockedOut)
            return RedirectToPage("/Account/Lockout");

        if (!result.Succeeded)
            return BadRequest("Invalid login.");

        // Cookie is already set — user is "logged in" as far as ASP.NET Core is concerned
        return RedirectToPage("/Index");
    }

    [HttpPost("logout")]
    public async Task<IActionResult> Logout()
    {
        await _signInManager.SignOutAsync();   // clears the auth cookie
        return RedirectToPage("/Index");
    }
}
```

**Notice:** you never called `UserManager.CheckPasswordAsync` yourself here — `SignInManager.PasswordSignInAsync` did it internally, along with the lockout bookkeeping
(`AccessFailedAsync`/`ResetAccessFailedCountAsync`) and cookie writing, all in one call.

**Where cookie fits with SignInManager**

This is exactly what `SignInManager.PasswordSignInAsync` does under the hood — instead of you writing `Set-Cookie` headers by hand, it calls `HttpContext.SignInAsync(...)`,
which serializes the user's identity into an encrypted cookie value and attaches the `Set-Cookie` header to the response for you:

```csharp
// What SignInManager.PasswordSignInAsync essentially does internally:
var claimsPrincipal = await _claimsFactory.CreateAsync(user); // user id, roles, etc. as claims
await HttpContext.SignInAsync(IdentityConstants.ApplicationScheme, claimsPrincipal);
// ^ this line is what actually issues the Set-Cookie header
```

On every subsequent request, ASP.NET Core's cookie authentication middleware reads that cookie, decrypts it, and populates `HttpContext.User` for you
automatically — which is why in a cookie-based app you can just write:

```csharp
[Authorize]
[HttpGet("profile")]
public IActionResult GetProfile()
{
    var userId = User.FindFirstValue(ClaimTypes.NameIdentifier);   // just works, no manual token parsing
    return Ok(new { userId });
}
```

## .AddIdentityCore&lt;ApplicationUser&gt;

`AddIdentityCore<TUser>` is the leaner, API-focused sibling of `AddIdentity<TUser, TRole>` — it registers only the core user-management services (password hashing,
`UserManager`, validators, stores) without any of the cookie-based web UI machinery that `AddIdentity` pulls in by default. It's the method most people building
pure Web APIs (like yours) should actually be using.

**What AddIdentityCore registers**

```csharp
builder.Services.AddIdentityCore<ApplicationUser>(options =>
{
    options.Password.RequiredLength = 8;
    options.Password.RequireNonAlphanumeric = false;
    options.User.RequireUniqueEmail = true;
})
.AddEntityFrameworkStores<AppDbContext>()
.AddDefaultTokenProviders();
```

**This gives you:**

- `UserManager<ApplicationUser>`
- `IUserStore<ApplicationUser>` (wired to EF Core via `AddEntityFrameworkStores`)
- Password hasher, validators (`IPasswordValidator`, `IUserValidator`)
- Token providers (for email confirmation, password reset, 2FA, etc.)

That's it. No roles by default, no `SignInManager`, no cookie authentication scheme, no external login (OAuth) cookie handler.

**What AddIdentity registers on top of that**

```csharp
builder.Services.AddIdentity<ApplicationUser, ApplicationRole>(options => { ... })
.AddEntityFrameworkStores<AppDbContext>()
.AddDefaultTokenProviders();
```

`AddIdentity` internally calls `AddIdentityCore` and then adds:

- `RoleManager<TRole>` and role store wiring
- `SignInManager<TUser>`
- Registers the cookie authentication scheme (`IdentityConstants.ApplicationScheme`) — sets ASP.NET Core up to expect cookie-based sign-in
- The external cookie scheme (`IdentityConstants.ExternalScheme`) — used during OAuth callbacks
- The two-factor cookie schemes used by `SignInManager`'s 2FA challenge flow

**The key practical difference:**

```csharp
// AddIdentity — assumes you want cookie-based sign-in as your default auth scheme
builder.Services.AddIdentity<ApplicationUser, ApplicationRole>()
    .AddEntityFrameworkStores<AppDbContext>();

// This SILENTLY sets your app's default authentication scheme to cookies —
// which conflicts with JWT bearer auth if you add that afterward
builder.Services.AddAuthentication(options =>
{
    options.DefaultAuthenticateScheme = JwtBearerDefaults.AuthenticationScheme;   // fights with AddIdentity's cookie default
})
.AddJwtBearer(...);
```

If you call `AddIdentity` in a pure API project and then also configure JWT bearer auth, you can end up with two competing authentication schemes both trying to
claim "default," which causes confusing behavior — like `[Authorize]` unexpectedly redirecting to a login page (a cookie-auth behavior) instead of returning 401.

`AddIdentityCore` sidesteps this entirely — it registers zero authentication schemes, so your `AddAuthentication().AddJwtBearer(...)` setup is the only one in
play, with no conflict:

```csharp
// Clean setup for a JWT-based API — this is your actual pattern
builder.Services.AddIdentityCore<ApplicationUser>(options =>
{
    options.Password.RequiredLength = 8;
})
.AddRoles<ApplicationRole>()              // add roles back in manually, since Core doesn't include them
.AddEntityFrameworkStores<AppDbContext>()
.AddDefaultTokenProviders();

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ValidateIssuerSigningKey = true,
            ValidIssuer = builder.Configuration["Jwt:Issuer"],
            ValidAudience = builder.Configuration["Jwt:Audience"],
            IssuerSigningKey = new SymmetricSecurityKey(
                Encoding.UTF8.GetBytes(builder.Configuration["Jwt:Key"]))
        };
    });
```

Notice `.AddRoles<ApplicationRole>()` — since `AddIdentityCore` doesn't include role support by default (unlike `AddIdentity<TUser, TRole>`, which takes the role
type as a generic parameter directly), you opt back into it explicitly with this chained call if you need `RoleManager`/roles at all.

**The dividing line to remember**

- Same app renders both the UI and handles the API → `AddIdentity` + cookies + `SignInManager`
- Separate frontend (Angular/React) calling a REST API → `AddIdentityCore` + JWT bearer

## AddEntityFrameworkStores

`AddEntityFrameworkStores<TContext>()` is the piece that wires `UserManager`/`RoleManager` to your actual database — without it, `UserManager` has no idea how to read/
write users, because Identity is deliberately storage-agnostic by default.

**Why this call exists at all**

`UserManager<TUser>` never talks to EF Core directly. It talks to an abstraction: `IUserStore<TUser>`. Internally, every `UserManager` method is just a thin wrapper
that delegates to this interface:

```csharp
// Conceptually, what CreateAsync looks like inside UserManager
public async Task<IdentityResult> CreateAsync(TUser user)
{
    // ... validation ...
    return await Store.CreateAsync(user);   // Store is an IUserStore<TUser>
}
```

If you call `AddIdentityCore<ApplicationUser>()` without `.AddEntityFrameworkStores<AppDbContext>()`, there's no registered `IUserStore<TUser>` implementation at all — `UserManager` gets injected, but any method you call on it throws at runtime because the underlying store is missing.

`.AddEntityFrameworkStores<AppDbContext>()` is what registers the EF Core-backed implementation of that store:

```csharp
// This is what the method does internally (Microsoft's implementation, not code you write):
services.AddScoped<IUserStore<ApplicationUser>>(sp =>
    new UserStore<ApplicationUser, ApplicationRole, AppDbContext, int>(sp.GetRequiredService<AppDbContext>()));

services.AddScoped<IRoleStore<ApplicationRole>>(sp =>
    new RoleStore<ApplicationRole, AppDbContext, int>(sp.GetRequiredService<AppDbContext>()));
```

`UserStore<TUser, TRole, TContext, TKey>` is Microsoft's built-in EF Core implementation of `IUserStore<TUser>` — it translates every abstract store call
(`CreateAsync`, `FindByIdAsync`, `AddToRoleAsync`, etc.) into actual EF Core `DbContext` operations (`Add`, `SaveChangesAsync`, LINQ queries) against your `AppDbContext`.

## AddDefaultTokenProviders

`AddDefaultTokenProviders()` registers the built-in token generation/verification mechanisms that power every token-based feature you've used so far — password
reset, email confirmation, 2FA/authenticator codes, and OTP. Without it, calling any of those methods throws at runtime, the same way `UserManager` methods throw
without `AddEntityFrameworkStores`.

## AddHttpContextAccessor

`AddHttpContextAccessor()` registers a service that lets you access the current HTTP request/response from places in your code where `HttpContext` isn't normally
available as a parameter — most commonly, inside services, repositories, or other classes that sit outside the controller layer.

**Why this is needed at all**

In a controller, `HttpContext` is just handed to you automatically:

```csharp
public class TaskController : ControllerBase
{
    [HttpGet]
    public IActionResult Get()
    {
        var userId = User.FindFirstValue(ClaimTypes.NameIdentifier);  // User = HttpContext.User, built in
        return Ok();
    }
}
```

But the moment you're inside a service class that a controller calls into — say, your Clean Architecture Application layer — there's no `HttpContext` parameter
available. Controllers and services are wired up differently in ASP.NET Core's DI: `HttpContext` is scoped to the current request internally by the framework,
not automatically injected into arbitrary classes.

```csharp
// This does NOT work — HttpContext isn't injectable directly into a plain service
public class TaskService
{
    public TaskService(HttpContext context)   // ❌ no provider registered for this by default
    {
    }
}
```

**What AddHttpContextAccessor actually provides**

```csharp
builder.Services.AddHttpContextAccessor();
```

This registers `IHttpContextAccessor` as a singleton in DI. Internally, it's backed by `AsyncLocal<T>` — a .NET mechanism that flows a value through the async call
chain of a single request, so even deeply nested service calls can reach back to "the current request's `HttpContext`" without it being explicitly passed down
through every method signature.

```csharp
public class TaskService
{
    private readonly IHttpContextAccessor _httpContextAccessor;

    public TaskService(IHttpContextAccessor httpContextAccessor)
    {
        _httpContextAccessor = httpContextAccessor;
    }

    public string GetCurrentUserId()
    {
        var user = _httpContextAccessor.HttpContext?.User;
        return user?.FindFirstValue(ClaimTypes.NameIdentifier);
    }
}
```

**A gotcha worth knowing — nullability**

`IHttpContextAccessor.HttpContext` is nullable by design — outside the context of an actual HTTP request (e.g. a background job, a hosted service, a
console-triggered operation, or even certain DI resolution timings), there is no current request, so it returns `null`. Always null-check, as shown in every
example above — code that assumes `HttpContext` is always present will throw a `NullReferenceException` the moment it runs somewhere without an active request (a
very common bug when the same service class gets reused inside a background job).

## Seed the roles (one-time, at startup)

```csharp
public static class RoleSeeder
{
    public static async Task SeedRolesAsync(IServiceProvider services)
    {
        var roleManager = services.GetRequiredService<RoleManager<ApplicationRole>>();

        string[] roleNames = { "Admin", "Manager", "User" };

        foreach (var roleName in roleNames)
        {
            if (!await roleManager.RoleExistsAsync(roleName))
            {
                await roleManager.CreateAsync(new ApplicationRole { Name = roleName });
            }
        }
    }
}

// Program.cs — run once at startup
using (var scope = app.Services.CreateScope())
{
    await RoleSeeder.SeedRolesAsync(scope.ServiceProvider);
}
```

## Keep these endpoints public always

Yes — and it's not optional, it's required. If you've set the `FallbackPolicy` to require authentication by default (as shown earlier), your login
endpoint becomes unreachable unless you explicitly mark it `[AllowAnonymous]` — which creates an obvious chicken-and-egg problem: you can't get a token
without hitting login, and you can't hit login without a token.

**Why this specific endpoint must be public**

```csharp
builder.Services.AddAuthorization(options =>
{
    options.FallbackPolicy = new AuthorizationPolicyBuilder()
        .RequireAuthenticatedUser()
        .Build();   // everything requires auth by default now
});
```

With this in place:

```csharp
[HttpPost("login")]
public async Task<IActionResult> Login(LoginDto dto) { ... }
// Without [AllowAnonymous], this now ALSO requires a valid JWT to even reach it — a dead end
```

```csharp
[HttpPost("login")]
[AllowAnonymous]   // required — this is the entry point, nobody has a token yet
public async Task<IActionResult> Login(LoginDto dto) { ... }
```

`[AllowAnonymous]` is an explicit escape hatch that overrides the `FallbackPolicy` for that specific endpoint — everything else stays locked down, this one is deliberately opened.

**Which other endpoints also need it**

Any endpoint that's part of getting a user to an authenticated state — not endpoints used by an authenticated user:

```csharp
[HttpPost("login")]
[AllowAnonymous]
public async Task<IActionResult> Login(LoginDto dto) { ... }

[HttpPost("register")]
[AllowAnonymous]
public async Task<IActionResult> Register(RegisterDto dto) { ... }

[HttpPost("refresh")]
[AllowAnonymous]   // the whole point of a refresh token is getting a new access token WITHOUT re-logging in
public async Task<IActionResult> Refresh(RefreshDto dto) { ... }

[HttpPost("forgot-password")]
[AllowAnonymous]
public async Task<IActionResult> ForgotPassword(ForgotPasswordDto dto) { ... }

[HttpPost("reset-password")]
[AllowAnonymous]
public async Task<IActionResult> ResetPassword(ResetPasswordDto dto) { ... }

[HttpPost("confirm-email")]
[AllowAnonymous]
public async Task<IActionResult> ConfirmEmail(ConfirmEmailDto dto) { ... }

[HttpPost("auth/google")]
[AllowAnonymous]   // external login callback — no local JWT exists yet at this point either
public async Task<IActionResult> GoogleLogin(GoogleLoginDto dto) { ... }
```

The refresh endpoint is worth calling out specifically — it's easy to instinctively lock it down since it feels like a "sensitive" auth operation, but
its entire purpose is issuing a new access token because the old one already expired. If you require a valid access token to reach it, it becomes
useless — you'd need a valid token to get a new token.

**What must stay locked down (the whole point of the fallback policy)**

```csharp
[HttpGet("tasks")]
[Authorize]   // implicit anyway due to FallbackPolicy, but fine to be explicit
public async Task<IActionResult> GetTasks() { ... }

[HttpPost("2fa/setup")]
[Authorize]   // must already be logged in to set up 2FA on your own account
public async Task<IActionResult> Setup2fa() { ... }

[HttpDelete("tasks/{id}")]
[Authorize(Roles = "Admin")]
public async Task<IActionResult> DeleteTask(int id) { ... }
```
