# ASP - Model Binding

Model binding in ASP.NET Core is a mechanism that automatically maps data from incoming HTTP requests to action method parameters or model properties,
eliminating the need for manual parsing and type conversion.

## How Model Binding Works

The model binding system automatically retrieves data from various parts of the HTTP request and attempts to match them to the target parameter or property
name (case-insensitive).

For complex types specified with the `[FromBody]` attribute, the system uses input formatters (like the default JSON formatter) to read data from the request
body.

**Big Picture Flow (VERY IMPORTANT)**

```text
Client Request
   ↓
Routing (find action)
   ↓
Model Binding (map data → parameters)
   ↓
Model Validation (check rules)
   ↓
Controller Action executes
   ↓
Response
```

**Example**

**Example 1 (Start Simple)**

```csharp
// GET /api/products/5?name=pen
[HttpGet("{id}")]
public IActionResult Get(int id, string name)
{
    return Ok(new { id, name });
}
```

👉 Quick question for you (don't skip):

Where does `id` come from? Route or Query?
(Answer in your head before reading ↓)

✔ **Answer:**

- `id` → Route (`/5`)
- `name` → Query (`?name=pen`)

## Key Attributes for Model Binding

You can use specific attributes to control where model binding retrieves data:

- `[FromQuery]`: Binds data exclusively from the query string.
- `[FromRoute]`: Binds data exclusively from route parameters.
- `[FromForm]`: Binds data exclusively from posted form fields.
- `[FromHeader]`: Binds data exclusively from HTTP headers.
- `[FromBody]`: Binds data from the request body (e.g., a JSON payload). An action method can have at most one parameter with this attribute.
- `[Bind]`: Specifies which properties of a model should be included in or excluded from model binding to protect against overposting vulnerabilities.
- `[BindNever]`: Instructs the model binder to skip a specific property.

## Why do we need [Bind] and [BindNever]?

👉 **Problem: Overposting (Mass Assignment)**

Imagine this model:

```csharp
public class Product
{
    public int Id { get; set; }
    public string Name { get; set; }
    public decimal Price { get; set; }
    public bool IsAdminOnly { get; set; }  // ⚠️ sensitive
}
```

❌ **Dangerous Scenario**

User sends:

```json
{
  "name": "Pen",
  "price": 10,
  "isAdminOnly": true
}
```

👉 Question for you:

Should a normal user be able to set `IsAdminOnly = true`?
(Think before reading 👇)

✔️ **Answer:** NO — but model binding will bind it automatically 😬

👉 That's overposting vulnerability

### 1. [Bind] — Control What Gets Bound

**What it does**

Allows you to include or exclude properties during model binding.

**Example (Include only safe fields)**

```csharp
[HttpPost]
public IActionResult Create([Bind("Name,Price")] Product product)
{
    return Ok(product);
}
```

🧠 **What happens?**

Even if user sends:

```json
{
  "name": "Pen",
  "price": 10,
  "isAdminOnly": true
}
```

👉 Result:

```csharp
product.IsAdminOnly == false  // ignored
```

🔥 **Key Idea**

- Only `Name` and `Price` are allowed
- Everything else is ignored

⚠️ **Limitation**

👉 `[Bind]` is:

- Hard to maintain for large models
- Easy to forget fields

### 🔥 2. [BindNever] — Block Specific Properties

**What it does**

Prevents a property from ever being bound from request.

**Example**

```csharp
using Microsoft.AspNetCore.Mvc.ModelBinding;

public class Product
{
    public int Id { get; set; }

    public string Name { get; set; }

    public decimal Price { get; set; }

    [BindNever]
    public bool IsAdminOnly { get; set; }
}
```

🧠 **What happens?**

Even if client sends:

```json
{
  "name": "Pen",
  "price": 10,
  "isAdminOnly": true
}
```

👉 Result:

```csharp
IsAdminOnly = false   // NOT bound
```

### 3. Real-World Best Practice (VERY IMPORTANT)

👉 In real projects:

- ❌ Don't rely heavily on `[Bind]`
- ❌ Don't expose entity directly

Use DTO (Data Transfer Object).

**Example (Best approach)**

```csharp
public class CreateProductDto
{
    public string Name { get; set; }
    public decimal Price { get; set; }
}
```

```csharp
[HttpPost]
public IActionResult Create(CreateProductDto dto)
{
    var product = new Product
    {
        Name = dto.Name,
        Price = dto.Price,
        IsAdminOnly = false  // controlled by server
    };

    return Ok(product);
}
```

| Feature         | `[Bind]`  | `[BindNever]` | DTO (Best) |
| --------------- | --------- | ------------- | ---------- |
| Control level   | Medium    | Specific      | Full       |
| Security        | ⚠️ Medium | Good          | 🔥 Best    |
| Maintainability | ❌ Poor    | Good          | Best       |

## Custom Model Binding

For scenarios where the default behavior doesn't meet your needs, you can implement custom model binders by creating a class that implements the `IModelBinder`
interface. This allows you to define specific logic for transforming input data into complex types, such as converting a custom formatted string into a
specific class instance.

🧠 **Problem**

Default model binding works for:

`int`, `string`, objects ✅

But what if you want:

- 👉 Convert a custom format → object
- 👉 Combine multiple inputs → one model
- 👉 Parse complex values (e.g., `"1,2,3"` → `List<int>`)

🎯 **Example Problem**

```http
GET /api/products?ids=1,2,3
```

👉 You want:

```csharp
List<int> ids = [1,2,3]
```

❌ Default binder cannot parse `"1,2,3"` into `List<int>` automatically

🔥 **Goal**

We will build:

```csharp
[HttpGet]
public IActionResult Get([FromQuery] List<int> ids)
```

👉 And make it work with:

```http
/api/products?ids=1,2,3
```

**Step 1: Create custom model binder**

```csharp
using Microsoft.AspNetCore.Mvc.ModelBinding;

public class CommaSeparatedModelBinder : IModelBinder
{
    public Task BindModelAsync(ModelBindingContext context)
    {
        var value = context.ValueProvider.GetValue(context.ModelName).FirstValue;

        if (string.IsNullOrEmpty(value))
            return Task.CompletedTask;

        var values = value.Split(',')
                          .Select(x => int.TryParse(x, out var val) ? val : 0)
                          .ToList();

        context.Result = ModelBindingResult.Success(values);

        return Task.CompletedTask;
    }
}
```

**Step 2: Create Binder Provider**

```csharp
using Microsoft.AspNetCore.Mvc.ModelBinding;

public class CommaSeparatedModelBinderProvider : IModelBinderProvider
{
    public IModelBinder GetBinder(ModelBinderProviderContext context)
    {
        if (context.Metadata.ModelType == typeof(List<int>))
        {
            return new CommaSeparatedModelBinder();
        }

        return null;
    }
}
```

**Step 3: Register Binder**

`Program.cs`

```csharp
builder.Services.AddControllers(options =>
{
    options.ModelBinderProviders.Insert(0, new CommaSeparatedModelBinderProvider());
});
```

🧠 **Why Insert(0)?**

👉 Gives highest priority

**Step 4: Use in Controller**

```csharp
[HttpGet]
public IActionResult Get([FromQuery] List<int> ids)
{
    return Ok(ids);
}
```

### Alternative (Simpler Way — Attribute Based)

Instead of provider, you can do:

```csharp
public IActionResult Get(
    [ModelBinder(BinderType = typeof(CommaSeparatedModelBinder))]
    List<int> ids)
{
    return Ok(ids);
}
```

### Real-World Use Cases

**1. Comma-separated values**

```text
ids=1,2,3
```

**2. Custom date format**

```text
date=20-03-2026
```

**3. Encrypted IDs**

```text
id=asdj123encoded
```

**4. Complex filtering**

```text
filter=name:pen|price>10
```

Can create for all of them.

# ASP - Model validation

Model Validation ensures incoming data is correct before your API logic runs.
Model validation in ASP.NET Core is primarily achieved using Data Annotations (attributes in the `System.ComponentModel.DataAnnotations` namespace), which
define validation rules directly on model properties.

Think like this:

```text
Client → sends data → Validation checks → Controller runs
```

## Core Concepts

- **Data Annotations:**
  These attributes are applied to model properties to specify validation rules declaratively.
- **Model Binding:**
  The process where incoming HTTP request data (from forms, query strings, or the request body) is mapped to a model class.
- **ModelState.IsValid:**
  A property in controllers that returns `true` if all validation rules passed, and `false` otherwise. You can check this property in your action methods
  and respond accordingly.
- **[ApiController] Attribute:**
  For Web API controllers, this attribute enables automatic model validation. If the model is invalid, it automatically returns an HTTP 400 Bad
  Request response with the validation errors, eliminating the need for explicit `ModelState.IsValid` checks in action methods.

If user sends:

## Custom Attribute with Dependency Injection

👉 When validation needs DB/service access

🎯 **Example: Email must be unique**

**Step 1: Create Service**

**Step 2: Custom Attribute**

```csharp
public class UniqueEmailAttribute : ValidationAttribute
{
    protected override ValidationResult IsValid(object value, ValidationContext context)
    {
        var userService = (IUserService)context.GetService(typeof(IUserService));

        if (value != null && userService.EmailExists(value.ToString()))
        {
            return new ValidationResult("Email already exists");
        }

        return ValidationResult.Success;
    }
}
```

**Step 3: Use it**

```csharp

{

}
```

# ASP - Fluent Validation

FluentValidation is a popular open-source .NET library that facilitates building strongly-typed validation rules using a fluent interface. It is commonly
used in ASP.NET Core projects to separate validation logic from models, making the code cleaner, more readable, and easier to maintain and test.

🧠 **Why not Data Annotations?**

Before FluentValidation, we used:

```csharp
[Required]
[StringLength(50)]
```

👉 **Problems:**

- Clutters your model ❌
- Hard to reuse ❌
- Limited for complex logic ❌

**Key Benefits**

- **Separation of Concerns:**
  Validation rules are defined in separate validator classes, keeping models (entities or DTOs) clean and focused solely on data properties.
- **Strongly Typed Rules:**
  Uses a fluent, lambda-expression-based syntax (`RuleFor(x => x.Property)...`) for building rules, offering better control than data annotations.
- **Complex and Asynchronous Validation:**
  Easily supports conditional, cross-property, and asynchronous validation rules (e.g., checking if an email exists in a database), which are difficult
  or impossible with data annotations.
- **Testability:**
  The separate validator classes are easy to unit test in isolation.

## Usage in ASP.NET Core

To use FluentValidation in an ASP.NET Core project:

**1. Install Necessary NuGet Packages:**

Install the core library and the dependency injection extensions package using the NuGet Package Manager or the .NET CLI:

```bash
dotnet add package FluentValidation
dotnet add package FluentValidation.DependencyInjectionExtensions
```

> **Note:** The `FluentValidation.AspNetCore` package is deprecated in version 12+ and automatic validation via the ASP.NET validation pipeline is no longer
> recommended. Use manual validation or endpoint filters instead.

**2. Define a Model:**

Create a plain C# class for your data transfer object (DTO) or model, without any `[DataAnnotation]` attributes.

**3. Create a Validator Class:**

Create a class that inherits from `AbstractValidator<T>`, where `T` is your model type. Define the validation rules within the constructor using the `RuleFor`
method:

```csharp
public class AuthorValidator : AbstractValidator<Author>
{
    public AuthorValidator()
    {
        RuleFor(x => x.FirstName).NotNull().WithMessage("Author first name cannot be null or empty");
        RuleFor(x => x.Email).NotNull().EmailAddress();
        RuleFor(author => author.NumberOfBooks).NotEmpty().GreaterThan(0);
    }
}
```

**4. Register Validators in Dependency Injection:**

In your `Program.cs` file (or `Startup.cs`), register your validators with the service provider. Assembly scanning is a common approach to register all
validators in an assembly with one line:

```csharp
builder.Services.AddValidatorsFromAssemblyContaining<Program>();
// Or for manual registration:
// builder.Services.AddScoped<IValidator<Author>, AuthorValidator>();
```

## Note

Using `AbstractValidator<T>` from the FluentValidation library within a custom `IActionFilter` (or `IAsyncActionFilter`) is a common pattern in ASP.NET Core
for automating request model validation. This approach separates validation logic from controller logic, keeping controllers clean.

To ensure a parameter is present in a request using FluentValidation, the rule you use depends on the data type of that parameter.

Here is the breakdown of how to handle each scenario to ensure "it's there."

## Check field available in request

**1. For Strings (The Most Common)**

If you want to ensure a string is present, not null, and not just empty whitespace:

Use: `.NotEmpty()`

```csharp
RuleFor(x => x.Value)
    .NotEmpty()
    .WithMessage("The value must be provided and cannot be empty.");
```

**Note:** `.NotEmpty()` is better than `.NotNull()` for strings because it checks for both `null` and `""` (empty string).

**2. For Value Types (int, decimal, DateTime, bool)**

In C#, value types are not nullable by default. If a user doesn't send an `int`, it defaults to `0`. If they don't send a `DateTime`, it defaults to `01/01/0001`.

**The Best Practice:** Make the property nullable in your DTO so you can distinguish between "user sent a 0" and "user sent nothing."

```csharp
// In your DTO/Request class
public int? Age { get; set; } 

// In your Validator
RuleFor(x => x.Age)
    .NotNull()
    .WithMessage("Age is a required field.");
```

## Note : To populate error in model state

Inside `.AddFluentValidation(...)` when configuring MVC: Scans the given assembly for all `IValidator<T>`
implementations and wires them into ASP.NET Core's model binding pipeline. This is what makes
FluentValidation errors flow into `ModelState`.

## Why keep DB validation out of FluentValidation rules

- **Request validation:** Ensures the request payload is structurally valid before it even reaches your service logic.
- **Business validation:** Often requires querying the database (e.g., "does this task already exist?", "is the user allowed to create tasks?"). That
  belongs in the service layer, not the validator.
- **Performance:** FluentValidation runs synchronously during model binding. Adding DB calls here can slow down every request and complicate error handling.
- **Separation of concerns:** Validators should only check request shape and simple rules; services enforce domain rules and interact with persistence.
