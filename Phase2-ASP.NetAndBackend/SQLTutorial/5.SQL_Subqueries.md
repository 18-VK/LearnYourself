# SQL Subqueries

A subquery is a query written inside another SQL query.

It is used to:

- Filter data
- Compare values
- Perform calculations
- Check existence of data

Very common in real backend systems (reporting, validations, business rules).

# Sample Table

```sql
CREATE TABLE Employees (
    Id INT PRIMARY KEY,
    Name NVARCHAR(100),
    Salary DECIMAL(10,2),
    DepartmentId INT
);

CREATE TABLE Departments (

INSERT INTO Departments VALUES

(1, 'Aman', 60000, 1),

(3, 'Priya', 40000, 2),
(4, 'Neha', 45000, 2),
(5, 'Karan', 70000, 3);
```

# Types of Subqueries

## Single-Row Subquery

Returns one value.

🎯 **Example: Employees earning more than average salary**

```sql
SELECT *
FROM Employees
WHERE Salary > (
    SELECT AVG(Salary)
    FROM Employees
);
```

**Inner Query Result**

```text
(60000 + 50000 + 40000 + 45000 + 70000) / 5 = 53000
```

**Result**

| Id | Name  | Salary | DepartmentId |
| -- | ----- | ------ | ------------ |
| 1  | Aman  | 60000  | 1            |
| 5  | Karan | 70000  | 3            |

✅ **Use Case:**

- Compare against calculated value
- Validation logic
- Business thresholds

## Multi-Row Subquery (IN / ANY / ALL)

Returns multiple values.

🎯 **Example: Employees in IT department**

```sql
SELECT *
FROM Employees
WHERE DepartmentId IN (
    SELECT Id
    FROM Departments
    WHERE DeptName = 'IT'
);
```

**Inner Query Result**

```text
Id = 1
```

**Final Result**

| Id | Name  | Salary | DepartmentId |
| -- | ----- | ------ | ------------ |
| 1  | Aman  | 60000  | 1            |
| 2  | Rahul | 50000  | 1            |

✅ **Use Case:**

- Filtering by category
- Role-based filtering
- Dynamic list filtering

## Correlated Subquery

Runs once per outer row.

🎯 **Example: Employees earning more than department average**

```sql
SELECT *
FROM Employees e
WHERE Salary > (
    SELECT AVG(Salary)
    FROM Employees
    WHERE DepartmentId = e.DepartmentId
);
```

🔎 The inner query depends on outer query row.

**Step-by-Step Calculation**

**IT Department (DeptId = 1)**

Employees: Aman (60000), Rahul (50000)
Average = 55000

- ✔ Aman (60000 > 55000)
- ❌ Rahul (50000 < 55000)

**HR Department (DeptId = 2)**

Employees: Priya (40000), Neha (45000)
Average = 42500

- ✔ Neha (45000 > 42500)
- ❌ Priya (40000 < 42500)

**Finance Department (DeptId = 3)**

Only Karan (70000)
Average = 70000

- ❌ 70000 is NOT greater than 70000

**Final Result**

| Id | Name | Salary | DepartmentId |
| -- | ---- | ------ | ------------ |
| 1  | Aman | 60000  | 1            |
| 4  | Neha | 45000  | 2            |

## Subquery in SELECT

Show employee count per department.

```sql
SELECT 
    d.DeptName,
    (SELECT COUNT(*) 
     FROM Employees e 
     WHERE e.DepartmentId = d.Id) AS EmployeeCount
FROM Departments d;
```

**Result**

| DeptName | EmployeeCount |
| -------- | ------------- |
| IT       | 2             |
| HR       | 2             |
| Finance  | 1             |

## 2nd Highest Salary

```sql
SELECT MAX(Salary)
FROM Employees
WHERE Salary < (
    SELECT MAX(Salary)
    FROM Employees
);
```

🔎 **Step 1:**

Highest Salary = 70000

🔎 **Step 2:**

Find max salary less than 70000

✅ **Result**

```text
60000
```

# Important Observations

- **Single-row subquery** → returns one value
- **IN subquery** → returns multiple values
- **Correlated subquery** → runs per row
- **SELECT subquery** → used for computed columns

# JOIN vs Subquery vs EXISTS

Difference Between JOIN vs IN (subquery) vs EXISTS:

| Feature                         | JOIN  | IN (Subquery)       | EXISTS  |
| ------------------------------- | ----- | -----------------   | ------  |
| Returns duplicates?             | Yes   | No                  | No      |
| Best for large data?            | ✅ Yes | ⚠️ Sometimes slow | ✅ Yes  |
| Stops after first match?        | ❌ No  | ❌ No             | ✅ Yes  |
| Needs columns from other table? | ✅ Yes | ❌ No             | ❌ No   |

## PERFORMANCE DIFFERENCE (Very Important)

**Case 1: Large Orders Table (Millions of rows)**

🔹 **EXISTS is usually fastest**

Why?

- EXISTS stops scanning after first match.
- It behaves like semi-join.
- Optimizer short-circuits.

🔹 **JOIN**

- Produces full row combinations.
- May create duplicates.
- Requires `DISTINCT` sometimes.
- More memory usage.

🔹 **IN**

- Older SQL versions:
- IN was slower.
- Could materialize full subquery.

**Modern SQL Server:**

- Optimizer often converts `IN` → `JOIN` or `EXISTS`.
- Performance almost similar.

## Real Performance Rule

| Scenario                      | Best Choice |
| ----------------------------- | ----------- |
| Need columns from both tables | JOIN        |
| Just check existence          | EXISTS      |
| Small dataset                 | Any         |
| Correlated logic              | EXISTS      |
| Avoid duplicates              | EXISTS      |

## If I have to fetch data from multiple tables, then will subquery work efficiently?

- Subqueries can work
- But JOIN is usually more efficient and more scalable when fetching data from multiple tables.

## EXISTS

🧠 **Use Case**

- Check if related data exists
- Validation before processing
- Fraud detection logic

⚡ **Performance**

- Stops at first match
- Uses semi-join
- Efficient for large datasets

**Example: Get customers who have orders**

```sql
SELECT *
FROM Customers c
WHERE EXISTS (
    SELECT 1
    FROM Orders o
    WHERE o.CustomerId = c.Id
);
```

**Result**

| Id | Name  |
| -- | ----- |
| 1  | Aman  |
| 2  | Rahul |

## NOT EXISTS

🧠 **Use Case**

- Find inactive users
- Identify missing records
- Data cleanup

**Example: Get customers with NO orders**

```sql
SELECT *
FROM Customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM Orders o
    WHERE o.CustomerId = c.Id
);
```

**Result**

| Id | Name  |
| -- | ----- |
| 3  | Priya |
| 4  | Neha  |

## IN

The `IN` operator in SQL is used to simplify filtering when you want to check if a column's value matches
any value in a list of options. It's essentially shorthand for multiple `OR` conditions.

**Example: Customer with order(s)**

```sql
SELECT *
FROM Customers
WHERE Id IN (
    SELECT CustomerId FROM Orders
);
```

**Result:**

| Id | Name  |
| -- | ----- |
| 1  | Aman  |
| 2  | Rahul |

**Same using EXISTS**

```sql
SELECT *
FROM Customers c
WHERE EXISTS (
    SELECT 1
    FROM Orders o
    WHERE o.CustomerId = c.Id
);
```

| Id | Name  |
| -- | ----- |
| 1  | Aman  |
| 2  | Rahul |

**Difference**

| Feature     | IN           | EXISTS    |
| ----------- | ------------ | --------- |
| Stops early | ❌ No         | ✅ Yes     |
| NULL safe   | ❌ Risky      | ✅ Safe    |
| Large data  | Medium       | Better    |
| Execution   | Compare list | Semi join |

🎯 **Rule**

Use `EXISTS` for large datasets.

### Multiple columns using INTERSECT

In SQL, the `INTERSECT` operator is used to return the common rows between two `SELECT` queries. When you want multiple columns in the output, you
simply need to ensure that both queries return the same number of columns with compatible data types.

**Example:**

```sql
-- Table: Employees_US
-- Columns: FirstName, LastName, Department

-- Table: Employees_UK
-- Columns: FirstName, LastName, Department

SELECT FirstName, LastName, Department
FROM Employees_US
INTERSECT
SELECT FirstName, LastName, Department
FROM Employees_UK;
```

**Is it mandatory to have same structure of table or same column type?**

It's not mandatory for the tables themselves to have the same structure, but the queries you use with `INTERSECT` must return the same
number of columns, and those columns must have compatible data types.

**Rules for INTERSECT**

- **Same number of columns:** Both `SELECT` statements must project the same count of columns.
- **Compatible data types:** Each column in the first query must be type-compatible with the corresponding column in the second query (e.g., `VARCHAR` with `VARCHAR`, `INT` with `INT`).
- **Column names don't matter:** The names of the columns can differ; what matters is the position and type.
- **Table structures don't need to match:** You can intersect queries from completely different tables, as long as the selected columns line up.

### INTERSECT and INNER JOIN

`INTERSECT` and `INNER JOIN` can look similar because both identify commonalities between datasets, but they
work differently under the hood and produce different kinds of results.

**Core Difference:**

- `INTERSECT` compares two result sets and returns only the distinct rows that appear in both.
- `INNER JOIN` combines tables based on a condition (usually matching keys) and returns rows where the
  condition is true.

**INNER JOIN**

- Combine related data across tables
- Duplicates may appear unless handled explicitly

**INTERSECT**

- Automatically removed (distinct results)
- Find common rows between two queries

# NOT IN vs NOT EXISTS with NULL example

**1) Find customers who do NOT have orders.**

## Using NOT IN (Problem)

```sql
SELECT *
FROM Customers
WHERE Id NOT IN (
    SELECT CustomerId FROM Orders
);
```

🔎 **What is inside subquery?**

```sql
SELECT CustomerId FROM Orders;
```

Result:

```text
1
2
NULL
```

So SQL evaluates:

```text
Id NOT IN (1, 2, NULL)
```

🚨 **Why This Fails**

Let's check for `Id = 3`:

```text
3 NOT IN (1,2,NULL)
```

Internally becomes:

```text
3 <> 1 AND 3 <> 2 AND 3 <> NULL
```

Now here's the problem:

```text
3 <> NULL  → UNKNOWN
```

And:

```text
TRUE AND TRUE AND UNKNOWN = UNKNOWN
```

SQL only returns rows when condition = TRUE.

UNKNOWN ≠ TRUE.

❌ **Final Result**

```text
Empty result set
| (No rows returned) |
```

> ⚠️ This is incorrect.

## Using NOT EXISTS (Correct)

```sql
SELECT *
FROM Customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM Orders o
    WHERE o.CustomerId = c.Id
);
```

🔎 **How It Works**

For each customer:

- Check if matching row exists.
- If none exists → return row.
- NULL in Orders does NOT affect comparison.

**Correct Result**

| Id | Name  |
| -- | ----- |
| 3  | Priya |
| 4  | Neha  |

## 🧠 Interview-Level Explanation (Short Version)

`NOT IN` fails when the subquery returns NULL because comparisons with NULL result in UNKNOWN, causing the entire condition to fail.
`NOT EXISTS` does not have this issue because it checks row existence rather than comparing values.
