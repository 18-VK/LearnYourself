# Client calling Web API

Use `HttpClient` to call your Web API from a C# client app. For bigger or long-running apps, Microsoft recommends `IHttpClientFactory` instead of creating a new
`HttpClient` for every request, because the factory helps manage lifetime, configuration, logging, and resilience.

# Simple Console App example

This is the easiest way to call a Web API and read JSON back into C# objects. `HttpClient` is the standard .NET class for sending HTTP requests and handling responses.

```csharp
using System.Net.Http.Json;

public class Product
{
    public int Id { get; set; }
    public string Name { get; set; } = string.Empty;
    public decimal Price { get; set; }
}

var client = new HttpClient
{
    BaseAddress = new Uri("https://localhost:5001/")
};

// GET all products
var products = await client.GetFromJsonAsync<List<Product>>("api/products");

if (products is not null)
{
    foreach (var p in products)
    {
        Console.WriteLine($"{p.Id} - {p.Name} - {p.Price}");
    }
}
```

`GetFromJsonAsync` reads JSON from the response body and deserializes it into your C# type.

# Recommended approach for ASP.NET Core client apps: IHttpClientFactory

Traditionally, making HTTP calls in .NET applications involved using the `HttpClient` class directly. This often led to issues with managing the lifecycle of
the `HttpClient` instances, resulting in socket exhaustion and performance problems.

The `IHttpClientFactory` was introduced in .NET Core 2.1 to address several issues with the direct use of `HttpClient`. It provides a centralized way to configure and create `HttpClient` instances, ensuring proper resource management and improved performance.

## Problems Solved by IHttpClientFactory

- **Socket Exhaustion:** Improper disposal of `HttpClient` instances can lead to socket exhaustion. `IHttpClientFactory` manages the lifetimes of
  `HttpClientMessageHandler` instances to prevent this.
- **Centralized Configuration:** It allows centralized configuration of `HttpClient` instances, making it easier to apply consistent settings.
- **Named and Typed Clients:** Provides a way to create named and typed clients, allowing specific configurations for different uses.

> ⚠️ **Warning:**
> Avoid injecting typed clients inside singleton services. The `HttpClient` is expected to be short lived. If typed client is captured in singleton, it may not
> get disposed appropriately, hence defeating the purpose of `IHttpClientFactory`.

### Register Services (Program.cs)

```csharp
using ApiClient.Config;
using ApiClient.Services;

var builder = WebApplication.CreateBuilder(args);

// Bind config
builder.Services.Configure<ApiSettings>(
    builder.Configuration.GetSection("ApiSettings")
);

// Typed HttpClient
builder.Services.AddHttpClient<IProductApiClient, ProductApiClient>((sp, client) =>
{
    var config = sp.GetRequiredService<IOptions<ApiSettings>>().Value;

    client.BaseAddress = new Uri(config.BaseUrl);
    client.Timeout = TimeSpan.FromSeconds(config.TimeoutSeconds);
});
```

### Interface (Clean Design)

```csharp
public interface IProductApiClient
{
    Task<List<Product>> GetAllAsync();
    Task<Product?> GetByIdAsync(int id);
    Task<bool> CreateAsync(CreateProductDto dto);
}
```

### Implementation (Production Grade)

```csharp
using System.Net.Http.Json;

public class ProductApiClient : IProductApiClient
{
    private readonly HttpClient _http;
    private readonly ILogger<ProductApiClient> _logger;

    public ProductApiClient(HttpClient http, ILogger<ProductApiClient> logger)
    {
        _http = http;
        _logger = logger;
    }

    public async Task<List<Product>> GetAllAsync()
    {
        try
        {
            var response = await _http.GetAsync("api/products");

            if (!response.IsSuccessStatusCode)
            {
                _logger.LogError("Failed to fetch products: {Status}", response.StatusCode);
                return new List<Product>();
            }

            return await response.Content.ReadFromJsonAsync<List<Product>>() 
                   ?? new List<Product>();
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Error calling API");
            throw;
        }
    }

    public async Task<Product?> GetByIdAsync(int id)
    {
        var response = await _http.GetAsync($"api/products/{id}");

        if (!response.IsSuccessStatusCode)
            return null;

        return await response.Content.ReadFromJsonAsync<Product>();
    }

    public async Task<bool> CreateAsync(CreateProductDto dto)
    {
        var response = await _http.PostAsJsonAsync("api/products", dto);
        return response.IsSuccessStatusCode;
    }
}
```

### Usage (Program.cs or UI)

### Add retry for failure scenario

❌ **Real-world issues**

When your client calls API:

```http
GET /api/products
```

It may fail because of:

- Network glitch 🌐
- API temporarily down ⚠️
- Timeout ⏱️
- 500 server error

🧠 **Without Polly**

```csharp
await client.GetAsync("api/products");
```

👉 If it fails → ❌ request fails immediately

✅ **With Polly**

👉 It will:

- Retry automatically
- Wait before retry
- Recover from temporary failures

**What is Polly?**

Polly is a .NET resilience library used to handle transient faults.

Think:

```text
Try → Fail → Retry → Success
```

**Install Polly:**

```bash
dotnet add package Polly
dotnet add package Microsoft.Extensions.Http.Polly
```

**Adding into configuration**

```csharp
builder.Services.AddHttpClient<IProductApiClient, ProductApiClient>()
            .AddPolicyHandler(HttpPolicyExtensions
                .HandleTransientHttpError()   // 5xx + network errors
                .WaitAndRetryAsync(
                    3,                        // retry count
                    retryAttempt => TimeSpan.FromSeconds(2)
                ));
```

| Part                         | Meaning                       |
| ---------------------------- | ----------------------------- |
| `3`                          | Retry 3 times                 |
| `2 seconds`                  | Wait before each retry        |
| `HandleTransientHttpError()` | Retry on 5xx + network issues |

**How it works internally**

```text
Call API
   ↓
Fail (500 error)
   ↓
Wait 2 sec
   ↓
Retry
   ↓
Fail again
   ↓
Retry
   ↓
Success
```

**Real Example (Flow)**

👉 API fails twice, succeeds third time:

```text
1st call → 500 ❌  
2nd call → 500 ❌  
3rd call → 200 ✅  
```

👉 Your app never sees failure

**Advanced Retry (Exponential Backoff)**

👉 Better approach

```csharp
.WaitAndRetryAsync(
    3,
    retryAttempt => TimeSpan.FromSeconds(Math.Pow(2, retryAttempt))
);
```

| Retry | Delay |
| ----- | ----- |
| 1     | 2 sec |
| 2     | 4 sec |
| 3     | 8 sec |

**Add Logging (VERY IMPORTANT)**

```csharp
.WaitAndRetryAsync(
    3,
    retryAttempt => TimeSpan.FromSeconds(2),
    (result, timeSpan, retryCount, context) =>
    {
        Console.WriteLine($"Retry {retryCount} after {timeSpan}");
    }
);
```

## Extra

Using an interface like `IProductApiClient` decouples the application from its implementation, making the system more testable, maintainable, and flexible. It
allows easy mocking for unit tests and supports multiple implementations without changing dependent code.

**Clean Architecture**

```text
Controller → Service → Interface → Implementation → API
```

👉 Layers stay independent ✔️
