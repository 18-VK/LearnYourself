# API Versioning in ASP.NET Core — Step by Step

## Step 1: Understand why you version APIs

Once clients (mobile apps, third-party integrators, other services) depend on your API's shape, you can't freely change request/response contracts without breaking them. Versioning lets you evolve the API while keeping old consumers working. The core tension is **breaking vs. non-breaking changes**.

- **Non-breaking** (usually no new version needed): adding a new optional field, adding a new endpoint
- **Breaking** (needs a new version): removing/renaming a field, changing a field's type, changing status codes, changing auth requirements

## Step 2: Pick a versioning scheme

There are four common strategies, each with trade-offs:

| Scheme | Example | Pros | Cons |
|---|---|---|---|
| URL path | `/api/v1/orders` | Explicit, cache-friendly, easy to route | "Pollutes" the URL, not RESTfully pure |
| Query string | `/api/orders?api-version=1.0` | Doesn't change the URL structure | Easy to forget, less visible in logs |
| Header | `X-Api-Version: 1.0` | Clean URLs | Less discoverable, harder to test in a browser |
| Media type (Accept header) | `Accept: application/json;v=1.0` | Most "RESTful" | Most complex to implement and consume |

For internal/enterprise APIs (which is what most .NET shops build), **URL path versioning** is by far the most common because it's explicit and simple to reason about. The example below is built around that, then shows how to add header/query support too.

## Step 3: Install the versioning package

Microsoft's official package is `Asp.Versioning.Mvc` (the old `Microsoft.AspNetCore.Mvc.Versioning` is deprecated/archived).

```bash
dotnet add package Asp.Versioning.Mvc
dotnet add package Asp.Versioning.Mvc.ApiExplorer
```

The `ApiExplorer` package is what lets Swagger/OpenAPI understand and group your versions.

## Step 4: Configure versioning in `Program.cs`

```csharp
builder.Services.AddApiVersioning(options =>
{
    options.DefaultApiVersion = new ApiVersion(1, 0);
    options.AssumeDefaultVersionWhenUnspecified = true;
    options.ReportApiVersions = true; // adds api-supported-versions header to responses

    // Choose how clients specify version — you can combine multiple readers
    options.ApiVersionReader = ApiVersionReader.Combine(
        new UrlSegmentApiVersionReader(),
        new HeaderApiVersionReader("X-Api-Version"),
        new QueryStringApiVersionReader("api-version")
    );
})
.AddApiExplorer(options =>
{
    options.GroupNameFormat = "'v'VVV"; // formats as v1, v1.1, v2 etc.
    options.SubstituteApiVersionInUrl = true;
});
```

## Step 5: Version your controllers

For URL-segment versioning, add `{version:apiVersion}` to the route template:

```csharp
[ApiController]
[ApiVersion(1.0)]
[Route("api/v{version:apiVersion}/orders")]
public class OrdersV1Controller : ControllerBase
{
    [HttpGet("{id}")]
    public IActionResult Get(int id)
    {
        // v1 shape
        return Ok(new { Id = id, Total = 100 });
    }
}

[ApiController]
[ApiVersion(2.0)]
[Route("api/v{version:apiVersion}/orders")]
public class OrdersV2Controller : ControllerBase
{
    [HttpGet("{id}")]
    public IActionResult Get(int id)
    {
        // v2 shape — e.g. Total is now broken into subtotal + tax
        return Ok(new { Id = id, Subtotal = 90, Tax = 10, Total = 100 });
    }
}
```

**Alternative: version at the action level** instead of separate controllers, useful when only one or two endpoints actually changed:

```csharp
[ApiController]
[Route("api/v{version:apiVersion}/orders")]
public class OrdersController : ControllerBase
{
    [HttpGet("{id}")]
    [MapToApiVersion(1.0)]
    public IActionResult GetV1(int id) => Ok(new { Id = id, Total = 100 });

    [HttpGet("{id}")]
    [MapToApiVersion(2.0)]
    public IActionResult GetV2(int id) => Ok(new { Id = id, Subtotal = 90, Tax = 10, Total = 100 });
}
```

## Step 6: Deprecate versions gracefully

Mark old versions as deprecated instead of deleting them outright — this tells clients (via the `api-supported-versions` / `api-deprecated-versions` response headers) to migrate, without breaking them yet:

```csharp
[ApiVersion(1.0, Deprecated = true)]
[ApiVersion(2.0)]
```

## Step 7: Wire up Swagger/OpenAPI per version

Since most teams use Swashbuckle, group endpoints by version so each version gets its own Swagger doc:

```csharp
builder.Services.AddSwaggerGen();
builder.Services.ConfigureOptions<ConfigureSwaggerOptions>(); // custom class that iterates IApiVersionDescriptionProvider
                                                                // and calls options.SwaggerDoc(desc.GroupName, ...) per version
```

This is a well-documented pattern (`ConfigureSwaggerOptions : IConfigureOptions<SwaggerGenOptions>`).

## Step 8: Decide your versioning policy going forward

A few practical rules worth adopting on your team:

- Bump the version only for breaking changes — additive changes go into the current version
- Support N-1 (current + previous) versions in production; deprecate and sunset older ones on a schedule
- Document the sunset date in response headers or API docs so consumers aren't surprised
- Keep version-specific DTOs/mapping profiles separate (e.g. via AutoMapper profiles per version) so v1 and v2 controllers don't end up tangled with conditional logic


## Swagger per version

Let's do the Swagger-per-version setup first — it's the natural next piece since you'll want to actually see and test each version in the UI. We'll do versioned DTOs right after.

### Step 1: Add the required packages

You already added these earlier, but confirming the full set:

```bash
dotnet add package Asp.Versioning.Mvc
dotnet add package Asp.Versioning.Mvc.ApiExplorer
dotnet add package Swashbuckle.AspNetCore
```

### Step 2: Create one Swagger document per API version

This is the core piece — it reads all discovered versions from IApiVersionDescriptionProvider and registers a Swagger doc for each one.

```csharp
public class ConfigureSwaggerOptions : IConfigureOptions<SwaggerGenOptions>
{
    private readonly IApiVersionDescriptionProvider _provider;

    public ConfigureSwaggerOptions(IApiVersionDescriptionProvider provider)
    {
        _provider = provider;
    }

    public void Configure(SwaggerGenOptions options)
    {
        foreach (var description in _provider.ApiVersionDescriptions)
        {
            options.SwaggerDoc(description.GroupName, new OpenApiInfo
            {
                Title = "Orders API",
                Version = description.ApiVersion.ToString(),
                Description = description.IsDeprecated
                    ? "This API version has been deprecated."
                    : "Active API version."
            });
        }
    }
}
```

### Step 3: Register everything in `Program.cs`

```csharp
builder.Services.AddApiVersioning(options =>
{
    options.DefaultApiVersion = new ApiVersion(1, 0);
    options.AssumeDefaultVersionWhenUnspecified = true;
    options.ReportApiVersions = true;
    options.ApiVersionReader = ApiVersionReader.Combine(
        new UrlSegmentApiVersionReader(),
        new HeaderApiVersionReader("X-Api-Version"),
        new QueryStringApiVersionReader("api-version")
    );
})
.AddApiExplorer(options =>
{
    options.GroupNameFormat = "'v'VVV";
    options.SubstituteApiVersionInUrl = true;
});

builder.Services.ConfigureOptions<ConfigureSwaggerOptions>();
builder.Services.AddSwaggerGen(); // options themselves are populated by ConfigureSwaggerOptions above
```

### Step 4: Filter operations by API version

Without this, every version's Swagger doc will show all controllers, regardless of version. Add an IOperationFilter (or use the built-in approach via ApiExplorer groups):

```csharp
public class SwaggerDefaultValues : IOperationFilter
{
    public void Apply(OpenApiOperation operation, OperationFilterContext context)
    {
        var apiDescription = context.ApiDescription;
        operation.Deprecated |= apiDescription.IsDeprecated();
    }
}
```

Then, in AddSwaggerGen, filter docs by matching the GroupName:

```csharp
builder.Services.AddSwaggerGen(options =>
{
    options.OperationFilter<SwaggerDefaultValues>();
    options.DocInclusionPredicate((docName, apiDesc) =>
    {
        var actionApiVersionModel = apiDesc.ActionDescriptor
            .EndpointMetadata
            .OfType<ApiVersionMetadata>()
            .FirstOrDefault()?.Map(ApiVersionMapping.Explicit | ApiVersionMapping.Implicit);

        if (actionApiVersionModel == null) return true;

        return actionApiVersionModel.DeclaredApiVersions.Any(v =>
            $"v{v}" == docName || $"v{v.MajorVersion}" == docName);
    });
});
```

(Depending on your exact package version, DocInclusionPredicate syntax can vary slightly — I'll adjust this if you hit a compile error, since the Asp.Versioning API surface has shifted a bit across releases.)

### Step 5: Set up the Swagger UI version dropdown

```csharp
app.UseSwagger();
app.UseSwaggerUI(options =>
{
    var descriptions = app.DescribeApiVersions(); // extension from Asp.Versioning.ApiExplorer

    foreach (var description in descriptions)
    {
        var url = $"/swagger/{description.GroupName}/swagger.json";
        var name = description.GroupName.ToUpperInvariant();
        options.SwaggerEndpoint(url, name);
    }
});
```

This gives you a dropdown in the top-right of Swagger UI to switch between v1, v2, etc.

### Step 6: Run and verify

Start the app and hit /swagger. You should see:

- A version dropdown showing v1 and v2
- Each version listing only its own controllers and actions
- Deprecated versions marked visually (strikethrough or a warning banner, depending on the Swashbuckle UI theme)

### Step 7: Common gotcha

If both `OrdersV1Controller` and `OrdersV2Controller` end up in the same Swagger doc, it's almost always because the `DocInclusionPredicate` isn't matching correctly, or the controllers aren't decorated with `[ApiVersion(...)]` correctly. Double-check that the version attribute is on the controller (or via `[MapToApiVersion]` on the action) and that `GroupNameFormat` matches your predicate's string comparison.


## Explanation

Let's break this into the two separate jobs this code is doing — they're unrelated to each other, just registered in the same place.

### Part 1: `SwaggerDefaultValues` marks deprecated operations

```csharp
public class SwaggerDefaultValues : IOperationFilter
{
    public void Apply(OpenApiOperation operation, OperationFilterContext context)
    {
        var apiDescription = context.ApiDescription;
        operation.Deprecated |= apiDescription.IsDeprecated();
    }
}
```

What an IOperationFilter is: Swashbuckle builds one OpenApiOperation object per endpoint (each combination of HTTP verb + route = one operation) while generating the Swagger JSON. An IOperationFilter is a hook that runs once per operation, letting you mutate that object before it's serialized into the final doc.

Line by line:

- `context.ApiDescription` — metadata about the specific action being processed, including its controller, route, and version information.
- `apiDescription.IsDeprecated()` — an extension method from `Asp.Versioning.Mvc.ApiExplorer` that checks whether the API version this action belongs to was marked `[ApiVersion(1.0, Deprecated = true)]`.
- `operation.Deprecated |= ...` — sets the OpenAPI specification's built-in `deprecated: true` flag on that operation, using OR assignment so it does not accidentally flip back to `false` if the filter runs twice.

Net effect: if OrdersV1Controller is marked deprecated, every operation Swagger generates for it gets "deprecated": true in the JSON — and Swagger UI renders that endpoint with a strikethrough and a warning, automatically, with zero manual work per endpoint.

### Part 2: `DocInclusionPredicate` keeps versions separate

This solves a different problem: by default, Swashbuckle dumps every single controller/action into every Swagger doc, regardless of version. Without this, your v1 Swagger JSON would show V1 controllers and V2 controllers and V3 controllers all mixed together. DocInclusionPredicate is the filter that decides, per operation, "does this belong in this doc or not?"

```csharp
options.DocInclusionPredicate((docName, apiDesc) =>
{
    var actionApiVersionModel = apiDesc.ActionDescriptor
        .EndpointMetadata
        .OfType<ApiVersionMetadata>()
        .FirstOrDefault()?.Map(ApiVersionMapping.Explicit | ApiVersionMapping.Implicit);

    if (actionApiVersionModel == null) return true;

    return actionApiVersionModel.DeclaredApiVersions.Any(v =>
        $"v{v}" == docName || $"v{v.MajorVersion}" == docName);
});
```

#### Parameters

- `docName` — the current Swagger document being built, such as `v1` or `v2`. This matches the `GroupName` strings registered in `ConfigureSwaggerOptions`.
- `apiDesc` — metadata about one specific action, as in Part 1.

#### How the predicate works

```csharp
apiDesc.ActionDescriptor.EndpointMetadata.OfType<ApiVersionMetadata>().FirstOrDefault()
```

Every controller/action has a bag of metadata attached to it by the framework (EndpointMetadata). When you decorate a controller with [ApiVersion(2.0)], the versioning package attaches an ApiVersionMetadata object to that metadata bag under the hood. This line digs through that bag looking for it.

```csharp
?.Map(ApiVersionMapping.Explicit | ApiVersionMapping.Implicit)
```

ApiVersionMetadata distinguishes between versions declared explicitly ([ApiVersion(2.0)] on the controller) vs. implicitly (inherited/assumed, e.g. via AssumeDefaultVersionWhenUnspecified). .Map(...) flattens both into one combined model regardless of how the version was declared, so you don't have to handle the two cases separately.

```csharp
if (actionApiVersionModel == null) return true;
```

Safety fallback: if an action has no version metadata at all (e.g. a health-check endpoint with no [ApiVersion] attribute), just include it in every doc rather than hiding it entirely.

```csharp
return actionApiVersionModel.DeclaredApiVersions.Any(v =>
    $"v{v}" == docName || $"v{v.MajorVersion}" == docName);
```

DeclaredApiVersions is the list of versions this action supports (usually one, e.g. 2.0). This checks: does the string "v2" (built from that version number) match the doc currently being generated (docName)? The second check (v.MajorVersion) is a looser match — it's there in case your GroupNameFormat collapses 2.0 and 2.1 both into a doc named "v2".

Net effect: when Swashbuckle builds the "v1" doc, this predicate returns true only for actions whose version is 1.0 — every V2/V3 action gets filtered out of that doc entirely, and vice versa.

### How the two pieces relate

They're independent filters running at different times in the same pipeline:

- `DocInclusionPredicate` decides which document an operation appears in.
- `SwaggerDefaultValues` (an `IOperationFilter`) then runs on the operations that made it into a given document and tweaks their deprecated flag.
