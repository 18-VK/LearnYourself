# Transactions & Concurrency

> **Must check:** <https://www.geeksforgeeks.org/dbms/acid-properties-in-dbms/>

ACID is the set of guarantees that a database transaction provides so that data remains correct and reliable. ACID = Atomicity, Consistency, Isolation, Durability.

## A — Atomicity

**Definition:** A transaction is an atomic unit: either all its operations succeed (commit) or none (rollback). No partial changes remain.

**Example (money transfer):**

```sql
BEGIN TRANSACTION;
UPDATE Accounts SET Balance = Balance - 100 WHERE Id = 1; -- debit
UPDATE Accounts SET Balance = Balance + 100 WHERE Id = 2; -- credit
COMMIT;
```

If the second update fails, the transaction should be rolled back so Account 1 is not debited without crediting Account 2.

**How DB ensures it:** transaction logs, undo/redo mechanisms.

## C — Consistency

**Definition:** A transaction moves the database from one valid state to another, preserving all defined rules (constraints, triggers, cascades, invariants).

**Examples of consistency rules:**

- `PRIMARY KEY`, `UNIQUE`, `FOREIGN KEY`
- `CHECK` constraints (e.g., `Amount >= 0`)
- Business invariants (e.g., total inventory ≥ 0)

> **Note:** Consistency is the application + DB rules — DB enforces structural constraints, business rules may be enforced by application logic or stored procedures.

## I — Isolation

**Definition:** Concurrent transactions should not interfere; isolation controls how/when the effects of one transaction become visible to others.

Isolation ensures that transactions run independently without affecting each other. Changes made by one transaction are not visible to others until they are committed.

It ensures that the result of concurrent transactions is the same as if they were run one after another, preventing issues like:

- **Dirty reads:** reading uncommitted data
- **Non-repeatable reads:** data changes between two reads
- **Phantom reads:** new rows appear during a transaction

**Phenomena (lower isolation allows these):**

- **Dirty Read:** read uncommitted data from another transaction.
- **Non-repeatable Read:** same query in a transaction returns different results because another transaction changed committed data.
- **Phantom Read:** a repeated query sees additional rows inserted by another committed transaction.

**SQL Server isolation levels (common mapping and behavior):**

- **READ UNCOMMITTED** — allows dirty reads (lowest isolation, fastest).
- **READ COMMITTED** — default in many DBs; no dirty reads, but non-repeatable and phantom reads possible.
- **REPEATABLE READ** — prevents non-repeatable reads; phantom rows still possible.
- **SERIALIZABLE** — highest; prevents phantoms by locking ranges (behaves like transactions executed serially).
- **SNAPSHOT / READ COMMITTED SNAPSHOT** — uses row-versioning to give a transaction a consistent snapshot (prevents many concurrency anomalies without range locks).

**Set isolation level (T-SQL example):**

```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
BEGIN TRANSACTION;
-- work
COMMIT;
```

## D — Durability

**Definition:** Once a transaction commits, its changes are permanent — they survive crashes, power loss, OS failures.

**How DB ensures it:**

- Write-Ahead Log (WAL) / transaction log: changes are written to stable storage before commit is acknowledged.
- Checkpoint and log flush; on restart DB uses log to recover committed transactions.

**Practical note:** Disk durability depends on fsync configuration and storage layer — databases may provide durability levels (e.g., group commit policies).

# Concrete examples: anomalies & how ACID prevents them

## Dirty read (bad)

**Txn A:**

```sql
BEGIN; UPDATE Accounts SET Balance=Balance-100 WHERE Id=1; -- not committed
-- Txn B (reads) SELECT Balance FROM Accounts WHERE Id=1; -- reads uncommitted value
```

Under `READ UNCOMMITTED` B sees A's uncommitted change (dirty read). Under `READ COMMITTED` B won't.

## Non-repeatable read

Txn A reads row X; Txn B updates and commits row X; Txn A reads row X again and sees changed data. `REPEATABLE READ` prevents this.

## Phantom

Txn A does `SELECT COUNT(*) FROM Orders WHERE Amount>100;` Txn B inserts such an order and commits; Txn A repeats the count and sees a new row (phantom). `SERIALIZABLE` prevents phantom inserts in the range.

# Transactions (BEGIN, COMMIT, ROLLBACK)

## BEGIN TRANSACTION

`BEGIN TRANSACTION` (or `BEGIN TRAN`) starts a transaction.
Until you `COMMIT` or `ROLLBACK`, the changes are not permanently saved.

**Example:**

```sql
BEGIN TRANSACTION;

UPDATE Accounts
SET Balance = Balance - 500
WHERE AccountId = 1;
```

At this point:

- Change is made
- But not permanently saved yet

## COMMIT

`COMMIT` permanently saves all changes made during the transaction.

**Example:**

```sql
BEGIN TRANSACTION;

UPDATE Accounts
SET Balance = Balance - 500
WHERE AccountId = 1;

COMMIT;
```

Now the change is saved permanently.

## ROLLBACK

`ROLLBACK` cancels the transaction and restores the database to its previous state.

**Example:**

```sql
BEGIN TRANSACTION;

UPDATE Accounts
SET Balance = Balance - 500
WHERE AccountId = 1;

ROLLBACK;
```

**Result:**

- The update is undone
- Data returns to its original state

## Using TRY...CATCH with Transactions

Best practice in SQL Server.

```sql
BEGIN TRY
    BEGIN TRANSACTION;

    UPDATE Accounts
    SET Balance = Balance - 500
    WHERE AccountId = 1;

    UPDATE Accounts
    SET Balance = Balance + 500
    WHERE AccountId = 2;

    COMMIT;
END TRY

BEGIN CATCH
    ROLLBACK;
END CATCH
```

This ensures safe rollback if any error occurs.

## Savepoints (Partial Rollback)

You can rollback to a specific point.

**Example:**

```sql
BEGIN TRANSACTION;

UPDATE Accounts SET Balance = Balance - 500 WHERE AccountId = 1;
SAVE TRANSACTION AfterDebit;

UPDATE Accounts SET Balance = Balance + 500 WHERE AccountId = 2;
ROLLBACK TRANSACTION AfterDebit;

COMMIT;
```

**Result:**

Only the debit is kept.

# Transaction vs Auto-Commit

Default behavior in SQL Server:

Each statement runs as its own transaction.

**Example:**

```sql
UPDATE Accounts
SET Balance = Balance - 100
WHERE AccountId = 1;
```

This automatically commits.

# Isolation Levels

Isolation levels control how transactions see data modified by other transactions.

> **Note:** Explained above — must check that.

| Isolation Level  | Dirty Read | Non-Repeatable Read | Phantom Read |
| ---------------- | ---------- | ------------------- | ------------ |
| READ UNCOMMITTED | Yes        | Yes                 | Yes          |
| READ COMMITTED   | No         | Yes                 | Yes          |
| REPEATABLE READ  | No         | No                  | Yes          |
| SERIALIZABLE     | No         | No                  | No           |
| SNAPSHOT         | No         | No                  | No           |

## 1. READ UNCOMMITTED

Lowest isolation.
Allows reading uncommitted data.

**Example:**

**Session 1**

```sql
BEGIN TRANSACTION
UPDATE Accounts SET Balance = 500 WHERE Id = 1
-- not committed
```

**Session 2**

```sql
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED

SELECT * FROM Accounts WHERE Id = 1
```

**Result:**

Reads uncommitted value 500.
This is called **Dirty Read**.

**Use Case**

Large reports where accuracy is not critical.

**Example:**

- Dashboard reporting
- Analytics queries

## 2. READ COMMITTED (Default)

Prevents dirty reads.

**Example:**

**Session 1**

```sql
BEGIN TRANSACTION
UPDATE Accounts SET Balance = 500 WHERE Id = 1
```

**Session 2**

```sql
SELECT * FROM Accounts WHERE Id = 1
```

Session 2 waits until transaction commits.

**Use Case:**

Most OLTP systems.

## 3. REPEATABLE READ

Prevents row modifications while transaction is running.

**Example:**

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ

BEGIN TRAN
SELECT * FROM Accounts WHERE Id = 1
```

Other transactions cannot modify that row.

**Use Case**

Financial systems requiring consistent reads.

## 4. SERIALIZABLE

Highest isolation level.
Locks range of data.

**Example:**

```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE
```

Prevents phantom rows.

**Use Case**

Critical systems like banking.

## 5. SNAPSHOT

Uses row versioning instead of locks.
Readers don't block writers.

**Example:**

```sql
SET TRANSACTION ISOLATION LEVEL SNAPSHOT
```

**Use Case**

High-concurrency systems.

# Blocking

Blocking occurs when one transaction holds a lock and another transaction waits.

**Example:**

Assume table `Accounts`.

**Session 1:**

```sql
BEGIN TRAN
UPDATE Accounts
SET Balance = 500
WHERE Id = 1
```

This creates an exclusive lock on row `Id = 1`.

**Session 2:**

```sql
SELECT * FROM Accounts WHERE Id = 1
```

**Result:**

Session 2 waits until Session 1 finishes.

When Session 1 runs:

```sql
COMMIT
```

Session 2 proceeds.

**Visualization**

```text
Session1: Lock row
Session2: Waiting...
Session1: Commit
Session2: Continue
```

**Why Blocking Happens**

Locks:

- Shared lock (read)
- Exclusive lock (write)

**Use Cases**

- Blocking is normal behavior.
- It ensures data consistency.

**How to Reduce Blocking**

- Keep transactions short
- Proper indexes
- Use snapshot isolation
- Avoid long-running transactions

# Deadlock

**Definition:**

A deadlock occurs when two or more transactions wait for each other to release locks, creating a circular dependency.
Neither transaction can continue.

**Example:**

**Session 1:**

```sql
BEGIN TRAN
UPDATE Accounts SET Balance = 100 WHERE Id = 1
```

**Session 2:**

```sql
BEGIN TRAN
UPDATE Accounts SET Balance = 200 WHERE Id = 2
```

Now:

**Session 1:**

```sql
UPDATE Accounts SET Balance = 300 WHERE Id = 2
```

**Session 2:**

```sql
UPDATE Accounts SET Balance = 400 WHERE Id = 1
```

**What happens**

```text
Session1 → waiting for row2
Session2 → waiting for row1
```

Circular dependency.

Database detects this and kills one transaction.

**Error:**

```text
Transaction was deadlocked on resources
```

**Visualization**

```text
Session1 → waiting for Session2
Session2 → waiting for Session1
```

Deadlock detected → one session terminated.

## How to prevent deadlocks

**1. Access resources in the same order**

Good:

```text
Table A → Table B
```

Bad:

```text
Session1: A → B
Session2: B → A
```

**2. Keep transactions short**

Avoid long transactions.

**3. Proper indexing**

Reduces lock time.

**4. Retry logic**

Applications should retry deadlocked transactions.

## Quick interview answer

Blocking happens when one transaction waits for another to release a lock.
Deadlock happens when two or more transactions wait for each other in a circular dependency, and SQL Server terminates one transaction to resolve it.

# Blocking vs Deadlock

## 1️⃣ Blocking (Waiting but will finish)

In blocking, one transaction waits for another, but once the first transaction finishes, the waiting transaction continues normally.

There is no circular dependency.

**Example:**

```sql
BEGIN TRAN
UPDATE Accounts
SET Balance = 500
WHERE Id = 1
```

Row `Id = 1` is now locked.

**Session 2**

```sql
SELECT * FROM Accounts WHERE Id = 1
```

Session 2 waits.

But when Session 1 runs:

```sql
COMMIT
```

Session 2 continues.

**Flow:**

```text
Session1: Lock row
Session2: Waiting
Session1: Commit
Session2: Continues
```

So waiting eventually ends.

## 2️⃣ Deadlock (Waiting forever)

In deadlock, both transactions wait for each other.
Neither can continue.

This creates a cycle.

**Example:**

**Session 1**

```sql
BEGIN TRAN
UPDATE Accounts SET Balance = 500 WHERE Id = 1
```

Locks row 1.

Then tries:

```sql
UPDATE Accounts SET Balance = 600 WHERE Id = 2
```

But row 2 is locked.

**Session 2**

```sql
BEGIN TRAN
UPDATE Accounts SET Balance = 700 WHERE Id = 2
```

Locks row 2.

Then tries:

```sql
UPDATE Accounts SET Balance = 800 WHERE Id = 1
```

But row 1 is locked.

**Now situation:**

```text
Session1 → waiting for row2
Session2 → waiting for row1
```

Neither can proceed.

```text
S1 → S2
S2 → S1
```

Circular wait.
