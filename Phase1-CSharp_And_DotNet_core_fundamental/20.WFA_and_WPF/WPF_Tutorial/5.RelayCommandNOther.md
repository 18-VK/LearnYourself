# ICommand, RelayCommand / DelegateCommand

> **Note:** prerequisite — Delegate

`ICommand` is the MVVM way to move button clicks and other actions out of code-behind into the ViewModel.

`RelayCommand` (aka `DelegateCommand`) is a small reusable implementation of `ICommand` that lets you pass delegates
for `Execute` and `CanExecute`.

## ICommand — the interface (what matters)

```csharp
public interface ICommand
{
    bool CanExecute(object parameter);
    void Execute(object parameter);
    event EventHandler CanExecuteChanged;
}
```

- `CanExecute`: controls whether the command is enabled.
- `Execute`: runs when invoked.
- `CanExecuteChanged`: notifies the UI to re-evaluate enabled state.

## RelayCommand / DelegateCommand

### 1. Simple RelayCommand (non-generic) — classic implementation

```csharp
public class RelayCommand : ICommand
{
    private readonly Action _execute;
    private readonly Func<bool> _canExecute;

    public RelayCommand(Action execute, Func<bool> canExecute = null)
    {
        _execute = execute ?? throw new ArgumentNullException(nameof(execute));
        _canExecute = canExecute;
    }

    public bool CanExecute(object parameter) => _canExecute?.Invoke() ?? true;

    public void Execute(object parameter) => _execute();

    // Use CommandManager.RequerySuggested to auto-update for common WPF scenarios.
    public event EventHandler CanExecuteChanged
    {
        add    { CommandManager.RequerySuggested += value; }
        remove { CommandManager.RequerySuggested -= value; }
    }

    // Optional helper to raise manually if not using CommandManager
    public void RaiseCanExecuteChanged()
        => CommandManager.InvalidateRequerySuggested();
}
```

### 2. Generic RelayCommand&lt;T&gt; — for typed parameter

```csharp
public class RelayCommand<T> : ICommand
{
    private readonly Action<T> _execute;
    private readonly Predicate<T> _canExecute;

    public RelayCommand(Action<T> execute, Predicate<T> canExecute = null)
    {
        _execute = execute ?? throw new ArgumentNullException(nameof(execute));
        _canExecute = canExecute;
    }

    public bool CanExecute(object parameter)
    {
        if (_canExecute == null) return true;
        return parameter == null && typeof(T).IsValueType == false
            ? _canExecute(default!)
            : _canExecute((T)parameter);
    }

    public void Execute(object parameter)
        => _execute((T)parameter);

    public event EventHandler CanExecuteChanged
    {
        add    { CommandManager.RequerySuggested += value; }
        remove { CommandManager.RequerySuggested -= value; }
    }
}
```

public class RelayCommand : ICommand

        _execute = execute;

**2. ViewModel (Button logic goes here)**

```csharp
using System.ComponentModel;
using System.Runtime.CompilerServices;
using System.Windows.Input;

public class MainViewModel : INotifyPropertyChanged
{
    private int _count;
    public int Count
    {
        get => _count;
        set
        {
            _count = value;
            OnPropertyChanged();
        }
    }

    public MainViewModel()
    {

    }

    }

    public event PropertyChangedEventHandler PropertyChanged;
    private void OnPropertyChanged([CallerMemberName] string prop = null)
        => PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(prop));
}
```

# CommandManager

## 1️⃣ What is CommandManager?

`CommandManager` is a WPF infrastructure class that:

Automatically asks commands whether they can execute and updates the UI accordingly.

In simple words:

- It re-evaluates `CanExecute()`
- It enables / disables buttons, menu items, etc.

You never create it yourself — WPF uses it internally.

## 2️⃣ Why does WPF need CommandManager?

Without it:

- WPF would not know when to re-check `CanExecute`
- Buttons would stay enabled/disabled incorrectly
- `CommandManager` listens to certain UI events and says:

> "Hey commands, something changed — should I call `CanExecute()` again?"

## 3️⃣ What triggers CommandManager automatically?

WPF calls `CanExecute()` again when:

- Keyboard focus changes
- Mouse clicks occur
- Window activates/deactivates
- Menu opens

That's why sometimes your button updates even when you didn't do anything.

## 4️⃣ Where does CommandManager fit in MVVM?

**Typical RelayCommand implementation**

```csharp
public event EventHandler CanExecuteChanged
{
    add    { CommandManager.RequerySuggested += value; }
    remove { CommandManager.RequerySuggested -= value; }
}
```

This line connects:

Your `RelayCommand` to WPF's command refresh system.

👉 When `CommandManager` raises `RequerySuggested`, WPF:

- Calls `CanExecute()`
- Updates button enabled state

## Why do we call InvalidateRequerySuggested()?

Sometimes WPF does not know that something changed.

**Example:**

```csharp
public Transaction SelectedTransaction { get; set; }
```

When selection changes:

- No keyboard event
- No mouse event
- WPF doesn't automatically re-evaluate commands

So we force it:

```csharp
CommandManager.InvalidateRequerySuggested();
```

This tells WPF:

> "Re-check all commands NOW."

## 6️⃣ Real example (your case)

**ViewModel**

```csharp
DeleteSelectedCommand =
    new RelayCommand(DeleteSelected, () => SelectedTransaction != null);
```

**When selection changes**

```csharp
public Transaction SelectedTransaction
{
    get => _selectedTransaction;
    set
    {
        _selectedTransaction = value;
        OnPropertyChanged();
        CommandManager.InvalidateRequerySuggested();
    }

```

> **Note:** complete project is in `ProjectExampleWithCommand.md` file.

**Result**

| State           | Button   |
| --------------- | -------- |
| No row selected | Disabled |
| Row selected    | Enabled  |

## 7️⃣ What happens internally (important)

```text
InvalidateRequerySuggested()
        ↓
CommandManager raises RequerySuggested
        ↓
Button asks Command: CanExecute?
        ↓
Button enables/disables
```

## 8️⃣ Do you ALWAYS need CommandManager?

❌ No.

**You need it when:**

- Using classic `RelayCommand`
- Relying on `CanExecute` for enable/disable
- Your logic depends on non-UI events

**You DON'T need it when:**

- You manually raise `CanExecuteChanged`
- Using modern MVVM toolkits
  - CommunityToolkit.MVVM
  - Prism
- Your command is always executable

## 9️⃣ Alternative (manual approach – purer MVVM)

Instead of relying on `CommandManager`, you can raise `CanExecuteChanged` yourself.

**RelayCommand (manual)**

```csharp
public class RelayCommand : ICommand
{
    public event EventHandler CanExecuteChanged;

    public void RaiseCanExecuteChanged()
        => CanExecuteChanged?.Invoke(this, EventArgs.Empty);
}
```

## 🔟 CommandManager drawbacks ⚠️

- Global refresh → less efficient
- Harder to control
- Can cause unexpected UI updates
- Not async-friendly

That's why modern MVVM frameworks avoid it.

## Example : Manual RelayCommand (PURE MVVM), best and suggested alternative to CommandManager

**1. Relay command**

```csharp
using System;
using System.Windows.Input;

public class RelayCommand : ICommand
{
    private readonly Action _execute;
    private readonly Func<bool> _canExecute;

    public RelayCommand(Action execute, Func<bool> canExecute = null)
    {
        _execute = execute;
        _canExecute = canExecute;
    }

    public bool CanExecute(object parameter)
        => _canExecute == null || _canExecute();

    public void Execute(object parameter)
        => _execute();

    public event EventHandler CanExecuteChanged;

    public void RaiseCanExecuteChanged()
        => CanExecuteChanged?.Invoke(this, EventArgs.Empty);

```

- ✔ No CommandManager
- ✔ Fully controlled
- ✔ Predictable

**2. ViewModel (IMPORTANT PART)**

```csharp
using System.Collections.ObjectModel;
using System.ComponentModel;
using System.Runtime.CompilerServices;
using System.Windows.Input;

public class TransactionViewModel : INotifyPropertyChanged
{
    public ObservableCollection<Transaction> Transactions { get; }
        = new();

    private Transaction _selectedTransaction;
    public Transaction SelectedTransaction
    {
        get => _selectedTransaction;
        set
        {
            _selectedTransaction = value;
            OnPropertyChanged();

            // 🔥 Explicitly notify command
            DeleteCommand.RaiseCanExecuteChanged();
        }
    }

    public RelayCommand DeleteCommand { get; }

    public TransactionViewModel()
    {
        Transactions.Add(new Transaction { Id = 1, Category = "Food", Amount = 200 });
        Transactions.Add(new Transaction { Id = 2, Category = "Salary", Amount = 50000 });

        DeleteCommand = new RelayCommand(Delete, CanDelete);
    }

    private bool CanDelete()
        => SelectedTransaction != null;

    private void Delete()
    {
        Transactions.Remove(SelectedTransaction);
        SelectedTransaction = null;
    }

    public event PropertyChangedEventHandler PropertyChanged;
    private void OnPropertyChanged([CallerMemberName] string name = null)
        => PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(name));
}
```

🔥 **Key line (THIS IS THE MAGIC)**

```csharp
DeleteCommand.RaiseCanExecuteChanged();
```

This replaces:

```csharp
CommandManager.InvalidateRequerySuggested();
```

### What happens at runtime (STEP-BY-STEP)

**App starts**

- `SelectedTransaction = null`
- `CanDelete()` → false
- Button disabled

**User selects a row**

```csharp
SelectedTransaction = value;
DeleteCommand.RaiseCanExecuteChanged();
```

- `CanExecute()` re-evaluated
- Button becomes enabled

| Async friendly    | ❌              | ✔        |

# CommandParameter

## 1️⃣ What is CommandParameter?

`CommandParameter` is an extra value passed to `ICommand.Execute()` and `CanExecute()`.

**Signature reminder:**

```csharp
bool CanExecute(object parameter);
void Execute(object parameter);
```

That parameter comes from XAML → `CommandParameter`.

**Example:**

**ViewModel**

```csharp
public RelayCommand<int> AddCommand { get; }

public MainViewModel()
{
    AddCommand = new RelayCommand<int>(Add);
}

private void Add(int value)
{
    Total += value;
}
```

**XAML**

```xml
<Button Content="Add 10"
        Command="{Binding AddCommand}"
        CommandParameter="10"/>
```

- ✔ `"10"` is converted to `int`
- ✔ Passed into `Execute(int value)`

## XAML (row-level delete)

```xml
<DataGrid ItemsSource="{Binding Transactions}">
    <DataGrid.Columns>

        <!-- other columns -->

        <DataGridTemplateColumn Header="Action">
            <DataGridTemplateColumn.CellTemplate>
                <DataTemplate>
                    <Button Content="Delete"
                            Command="{Binding DataContext.DeleteItemCommand,
                                      RelativeSource={RelativeSource AncestorType=DataGrid}}"
                            CommandParameter="{Binding}" />
                </DataTemplate>
            </DataGridTemplateColumn.CellTemplate>
        </DataGridTemplateColumn>

    </DataGrid.Columns>
</DataGrid>
```

🔥 **Important**

```xml
CommandParameter="{Binding}"
```

This passes the current row object (`Transaction`) to the command.

### SelectedItem vs CommandParameter (INTERVIEW FAVORITE)

❌ **Using SelectedItem**

```csharp
DeleteSelected()
```

- Depends on selection
- One global delete

✅ **Using CommandParameter**

```csharp
DeleteItem(Transaction item)
```

- Acts on exact row
- No dependency on selection
- Cleaner MVVM

👉 Row actions should use `CommandParameter`

# AsyncRelayCommand implementation

## 1️⃣ Classic AsyncRelayCommand (manual, pure MVVM)

📁 `Commands/AsyncRelayCommand.cs`

```csharp
using System;
using System.Threading.Tasks;
using System.Windows.Input;

public class AsyncRelayCommand : ICommand
{
    private readonly Func<Task> _executeAsync;
    private readonly Func<bool> _canExecute;
    private bool _isExecuting;

    public AsyncRelayCommand(Func<Task> executeAsync, Func<bool> canExecute = null)
    {
        _executeAsync = executeAsync ?? throw new ArgumentNullException(nameof(executeAsync));
        _canExecute = canExecute;
    }

    public bool CanExecute(object parameter)
        => !_isExecuting && (_canExecute?.Invoke() ?? true);

    public async void Execute(object parameter)
    {
        if (!CanExecute(parameter))
            return;

        try
        {
            _isExecuting = true;
            RaiseCanExecuteChanged();
            await _executeAsync();
        }
        finally
        {
            _isExecuting = false;
            RaiseCanExecuteChanged();
        }
    }

    public event EventHandler CanExecuteChanged;

    public void RaiseCanExecuteChanged()
        => CanExecuteChanged?.Invoke(this, EventArgs.Empty);
}
```

🔑 **Key points**

- Prevents double-click execution
- Button disables while async work runs
- No CommandManager
- Fully testable

## 2️⃣ Real ViewModel example (Async DB / API load)

📁 `ViewModels/TransactionViewModel.cs`

```csharp
using System.Collections.ObjectModel;
using System.ComponentModel;
using System.Runtime.CompilerServices;
using System.Threading.Tasks;

public class TransactionViewModel : INotifyPropertyChanged
{
    public ObservableCollection<string> Transactions { get; } = new();

    public AsyncRelayCommand LoadCommand { get; }

    private bool _isBusy;
    public bool IsBusy
    {
        get => _isBusy;
        set
        {
            _isBusy = value;
            OnPropertyChanged();
        }
    }

    public TransactionViewModel()
    {
        LoadCommand = new AsyncRelayCommand(LoadAsync, () => !IsBusy);
    }

    private async Task LoadAsync()
    {
        IsBusy = true;

        // Simulate DB / API call
        await Task.Delay(2000);

        Transactions.Clear();
        Transactions.Add("Transaction 1");
        Transactions.Add("Transaction 2");
        Transactions.Add("Transaction 3");

        IsBusy = false;
    }

    public event PropertyChangedEventHandler PropertyChanged;
    private void OnPropertyChanged([CallerMemberName] string name = null)
        => PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(name));
}
```

## 4️⃣ Runtime behavior (IMPORTANT)

**Initial state**

- `IsBusy = false`
- Button enabled

**User clicks button**

- `Execute()` runs
- `_isExecuting = true`
- Button disabled
- ProgressBar visible

**Async work completes**

- `_isExecuting = false`
- Button enabled again
- UI updates automatically

## 6️⃣ Common mistakes ❌

- ❌ Using `async void` in ViewModel methods
- ❌ Not disabling button during async work
- ❌ Using `Task.Run` for I/O
- ❌ Calling `MessageBox` inside ViewModel
- ❌ Using `CommandManager` with async commands
