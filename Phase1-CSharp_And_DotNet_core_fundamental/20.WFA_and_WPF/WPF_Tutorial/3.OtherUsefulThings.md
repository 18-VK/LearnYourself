# Dependency Property 
In WPF, a DependencyProperty is a special kind of property backed by the WPF property system, enabling advanced features like data binding, styling, animation, property value 
inheritance, and default values. Unlike normal CLR properties, dependency properties are registered with the framework and can participate in WPF’s powerful UI mechanisms.

>> Key Characteristics of DependencyProperty
Backed by WPF property system → Not just a private field; values are stored and managed by WPF.

Supports advanced features:

- Data Binding → Bind UI elements directly to ViewModel properties.
- Styling & Templates → Apply styles/resources dynamically.
- Animations → Animate property values (e.g., Opacity, Width).
- Property Value Inheritance → Child elements can inherit values from parent elements.
- Default Values & Validation → Define defaults and callbacks for property changes.

>> Example: Creating a DependencyProperty

public class CustomControl : Control
{
    // Register dependency property
    public static readonly DependencyProperty IsHighlightedProperty =
        DependencyProperty.Register(
            "IsHighlighted",                // Property name
            typeof(bool),                   // Property type
            typeof(CustomControl),          // Owner type
            new PropertyMetadata(false));   // Default value

    // CLR wrapper
    public bool IsHighlighted
    {
        get => (bool)GetValue(IsHighlightedProperty);
        set => SetValue(IsHighlightedProperty, value);
    }
}

Usage in XAML:
<local:CustomControl IsHighlighted="True" />


>> Automatic Visual Changes (Triggers)

You can define a Style inside the control that says: "When IsHighlighted becomes True, change the Background to Yellow." The WPF engine listens to the DP and applies 
the change instantly without extra C# code.

<Style TargetType="local:CustomControl">
    <Setter Property="Background" Value="White"/>
    <Style.Triggers>
        <!-- Automatically reacts to DP changes -->
        <Trigger Property="IsHighlighted" Value="True">
            <Setter Property="Background" Value="Yellow"/>
            <Setter Property="FontWeight" Value="Bold"/>
        </Trigger>
    </Style.Triggers>
</Style>

## Dependency vs CLR Property

**CLR properties** are standard C# properties backed by private fields, offering simple storage and retrieval with direct memory access, while **dependency properties** are managed 
by the WPF property system, storing values in a dictionary and enabling advanced features like data binding, styling, animations, and value inheritance.

The key distinctions between the two are:

*   **Storage and Memory**: CLR properties store values directly in instance fields, consuming memory for every instance even if defaults are used. Dependency properties store values only when they differ from defaults, significantly reducing memory usage in UI-heavy applications.
*   **Value Resolution**: CLR properties use direct get/set accessors. Dependency properties use a complex precedence system that resolves values from multiple sources, including styles, templates, animations, and inheritance.
*   **Change Notification**: CLR properties do not notify changes automatically; implementing `INotifyPropertyChanged` is required for binding updates. Dependency properties have built-in change notification and can register callbacks to react to value changes.
*   **XAML and Binding**: CLR properties have basic binding support (as sources) but cannot receive bound values in XAML. Dependency properties have full support for two-way data binding and are the standard for WPF UI controls.
*   **Implementation**: CLR properties require simple get/set code. Dependency properties require registration via `DependencyProperty.Register` and the class must inherit from `DependencyObject`.

In practice, **CLR properties** are used for standard data storage and ViewModel logic, whereas **dependency properties** are essential for custom WPF controls to leverage the 
framework's visual and data-binding engine.

>> Example : 

In WPF, TextBox.Text is a standard CLR (Common Language Runtime) property that acts as a wrapper for the TextBox.TextProperty, which is the actual Dependency Property. 

The Text property provides a simple get/set interface for developers, but it internally delegates to the dependency property system using GetValue and SetValue. This allows the text 
value to participate in data binding, styling, animation, and property inheritance. 

Key distinctions:

TextBox.Text: The instance-level CLR property used in C# code and XAML attribute syntax. 
TextBox.TextProperty: The static, readonly DependencyProperty identifier registered with the WPF property system, used for binding paths and metadata. 

To bind to a TextBox's text, you reference the CLR property name (e.g., Text="{Binding MyViewModelProperty}"), but the underlying mechanism relies on the registered TextProperty 
dependency property.

### Use CLR Properties for your ViewModels and data models, and Dependency Properties (DP) for Custom Controls and UI elements. 

When to Use CLR Properties
Context: ViewModels, Models, and plain C# classes (POCOs).

- Data Storage: Use for holding business logic data where you only need simple get/set access. 
- Binding Source: Use as the source of a data binding.  The WPF engine reads these values easily.
- Notification: Implement INotifyPropertyChanged to manually notify the UI of changes. This keeps your logic testable and free from WPF-specific dependencies. 
- Performance: Preferable for high-frequency updates in non-UI classes due to faster direct field access.

When to Use Dependency Properties
Context: Custom Controls, UserControls, and classes inheriting from DependencyObject. 

- Binding Targets: Use for any property on a control that needs to receive a value from a binding (e.g., a SelectedIndex on a custom dropdown). 
- XAML Integration: Use for properties you intend to set directly in XAML, via Styles, Triggers, or Dynamic Resources. 
- Advanced Features: Required if the property needs to support animations, value inheritance (like FontSize or DataContext), or default value coercion. 
- Public Control API: As a rule of thumb, every public property on a custom WPF control should be a Dependency Property to ensure it behaves like a standard WPF element. 

Summary Rule of Thumb

- ViewModel (Data): CLR Property + INotifyPropertyChanged. 
- View/Control (UI): Dependency Property.


## Secured password Binding using Dependency property

>> What is SecureString?

A special class in .NET (System.Security.SecureString) designed to store sensitive text (like passwords) in memory more securely than a normal string.

It encrypts the value in memory and allows you to:

Append/remove characters.
Clear the value when done.
Dispose of it properly so it doesn’t linger in RAM.
Unlike a plain string, which is immutable and stays in memory until garbage collected, SecureString can be wiped immediately.

>> Why SecureString?

A normal string keeps the password in memory as plain text, which is unsafe.
SecureString encrypts the value in memory and allows you to clear it when no longer needed.

It’s recommended for authentication flows (e.g., JWT, OAuth, PKCE) where you don’t want passwords exposed.

Here is a complete, secure implementation using an Attached Dependency Property with SecureString.  This avoids storing the password as a plain string in the ViewModel. 

1. SecureString Extensions
First, helper methods to safely convert between string and SecureString without leaving plain text in memory longer than necessary. 

using System;
using System.Runtime.InteropServices;
using System.Security;

public static class SecureStringExtensions
{
    public static SecureString ToSecureString(this string plainText)
    {
        if (string.IsNullOrEmpty(plainText)) return new SecureString();

        var secureString = new SecureString();
        foreach (char c in plainText)
        {
            secureString.AppendChar(c);
        }
        secureString.MakeReadOnly();
        return secureString;
    }

    public static string ToUnsecuredString(this SecureString secureString)
    {
        if (secureString == null) return string.Empty;

        IntPtr bstrPtr = IntPtr.Zero;
        try
        {
            bstrPtr = Marshal.SecureStringToBSTR(secureString);
            return Marshal.PtrToStringBSTR(bstrPtr);
        }
        finally
        {
            if (bstrPtr != IntPtr.Zero)
            {
                Marshal.ZeroFreeBSTR(bstrPtr); // Critical: Zero out unmanaged memory
            }
        }
    }
}

2. The Attached Property Helper
This class bridges the PasswordBox and the ViewModel using SecureString. It handles the two-way synchronization while preventing infinite loops. 

using System.Security;
using System.Windows;
using System.Windows.Controls;

public static class PasswordBoxHelper
{
    // 1. Define the Attached DP as SecureString
    public static readonly DependencyProperty SecurePasswordProperty =
        DependencyProperty.RegisterAttached(
            "SecurePassword",
            typeof(SecureString),
            typeof(PasswordBoxHelper),
            new FrameworkPropertyMetadata(
                new SecureString(), 
                FrameworkPropertyMetadataOptions.BindsTwoWayByDefault, 
                OnSecurePasswordChanged));

    // 2. Internal marker to prevent recursive updates
    private static readonly DependencyProperty IsUpdatingProperty =
        DependencyProperty.RegisterAttached(
            "IsUpdating", 
            typeof(bool), 
            typeof(PasswordBoxHelper), 
            new PropertyMetadata(false));

    // Getters and Setters
    public static void SetSecurePassword(DependencyObject obj, SecureString value) => 
        obj.SetValue(SecurePasswordProperty, value);

    public static SecureString GetSecurePassword(DependencyObject obj) => 
        (SecureString)obj.GetValue(SecurePasswordProperty);

    private static void SetIsUpdating(DependencyObject obj, bool value) => 
        obj.SetValue(IsUpdatingProperty, value);

    private static bool GetIsUpdating(DependencyObject obj) => 
        (bool)obj.GetValue(IsUpdatingProperty);

    // 3. Callback: ViewModel changed -> Update UI
    private static void OnSecurePasswordChanged(DependencyObject d, DependencyPropertyChangedEventArgs e)
    {
        if (d is PasswordBox passwordBox && !GetIsUpdating(passwordBox))
        {
            passwordBox.PasswordChanged -= PasswordBox_PasswordChanged;
            
            var newSecureString = e.NewValue as SecureString;
            if (newSecureString != null)
            {
                // Only update if length differs to avoid cursor jumps, or force update if needed
                // Note: Setting .Password requires a string, so we must temporarily unsecure it
                passwordBox.Password = newSecureString.ToUnsecuredString();
            }
            else
            {
                passwordBox.Password = string.Empty;
            }

            passwordBox.PasswordChanged += PasswordBox_PasswordChanged;
        }
    }

    // 4. Event Handler: User typed -> Update ViewModel
    private static void PasswordBox_PasswordChanged(object sender, RoutedEventArgs e)
    {
        if (sender is PasswordBox passwordBox)
        {
            SetIsUpdating(passwordBox, true);
            // Use .SecurePassword directly (no plain string involved here)
            // .Copy() creates a new instance so the VM owns its own copy
            SetSecurePassword(passwordBox, passwordBox.SecurePassword.Copy()); 
            SetIsUpdating(passwordBox, false);
        }
    }
}

3. The ViewModel
The ViewModel uses SecureString and implements IDisposable to ensure the password is wiped from memory when the ViewModel is done. 

using System;
using System.Security;
using System.ComponentModel;
using System.Runtime.CompilerServices;

public class LoginViewModel : INotifyPropertyChanged, IDisposable
{
    private SecureString _password;

    public SecureString Password
    {
        get => _password;
        set
        {
            if (_password != value)
            {
                // Clean up old secure string
                _password?.Dispose(); 
                _password = value;
                OnPropertyChanged();
            }
        }
    }

    public void Dispose()
    {
        // CRITICAL: Zero out memory when ViewModel is destroyed
        _password?.Dispose();
        _password = null;
    }

    public event PropertyChangedEventHandler PropertyChanged;
    protected void OnPropertyChanged([CallerMemberName] string name = "") => 
        PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(name));
}

4. Usage in XAML
Bind the attached property local:PasswordBoxHelper.SecurePassword to your ViewModel. 

<Window x:Class="MyApp.LoginView"
        xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
        xmlns:local="clr-namespace:MyApp"
        Title="Secure Login">
    
    <StackPanel Margin="20" Width="250">
        <TextBlock Text="Password:" Margin="0,0,0,5"/>
        
        <!-- Bind the Attached Property, not the native Password property -->
        <PasswordBox 
            local:PasswordBoxHelper.SecurePassword="{Binding Password, UpdateSourceTrigger=PropertyChanged}" 
            Width="200" 
            HorizontalAlignment="Left"/>
        
        <Button Content="Login" Command="{Binding LoginCommand}" Margin="0,15,0,0"/>
    </StackPanel>
</Window>

## What are Resources in WPF?
Resources are reusable objects stored with a key, such as:
- Styles
- Brushes (colors)
- Templates
- Converters
- DataTemplates
- ControlTemplates

👉 Instead of repeating XAML again and again, you define it once and reuse it.

## Resource Scope (Most Important Concept)
WPF resources work in a hierarchical scope:

Control → Window → Application → System

A Control can access:

- Its own resources
- Parent Window resources
- Application resources

A Window can access:

- Its own resources
- Application resources

Application resources are available everywhere

## Control.Resources

- Inside any control (Button, Grid, StackPanel, TextBox, etc.)
- Available ONLY to that control and its children

✅ Use When
- Style/template is used only inside a specific control
- You want local customization
- Avoid affecting other UI parts

Example: Control-level Style

<StackPanel>
    <StackPanel.Resources>
        <Style TargetType="Button">
            <Setter Property="Background" Value="LightBlue"/>
            <Setter Property="Margin" Value="5"/>
        </Style>
    </StackPanel.Resources>

    <Button Content="Save"/>
    <Button Content="Cancel"/>
</StackPanel>

✔ Only buttons inside this StackPanel get the style
❌ Buttons outside are unaffected

Example: Resource for Single Control

<Button Content="Login">
    <Button.Resources>
        <SolidColorBrush x:Key="BtnBrush" Color="Green"/>
    </Button.Resources>

    <Button.Background>
        {StaticResource BtnBrush}
    </Button.Background>
</Button>

## Window.Resources

- Inside a Window or UserControl
- Available to all controls inside that Window/UserControl

✅ Use When

- Resource used multiple times in one window
- Page-specific styles
- Avoid global impact

Example: Window-Level Style

<Window x:Class="Demo.MainWindow"
        xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation">

    <Window.Resources>
        <Style TargetType="TextBox">
            <Setter Property="Margin" Value="10"/>
            <Setter Property="Width" Value="200"/>
        </Style>
    </Window.Resources>

    <StackPanel>
        <TextBox/>
        <TextBox/>
    </StackPanel>
</Window>

✔ Applies to all TextBoxes in this window
❌ Not applied in other windows

Example: Window-level Brush

<Window.Resources>
    <SolidColorBrush x:Key="PrimaryColor" Color="#007ACC"/>
</Window.Resources>

<Button Background="{StaticResource PrimaryColor}"
        Content="Submit"/>

## Application.Resources

- Inside App.xaml
- Available throughout the entire application

✅ Use When

- Common styles
- Theme colors
- Converters
- Templates used everywhere

Example: Global Button Style

App.xaml

<Application.Resources>
    <Style TargetType="Button">
        <Setter Property="Padding" Value="10"/>
        <Setter Property="FontSize" Value="14"/>
    </Style>
</Application.Resources>


✔ All buttons in all windows get this style
✔ Centralized UI management

Example: Global Colors

<Application.Resources>
    <SolidColorBrush x:Key="PrimaryBrush" Color="#2196F3"/>
    <SolidColorBrush x:Key="DangerBrush" Color="Red"/>
</Application.Resources>

<Button Background="{StaticResource PrimaryBrush}" />

## Note : How Resource Lookup Works (IMPORTANT)

When WPF looks for a resource:

- Current control
- Parent control(s)
- Window
- Application
- System resources

👉 Closest resource wins

Example: Resource Override

<Application.Resources>
    <SolidColorBrush x:Key="ThemeColor" Color="Blue"/>
</Application.Resources>

<Window.Resources>
    <SolidColorBrush x:Key="ThemeColor" Color="Green"/>
</Window.Resources>

<Button Background="{StaticResource ThemeColor}"/>

✔ Button background = Green

## StaticResource vs DynamicResource (Quick Tip)

| StaticResource           | DynamicResource       |
| ------------------------ | --------------------- |
| Loaded once              | Updates at runtime    |
| Faster                   | Slightly slower       |
| Cannot change after load | Supports theme change |

e.g : 
Background="{DynamicResource PrimaryBrush}"

Use DynamicResource for themes / runtime changes.
Use DynamicResource for:

- Light/Dark theme
- Runtime color change

# ContentTemplate and ContentPresenter

## What is ControlTemplate?

A ControlTemplate defines the visual structure of a control.
Think of it as:

“How the control looks internally”
Examples:

Button → Border + content
TextBox → Border + ScrollViewer
CheckBox → Box + text

⚠️ ControlTemplate does NOT define behavior, only appearance.

## Why ControlTemplate is Needed?

Default WPF controls already have templates, but:

- You want custom look
- You want modern UI
- You want rounded buttons
- You want icons inside buttons

👉 You replace the ControlTemplate.

## What is ContentPresenter?

ContentPresenter is the placeholder that displays the control’s content.
Whatever is set in Content property appears inside ContentPresenter.

Relationship Between ControlTemplate & ContentPresenter : 
🔑 Golden Rule

ControlTemplate defines the structure
ContentPresenter shows the content inside that structure

👉 Without ContentPresenter, the control’s content is LOST.

Simple Example: Custom Button
-----------------------------
🔹 XAML (Style with ControlTemplate)

<Window.Resources>
    <Style TargetType="Button">
        <Setter Property="Background" Value="#007ACC"/>
        <Setter Property="Foreground" Value="White"/>
        <Setter Property="Padding" Value="10"/>

        <Setter Property="Template">
            <Setter.Value>
                <ControlTemplate TargetType="Button">

                    <Border Background="{TemplateBinding Background}"
                            Padding="{TemplateBinding Padding}"
                            CornerRadius="6">

                        <!-- Content goes here -->
                        <ContentPresenter
                            HorizontalAlignment="Center"
                            VerticalAlignment="Center"/>

                    </Border>

                </ControlTemplate>
            </Setter.Value>
        </Setter>
    </Style>
</Window.Resources>

Usage
-------
<Button Content="Save"/>

or

<Button>
    <StackPanel Orientation="Horizontal">
        <TextBlock Text="💾"/>
        <TextBlock Text=" Save"/>
    </StackPanel>
</Button>


✔ Both work because of ContentPresenter

What Happens Internally? : 

Button
 └── ControlTemplate
      └── Border
           └── ContentPresenter
                └── Button.Content

Example : Target control with name 

<Window.Resources>
    <ControlTemplate x:Key="SpecificControlTemplate" TargetType="{x:Type Button}">
        <!-- Visual structure of the template (e.g., a Grid, Border, ContentPresenter, etc.) -->
        <Border Background="Orange" BorderBrush="Black" BorderThickness="1">
            <ContentPresenter HorizontalAlignment="Center" VerticalAlignment="Center"/>
        </Border>
    </ControlTemplate>
</Window.Resources>

usage : 

<Button x:Name="MySpecificButton" 
        Content="Click Me" 
        Template="{StaticResource SpecificControlTemplate}" />

<!-- A different button that does not use this template -->
<Button Content="Normal Button" />

## What if ContentPresenter is Missing?

    </Border>

🚫 All buttons show same text

## TemplateBinding Explained (IMPORTANT)
TemplateBinding is a lightweight binding used inside a ControlTemplate to connect:
Control’s public properties → template visuals

In simple words:
“Use the value from the control that is using this template.”

Background="{TemplateBinding Background}"


✔ Binds template to control property
✔ Faster than normal Binding
✔ Used only inside ControlTemplate

example : 
<Style TargetType="Button">
    <Setter Property="Background" Value="#1976D2"/>
    <Setter Property="Padding" Value="10"/>

    <Setter Property="Template">
        <Setter.Value>
            <ControlTemplate TargetType="Button">
                <Border
                    Background="{TemplateBinding Background}"
                    Padding="{TemplateBinding Padding}"
                    CornerRadius="6">

                    <ContentPresenter
                        HorizontalAlignment="Center"
                        VerticalAlignment="Center"/>
                </Border>
            </ControlTemplate>
        </Setter.Value>
    </Setter>
</Style>

## DataTemplate 
A DataTemplate in Windows Presentation Foundation (WPF) defines the visual appearance of your data objects when 
they are displayed in UI controls. Without a DataTemplate, controls that are bound to a collection of custom 
objects will simply display the fully qualified name of each object (or the result of its ToString() method). 

E.g : ListBox 
### Why put DataTemplate in resources?

Instead of writing templates inline:

✔ Reuse templates in multiple controls
✔ Keep XAML clean
✔ Centralize UI changes
✔ Enable MVVM-friendly design

### Basic example — DataTemplate in Window resources

Model
public class Person
{
    public string Name { get; set; }
    public int Age { get; set; }
}

<Window.Resources>

    <!-- Reusable template -->
    <DataTemplate x:Key="PersonTemplate">
        <StackPanel Orientation="Horizontal" Margin="4">
            <TextBlock Text="{Binding Name}" FontWeight="Bold"/>
            <TextBlock Text=" (" />
            <TextBlock Text="{Binding Age}" />
            <TextBlock Text=")" />
        </StackPanel>
    </DataTemplate>

</Window.Resources>

Usage : 

<ListBox ItemsSource="{Binding People}"
            ItemTemplate="{StaticResource PersonTemplate}" />
    
✔ Clean
✔ Reusable
✔ No duplication

### Auto-applied DataTemplate (by data type)

You can omit x:Key and let WPF apply it automatically.

<DataTemplate DataType="{x:Type local:Person}">
    <StackPanel Orientation="Horizontal">
        <TextBlock Text="{Binding Name}" />
        <TextBlock Text=" - " />
        <TextBlock Text="{Binding Age}" />
    </StackPanel>
</DataTemplate>

Bound to binding type 'Person'

Usage
<ListBox ItemsSource="{Binding People}" />

Note : Wherever Control is Bind with People, this DataTemplate will be applied 

## ControlTemplate vs DataTemplate (Quick Compare)

| ControlTemplate          | DataTemplate                  |
| ------------------------ | ----------------------------- |
| Changes control look     | Changes data display          |
| Used for Button, TextBox | Used in ListBox, ItemsControl |
| Uses ContentPresenter    | Uses bindings                 |

ControlTemplate = how a control looks
DataTemplate = how data looks

>> ControlTemplate

Defines the visual structure of a control itself.

“How should this Button / CheckBox / TextBox be drawn?”

Used for:
Buttons, CheckBoxes, TextBoxes, Sliders, ScrollBars, DataGridRow / Cell visuals

>> DataTemplate

Defines how a data object is displayed.

“How should this object appear in a list/grid?”

Used for : 
ListBox, ListView, ComboBox, ItemsControl, DataGrid cells

<ListBox ItemsSource="{Binding Tasks}">
    <ListBox.ItemTemplate>
        <DataTemplate>
            <StackPanel Orientation="Horizontal">
                <CheckBox IsChecked="{Binding IsCompleted}"/>
                <TextBlock Text="{Binding Name}" Margin="6,0,0,0"/>
            </StackPanel>
        </DataTemplate>
    </ListBox.ItemTemplate>
</ListBox>

### Common confusion (very important)

<DataTemplate>
    <Border Background="Red"/>
</DataTemplate>

❌ This does NOT style a Button

<ControlTemplate>
    <TextBlock Text="{Binding Name}"/>
</ControlTemplate>

❌ ControlTemplate does NOT know about data items

## When to Use ControlTemplate?

| Scenario                  | Use |
| ------------------------- | --- |
| Change control appearance | ✔   |
| Re-skin Button/TextBox    | ✔   |
| Custom UI theme           | ✔   |
| Change data layout        | ❌  |

## Style VS ContentTemplate 

What is a Style?

A Style is used to:

- Set properties
- Reuse appearance logic
- Add Triggers
- Apply consistent UI

It does NOT change the internal structure of a control.

What is a ControlTemplate?

A ControlTemplate defines:

- Visual tree
- Layout (Border, Grid, Shapes)
- Where content appears

It completely replaces the default UI of the control.

Real-World Analogy

| Concept         | Analogy                       |
| --------------- | ----------------------------- |
| Style           | Changing paint, font, padding |
| ControlTemplate | Rebuilding the house          |


Style vs ControlTemplate — Side-by-Side : 

| Feature               | Style | ControlTemplate |
| --------------------- | ----- | --------------- |
| Changes colors        | ✔     | ✔               |
| Changes layout        | ❌     | ✔               |
| Adds Border / Grid    | ❌     | ✔               |
| Reusable              | ✔     | ✔               |
| Safe to use           | ✔     | ⚠               |
| Easy to maintain      | ✔     | ❌               |
| Uses ContentPresenter | ❌     | ✔               |

Style is used to set and reuse control properties, while ControlTemplate is used to redefine the internal 
visual structure of a control. Style is preferred for most UI changes, and ControlTemplate is used only when 
the default structure is insufficient.

Note : 
Always try Style first.
Use ControlTemplate only if Style is not enough.

# Resource Directory 

A ResourceDictionary is a container for reusable resources, such as:

- Styles
- Brushes (colors)
- Templates
- Converters
- DataTemplates

👉 It helps you organize, reuse, and maintain resources cleanly.

## Why ResourceDictionary is Needed

Without it, everything goes into:

App.xaml file 

Which becomes:

- Huge
- Hard to manage
- Difficult to reuse

👉 ResourceDictionary lets you split resources into separate files.

## Where Can You Use ResourceDictionary?

| Level                        | Scope             |
| ---------------------------- | ----------------- |
| Control.Resources            | Only that control |
| Window/UserControl.Resources | That window       |
| Application.Resources        | Entire app        |

## Basic ResourceDictionary File
🔹 Create a ResourceDictionary

- Add New Item
- Select Resource Dictionary
- Name it Colors.xaml

Colors.xaml

<ResourceDictionary
    xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
    xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml">

    <SolidColorBrush x:Key="PrimaryBrush" Color="#2196F3"/>
    <SolidColorBrush x:Key="DangerBrush" Color="Red"/>

</ResourceDictionary>

## Using ResourceDictionary in App.xaml (MOST COMMON)

<Application.Resources>
    <ResourceDictionary>
        <ResourceDictionary.MergedDictionaries>
            <ResourceDictionary Source="Resources/Colors.xaml"/>
        </ResourceDictionary.MergedDictionaries>
    </ResourceDictionary>
</Application.Resources>

## Window-Level ResourceDictionary

<Window.Resources>
    <ResourceDictionary>
        <ResourceDictionary.MergedDictionaries>
            <ResourceDictionary Source="ButtonStyles.xaml"/>
        </ResourceDictionary.MergedDictionaries>
    </ResourceDictionary>
</Window.Resources>

✔ Used only in that window

## MergedDictionaries (IMPORTANT)

You can merge multiple dictionaries:

<ResourceDictionary.MergedDictionaries>
    <ResourceDictionary Source="Resources/Colors.xaml"/>
    <ResourceDictionary Source="Resources/ButtonStyles.xaml"/>
    <ResourceDictionary Source="Resources/TextStyles.xaml"/>
</ResourceDictionary.MergedDictionaries>

## Best Practices (REAL PROJECTS)

✔ Separate dictionaries by purpose
✔ Keep App.xaml small
✔ Use meaningful keys
✔ Avoid duplicate keys
✔ Use DynamicResource for themes
✔ Prefer BasedOn for style reuse

## Common Mistakes

❌ Putting everything in App.xaml
❌ Forgetting to merge dictionary
❌ Duplicate resource keys
❌ Using ControlTemplate everywhere

# Sizing in WPF 
What “viewport” means in WPF

In WPF, viewport = the space a control is given by its parent.

A control does NOT decide its size.
The parent decides, then the child adapts.

This happens in two passes:

## Key properties that affect viewport sizing

| Property                                | What it does            |
| --------------------------------------- | ----------------------- |
| Width / Height                          | Hard constraint         |
| MinWidth / MinHeight                    | Lower bound             |
| MaxWidth / MaxHeight                    | Upper bound             |
| Margin                                  | Reduces available space |
| Padding                                 | Reduces internal space  |
| HorizontalAlignment / VerticalAlignment | How to use extra space  |
| Stretch                                 | How content fills space |

## How different panels define the viewport

1. Grid (MOST IMPORTANT PANEL)

Column/Row sizing rules:

| Size        | Meaning               |
| ----------- | --------------------- |
| Auto        | Size to content       |
| * (Star)    | Share remaining space |
| Fixed (100) | Absolute              |

2. 📐 DockPanel
<DockPanel>
    <Border DockPanel.Dock="Top" Height="50"/>
    <Grid/>
</DockPanel>


✔ Simple layouts
✔ Header / Footer

3. 🖼️ Viewbox (RESPONSIVE SCALING)
<Viewbox Stretch="Uniform">
    <Grid Width="400" Height="300">
        <!-- Fixed design -->
    </Grid>
</Viewbox>


✔ Scales entire UI
✔ Preserves aspect ratio
⚠ Text may blur if overused

Use for:

- Logos
- Icons
- Splash screens

## Alignment vs Stretch (CRITICAL)

| Alignment         | Effect               |
| ----------------- | -------------------- |
| Stretch (default) | Fill available space |
| Center            | Use desired size     |
| Left / Top        | Stick to edge        |

## 🧠 How to make WPF UI responsive (REAL RULES)

✅ Rule 1: Avoid fixed Width / Height

❌ Bad:

<Button Width="200"/>

✔ Good:

<Button MinWidth="120"/>

✅ Rule 2: Use Grid + Star sizing
<Grid>
    <Grid.RowDefinitions>
        <RowDefinition Height="Auto"/>
        <RowDefinition Height="*"/>
    </Grid.RowDefinitions>
</Grid>

✅ Rule 3: Let content stretch
<TextBox HorizontalAlignment="Stretch"/>


(Default, but often overridden accidentally)

✅ Rule 4: Use SizeToContent carefully
<Window SizeToContent="WidthAndHeight"/>

✔ Dialogs
❌ Main windows

✅ Rule 5: Use Viewbox ONLY for vector visuals

✔ Logos
✔ Icons
❌ Forms
❌ Data grids

🧪 Responsive example (production ready)
<Grid>
    <Grid.RowDefinitions>
        <RowDefinition Height="Auto"/>
        <RowDefinition Height="*"/>
    </Grid.RowDefinitions>

    <!-- Header -->
    <Border Height="56"/>

    <!-- Content -->
    <Grid Grid.Row="1">
        <Grid.ColumnDefinitions>
            <ColumnDefinition Width="2*"/>
            <ColumnDefinition Width="3*"/>
        </Grid.ColumnDefinitions>
    </Grid>
</Grid>


Resize window → everything adapts.

# Why WPF has no % sizing

WPF is not pixel-based and not layout-once like HTML/CSS.

WPF layout is:

- Parent-driven
- Two-pass (Measure / Arrange)
- DPI-aware
- Resolution-independent

So % doesn’t fit WPF’s design model.

✅ WPF’s “percentage sizing” equivalents (THIS IS IMPORTANT)

🥇 1️⃣ Grid star sizing (*) — THIS IS %
<Grid>
    <Grid.ColumnDefinitions>
        <ColumnDefinition Width="30*"/>
        <ColumnDefinition Width="70*"/>
    </Grid.ColumnDefinitions>
</Grid>


✔ 30% / 70%
✔ Resizes automatically
✔ DPI safe
✔ Layout-safe

Star sizing IS percentage sizing in WPF

🥈 2️⃣ Equal distribution
<ColumnDefinition Width="*"/>
<ColumnDefinition Width="*"/>


= 50% / 50%

🥉 3️⃣ Mixed sizing (responsive)
<ColumnDefinition Width="Auto"/>
<ColumnDefinition Width="3*"/>
<ColumnDefinition Width="7*"/>


✔ Content-sized + percentage layout

❌ What NOT to do

❌ Try to calculate % in code-behind
❌ Bind Width to ActualWidth * 0.3
❌ Use Canvas for layout
❌ Use StackPanel for main layout

Example of bad practice:

Width="{Binding ActualWidth, ElementName=RootGrid}"


This breaks layout passes and causes bugs.

✅ Height percentages (same rule)
<Grid.RowDefinitions>
    <RowDefinition Height="20*"/>
    <RowDefinition Height="80*"/>
</Grid.RowDefinitions>

## Width="*" vs Width="2*"
Simple rule:

2* means twice as much space as *

Example 1 — Two columns
<Grid>
    <Grid.ColumnDefinitions>
        <ColumnDefinition Width="*"/>
        <ColumnDefinition Width="2*"/>
    </Grid.ColumnDefinitions>
</Grid>

Result:

Total parts = 1 + 2 = 3
Column 1 = 1/3 (~33%)
Column 2 = 2/3 (~67%)

📐 Example 2 — Three columns
<ColumnDefinition Width="*"/>
<ColumnDefinition Width="*"/>
<ColumnDefinition Width="*"/>


Each column:

1 + 1 + 1 = 3 parts
Each = 33.33%

📐 Example 3 — Mixed ratios
<ColumnDefinition Width="2*"/>
<ColumnDefinition Width="3*"/>
<ColumnDefinition Width="5*"/>


Total = 10 parts
20% / 30% / 50%
