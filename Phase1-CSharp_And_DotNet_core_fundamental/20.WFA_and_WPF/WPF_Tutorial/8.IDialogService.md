# Note : ViewModel should not directly communicate with view (WPF), it breaks MVVM pattern

❌ **Direct communication — NO**

ViewModel should not:

- Call methods on View
- Create or open windows
- Access controls (TextBox, DataGrid, etc.)

✅ **Indirect communication — YES**

- Communication happens via:
- DataBinding
- Commands
- Events / Services / Messaging

```text
View ⇄ (Binding / Command) ⇄ ViewModel
```

No, ViewModel should not call `Window.Show()` or directly communicate with the View.
Communication should be indirect using data binding, commands, or services to keep MVVM clean, testable, and
loosely coupled.

# Want to communicate between windows? - use IDialogService Interface

**What is IDialogService in WPF?**

`IDialogService` is not built into WPF.
It is a custom abstraction used in MVVM to:

Show dialogs (MessageBox, custom windows) without referencing UI types in ViewModels.

**Problem it solves**

ViewModels must not do this:

```csharp
MessageBox.Show("Saved");
```

**Because:**

- Couples VM to UI
- Breaks MVVM
- Hard to unit test

## Example : MessageBox

### 1. Introduce an interface

```csharp
public interface IDialogService
{
    void ShowMessage(string message, string title);
    bool ShowConfirmation(string message, string title);
}
```

ViewModels depend on the interface, not WPF.

**Architecture Overview**

```text
ViewModel → IDialogService (interface)
                     ↓
             DialogService (WPF)
                     ↓
                MessageBox / Window
```

### 2. Implement WPF dialog service

```csharp
using System.Windows;

public class DialogService : IDialogService
{
    public void ShowMessage(string message, string title)
    {
        MessageBox.Show(
            message,
            title,
            MessageBoxButton.OK,
            MessageBoxImage.Information);
    }

    public bool ShowConfirmation(string message, string title)
    {
        return MessageBox.Show(
            message,
            title,
            MessageBoxButton.YesNo,
            MessageBoxImage.Question)
            == MessageBoxResult.Yes;
    }
}
```

### 3. Register in DI container (WPF App) — if using DI

```csharp
services.AddSingleton<IDialogService, DialogService>();
```

### 4. Use it in ViewModel (Correct MVVM)

```csharp
public class MainViewModel
{
    private readonly IDialogService _dialogService;

    public ICommand SaveCommand { get; }

    public MainViewModel(IDialogService dialogService)
    {
        _dialogService = dialogService;

        SaveCommand = new RelayCommand(Save);
    }

    private void Save()
    {
        _dialogService.ShowMessage(
            "Data saved successfully",
            "Success");
    }

    private void Delete()
    {
        bool confirmed = _dialogService.ShowConfirmation(
            "Are you sure you want to delete?",
            "Confirm");

        if (!confirmed)
            return;

        // delete logic
    }
}
```

## When to use IDialogService

- ✔ MessageBox
- ✔ Confirmation dialogs
- ✔ Custom modal dialogs
- ✔ File open/save dialogs
- ✔ Error / validation dialogs

## File Dialog Service (OpenFileDialog)

### 1. Interface (ViewModel-safe)

```csharp
public interface IFileDialogService
{
    string? OpenFile(
        string filter,
        string title,
        string initialDirectory = "");
}
```

### 2. WPF implementation

```csharp
using Microsoft.Win32;

public class FileDialogService : IFileDialogService
{
    public string? OpenFile(
        string filter,
        string title,
        string initialDirectory = "")
    {
        var dialog = new OpenFileDialog
        {
            Filter = filter,
            Title = title,
            InitialDirectory = initialDirectory,
            CheckFileExists = true
        };

        return dialog.ShowDialog() == true
            ? dialog.FileName
            : null;
    }
}
```

### 3. Register in DI

```csharp
services.AddSingleton<IFileDialogService, FileDialogService>();
```

### 4. Use in ViewModel (Correct MVVM)

```csharp
public class ImportViewModel
{
    private readonly IFileDialogService _fileDialogService;

    public ICommand BrowseCommand { get; }

    public string? SelectedFile { get; private set; }

    public ImportViewModel(IFileDialogService fileDialogService)
    {
        _fileDialogService = fileDialogService;
        BrowseCommand = new RelayCommand(Browse);
    }

    private void Browse()
    {
        SelectedFile = _fileDialogService.OpenFile(
            filter: "CSV Files (*.csv)|*.csv|All Files (*.*)|*.*",
            title: "Select data file");

        if (SelectedFile == null)
            return;

        // continue processing
    }
}
```

### 2. Dialog Window (XAML)

**DialogWindow.xaml**

```xml
<Window x:Class="MyApp.Views.InputDialog"

            <Button Content="OK"

                    Width="80"
                    Command="{Binding CancelCommand}" />
        </StackPanel>
    </StackPanel>

```

> **Note:** `MyApp.Views.InputDialog` — `InputDialog()` => View code-behind

### 3. Dialog ViewModel (NO Window references)

```csharp
public class InputDialogViewModel : ViewModelBase
{
    public string? UserInput { get; set; }

    public ICommand OkCommand { get; }
    public ICommand CancelCommand { get; }

    public bool? DialogResult { get; private set; }

    public InputDialogViewModel()
    {
        OkCommand = new RelayCommand(Accept);
        CancelCommand = new RelayCommand(Cancel);
    }

    private void Accept()
    {
        DialogResult = true;
        RequestClose?.Invoke();
    }

    private void Cancel()
    {
        DialogResult = false;
        RequestClose?.Invoke();
    }

    public event Action? RequestClose;
}
```

### 4. Dialog Service implementation (WPF-only)

```csharp
public class DialogService : IDialogService
{
    public bool ShowDialog<TViewModel>(TViewModel viewModel)
        where TViewModel : class
    {
        var window = CreateWindowForViewModel(viewModel);

        window.ShowDialog();

        return (viewModel as dynamic)?.DialogResult == true;
    }

    private Window CreateWindowForViewModel(object viewModel)
    {
        // this will be replaced by DI Injection check file 10.RealAppSetup_mustcheck.md
        Window window = viewModel switch
        {
            InputDialogViewModel => new InputDialog(),
            _ => throw new InvalidOperationException("No dialog registered")
        };

        window.DataContext = viewModel;

        if (viewModel is InputDialogViewModel vm)
        {
            vm.RequestClose += () => window.Close();
        }

        return window;
    }
}
```

# IMessageBus

`IMessageBus` lets parts of your app talk to each other without knowing about each other.

**Use:** Publish-subscribe model

## When do you NEED a MessageBus in WPF?

| Scenario            | Example                  |
| ------------------- | ------------------------ |
| Background → UI     | Autosave status          |
| Window → Window     | Tool window updates main |
| Service → ViewModel | Sync progress            |
| Global events       | Logout, shutdown, errors |
| Non-modal windows   | Live monitor             |

## Explained

**IMessageBus interface (minimal & correct)**

```csharp
public interface IMessageBus
{
    void Publish<TMessage>(TMessage message);
    void Subscribe<TMessage>(Action<TMessage> handler);
    void Unsubscribe<TMessage>(Action<TMessage> handler);
}
```

No WPF references.
Pure .NET.

Example: background service publishing data to update status.

### 1. MessageBus implementation

```csharp
public class MessageBus : IMessageBus
{
    private readonly Dictionary<Type, List<Delegate>> _handlers = new();
    private readonly object _lock = new();

    public void Publish<TMessage>(TMessage message)
    {
        List<Delegate>? subscribers;

        lock (_lock)
        {
            if (!_handlers.TryGetValue(typeof(TMessage), out subscribers))
                return;

            subscribers = subscribers.ToList(); // snapshot
        }

        foreach (var handler in subscribers.Cast<Action<TMessage>>())
        {
            handler(message);
        }
    }

    public void Subscribe<TMessage>(Action<TMessage> handler)
    {
        lock (_lock)
        {
            if (!_handlers.TryGetValue(typeof(TMessage), out var list))
            {
                list = new List<Delegate>();
                _handlers[typeof(TMessage)] = list;
            }

            list.Add(handler);
        }
    }

    public void Unsubscribe<TMessage>(Action<TMessage> handler)
    {
        lock (_lock)
        {
            if (_handlers.TryGetValue(typeof(TMessage), out var list))
            {
                list.Remove(handler);
            }
        }
    }
}
```

### 2. Register in DI (singleton)

```csharp
services.AddSingleton<IMessageBus, MessageBus>();
```

`MessageBus` must be singleton, otherwise messages won't reach other components.

### 3. Define message types (IMPORTANT)

Message data to publish:

```csharp
public record AutoSaveStatus(DateTime Time, bool Success, string Message);
public record ProgressUpdated(int Percentage);
public record ProjectChanged(int ProjectId);
```

✔ `record` is perfect here

### 4. Publishing a message (background service)

```csharp
_bus.Publish(new AutoSaveStatus(
    DateTime.Now,
    true,
    "Autosave completed"));
```

**Publisher:**

- Does NOT know who receives
- Does NOT care

### 5. Subscribing in ViewModel (MainWindow)

```csharp
public class MainViewModel : ViewModelBase
{
    private readonly IMessageBus _bus;

    public string StatusText { get; private set; }

   public MainViewModel(IMessageBus bus)
    {
        _bus = bus;
        _bus.Subscribe<AutoSaveStatus>(OnAutoSaveStatus);
    }

    private void OnAutoSaveStatus(AutoSaveStatus status)
    {
        Application.Current.Dispatcher.BeginInvoke(() =>
        {
            StatusText = status.Success
                ? $"Saved at {status.Time:t}"
                : $"Save failed: {status.Message}";

            OnPropertyChanged(nameof(StatusText));
        });
    }
}
```

| Copy references    | ✅        |

| Await              | ❌        |
| I/O                | ❌        |
| UI access          | ❌        |
| Network calls      | ❌        |

## Publish message from background service : Common use

`BackgroundService`: This is managed by generic host, execute function `ExecuteAsync`.

### 1. Background autosave service

```csharp
public class AutoSaveService : BackgroundService
{
    private readonly IDataChangeTracker _tracker; // this is the class representing change like a flag 
    private readonly IMessageBus _bus;
    private readonly IRepository<TaskItem> _repository;
    private readonly ILogger<AutoSaveService> _logger;
    private readonly int _intervalSeconds;

    public AutoSaveService(
        IDataChangeTracker tracker,
        IMessageBus bus,
        IRepository<TaskItem> repository,
        IOptions<ApplicationSettings> options,
        ILogger<AutoSaveService> logger)
    {
        _tracker = tracker;
        _bus = bus;
        _repository = repository;
        _logger = logger;
        _intervalSeconds = options.Value.AutoSaveIntervalSeconds;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        _logger.LogInformation("AutoSaveService started");

        while (!stoppingToken.IsCancellationRequested)
        {
            try
            {
                await Task.Delay(TimeSpan.FromSeconds(_intervalSeconds), stoppingToken);

                if (!_tracker.HasChanges)
                    continue;

                // Simulate save
                await _repository.SaveChangesAsync();

                _tracker.MarkClean();

                _bus.Publish(new AutoSaveStatus(
                    DateTime.Now, true, "Autosave completed"));

                _logger.LogInformation("Autosave completed");
            }
            catch (OperationCanceledException)
            {
                // expected on shutdown
            }
            catch (Exception ex)
            {
                _bus.Publish(new AutoSaveStatus(
                    DateTime.Now, false, ex.Message));

                _logger.LogError(ex, "Autosave failed");
            }
        }
    }
}
```

### 2. Create a data change tracker (simple)

```csharp
public interface IDataChangeTracker
{
    bool HasChanges { get; }
    void MarkDirty();
    void MarkClean();
}

public class DataChangeTracker : IDataChangeTracker
{
    private bool _hasChanges;

    public bool HasChanges => _hasChanges;

    public void MarkDirty() => _hasChanges = true;
    public void MarkClean() => _hasChanges = false;
}
```

### 3. Mark data as dirty from ViewModels

```csharp
public class TaskEditViewModel
{
    private readonly IDataChangeTracker _tracker;

    public TaskEditViewModel(IDataChangeTracker tracker)
    {
        _tracker = tracker;
    }

    private string _title;
    public string Title
    {
        get => _title;
        set
        {
            _title = value;
            _tracker.MarkDirty();
            OnPropertyChanged();
        }
    }
}
```

## ✅ Short answer (memorize this)

Call `_host.StopAsync()` only in `App.OnExit()`
(or `Application.Exit` equivalent)

Never from:

- ViewModels ❌
- Windows ❌
- BackgroundServices ❌

### 1️⃣ Why OnExit is the correct place

`_host.StopAsync()` means:

- Signal cancellation to all BackgroundServices
- Wait for them to finish gracefully
- Flush logs
- Dispose services
- That is application-level responsibility.

Only `App.xaml.cs` owns the application lifecycle.

# Application.Current.Dispatcher.Invoke(() => handler(message)) vs handler.Invoke(Message)

## The two lines compared

**1️⃣ UI-thread marshaled call**

```csharp
Application.Current.Dispatcher.Invoke(() =>
    handler(message));
```

**2️⃣ Direct invocation**

```csharp
handler?.Invoke(message);
```

They are NOT equivalent.

## Why this matters in WPF

WPF has thread affinity:

> UI objects may only be accessed on the UI thread

If a subscriber touches:

- `ObservableCollection`
- `INotifyPropertyChanged`
- `DependencyProperty`
- UI-bound state

and you call it from a background thread, your app will:

💥 crash with

```text
The calling thread cannot access this object...
```

## What each line actually does

🔹 **`handler?.Invoke(message);`**

- ✔ Executes on current thread
- ❌ No thread switch
- ❌ Unsafe if current thread ≠ UI thread

Use only if:

- You are 100% sure you're already on UI thread
- Or subscriber does not touch UI at all

🔹 **`Dispatcher.Invoke(...)`**

- ✔ Forces execution on UI thread
- ✔ Safe for UI-bound subscribers
- ✔ Correct for background → UI communication

This is what your MessageBus → ViewModel → UI scenario needs.
