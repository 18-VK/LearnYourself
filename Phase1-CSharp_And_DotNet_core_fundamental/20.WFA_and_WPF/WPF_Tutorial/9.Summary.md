## Best Practices (REAL PROJECTS)

- ✔ Separate dictionaries by purpose
- ✔ Keep App.xaml small
- ✔ Use meaningful keys
- ✔ Avoid duplicate keys
- ✔ Use DynamicResource for themes
- ✔ Prefer BasedOn for style reuse

## Common Mistakes

- ❌ Putting everything in App.xaml
- ❌ Forgetting to merge dictionary
- ❌ Duplicate resource keys
- ❌ Using ControlTemplate everywhere

## Common MVVM separation mistakes ❌

❌ **Logic in View**

```xml
<Button Click="if(User.IsAdmin) Save()"/>
```

❌ **UI in ViewModel**

```csharp
MessageBox.Show("Saved!");
```

❌ **Business logic in Converter**

Converter checks user role from DB

## Basic pieces you need in real apps

- ViewModel implementing `INotifyPropertyChanged`
- `ObservableCollection<T>` for lists, so UI updates on add/remove
- Commands (`ICommand`) for actions (login/save/delete)
- `DataContext` set on window/usercontrol (ViewModel-first or View-first)
- XAML bindings referencing ViewModel properties/commands

### Common mistakes - Converter ❌

- ❌ Doing DB / API calls in converters
- ❌ Changing ViewModel state
- ❌ Throwing exceptions
- ❌ Forgetting `Binding.DoNothing` in `ConvertBack`

## Common mistakes - Async relayCommand ❌

- ❌ Using `async void` in ViewModel methods
- ❌ Not disabling button during async work
- ❌ Using `Task.Run` for I/O
- ❌ Calling `MessageBox` inside ViewModel
- ❌ Using `CommandManager` with async commands

## Practical Recommendations for You (Aman)

Use MVVM + Clean Architecture for long-term WPF projects.

Structure your solution like this:

- **MyApp.Domain** → Entities, Value Objects, Domain Services
- **MyApp.Application** → Use Cases, Interfaces, CQRS Handlers
- **MyApp.Infrastructure** → EF Core, Logging, API Clients
- **MyApp.Presentation** → WPF Views + ViewModels (with CommunityToolkit.Mvvm)

Integrate Generic Host in `App.xaml.cs` for DI, logging, and configuration (like ASP.NET Core).

Test Domain and Application layers independently without WPF or EF Core.
