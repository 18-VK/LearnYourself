# ASP - Controller

A controller is a class that handles HTTP requests, coordinates with models/services, and returns responses.
In Web APIs, controllers typically inherit from `ControllerBase` (no view support) and are decorated with `[ApiController]`. `Controller` (inherits
`ControllerBase`) is used when you also need view rendering (Razor views).

## Core Responsibilities

- **Request Handling:**
  Controllers receive HTTP requests (e.g., GET, POST) and determine which action to execute based on routing rules.
- **Action Methods:**
  Public methods within a controller are called actions. Each action handles a specific request and returns a result (e.g., a view, JSON,
  redirect).
- **Response Generation:**
  Actions return types like `IActionResult`, `ViewResult`, `JsonResult`, `RedirectResult`, or even raw strings, which are converted into HTTP
  responses.

## Key Conventions

- **Naming:**
  Controller class names must end with `Controller` (e.g., `HomeController`, `ProductController`).
- **Location:**
  Controllers are typically placed in the `Controllers` folder at the project root.
- **Inheritance:**
  - ASP.NET Core MVC: Controllers inherit from `Controller` (which itself inherits from `ControllerBase`).
  - ASP.NET Core Web API: Use `ControllerBase` directly to avoid view-related features. Use `Controller` only if the controller serves both views
    and APIs.

## Important attributes:

### [ApiController]

Automatic model-state validation, improved parameter binding behaviors, and better 400 responses.
It tells ASP.NET Core that this controller is an API controller, not a traditional MVC controller.
It enables automatic API-specific behaviors.

**What [ApiController] Does Automatically?**

#### 1. Automatic Model Validation

If the request body is invalid, ASP.NET automatically returns `400 Bad Request`.

**Example DTO:**

```csharp
public class ProductDto
{
    [Required]
    public string Name { get; set; }

    [Range(1, 100000)]
    public decimal Price { get; set; }
}
```

**Controller:**

```csharp
[ApiController]
public class ProductsController : ControllerBase
{
    [HttpPost]
    public IActionResult Create(ProductDto product)
    {
        return Ok(product);
    }
}
```

If request body:

```json
{
 "price": 100
}
```

Response automatically:

```text
400 Bad Request
```

Without writing manual validation code.

#### 2. Automatic Parameter Binding

ASP.NET Core automatically determines where parameters come from.

**Example:**

```csharp
[HttpGet("{id}")]
public IActionResult GetProduct(int id)
```

Here:
`id` → automatically taken from URL

**Example request:**

```http
GET /api/products/10
```

#### 3. Better Error Responses

Errors return structured responses.

**Example response:**

```json
{
 "errors": {
  "Name": ["The Name field is required."]
 }
}
```

#### 4. Binding Source Inference

ASP.NET automatically understands where data comes from:

| Source | Example                |
| ------ | ---------------------- |
| Route  | `/api/products/10`     |
| Query  | `/api/products?page=1` |
| Body   | JSON request body      |

### [Route("api/[controller]")]

Typical base route for controller-based APIs.
`[Route]` defines the URL pattern used to access the controller.

**Example:**

```csharp
[Route("api/[controller]")]
```

`[controller]` is a token.

ASP.NET replaces it with the controller name.

**Example**

**Controller:**

```csharp
[ApiController]
[Route("api/[controller]")]
public class ProductsController : ControllerBase
{

}
```

`[controller]` becomes:

```text
products
```

Final route:

```text
api/products
```

### 3️⃣ Example Controller

```csharp

[Route("api/[controller]")]
public class ProductsController : ControllerBase

    [HttpGet]
    public IActionResult GetProducts()
    {
        return Ok("All products");
    }

    [HttpGet("{id}")]
    public IActionResult GetProduct(int id)
    {
        return Ok($"Product {id}");
    }

    [HttpPost]

    {
        return Ok(product);
    }

```

**Extra:** (Will go through them, in action tutorial)

**Action Result Types**

- `View()`: Renders a Razor view.
- `Json()`: Returns JSON data (used in APIs).
- `RedirectToAction()`: Performs a redirect.
- `Content()`: Returns plain text.
- `Ok()`, `BadRequest()`, `CreatedAtRoute()`: Used in RESTful APIs.

# ASP - Routing

Routing determines which controller and action method is invoked based on the URL and other request attributes. This is handled by the Routing Middleware in
the application pipeline.

## Types of Routing

ASP.NET Core supports two main routing approaches:

## Conventional Routing

Conventional routing defines a default URL structure for all controllers and actions in a single location, typically in the `Program.cs` file using the
`MapControllerRoute` method.

**How it works:** It establishes a convention for URL paths, tokenizing segments of the URL to match the controller name, action method name, and optional
parameters.

**Default Pattern:** The common default template is `"{controller=Home}/{action=Index}/{id?}"`.

- `{controller}` maps to the controller name (default is `Home`).
- `{action}` maps to the action method name (default is `Index`).
- `{id?}` is an optional parameter (the `?` makes it optional).

**Use Case:** This approach is commonly used in traditional web applications that use controllers and views, providing a simple and consistent URL structure
across the application.

**Example:** A request to `/Home/About` would map to the `About` action in `HomeController`. The `{id?}` makes the ID parameter optional.

✅ **Configuration**

```csharp
app.MapControllerRoute(
    name: "default",
    pattern: "api/{controller=Home}/{action=Index}/{id?}"
);
```

⚠️ **Why not preferred for APIs?**

- URLs are not RESTful
- Harder to control endpoints
- Less explicit mapping

### Configuration breakdown

```csharp
app.MapControllerRoute(
    name: "default",
    pattern: "api/{controller=Home}/{action=Index}/{id?}"
);
```

✅ **What this means**

This is a conventional route template that tells ASP.NET Core:
"Use this URL pattern to map requests to controllers and actions."

🔍 **Breakdown of the pattern**

```text
api/{controller=Home}/{action=Index}/{id?}
```

| Part                | Meaning                          |
| ------------------- | -------------------------------- |
| `api/`              | Fixed prefix in URL              |
| `{controller=Home}` | Controller name (default = Home) |
| `{action=Index}`    | Method name (default = Index)    |
| `{id?}`             | Optional parameter               |

🧠 **Default values**

If something is missing in URL:

- Controller → `Home`
- Action → `Index`
- `id` → optional

### How Routing Maps URLs → Methods

✅ **Example 1**

```http

```

```text

action = Index (default)
id = null
```


✅ **Example 2**


```text

id = 5
```

👉 Executes:


✅ Response:

```text
"Product 5"
```

✅ **Example 3 (Default route)**

```http
GET /api
```

Mapping:

```text
controller = Home (default)
action = Index (default)
```

👉 Looks for:

```csharp
HomeController.Index()
```

### 4. Important Concepts

✅ **1. Controller name mapping**

```text
products → ProductsController
```

👉 ASP.NET automatically removes "Controller" suffix

✅ **2. Action name mapping**

```text
/details → Details()
```

👉 URL segment maps directly to method name

✅ **3. Parameter binding**

```text

```

👉 `5` → mapped to:

```csharp

```

✅ **4. Optional parameter**

```text

```

Means:

```text

/api/products/details/5 → valid
```

### Why this is called "Conventional Routing"

Because:

- You follow a fixed convention (pattern)
- No attributes like `[HttpGet]`, `[Route]`

👉 Everything is controlled centrally in `Program.cs`

## Attribute Routing

Attribute routing uses attributes applied directly to controllers and action methods to define routes, offering more explicit and fine-grained control over
the URIs.

This approach uses attributes (`[Route]`, `[HttpGet]`, `[HttpPost]`, etc.) directly on the controller class and action methods to define specific, fine-grained
routes. This is the recommended style for building RESTful APIs.

**How it works:** Route templates are defined using attributes like `[Route]`, `[HttpGet]`, `[HttpPost]`, etc., directly above the methods
or controller classes.

**Use Case:** This is the recommended and default approach for building RESTful APIs, as it allows for specific URL patterns, including versioning and complex
hierarchies of resources, to be defined right alongside the code that handles the request.

**Key Features:**

- **HTTP Method Attributes:** Specific attributes like `[HttpGet]`, `[HttpPost]`, `[HttpPut]`, etc., are used to match the HTTP verb of the request.
- **Route Constraints:** You can apply constraints to parameters within the route template (e.g., `"{id:int}"`) to ensure they match specific data types or
  criteria.
- **Route Prefixes:** The `[Route]` attribute can be applied at the controller level to define a common base path for all actions within that controller (e.g.,
  `[Route("api/[controller]")]`).

**Example:** As shown in the `ProductsController` above, `[Route("api/[controller]")]` on the class combined with `[HttpGet("{id}")]` on a method results in a URL
like `/api/products/1`.

Attribute routing provides explicit control over the URL structure, improving readability and maintainability for APIs.

✅ **Configuration**

```csharp
builder.Services.AddControllers();
app.MapControllers();
```

### Real world example:

```csharp
[ApiController]
[Route("api/products")]
public class ProductsController : ControllerBase
{
    // GET /api/products
    [HttpGet]
    public IActionResult GetAll() => Ok();


    // GET /api/products/5
    [HttpGet("{id:int}")]
    public IActionResult Get(int id) => Ok();


    // GET /api/products/search?name=pen
    [HttpGet("search")]
    public IActionResult Search(string name) => Ok();


    // POST /api/products
    // Body: { "name": "Pen", "price": 10 }
    [HttpPost]
    public IActionResult Create() => Ok();


    // PUT /api/products/5
    // Body: { updated data }
    [HttpPut("{id}")]
    public IActionResult Update(int id) => Ok();


    // DELETE /api/products/5
    [HttpDelete("{id}")]
    public IActionResult Delete(int id) => Ok();
}
```

**Key Understanding**

- `"{id:int}"` → comes from route
- `string name` → comes from query string
- POST/PUT → data comes from request body
- HTTP method (GET/POST/...) decides action execution

## Hybrid Routing (Attribute + Conventional)

✅ **What it is**

Combination of:

- Attribute routing for APIs
- Conventional routing for MVC/UI

👉 Used in real-world apps with both API + UI

**Combining Routing Types**

It is possible to use both conventional and attribute routing within the same ASP.NET Core application. Attribute routes typically take precedence over
conventional routes, meaning if an action has an attribute route defined, that one will be used first.

✅ **Configuration**

```csharp
builder.Services.AddControllersWithViews(); // MVC 
builder.Services.AddControllers(); // Web API, use any one of them as per requirement 

app.MapControllers(); // Attribute routing

app.MapControllerRoute(
    name: "default",
    pattern: "{controller=Home}/{action=Index}/{id?}"
);
```

🚀 **What You Should Focus (As .NET Dev)**

- ✅ Attribute routing (must master)
- ✅ Route constraints
- ✅ RESTful URL design
- ✅ HTTP verbs mapping
- ⚠️ Conventional routing (basic knowledge enough)

# What is Endpoint Routing?

Endpoint Routing is the middleware-based routing system in ASP.NET Core that matches incoming HTTP requests to endpoints (like controller actions or minimal
APIs) and executes them. It separates routing from MVC and allows routing to work with the entire middleware pipeline, improving flexibility and performance.

Endpoint Routing is the core routing system in ASP.NET Core that:

- ✅ Matches an incoming HTTP request to an endpoint
- ✅ An endpoint = controller action, minimal API, Razor page, etc.
- ✅ Then executes the matched endpoint

## Configuration Example

🔹 **.NET 5 (explicit style)**

```csharp
app.UseRouting();

app.UseAuthorization();

app.UseEndpoints(endpoints =>
{
    endpoints.MapControllers();
});
```

🔹 **.NET 6+ (modern simplified)**

```csharp
app.MapControllers();
```

👉 Internally this still uses Endpoint Routing

## Final Mental Model

```text
[HttpGet("api/products")]  → Defines endpoint
app.MapControllers()       → Registers endpoints
Endpoint Routing           → Matches & executes
```

## Configuration in Program.cs

In your application's `Program.cs` file, you add the necessary middleware for routing to work:

```csharp
var builder = WebApplication.CreateBuilder(args);

// Add services to the container.
builder.Services.AddControllers(); // Add controller support
// For MVC apps with views, use: builder.Services.AddControllersWithViews();

var app = builder.Build();

// Configure the HTTP request pipeline.

app.UseRouting(); // Adds the routing middleware

// Other middleware like authentication/authorization goes here

//
app.UseEndpoints(endpoints =>
{
    endpoints.MapControllers(); // Maps attribute-routed controllers
    // For conventional routing in MVC, you might use:
    // endpoints.MapControllerRoute(
    //     name: "default",
    //     pattern: "{controller=Home}/{action=Index}/{id?}");
});

app.Run();
```

# App.MapControllers();

It is a method in ASP.NET Core used to enable attribute-based routing for controllers. It is primarily used in Web API applications where routes are defined
directly on controller classes and actions using attributes like `[Route]`, `[HttpGet]`, or `[HttpPost]`.

**Key Functions**

- **Endpoint Discovery:** It scans the application for classes inheriting from `ControllerBase` or `Controller` and identifies their action methods.
- **Route Mapping:** It registers these actions as endpoints in the application's request pipeline based on the routing attributes found.
- **Pipeline Integration:** It acts as the bridge that connects incoming HTTP requests to the specific backend logic defined in your controllers.

# Action method naming rules for production grade API

For production-grade APIs, action naming should be:

- predictable
- RESTful
- clean
- easy for frontend/mobile teams to understand

The biggest mistake beginners make is naming endpoints like:

```csharp
CreateTask()
GetAllTasks()
DeleteTaskById()
```

That's not production REST style.

✅ **Production-Grade Rule**

- Use HTTP verbs for action meaning
- Use nouns for routes

## ✅ Correct RESTful Design

**Controller**

```csharp
[Route("api/tasks")]
```

# Controller : Action method with Cancellation Token

The `CancellationToken` in your controller method is a way to let ASP.NET Core (and ultimately the client) signal
that the request should be aborted. It's part of the cooperative cancellation pattern in .NET.

**How it works in your method**

```csharp
public async Task<ActionResult<TaskResponse>> Create(
    [FromBody] CreateTaskRequest request, 
    CancellationToken ct)
```

- **ASP.NET Core automatically provides the token:** When a request comes in, the framework creates a
  `CancellationToken` tied to the HTTP request lifecycle.

- **Triggered when the client disconnects:** If the client cancels the request (e.g., closes the browser tab, times
  out, or disconnects), the token is signaled (`ct.IsCancellationRequested` becomes `true`).

- **Your code can observe it:** Any async operation that supports cancellation (like EF Core queries, HTTP calls, or
  long-running loops) can accept this token. If the request is aborted, those operations can stop early instead of
  wasting resources.

**Example Usage in Service**

```csharp
public async Task<TaskDTO?> CreateTask(CreateTaskRequest request, CancellationToken ct)
{
    // Check cancellation before doing heavy work
    ct.ThrowIfCancellationRequested();

    var entity = _mapper.Map<Task>(request);

    // Pass token into async repository call
    await _repository.AddAsync(entity, ct);

    return _mapper.Map<TaskDTO>(entity);
}
```

- `ct.ThrowIfCancellationRequested()` → throws `OperationCanceledException` if the request was canceled.
- Passing `ct` into EF Core's `AddAsync` or `SaveChangesAsync` ensures the database operation stops if cancellation is requested.

**Why it matters**

- **Resource efficiency:** Prevents wasted CPU/DB work when the client no longer cares.
- **Scalability:** Important in high-load systems where abandoned requests can pile up.
- **Consistency:** ASP.NET Core middleware will catch `OperationCanceledException` and translate it into a 499 (Client Closed Request) or similar response.
