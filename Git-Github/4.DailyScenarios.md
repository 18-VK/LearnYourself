# Daily Git Scenarios

> Added for the LearnYourself site on 2026-10-24; this note is not part of the original study notes. Each scenario is a
> situation developers meet most days, with the commands that handle it. The commands were checked against the official
> Git reference at https://git-scm.com/docs and assume Git 2.23 or newer (`git switch` and `git restore`).

---

## 1. Start work on a new task

### Situation
You are on `main` and need a branch for a ticket.

### Commands

```bash
git switch main
git pull
git switch -c feature/login-form
```

### Why
Branching from an up-to-date `main` avoids conflicts later, and the feature branch keeps `main` clean until review.

### Careful
`git checkout -b feature/login-form` is the older spelling of `git switch -c`; both work.

---

## 2. Someone needs a quick fix while your work is half done

### Situation
You have uncommitted changes and must switch branches now.

### Commands

```bash
git stash push -m "login form: wip validation"
git switch hotfix/null-check
# fix, commit, push ...
git switch feature/login-form
git stash pop
```

### Why
A stash parks the working-tree and index changes without a half-finished commit, and brings them back where you left off.

### Careful
`git stash pop` drops the stash only when it applies cleanly; after a conflict, resolve it, then `git stash drop`.
Untracked files are not stashed unless you add `-u`.

---

## 3. You committed on the wrong branch (not pushed yet)

### Situation
The commit landed on `main` instead of your feature branch.

### Commands

```bash
git branch feature/login-form        # a new branch pointing at the commit you just made
git reset --hard HEAD~1              # move main back one commit
git switch feature/login-form        # the commit is here now
```

### Why
`git branch <name>` only creates a pointer at the current commit, so nothing is lost; the reset moves `main` back.

### Careful
Only for commits that were never pushed. If the feature branch already exists, use `git switch feature/login-form`,
`git cherry-pick <sha>`, and reset `main` afterwards.

---

## 4. Fix the last commit: wrong message, or a file left out

### Commands

```bash
git commit --amend -m "Add login form validation"

# forgot a file:
git add Validation.cs
git commit --amend --no-edit
```

### Why
Amending rewrites the last commit instead of adding a "fix typo" commit on top.

### Careful
Amending a commit that is already pushed changes its hash: you then need `git push --force-with-lease`, and teammates
who pulled the old commit must re-sync. For pushed work, prefer a new commit.

---

## 5. Undo a commit that is already on the remote

### Commands

```bash
git revert <sha>
git push
```

### Why
`git revert` adds a new commit that undoes the change, so the shared history stays intact.

### Careful
`git reset` on a pushed branch rewrites history that others already have; keep it for your own unpushed commits.
To revert a merge commit, name the parent to keep: `git revert -m 1 <merge-sha>`.

---

## 6. Throw away local edits, or unstage something

### Commands

```bash
git restore Program.cs              # discard the working-tree edits of one file
git restore --staged Program.cs     # unstage it, keep the edits
git restore .                       # discard every unstaged edit (careful)
```

### Why
`restore` works on files; it never touches commits.

### Careful
`git restore <file>` cannot be undone: the edits were never committed, so there is nothing to recover them from.

---

## 7. Bring your branch up to date with main

### Commands

```bash
git fetch origin
git rebase origin/main

# or, to keep a merge commit instead:
git merge origin/main
```

### Why
A rebase replays your commits on top of the latest `main`: a linear history, and conflicts show up now rather than at
merge time. A merge keeps the exact history but adds a merge commit.

### Careful
After rebasing a branch you had already pushed, push with `git push --force-with-lease`, never plain `--force`.
Do not rebase a branch other people are committing to.

---

## 8. Resolve a merge or rebase conflict

### Commands

```bash
git status                           # lists the files marked "both modified"
# open each file, keep the right content, delete the <<<<<<<, ======= and >>>>>>> markers
git add Program.cs
git rebase --continue                # after a rebase;  git merge --continue after a merge

# to back out instead:
git rebase --abort                   # or: git merge --abort
```

### Why
Git stops at every conflicting file and waits; staging a file tells Git it is resolved.

### Careful
Build and run the tests before continuing; `git diff` shows what you resolved.

---

## 9. `git push` was rejected (non-fast-forward)

### Situation
Someone pushed to the same branch before you.

### Commands

```bash
git pull --rebase
# resolve conflicts if any
git push
```

### Why
`--rebase` puts your commits after theirs without a merge commit.

### Careful
Never answer a rejected push with `git push --force` on a shared branch: it deletes their commits.

---

## 10. Take one commit from another branch

### Commands

```bash
git cherry-pick <sha>
```

### Why
Copies a single commit, for example a bug fix, onto your branch without merging everything else.

### Careful
The copy has a new hash. If you need the whole branch, merge it instead of cherry-picking commit by commit.

---

## 11. Recover a deleted branch, or undo a bad reset

### Commands

```bash
git reflog                           # find the commit you were on
git branch recovered <sha>           # or: git reset --hard <sha>
```

### Why
The reflog records where `HEAD` pointed over the last weeks, including commits no branch points to any more.

### Careful
The reflog is local: a fresh clone has none, and entries expire (90 days by default).

---

## 12. Find the commit that broke something

### Commands

```bash
git bisect start
git bisect bad                       # the current commit is broken
git bisect good v1.4.0               # a commit or tag that worked
# test the commit Git checks out, then mark it:  git bisect good   or   git bisect bad
git bisect reset                     # back to where you started
```

### Why
A binary search over the history: about ten steps for a thousand commits.

---

## 13. A file should never have been committed (local settings, build output)

### Commands

```bash
echo "appsettings.Local.json" >> .gitignore
git rm --cached appsettings.Local.json
git commit -m "Stop tracking local settings"
```

### Why
`.gitignore` only affects files that are not tracked yet; `git rm --cached` removes the file from the index and keeps
your copy on disk.

### Careful
The file is still in the old commits. If it held a secret, rotate the secret; removing it from history needs a tool
such as `git filter-repo` and a coordinated force push.

---

## 14. Tidy the commits before opening a pull request

### Commands

```bash
git fetch origin
git rebase -i origin/main            # pick, squash or reword each commit in the editor
git push --force-with-lease
```

### Why
Reviewers read three meaningful commits more easily than twelve "wip" ones.

### Careful
Only on your own branch, before anyone builds on it.

---

## 15. Keep a fork in sync with the original project

### Commands

```bash
git remote add upstream https://github.com/org/project.git   # once
git fetch upstream
git switch main
git merge upstream/main              # or: git rebase upstream/main
git push origin main
```

### Why
`origin` is your fork, `upstream` the project you forked; fetching from `upstream` brings in their changes.

---

## 16. Mark a release

### Commands

```bash
git tag -a v1.2.0 -m "Release 1.2.0"
git push origin v1.2.0
# every tag at once: git push origin --tags
```

### Why
An annotated tag stores who tagged, when and why; CI pipelines and GitHub Releases pick tags up.

---

## 17. See what you are about to pull, and who changed a line

### Commands

```bash
git fetch origin
git log --oneline HEAD..origin/main          # the commits you don't have yet
git diff HEAD...origin/main --stat           # the files they touch
git blame -L 40,60 Program.cs                # who last changed lines 40 to 60
git log -S "ConnectionString" --oneline      # commits that added or removed that text
```

### Why
Fetching first lets you review what is coming before it touches your branch; `blame` and `log -S` find the commit
behind a line.

---

## 18. Clean up when the work is merged

### Commands

```bash
git switch main
git pull
git branch -d feature/login-form             # local branch, only if it is merged
git push origin --delete feature/login-form  # remote branch (GitHub's "Delete branch" button does the same)
git fetch --prune                            # forget remote branches that no longer exist
```

### Careful
`git branch -D` deletes a branch that is not merged; use it only when you are sure.

## Quick map

| I want to… | Command |
| --- | --- |
| start a task | `git switch -c feature/x` |
| park unfinished work | `git stash push -m "…"` / `git stash pop` |
| fix the last (unpushed) commit | `git commit --amend` |
| undo a pushed commit | `git revert <sha>` |
| discard a file's edits | `git restore <file>` |
| unstage a file | `git restore --staged <file>` |
| update my branch | `git fetch origin` + `git rebase origin/main` |
| push after a rebase | `git push --force-with-lease` |
| push rejected | `git pull --rebase` then `git push` |
| copy one commit | `git cherry-pick <sha>` |
| recover anything | `git reflog` |
| find the breaking commit | `git bisect` |
| stop tracking a file | `git rm --cached <file>` + `.gitignore` |
| release | `git tag -a v1.2.0 -m "…"` + `git push origin v1.2.0` |
