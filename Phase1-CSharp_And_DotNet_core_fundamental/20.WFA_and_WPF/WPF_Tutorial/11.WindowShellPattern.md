# How to separate XAML cleanly, where binding lives, and how everything connects — step by step

## Goal (what we want)

The goal is to split a window into separate components to make window logic readable and testable.
This is the production-ready approach.

## Example

You have one Window (Shell) with:

- Header
- Content
- Footer

You want:

- Each part in its own XAML
- Clean MVVM
- Window only hosts
- Views swapped cleanly

**Final architecture (industry-standard)**

```text
MainWindow (Shell)
 └── MainWindowViewModel
      ├── HeaderViewModel
      ├── FooterViewModel
      └── CurrentView (content)
```

**XAML side:**

```text
Views
 ├── MainWindow.xaml   (Shell only)
 ├── HeaderView.xaml
 ├── FooterView.xaml
 ├── DashboardView.xaml
 └── SettingsView.xaml
```

## ✅ Step-by-step implementation

### 1️⃣ MainWindow.xaml (Shell ONLY)

```xml
<Window
    x:Class="Taskflow.MainWindow"
    xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
    xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
    Title="Taskflow Studio">

    <Grid>
        <Grid.RowDefinitions>
            <RowDefinition Height="Auto"/>   <!-- Header -->
            <RowDefinition Height="*"/>      <!-- Content -->
            <RowDefinition Height="Auto"/>   <!-- Footer -->
        </Grid.RowDefinitions>

        <!-- Header -->
        <ContentControl
            Content="{Binding Header}" />

        <!-- Content -->
        <ContentControl
            Grid.Row="1"
            Content="{Binding MainContent}" />

        <!-- Footer -->
        <ContentControl
            Grid.Row="2"
            Content="{Binding Footer}" />
    </Grid>
</Window>
```

- ✔ Window knows nothing about views
- ✔ Only binding

### 2️⃣ MainWindowViewModel.cs (Shell VM)

```csharp
public class MainWindowViewModel : ViewModelBase
{
    public object Header { get; }
    public object Footer { get; }

    private object MainContent{get;}

    public MainWindowViewModel()
    {
        Header = new HeaderViewModel();
        Footer = new FooterViewModel();

        // Initial content
        MainContent = new DashboardViewModel();
    }
}
```

### 3️⃣ Views (separate XAML files)

**HeaderView.xaml**

```xml
<UserControl
    xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
    xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml">
    <Grid Height="56">
        <!-- Header UI -->
    </Grid>
</UserControl>
```

Same for `FooterView`.

### 4️⃣ DataTemplates (MAGIC that binds it all)

This removes view creation from ViewModels.

**App.xaml**

```xml
<Application.Resources>

    <DataTemplate DataType="{x:Type vm:HeaderViewModel}">
        <views:HeaderView />
    </DataTemplate>

    <DataTemplate DataType="{x:Type vm:FooterViewModel}">
        <views:FooterView />
    </DataTemplate>

    <DataTemplate DataType="{x:Type vm:DashboardViewModel}">
        <views:DashboardView />
    </DataTemplate>

</Application.Resources>
```

- ✔ ViewModels decide state
- ✔ XAML decides visuals

## Why this pattern is correct

| Problem             | Solved |
| ------------------- | ------ |
| Massive Window XAML | ❌ gone |
| Tight coupling      | ❌ gone |
| Hard navigation     | ❌ gone |
| Testability         | ✅      |
| Reuse               | ✅      |
| Maintainability     | ✅      |

## ❌ Common wrong approaches (avoid)

- ❌ Putting Header/Footer directly in Window XAML
- ❌ Creating Views inside ViewModels
- ❌ Code-behind navigation
- ❌ Using UserControls without ViewModels

## 🏆 Best practices summary

- ✔ Window = Shell only
- ✔ Each section = UserControl
- ✔ Bind sections via properties
- ✔ Use DataTemplates
- ✔ ViewModel-first navigation

## Header = new HeaderViewModel(); — how is this returning a visual?

**The missing link (this is CRITICAL)**

Somewhere in XAML you have this:

```xml
<ContentControl Content="{Binding Header}" />
```

And in `App.xaml` (or merged dictionary):

```xml
<DataTemplate DataType="{x:Type vm:HeaderViewModel}">
    <views:HeaderView />
</DataTemplate>
```

> **Note:** need to update this in resource dictionary.

**Example:**

```xml
xmlns:views="clr-namespace:YourApp.Views.RightPanel"
xmlns:vm="clr-namespace:YourApp.ViewModels.RightPanel"
```

Put exact namespace of views and vm.

Now the magic can happen.

### Step-by-step: what actually happens internally

**Step 1️⃣ ViewModel property is set**

```csharp
Header = new HeaderViewModel();
```

Now:

- `Header` is a ViewModel instance
- Nothing visual yet

**Step 2️⃣ Binding pushes object into ContentControl**

```xml
Content="{Binding Header}"
```

So WPF sees:

```text
Content = (object) HeaderViewModel
```

**Step 3️⃣ ContentControl asks:**

> "I have an object. How do I draw this?"

This is where DataTemplate lookup starts.

**Step 4️⃣ WPF searches for a DataTemplate**

Lookup order (simplified):

- `ContentControl.Resources`
- Parent resources
- Window resources
- `Application.Resources`
- Theme resources

It searches for:

```text
DataTemplate with DataType == HeaderViewModel
```

**Step 5️⃣ Match found ✅**

```xml
<DataTemplate DataType="{x:Type vm:HeaderViewModel}">
    <views:HeaderView />
</DataTemplate>
```

So WPF says:

> "Aha! When I see `HeaderViewModel`, I should render `HeaderView`."

**Step 6️⃣ View is created automatically**

WPF internally does (conceptually):

```csharp
var view = new HeaderView();
view.DataContext = headerViewModel;
```

> ⚠️ You never write this code — WPF does.

# Note : This approach is for medium-to-large applications

For a small application, or a window having small window logic, don't use it.

## Correct way to inject UserControl ViewModels

**DataTemplate-based VM → View mapping**

This is the most WPF-native approach.

```xml
<Application.Resources>
    <DataTemplate DataType="{x:Type vm:TaskFilterViewModel}">
        <views:TaskFilterView/>
    </DataTemplate>
</Application.Resources>
```

Now in your Window XAML:

```xml
<ContentControl Content="{Binding FilterVM}" />
```

**Window VM**

```csharp
public class MainWindowViewModel
{
    public TaskFilterViewModel FilterVM { get; }

    public MainWindowViewModel(TaskFilterViewModel filterVM)
    {
        FilterVM = filterVM;
    }
}
```

- ✔ ViewModel injected via DI
- ✔ View resolved by WPF
- ✔ No code-behind creation
- ✔ Very clean

```xml
<Window
    x:Class="Taskflow.MainWindow"
    xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
    xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"

        <Grid.RowDefinitions>
            <RowDefinition Height="Auto"/>
            <RowDefinition Height="*"/>
            <RowDefinition Height="Auto"/>
        </Grid.RowDefinitions>

        <!-- Header -->
        <local:HeaderView />

        <!-- Content -->
        <local:MainContentView />

        <!-- Footer -->
```

Use like this `<local:HeaderView />` and no need of data template also.

# Binding data without separate view model

You need code-behind with DependencyProperties so that the parent View can bind data into your UserControl.

## What happens WITHOUT Dependency Properties

Imagine this UserControl:

```xml
<local:BorderlessComboBox
    ItemsSource="{Binding Countries}"
    SelectedItem="{Binding SelectedCountry}" />
```

Inside `BorderlessComboBox.xaml`:

```xml
<ComboBox ItemsSource="{Binding Countries}" /> ❌
```

## What Dependency Properties fix

Dependency Properties let you say:

> "Hey parent, give me this value, and I'll pass it to my inner controls."

**Flow becomes:**

```text
Parent ViewModel
   ↓
UserControl DependencyProperty
   ↓
Inner ComboBox
```

Clean. Predictable. MVVM-safe.

## Example

**BorderlessComboBox.xaml**

```xml
<UserControl x:Class="YourApp.Views.Shared.BorderlessComboBox"
             xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
             xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
             x:Name="root">

    <ComboBox
        ItemsSource="{Binding ItemsSource, ElementName=root}"
        SelectedItem="{Binding SelectedItem, ElementName=root, Mode=TwoWay}"
        SelectedValue="{Binding SelectedValue, ElementName=root, Mode=TwoWay}"
        SelectedValuePath="{Binding SelectedValuePath, ElementName=root}"
        DisplayMemberPath="{Binding DisplayMemberPath, ElementName=root}"

        Background="Transparent"
        BorderThickness="0"
        Padding="4"
        IsEditable="{Binding IsEditable, ElementName=root}"
        />
</UserControl>
```

**Example from your control (real flow)**

**Parent View**

```xml
<local:BorderlessComboBox
    ItemsSource="{Binding Countries}"
    SelectedItem="{Binding SelectedCountry}" />
```

**UserControl DP**

```csharp
public IEnumerable ItemsSource
{
    get => (IEnumerable)GetValue(ItemsSourceProperty);
    set => SetValue(ItemsSourceProperty, value);
}
```

**Internal binding**

```xml
<ComboBox ItemsSource="{Binding ItemsSource, ElementName=root}" />
```

- ✔ Parent controls data
- ✔ UserControl only displays it

## When you DO need code-behind (like now)

- ✔ Reusable UserControl
- ✔ Needs bindings from parent
- ✔ Exposes configuration options
- ✔ No ViewModel inside

This is the correct place for code-behind.

## When you do NOT need Dependency Properties

You don't need them if:

- Control is never reused
- Control never accepts bindings
- Control has a ViewModel
- Control is purely static

**Code-behind (Dependency Properties)**

```csharp
public partial class BorderlessComboBox : UserControl
{
    public BorderlessComboBox()
    {
        InitializeComponent();
    }

    public IEnumerable ItemsSource
    {
        get => (IEnumerable)GetValue(ItemsSourceProperty);
        set => SetValue(ItemsSourceProperty, value);
    }

    public static readonly DependencyProperty ItemsSourceProperty =
        DependencyProperty.Register(nameof(ItemsSource),
            typeof(IEnumerable),
            typeof(BorderlessComboBox));

    public object SelectedItem
    {
        get => GetValue(SelectedItemProperty);
        set => SetValue(SelectedItemProperty, value);
    }

    public static readonly DependencyProperty SelectedItemProperty =
        DependencyProperty.Register(nameof(SelectedItem),
            typeof(object),
            typeof(BorderlessComboBox));

    public object SelectedValue
    {
        get => GetValue(SelectedValueProperty);
        set => SetValue(SelectedValueProperty, value);
    }

    public static readonly DependencyProperty SelectedValueProperty =
        DependencyProperty.Register(nameof(SelectedValue),
            typeof(object),
            typeof(BorderlessComboBox));

    public string DisplayMemberPath
    {
        get => (string)GetValue(DisplayMemberPathProperty);
        set => SetValue(DisplayMemberPathProperty, value);
    }

    public static readonly DependencyProperty DisplayMemberPathProperty =
        DependencyProperty.Register(nameof(DisplayMemberPath),
            typeof(string),
            typeof(BorderlessComboBox));

    public string SelectedValuePath
    {
        get => (string)GetValue(SelectedValuePathProperty);
        set => SetValue(SelectedValuePathProperty, value);
    }

    public static readonly DependencyProperty SelectedValuePathProperty =
        DependencyProperty.Register(nameof(SelectedValuePath),
            typeof(string),
            typeof(BorderlessComboBox));

    public bool IsEditable
    {
        get => (bool)GetValue(IsEditableProperty);
        set => SetValue(IsEditableProperty, value);
    }

    public static readonly DependencyProperty IsEditableProperty =
        DependencyProperty.Register(nameof(IsEditable),
            typeof(bool),
            typeof(BorderlessComboBox),
            new PropertyMetadata(false));
}
```
