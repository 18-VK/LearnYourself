# Authentication and authorization

Authentication and authorization are distinct but complementary processes for securing a web API.

- **Authentication** verifies the identity of the user or client ("Who are you?").
- **Authorization** determines what the authenticated user or client is permitted to do or access ("What are you allowed to do?").

## Authentication Methods

Common methods for authenticating a client with a web API include:

### HTTP Basic Authentication

Credentials (username and password) are sent in the request header, Base64 encoded. This method is simple but less secure and must always be used with HTTPS.

**Flow:**

```text
User
  │
  │ Username + Password
  ▼
Server
  │
  │ Verify password hash
  ▼
Authenticated
```

**Example:**

```text
Username : aman123
Password : MyPassword@123
```

**Database stores:**

- Username
- PasswordHash
- Salt

**Server:**

```csharp
if(Hash(password)==storedHash)
{
    Login Success;
}
```

**Used in:**

- Banking
- E-commerce
- Internal applications

### API Keys

A unique, static key is issued to a registered user and included with every request. This offers limited security control and is often used for
server-to-server or limited-access scenarios.

An API Key is a unique secret string issued by a server to identify and authenticate a client (an application, script, or service) when it makes requests to an API.

**Simple Example:**

Suppose you have a Weather API.

**Without an API key:**

```http
GET /weather?city=Delhi
```

The server doesn't know who is making the request.

**With an API key:**

```http
GET /weather?city=Delhi
x-api-key: 8f3c1d9b7e...
```

The server now knows:

- Which application is calling
- Whether the key is valid
- What permissions or rate limits apply

**How it works:**

```text
Client Application
      │
      │ Request + API Key
      ▼
API Server
      │
      │ Verify API Key
      ▼
Database / Key Store
      │
      ├── Valid → Process request
      └── Invalid → Return 401/403
```

**What information does an API Key contain?**

Usually, it's just a random identifier, for example:

```text
ak_live_3H6Y7QxP8LmN2AbC
```

Unlike a JWT, it does not contain user information.
The server looks up the key in its database:

| API Key | Owner       | Active | Rate Limit |
| ------- | ----------- | ------ | ---------- |
| abc123  | Weather App | Yes    | 1000/day   |
| xyz789  | Mobile App  | Yes    | 5000/day   |

### JSON Web Tokens (JWT)

A popular, stateless mechanism where the server generates a signed token upon successful login. The client includes this token (usually as a Bearer
token in the `Authorization` header) in subsequent requests. The API server validates the token's signature and claims without needing to check a
database for every request, improving scalability.

### OAuth 2.0 / OpenID Connect (OIDC)

OAuth 2.0 is primarily an authorization framework that allows third-party applications limited access to user data without handling the user's
credentials. OIDC is an identity layer built on top of OAuth 2.0 that provides a standard protocol for verifying user identity. These are the modern
standards for user login and delegated access (e.g., "Sign in with Google").

#### OAuth 2.0

OAuth is authorization, not authentication by itself. It lets a user grant one application access to resources in another application without sharing their
password.

**Example:**

```text
Spotify
    ↓
Login with Google
    ↓
Google asks
"Allow Spotify to access your profile?"
    ↓
User clicks Allow
    ↓
Spotify receives an Access Token
```

**Flow:**

```text
Client
    ↓
Authorization Server
    ↓
Access Token
    ↓
Resource Server
```

**Used by:**

- Google
- GitHub
- Microsoft
- Facebook

## Authorization Models

Authorization models define how access decisions are made after a user is authenticated.
Once a user's identity is confirmed, authorization determines their access level:

### Role-Based Access Control (RBAC)

Permissions are assigned based on the user's role (e.g., "Admin", "Editor", "Viewer").
Access is granted based on the user's role.

**Example:**

- Admin can create, edit, delete users
- Manager can approve requests
- Employee can only view their own data

**In real life**

A banking app:

- Admin → manage all accounts
- Teller → process transactions
- Customer → view own balance only

**Think of it like:**

> "Your job title decides what you can do."

### Attribute-Based Access Control (ABAC)

Access decisions are made based on various attributes related to the user, resource, and environment (e.g., time of access, device used), offering
more granular control than RBAC.
Access is granted based on attributes such as user, resource, action, time, or location.

**Example:**

A file can be downloaded only if:

```text
user.department = HR
document.classification = Confidential
request.time is during office hours
```

**In real life**

A hospital system:

- Doctor can view patient record only if they are assigned to that patient
- Access allowed only from hospital network

**Think of it like**

> "Your access depends on multiple conditions."

### Policy-Based Access Control (PBAC)

Authorization logic is externalized into centralized, manageable policies, rather than being hardcoded throughout the application, improving
maintainability and audibility.

Access is decided by a policy engine using defined rules.

**Example**

Policy:

- Allow export of report only if user is Manager
- and device is company-owned
- and MFA was completed

**In real life:**

Enterprise security systems where policies are written centrally and evaluated automatically.

**Think of it like**

> "Access is decided by a policy rule set."

### In ASP.NET Core terms

Most apps use RBAC first because it is simple.

**Role example:**

```csharp
[Authorize(Roles = "Admin")]
public IActionResult DeleteUser()
{
    return Ok("User deleted");
}
```

**Policy example:**

```csharp
[Authorize(Policy = "CanApproveLeave")]
public IActionResult ApproveLeave()
{
    return Ok("Approved");
}
```

**Policy setup:**

```csharp
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("CanApproveLeave", policy =>
        policy.RequireClaim("Permission", "ApproveLeave"));
});
```

# JWT (JSON Web Token)

A JSON Web Token (JWT) is used for securely transmitting information between parties—usually a client and server—as a compact, URL-safe, and digitally signed
JSON object. It is primarily used for stateless user authentication, authorization (access control), and secure information exchange, allowing servers to
verify identity without storing session data.

The JWT is sent in header with every request.
A JSON Web Token (JWT) is a secure way to send information between a client and a server. It is mainly used in web applications and APIs to verify users and
prevent unauthorized access. A JWT is JSON data secured with a cryptographic signature.

The signing can be done using these cryptographic methods:

- HMAC (Hash-based Message Authentication Code)
- RSA or ECDSA (Asymmetric cryptographic algorithms)

## JWT Structure

Here is the structure of a JWT:

A JWT consists of three parts, separated by dots (`.`)

```text
Header. Payload. Signature
```

- **Header:** Contains metadata about the token, such as the algorithm used for signing.
- **Payload:** Stores the claims, i.e., data being transmitted.
- **Signature:** Ensures the token's integrity and authenticity.

### 1. Header

The header contains metadata about the token, including the signing algorithm and token type — here metadata means data about data.

```json
{
    "alg": "HS256",
    "typ": "JWT",
    "kid": "abc123"
}
```

- `alg`: Algorithm used for signing (e.g., HS256, RS256).
- `typ`: Token type, always `"JWT"`.
- `kid`: Key ID (used to match the correct public key in JWKS).

**Base64Url Encoded Header**

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
```

### 2. Payload

The payload contains the information about the user also called as a claim and some additional information including the timestamp at which it was issued and the expiry time of the token.
The payload contains claims about the authenticated user or client.

**Example:**

```json
{
  "sub": "12345",
  "name": "Aman Kumar",
  "email": "aman@example.com",
  "role": "Admin",
  "department": "Engineering",
  "exp": 1783200000,
  "iat": 1783196400,
  "iss": "https://auth.company.com",
  "aud": "TaskManagementAPI"
}
```

| Claim | Meaning                        | Example                    |
| ----- | ------------------------------ | -------------------------- |
| `iss` | Issuer                         | `https://auth.company.com` |
| `sub` | Subject (user ID)              | `12345`                    |
| `aud` | Audience (intended API/client) | `TaskManagementAPI`        |
| `exp` | Expiration time                | Unix timestamp             |
| `nbf` | Not valid before               | Unix timestamp             |
| `iat` | Issued at                      | Unix timestamp             |
| `jti` | Unique token ID                | `3f8d7a9b...`              |

**Base64Url Encoded Payload**

```text
eyJzdWIiOiIxMjM0NSIsIm5hbWUiOiJBbWFuIEt1bWFyIiwi...
```

### 3. Signature

The signature ensures token integrity and is generated using the header, payload, and a secret key. In this example we will use HS256 algorithm to implement the Signature part.

```text
HMACSHA256(
    base64UrlEncode(header) + "." + base64UrlEncode(payload),
    secret
)
```

**Example Signature:**

```text
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

### 4. Final JWT token

After all these steps the final JWT token is generated by joining the Header, Payload and Signature via a dot. It looks like as it is shown below.

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNzA4MzQ1MTIzLCJleHAiOjE3MDgzNTUxMjN9.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

## Key Uses of JWTs

- **Authentication (Most Common):**
  Once a user logs in, the server generates a JWT and sends it back to the client. The client includes this token in subsequent requests, allowing the
  user to access protected routes and resources without re-authenticating.
- **Authorization:**
  JWTs can contain information about user roles, permissions, or specialized claims (e.g., user ID), which the server uses to determine if the user is
  allowed to access specific APIs or functionalities.
- **Information Exchange:**
  Because JWTs are signed (using public/private keys or HMAC), they provide a secure way to transmit data, as the recipient can verify the sender and
  ensure the information has not been tampered with.

## Why JWTs are Popular

- **Stateless:**
  The server does not need to store session information in a database, making them perfect for microservices and scalable applications.
- **Secure:**
  Cryptographically signed, preventing unauthorized tampering.
- **Compact:**
  Small enough to be sent via HTTP headers or URLs.

# JWT authentication flow

To understand the JWT (JSON Web Token) flow in a .NET ecosystem, it is helpful to break the process down into the Identity Provider interaction, Client usage, and .NET API validation.

## 1. Acquiring the Token (The Handshake)

The client application requests access by proving its identity to the Authorization Server (e.g., IdentityServer, Auth0, or Microsoft Entra ID).

- **Request:** The client sends a POST request to the token endpoint containing user credentials (or a client secret/code).
- **Validation:** The Authorization Server verifies the credentials against its user store.
- **Response:** If valid, the server returns a signed JWT. This token contains claims (data about the user, such as `sub`, `role`, and `exp` for expiration).

## 2. Using the Token (The Request)

Once the client receives the JWT, it must include it in every subsequent request to the .NET API to prove it is authorized.

- **Storage:** The client typically stores the token (e.g., in memory, or a secure browser cookie).
- **Header:** For every API call, the client adds the token to the HTTP header:

```http
Authorization: Bearer <your-jwt-here>
```

## 3. API Validation (The Gatekeeper)

When a request hits your .NET API, the JwtBearer authentication middleware processes the token before it ever reaches your controller.

**Token Extraction (Middleware Intercepts the Request)**

- The client sends the JWT in the `Authorization` header.
- Format: `Authorization: Bearer <JWT>`
- The JWT authentication middleware extracts the token by removing the `Bearer` prefix.

**Signature Validation (Cryptographic Verification)**

The authentication handler verifies the token's digital signature.

It uses:

- The public key (for asymmetric algorithms like RSA), or
- The shared secret (for symmetric algorithms like HMAC).

This ensures the token:

- Was issued by a trusted Identity Provider.
- Has not been modified or tampered with.

**Claims Validation (Token Metadata Check)**

After the signature is verified, the middleware validates the token's claims, including:

- **Issuer (`iss`)** – Was the token issued by the expected Identity Provider?
- **Audience (`aud`)** – Is the token intended for this API?
- **Expiration (`exp`)** – Has the token expired?
- **Not Before (`nbf`)** (optional) – Is the token valid yet?
- **Issued At (`iat`)** (optional) – When was the token issued?

**Create User Identity**

If all validations succeed:

- ASP.NET Core creates a `ClaimsPrincipal`.
- The token's claims are stored in `HttpContext.User` (accessible as `User` in controllers).

**Authorization (Role or Policy Check)**

The authorization middleware evaluates access rules such as:

```csharp
[Authorize]
[Authorize(Roles = "Admin")]
```

Policy-based authorization.

If the user satisfies the required roles or policies, the request proceeds to the controller.

Otherwise:

- **401 Unauthorized** – Authentication failed or no valid token was provided.
- **403 Forbidden** – Authentication succeeded, but the user lacks the required permissions.

# Basic API side setup of JWT : Authentication and Authorization Implementation using JWT in Web APIs

(For now, forget about how it gets generated, just focus on how to add auth validation in web API)

In ASP.NET Core, authentication is handled by the authentication service through authentication middleware, and authorization is handled by the
authorization middleware using policies, roles, and claims.

You use them because most APIs should not be public. Authentication protects the API from anonymous callers, and authorization protects sensitive
operations such as admin-only endpoints, user-owned data, and internal actions. For JWT-secured APIs, Microsoft's guidance is that the API should validate
the token and return 401 or 403 rather than redirecting the caller to a login page.

You use authentication at the point where a request proves identity, usually through a bearer token in the `Authorization` header. You use authorization on
the endpoints that need protection, such as `[Authorize]`, `[Authorize(Roles = "Admin")]`, or `[Authorize(Policy = "EmployeeOnly")]`. You can allow public endpoints with `[AllowAnonymous]`, such as login and health-check endpoints.

## Authentication

The API does NOT store users or tokens. It only validates the token sent by client.
It uses the configuration as the source of truth to validate incoming tokens.

> **Note:** check this video - <https://youtu.be/Y4joeekt5Ew>

### How Validation Happens (RUNTIME FLOW)

🧠 **Step-by-step**

Client → sends request with token

```http
Authorization: Bearer <JWT>
```

**Step 1: Authentication Middleware runs**

```csharp
app.UseAuthentication();
```

**Step 2: JWT Handler extracts token**

**Step 3: Validation starts**

- Check Signature
- Check Issuer
- Check Audience
- Check Expiry

**Step 4: If valid**

`HttpContext.User` is created ✅

**Step 5: If invalid**

401 Unauthorized ❌

> **Note:** API depends on configuration given in appsettings related to JWT. It uses this to validate token sent by Client.

**More brief:** All these steps are done by API `JwtBearerHandler` middleware, you don't need to do it.

**Core principle:** Private key signs. Public key verifies. These are two different mathematical operations — not the
same computation run by two different keys.

**1. Signing (Auth Server — private key)**

```text
signing_input = base64url(header) + "." + base64url(payload)
hash = SHA256(signing_input)
signature = hash ^ d mod n        ← d = private exponent (secret)
```

Produces a brand-new signature. Only possible with `d`.

**2. Verifying (Your API — public key)**

```text
recomputed_hash = SHA256(header + "." + payload)   ← computed fresh from the token
recovered_hash  = signature ^ e mod n              ← e = public exponent (shared freely)
```

**3. Valid if:** `recomputed_hash == recovered_hash`

The API never creates a signature. It reverses the one already in the token and checks whether that reversal
matches an independently computed hash.

### Full Runtime Flow (IMPORTANT)

```text
Client sends request
   ↓
Authorization Header (JWT)
   ↓
Authentication Middleware
   ↓
JWT Handler validates:
   - Signature ✅
   - Issuer ✅
   - Audience ✅
   - Expiry ✅
   ↓
User created in HttpContext
   ↓
Authorization Middleware checks roles/policies
   ↓
Controller executes
```

### Configuration (App Setup)

```csharp
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.RequireHttpsMetadata = true;
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidIssuer = builder.Configuration["Jwt:Issuer"],

            ValidateAudience = true,
            ValidAudience = builder.Configuration["Jwt:Audience"],

            ValidateLifetime = true,
            ValidateIssuerSigningKey = true,

            IssuerSigningKey = new SymmetricSecurityKey(
                Encoding.UTF8.GetBytes(builder.Configuration["Jwt:SigningKey"]!)),

            ClockSkew = TimeSpan.FromMinutes(1)
        };
    });
```

**1. Identity & Origin Checks**

`ValidateIssuer = true` & `ValidIssuer`: This checks the `iss` (Issuer) claim inside the JWT. It confirms the token was created by an authority you trust (e.g.,
your own Auth server). If the issuer in the token doesn't match your configuration, the token is rejected.

`ValidateAudience = true` & `ValidAudience`: This checks the `aud` (Audience) claim. It ensures the token was specifically intended for your API. This prevents a
token generated for "Service A" from being used to access your "Service B."

**2. Integrity & Cryptography**

`ValidateIssuerSigningKey = true` & `IssuerSigningKey`: This is the most critical security step.
The JWT signature is created by hashing the header and payload with a secret key.

By providing the `IssuerSigningKey` (the same secret key used to sign the token), the .NET middleware can re-calculate the signature. If the re-calculated
signature doesn't match the one on the token, it means someone tampered with the payload (e.g., tried to change their user ID or role).

**3. Expiration & Grace Period**

`ValidateLifetime = true`: This checks the `exp` (Expiration) claim. If the current time is past the `exp` time, the token is rejected.

`ClockSkew = TimeSpan.FromMinutes(1)`: Distributed systems often have slight differences in system time. `ClockSkew` provides a tiny "grace period" (here, 1
minute) to account for these synchronization issues. Without this, a perfectly valid token might be rejected just because the server's clock is 5 seconds
behind the client's clock.

**4. Security Enforcement**

`RequireHttpsMetadata = true`: This ensures that your API will only fetch metadata (like public keys) from the identity provider over an encrypted HTTPS connection. It prevents "Man-in-the-Middle" attacks where an attacker could intercept the configuration discovery process.

## Authorization

### 1. Role-Based Authorization (RBAC)

✅ **What it is**

Access is controlled based on roles assigned to a user.

**Examples:**

- Admin
- Manager
- User

📌 **When to use**

- Simple systems
- Fixed user categories
- Admin panels

💻 **Example**

Token contains role:

```json
{
  "role": "Admin"
}
```

**Controller:**

```csharp
[Authorize(Roles = "Admin")]
[HttpGet("admin-data")]
public IActionResult GetAdminData()
{
    return Ok("Only admin can see this");
}
```

🧠 **Behavior**

- If user has role → ✅ allowed
- If not → ❌ 403 Forbidden

⚠️ **Limitation**

Not flexible enough for complex logic like:

> "User can only access their own data"

### 2. Claim-Based Authorization

✅ **What it is**

Access is based on claims (key-value data about user).

**Examples:**

- EmployeeNumber
- Department
- Country
- SubscriptionType

📌 **When to use**

- Fine-grained control
- Business rules based on user data

💻 **Example**

Token contains claim:

```json
{
  "EmployeeNumber": "EMP001"
}
```

**Policy:**

```csharp
options.AddPolicy("EmployeeOnly",
    policy => policy.RequireClaim("EmployeeNumber"));
```

**Controller:**

```csharp
[Authorize(Policy = "EmployeeOnly")]
public IActionResult GetEmployeeData()
{
    return Ok("Employee data");
}
```

🧠 **Behavior**

- Claim exists → ✅ allowed
- Missing → ❌ 403

🔥 **Advantage**

Much more flexible than roles.

### 3. Policy-Based Authorization (Recommended)

✅ **What it is**

You define rules (policies) combining roles, claims, or custom logic.

📌 **When to use**

- Production APIs
- Complex access rules
- Scalable systems

💻 **Example**

```csharp
options.AddPolicy("AdminOrHR", policy =>
{
    policy.RequireRole("Admin");
    policy.RequireClaim("Department", "HR");
});
```

**Controller:**

```csharp
[Authorize(Policy = "AdminOrHR")]
```

🧠 **Behavior**

User must:

- be Admin AND
- belong to HR

🔥 **Why best?**

- Centralized
- Reusable
- Clean architecture

### 4. Resource-Based Authorization

✅ **What it is**

Authorization based on specific resource instance.

👉 **Example:**

User can only edit their own profile.

📌 **When to use**

- Ownership checks
- Dynamic decisions
- Per-record authorization

💻 **Example**

**Scenario**

User tries to edit profile:

```csharp
[HttpPut("{userId}")]
public IActionResult UpdateUser(int userId)
{
    var currentUserId = User.FindFirst("id")?.Value;

    if (currentUserId != userId.ToString())
    {
        return Forbid();
    }

    return Ok("Updated");
}
```

🧠 **Behavior**

- Own resource → ✅
- Others' resource → ❌

### Configuration (App Setup)

```csharp
builder.Services.AddAuthorization(options =>
{
    options.FallbackPolicy = new AuthorizationPolicyBuilder()
        .RequireAuthenticatedUser()
        .Build();

    options.AddPolicy("AdminOnly", policy => policy.RequireRole("Admin"));
    options.AddPolicy("EmployeeOnly", policy => policy.RequireClaim("EmployeeNumber"));
});
```

### The Fallback Policy

```csharp
options.FallbackPolicy = new AuthorizationPolicyBuilder()
    .RequireAuthenticatedUser()
    .Build();
```

**What it does:** This sets a "Global Default." Any controller or endpoint in your API that does not have an explicit `[Authorize]` attribute will now
automatically require a valid user.

**Why use it:** It is a security best practice known as "Secure by Default." It prevents you from accidentally leaving an endpoint public because you forgot to
add the `[Authorize]` attribute. If you do want a public endpoint, you must explicitly mark it with `[AllowAnonymous]`.

**Why should you use this?**

Because it centralizes security rules in one place instead of repeating logic in every controller.

**Benefits:**

- Secure by default
- Less duplication
- Easier maintenance
- Clear access rules
- Production-friendly design

Without this, you might forget to protect a new endpoint and accidentally expose data.

### Custom Policies

Policies are reusable sets of rules that you can apply to specific actions or controllers using `[Authorize(Policy = "PolicyName")]`.

**"AdminOnly":**

```csharp
options.AddPolicy("AdminOnly", policy => policy.RequireRole("Admin"));
```

**The Check:** The API looks at the user's claims for one where `Type == ClaimTypes.Role` and `Value == "Admin"`. If the user doesn't have the "Admin" role, the
API returns a 403 Forbidden (not 401 Unauthorized, because the user is logged in, but they lack the required permission).

**"EmployeeOnly":**

```csharp
options.AddPolicy("EmployeeOnly", policy => policy.RequireClaim("EmployeeNumber"));
```

**The Check:** This is a Claim-based check. It doesn't care about roles; it simply checks if the JWT contains a claim named `EmployeeNumber`. This is useful for
feature-based authorization (e.g., if a user has a specific ID attached to their identity, they can access this data).

### Effect on controllers

Let us see how this changes controller behavior.

**Example 1: Controller with no [Authorize]**

```csharp
[ApiController]
[Route("api/[controller]")]
public class ProductsController : ControllerBase
{
    [HttpGet]
    public IActionResult GetAll()
    {
        return Ok("All products");
    }
}
```

**With FallbackPolicy:**

This endpoint is still protected.
Even though you did not add `[Authorize]`, the fallback policy requires the user to be authenticated.

So:

- unauthenticated user → 401 Unauthorized
- authenticated user → allowed

**Example 2: Public endpoint with [AllowAnonymous]**

```csharp
[ApiController]
[Route("api/[controller]")]
public class AuthController : ControllerBase
{
    [AllowAnonymous]
    [HttpPost("login")]
    public IActionResult Login()
    {
        return Ok("Login page");
    }
}
```

**Effect**

This endpoint stays public even though `FallbackPolicy` requires authentication.

`[AllowAnonymous]` overrides the fallback policy.

**Example 3: Admin-only controller**

```csharp
[ApiController]
[Route("api/[controller]")]
[Authorize(Policy = "AdminOnly")]
public class AdminController : ControllerBase
{
    [HttpGet("dashboard")]
    public IActionResult Dashboard()
    {
        return Ok("Admin dashboard");
    }
}
```

**Effect**

Only users who are:

- authenticated, and
- have role Admin

can access this controller.

So:

- anonymous user → 401
- logged-in non-admin user → 403 Forbidden
- admin user → allowed

**Example 4: Employee-only action**

```csharp
[ApiController]
[Route("api/[controller]")]
public class HrController : ControllerBase
{
    [Authorize(Policy = "EmployeeOnly")]
    [HttpGet("profile")]
    public IActionResult Profile()
    {
        return Ok("Employee profile");
    }
}
```

**Effect**

The user must have an `EmployeeNumber` claim.

If the claim is missing:

- authenticated user without claim → 403 Forbidden
- authenticated user with claim → allowed

### Important difference: 401 vs 403

This is a key production concept.

- **401 Unauthorized** = user is not authenticated
- **403 Forbidden** = user is authenticated, but does not have permission

So with your policies:

- `FallbackPolicy` usually causes 401 for anonymous users
- `AdminOnly` or `EmployeeOnly` may cause 403 when the user is logged in but lacks role/claim

    {

        {

            ValidIssuer = builder.Configuration["Jwt:Issuer"],

            ValidateAudience = true,
            ValidAudience = builder.Configuration["Jwt:Audience"],

            ValidateLifetime = true,
            ValidateIssuerSigningKey = true,

# ClaimsIdentity and ClaimsPrincipal

To understand how .NET handles user information after a successful login, you have to look at `ClaimsIdentity` and `ClaimsPrincipal`. Think of these as the
"passport" and the "person holding the passport."

## 1. ClaimsIdentity (The Passport)

A `ClaimsIdentity` represents the identity of a specific user. It contains a collection of `Claims`. A claim is a single piece of information about the user,
such as their username, email, role, or employee ID.

- **Analogy:** If you have an ID card, the card itself is the `ClaimsIdentity`. The name, date of birth, and photo printed on it are the `Claims`.
- **Role:** It groups all the facts about a user into one object.
- **Authentication Type:** It also tracks how the user was authenticated (e.g., "Bearer" token, "Cookies", "Windows").

## 2. ClaimsPrincipal (The Person)

A `ClaimsPrincipal` is the "container" for one or more `ClaimsIdentity` objects.

- **Analogy:** A person might have a driver's license (one identity) and a work badge (another identity). The person carrying both is the `ClaimsPrincipal`.
- **Role:** In a standard .NET web application, you typically have one `ClaimsPrincipal` that holds one `ClaimsIdentity`.
- **Accessibility:** In your code, this is what you access via `User` inside your Controllers.

## How they work together in .NET

When the JwtBearer middleware validates your token, it performs the following sequence:

- **Read:** It parses the JWT and reads the payload.
- **Create Identity:** It creates a `ClaimsIdentity` object, taking the claims from the JWT (like `sub`, `role`, `email`) and adding them to the collection.
- **Create Principal:** It wraps that identity in a `ClaimsPrincipal`.
- **Assign:** It assigns this `ClaimsPrincipal` to `HttpContext.User`.

## Practical Usage in a Controller

Once the middleware has done its job, you can access these claims anywhere in your application:

```csharp
[HttpGet]
public IActionResult GetProfile()
{
    // 'User' is the ClaimsPrincipal
    // We can extract specific claims from the underlying ClaimsIdentity
    var userId = User.FindFirst(ClaimTypes.NameIdentifier)?.Value;
    var userRole = User.FindFirst(ClaimTypes.Role)?.Value;

    return Ok(new { UserId = userId, Role = userRole });
}
```

> **Note:** This assignment is performed by the authentication middleware (specifically, the authentication handler through the authentication service), not by your application code.

## How Claims Become HttpContext.User

```text
Claims
   │
   ▼
JwtSecurityToken
   │
   ▼
JWT String
   │
   ▼
Client stores token
   │
   ▼
Authorization: Bearer <JWT>
   │
   ▼
JWT Authentication Handler
   │
   ▼
Validates Signature
   │
   ▼
Extracts Claims
   │
   ▼
ClaimsIdentity
   │
   ▼
ClaimsPrincipal
   │
   ▼
HttpContext.User
```

## So the hierarchy is:

```text
ClaimsPrincipal (the "user")
 └── ClaimsIdentity[] (one per auth scheme)
       └── Claim[] (the actual data)
```

## Basic example — building one manually (Will help while building Auth server)

```csharp
var claims = new List<Claim>
{
    new Claim(ClaimTypes.NameIdentifier, "user-123"),
    new Claim(ClaimTypes.Name, "Aman Kumar"),
    new Claim(ClaimTypes.Role, "Admin"),
    new Claim("department", "Engineering") // custom claim
};

var identity = new ClaimsIdentity(claims, authenticationType: "Bearer");
var principal = new ClaimsPrincipal(identity);

// Reading it back
Console.WriteLine(principal.Identity.Name);           // "Aman Kumar"
Console.WriteLine(principal.IsInRole("Admin"));       // true
Console.WriteLine(principal.FindFirst("department")?.Value); // "Engineering"
```

### Multiple identities on one principal

This is the less-common but real use case for `ClaimsPrincipal` wrapping multiple `ClaimsIdentity` objects — say a request is authenticated by both a cookie
and an API key scheme:

```csharp
var cookieIdentity = new ClaimsIdentity(cookieClaims, "Cookies");
var apiKeyIdentity = new ClaimsIdentity(apiKeyClaims, "ApiKey");

var principal = new ClaimsPrincipal(new[] { cookieIdentity, apiKeyIdentity });

// FindFirst searches across ALL identities
var name = principal.FindFirst(ClaimTypes.Name);
```

> **Note:**
>
> `Principal.Identity.IsAuthenticated` is true only because we passed a non-null `authenticationType`. If you construct `new ClaimsIdentity(claims)` without
> an auth type, `IsAuthenticated` is false — this trips people up a lot.

### A gotcha worth knowing for your JWT work

By default, `JwtSecurityTokenHandler` maps standard JWT claim names (`sub`, `role`, etc.) to long Microsoft URIs (`ClaimTypes.NameIdentifier`, `ClaimTypes.Role`)
via `JwtSecurityTokenHandler.DefaultInboundClaimTypeMap`. If you want the raw `"sub"` and `"role"` names to survive as-is (common when building APIs consumed by
non-.NET clients), disable that mapping:

```csharp
services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.MapInboundClaims = false; // keep "sub" as "sub", not nameidentifier URI
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuerSigningKey = true,
            IssuerSigningKey = _rsaPublicKey,
            ValidateIssuer = true,
            ValidIssuer = _issuer,
            ValidateAudience = true,
            ValidAudience = _audience,
            ValidateLifetime = true,
        };
    });
```

## ClaimsIdentity : AuthenticationType

The `authenticationType` parameter in a `ClaimsIdentity` constructor tells the .NET security system exactly how the user was verified. While "Bearer" is the
standard for JWT-based API authentication, other types are used depending on your architecture.

**Common Authentication Types**

| Authentication Type | Use Case              | Description                                                               |
| ------------------- | --------------------- | ------------------------------------------------------------------------- |
| `"Bearer"`          | Web APIs              | Used for token-based authentication (JWTs).                               |
| `"Cookies"`         | Web Apps (MVC/Blazor) | The browser stores the identity in an encrypted, secure cookie.           |
| `"Windows"`         | Intranet/Enterprise   | Uses Windows Integrated Authentication (Active Directory).                |
| `"Basic"`           | Legacy/Simple APIs    | Sends username and password (Base64 encoded) in the Authorization header. |

### 1. The "Cookies" Authentication (Detailed Example)

In traditional web applications (like ASP.NET MVC or Razor Pages), we often use Cookies instead of JWTs. The browser handles sending the "token"
automatically with every request.

**Setup in Program.cs**

```csharp
builder.Services.AddAuthentication("Cookies")
    .AddCookie("Cookies", options =>
    {
        options.LoginPath = "/Account/Login";
        options.AccessDeniedPath = "/Account/AccessDenied";
    });
```

**Creating the Identity**

When the user logs in via a form, you manually create the `ClaimsPrincipal` and "sign in" the user:

```csharp
[HttpPost]
public async Task<IActionResult> Login(string username)
{
    var claims = new List<Claim> { new Claim(ClaimTypes.Name, username) };
    
    // Note the "Cookies" type here
    var claimsIdentity = new ClaimsIdentity(claims, "Cookies");
    var claimsPrincipal = new ClaimsPrincipal(claimsIdentity);

    // This creates the encrypted cookie in the browser
    await HttpContext.SignInAsync("Cookies", claimsPrincipal);

    return Redirect("/");
}
```

### 2. The "Windows" Authentication

This is common in corporate environments where the user is already logged into their company computer. The server trusts the Windows operating system to
identify the user.

- **Setup:** You do not typically configure this in code; it is enabled via IIS or Kestrel settings.
- **The Identity:** When a user visits your site, .NET automatically populates `User` with a `ClaimsIdentity` where `AuthenticationType` is set to `"Windows"`.

**Accessing Info:**

```csharp
// The name will be in the format: DOMAIN\Username
var windowsIdentity = User.Identity as WindowsIdentity;
```

**Important: How to use AuthenticationType**

You can inspect the `AuthenticationType` at any time to see if the user is who they claim to be based on your security rules:

```csharp
if (User.Identity.IsAuthenticated)
{
    // Check if they are using the expected method
    if (User.Identity.AuthenticationType == "Bearer") 
    {
        // Proceed with API logic
    }
    else if (User.Identity.AuthenticationType == "Cookies")
    {
        // Proceed with Web UI logic
    }
}
```

**Why use different types?**

- **Security:** If your API strictly requires a JWT, you can reject any `ClaimsIdentity` that arrives with a "Cookies" or "Basic" authentication type.
- **Flexibility:** A single .NET application can support multiple authentication types simultaneously (e.g., an API that accepts both JWTs and Cookies), allowing it to serve both mobile apps and web browsers.

> **Note:** above two methods are for knowledge only, currently focusing on JWT only.
>
> Also after that, check for other authentication methods: Cookie, APIKey.

## Yes, you can encrypt data using a public key, but a JSON Web Token (JWT) is signed, not encrypted

A private key is required to create a JWT signature because signing proves the token's origin, which requires a secret that only the trusted issuer owns.

**Encryption vs. Signing in Keys**

- **Encryption with Public Key:** Anyone can use a public key to lock (encrypt) a message, but only the private key holder can unlock (decrypt) it.
- **Signing with Private Key:** The issuer uses a private key to stamp (sign) a token. Anyone with the public key can verify that the stamp is real.

**Why Only a Private Key Creates a JWT**

- **Proof of Identity:** A signature proves who made the token. If a public key could sign a token, anyone could forge a valid token, destroying trust.
- **Secrecy of the Issuer:** Only the auth server keeps the private key safe.
- **Open Verification:** The public key is shared freely so any API or client can check if the token is real.
