# Auth Server

## Before any code, understand the shape of the system. There are always **3 parties**:

```text
┌──────────┐        ┌──────────────┐           ┌──────────────┐
│  Client  │  <---> │   Auth Server│  <--->    │  Resource API│
│ (SPA/App)│        │(Identity Svc)│           │(Your Backend)│
└──────────┘        └──────────────┘           └──────────────┘
```

**The core flow (Login → Access → Refresh):**

1. **Login:** Client sends `username + password` → Auth Server.
2. Auth Server verifies credentials against the DB (hashed password check).
3. Auth Server **issues two tokens**:
   - `access_token` (JWT, short-lived, e.g. 15 min) — proves identity to APIs
   - `refresh_token` (opaque or JWT, long-lived, e.g. 7–30 days) — used only to get a new access token
4. Client stores tokens (memory / httpOnly cookie — never localStorage for the refresh token in production).
5. Client calls Resource API with `Authorization: Bearer <access_token>`.
6. API middleware **validates the JWT signature + claims** (no DB call needed — this is the whole point of JWTs).
7. When access token expires, client silently calls `/auth/refresh` with the refresh token to get a new pair.
8. On logout or breach detection, refresh token is **revoked**.

That single loop — **login → issue → validate → refresh → revoke** — is 90% of every auth server on earth. Everything else (RS256, JWKS, rotation, reuse
detection) is hardening around this loop.

## Introduction: Auth Server

An Authentication Server (Auth Server) is a specialized type of API whose primary responsibility is authenticating users/clients and issuing security
tokens.

Instead of exposing business endpoints like `/orders` or `/products`, it exposes authentication endpoints such as `/login`, `/token`, or `/authorize`.

```text
+---------------------+
|   Client (SPA/App)  |
+----------+----------+
            |
    Login Request
            |
            ▼
+------------------------+
| Authentication Server  |
|   (Identity Provider)  |
+-----------+------------+
            |
    Issues JWT/ID Token
            |
            ▼
        Access Token
            |
            ▼
+----------------------+
|   Resource API       |
| (Business API)       |
+----------------------+
```

Notice:

- **Auth Server** → verifies identity and issues tokens.
- **Resource API** → validates tokens and serves business data.

### Responsibilities of an Auth Server

An authentication server typically:

- Authenticates users
- Validates passwords
- Supports MFA
- Issues JWTs or access tokens
- Issues refresh tokens
- Revokes tokens
- Manages clients/applications
- Manages user accounts
- Supports OAuth 2.0 / OpenID Connect

### Example Endpoints

An auth server may expose:

| Endpoint                      | Purpose                                                                                             |
| ----------------------------- | --------------------------------------------------------------------------------------------------- |
| `POST /auth/register`         | Create a new user account (typically gated by invite or whitelist in production).                   |
| `POST /auth/login`            | Verify user credentials and issue an access token + refresh token pair.                             |
| `POST /auth/refresh`          | Validate and rotate the refresh token, then issue a new access token + refresh token pair.          |
| `POST /auth/revoke`           | Revoke the current refresh token (logout) or invalidate the entire refresh token family.            |
| `GET /.well-known/jwks.json`  | Expose public signing keys (JWKS) for APIs to verify RS256-signed JWTs.                             |
| `GET /auth/me`                | Return information about the currently authenticated user (claims/profile) for UI or debugging.     |

# JWT Secured Web API

A JWT-secured Web API usually has three parts: an authentication server that signs tokens, the API that validates tokens, and the client app that sends the
token on every request.

## How the developer usually builds it

There are two common production models.

- **User-based access:**
  The client logs in as a user, then gets an access token. Microsoft's auth-code flow is the standard way for a user-facing client to obtain access to APIs,
  and it can also use refresh tokens to get new access tokens later. Access tokens are for API authorization; ID tokens are for signing the user in and
  should not be used to call APIs.

- **Service-to-service access:**
  One backend service calls another backend service using the client credentials flow. That flow uses the application's own identity instead of a user's
  identity, which is common for daemons and background jobs.

## How users are created

If the developer is building their own login system, ASP.NET Core Identity is often used. Identity manages users, passwords, profile data, roles, claims,
tokens, and email confirmation. Users can be created in the app, or through an external identity provider such as Microsoft Entra ID or Google.

In production, many teams do not let the API itself "invent" users. Instead, they use an identity provider, then map users into roles, groups, or claims.
Roles are claims, but not every claim is a role; in ASP.NET Core, roles and policies are both common ways to control access.

## How the token is created

A JWT is created by the issuer after the user or client is authenticated. The issuer puts claims into the token, signs it, and returns it to the client.
The API later checks the token's signature, issuer, audience, and expiration before trusting it. Microsoft explicitly recommends full validation of those
parts.

A simple custom flow looks like this:

```text
Client -> Auth Server: username/password or sign-in flow
Auth Server -> validates identity
Auth Server -> creates signed JWT with claims
Auth Server -> returns access token to client
Client -> calls API with Authorization: Bearer <token>
API -> validates token and authorizes request
```

## A practical production architecture

A common setup looks like this:

- **Auth server:**
  Creates users, stores passwords safely, signs JWTs, exposes login/token endpoints.

- **API server:**
  Has `AddJwtBearer`, validates tokens, checks roles/policies, returns protected data.

- **Client app:**
  Logs in through OAuth/OIDC or gets a machine token through client credentials, stores the access token securely, and sends it in the bearer header.

- **Secret storage:**
  Signing certificate or key is kept in Key Vault or another secure secret manager, not in source code.

# Identity Provider

An Identity Provider (IdP) and an Authorization Server are often discussed interchangeably because modern software (like Auth0, Okta, or Keycloak) usually
performs both functions. However, they serve distinct conceptual purposes in the identity and access management (IAM) ecosystem.

## 1. What is an Identity Provider (IdP)?

An Identity Provider is a service that stores and verifies user identities. Its primary job is to answer the question: "Who are you?" (Authentication).

- **Primary Function:** It acts as the "source of truth" for user credentials.
- **What it does:** It manages user accounts, passwords, MFA settings, and profile information. It often connects to databases, Active Directory, or LDAP to
  verify if the user exists and if their password is correct.
- **Examples:** Microsoft Entra ID (formerly Azure AD), Google, GitHub, or a local Users table in your SQL database.

## 2. What is an Authorization Server?

An Authorization Server is a service that manages access rights. Its primary job is to answer the question: "What are you allowed to do?" (Authorization).

- **Primary Function:** It issues "permission slips" (tokens) that grant applications access to protected resources.
- **What it does:** It handles the OAuth 2.0 or OIDC protocols, validates the user's identity (often by talking to the IdP), defines scopes, grants permissions,
  and issues the JWTs (access tokens) that the client uses to call APIs.
- **Examples:** IdentityServer4, Duende IdentityServer, or the authorization component of Auth0.

## How they work together (The Flow)

In a real-world scenario, they work as a team:

- **Login:** You enter your username/password in your app. The request goes to the Authorization Server.
- **Verify Identity:** The Authorization Server contacts the Identity Provider and asks, "Is this person who they say they are?"
- **Confirm:** The IdP checks its database and tells the Authorization Server, "Yes, that is User #123."
- **Issue Token:** The Authorization Server decides what that user is allowed to do (based on your rules) and generates a signed JWT containing those
  permissions.
- **Access:** You present that JWT to the API. The API trusts the token because it was signed by the Authorization Server.

# How to create a JWT Token : Add claim and all

To create a JWT in .NET, you use the `System.IdentityModel.Tokens.Jwt` library. The process involves defining the Claims (data), setting the Expiration, and
Signing the token with a secret key.

## 1. The Dependencies

Ensure you have the following NuGet package installed:

```text
Microsoft.AspNetCore.Authentication.JwtBearer
```

## 2. Implementation: Creating the Token

This is a service method you would typically call in your Login endpoint after verifying a user's password.

```csharp
using System.IdentityModel.Tokens.Jwt;
using System.Security.Claims;
using System.Text;
using Microsoft.IdentityModel.Tokens;

public string GenerateJwtToken(string userId, string email, string role)
{
    // 1. Define the Claims (The data inside the token)
    var claims = new List<Claim>
    {
        new Claim(JwtRegisteredClaimNames.Sub, userId),
        new Claim(JwtRegisteredClaimNames.Email, email),
        new Claim(ClaimTypes.Role, role),
        new Claim(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString()) // Unique ID for this token
    };

    // 2. Define the Signing Key
    // IMPORTANT: The key should be at least 16 characters long for HMACSHA256
    var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes("YourSuperSecretKeyMustBeLongEnough123!"));
    var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

    // 3. Create the Token
    var token = new JwtSecurityToken(
        issuer: "YourAppIssuer",      // Who created the token
        audience: "YourAppAudience",  // Who is it for
        claims: claims,
        expires: DateTime.Now.AddHours(2), // How long it lasts
        signingCredentials: creds
    );

    // 4. Return the string representation
    return new JwtSecurityTokenHandler().WriteToken(token);
}
```

### Key Components Explained

**The Claims**

Claims are key-value pairs stored in the JWT payload.

- **JwtRegisteredClaimNames:** These are standard names (like `sub` for subject, `iat` for issued at). Always prefer these over custom strings when possible to
  maintain interoperability.
- **Custom Claims:** You can add anything you need, e.g., `new Claim("Department", "Engineering")`.

**The Expiration (`expires`)**

Always set an expiration time. Once a JWT is issued, it cannot be "revoked" by the server easily (it is stateless). A short expiration (e.g., 15 minutes to
2 hours) is standard practice to minimize the damage if a token is stolen.

**How to use it in your Controller**

Once you generate the string, you return it in your HTTP response:

```csharp
[HttpPost("login")]
public IActionResult Login(LoginDto login)
{
    // Validate credentials against DB...
    
    var token = GenerateJwtToken("123", "user@example.com", "Admin");
    return Ok(new { access_token = token });
}
```

## Signing key and its type

In .NET authentication, the Signing Key is the cryptographic piece of data used by the Authorization Server to digitally "sign" the JWT. This signature is what allows the API to verify that the token was created by a trusted source and has not been tampered with.

### Types of Signing Keys

There are two primary ways to sign tokens, depending on your security requirements:

#### Symmetric Keys (HS256)

A single "shared secret" is used by both the issuer (Auth Server) and the validator (API).

**How it works:** Both sides know the exact same password string.

**Pros:** Simple to implement; very fast.

**Cons:** Security risk. If the API is compromised, the attacker gets the key and can forge their own tokens. You cannot easily rotate this key without
updating all your services simultaneously.

**Use Case:** Small, internal microservices or simple applications where you control both the Auth Server and the API.

> **Note:** It is just a random string value.

#### Asymmetric Keys (RS256 / ES256)

A pair of keys is used: a Private Key (for signing) and a Public Key (for verification).

**How it works:**

```text
Auth Server: Uses the Private Key to sign the JWT.
API: Uses the Public Key to verify the signature.
```

**Pros:** Highly secure. You only share the Public Key with your APIs. If an API is hacked, the attacker cannot forge tokens because they don't have the
Private Key. It also supports Key Rotation (using an endpoint like `/.well-known/jwks.json` to publish public keys).

**Use Case:** Production environments, public-facing APIs, and distributed systems.

### How to share signing key between auth server and API

**Short answer:**

- ❗ In production, you don't "share" a secret key
- ✅ You use asymmetric keys (public/private)

**Two ways to handle signing keys**

#### ❌ Option 1: Shared Secret (Symmetric key)

Auth Server ↔ API use same secret key.

**Example:**

```csharp
IssuerSigningKey = new SymmetricSecurityKey(Encoding.UTF8.GetBytes("my-secret"))
```

🚫 **Problems:**

- Secret must be copied to all APIs
- If leaked → attacker can create tokens
- Hard to rotate keys

👉 Only okay for learning / small apps

#### ✅ Option 2: Public / Private Key (Asymmetric) ⭐

- Auth Server → PRIVATE key (signs token)
- API → PUBLIC key (validates token)

✔ **Benefits:**

- API never sees private key
- Much more secure
- Scales to multiple APIs

🔐 **How it actually works**

- Auth Server signs JWT using PRIVATE key
- API receives JWT
- API verifies signature using PUBLIC key
- If valid → trusted

### Generating keys : Symmetric Keys and Asymmetric Keys

#### Generating Symmetric Keys (HS256)

Symmetric keys are essentially "random high-entropy strings." The security of an HS256 key depends entirely on its length and randomness.

**Step-by-Step Generation:**

- **Requirement:** The key must be at least 32 bytes (256 bits) for HMAC-SHA256 to be secure.
- **Generate:** You can generate a secure random key using the `RandomNumberGenerator` class in .NET.

```csharp
using System.Security.Cryptography;

// Generate a 32-byte (256-bit) cryptographically strong random key
byte[] keyBytes = new byte[32];
using (var rng = RandomNumberGenerator.Create())
{
    rng.GetBytes(keyBytes);
}

// Convert to a Base64 string for storage in your appsettings.json or environment variables
string base64Key = Convert.ToBase64String(keyBytes);
Console.WriteLine($"Your Symmetric Key: {base64Key}");
```

#### Generating Asymmetric Keys (RS256)

Asymmetric keys involve a Private Key (for signing) and a Public Key (for verification). You usually store these in a standard format like PEM or PFX.

**Step-by-Step Generation:**

You can use OpenSSL (built into most OSs) or .NET code to generate these.

**Option A: Using OpenSSL (Recommended for Production)**

Run these commands in your terminal to generate an RSA 2048-bit key pair:

**Generate Private Key:**

```bash
openssl genrsa -out private.pem 2048
```

**Extract Public Key:**

```bash
openssl rsa -in private.pem -pubout -out public.pem
```

**Option B: Using .NET (Programmatic)**

If you need to generate these keys at runtime or for testing:

```csharp
using System.Security.Cryptography;

using (RSA rsa = RSA.Create(2048))
{
    // Export the private key (usually as XML or PKCS#8)
    string privateKey = rsa.ExportRSAPrivateKeyPem();
    
    // Export the public key
    string publicKey = rsa.ExportSubjectPublicKeyInfoPem();

    // Save these to files or a Key Vault
    File.WriteAllText("private.pem", privateKey);
    File.WriteAllText("public.pem", publicKey);
}
```

#### How to Use These Keys in .NET

**For Symmetric (HS256):**

In `Program.cs`, you convert the base64 string back into bytes:

```csharp
var keyBytes = Convert.FromBase64String(builder.Configuration["Jwt:Key"]);
var key = new SymmetricSecurityKey(keyBytes);
```

**For Asymmetric (RS256):**

You load the `private.pem` file into an RSA object to sign tokens, and share the `public.pem` with your APIs:

```csharp
// To Sign (Auth Server side)
var rsa = RSA.Create();
rsa.ImportFromPem(File.ReadAllText("private.pem"));
var key = new RsaSecurityKey(rsa);
var credentials = new SigningCredentials(key, SecurityAlgorithms.RsaSha256);
```

#### Best Practices for Key Management

**Never commit raw keys to Source Control:** If you generate a key for development, keep it in `appsettings.Development.json` and add that file to your
`.gitignore`.

**Use Key Vaults:** For production, use Azure Key Vault, AWS KMS, or HashiCorp Vault. These services generate the keys for you, and your app accesses them via
a managed identity, meaning the key never actually sits in your codebase.

**Rotation:** When using Asymmetric keys, you can keep a "current" key and a "previous" key active simultaneously for a short time to ensure zero downtime
during key rotation.

# How do we generate RSA key in production and how to use in auth server and web API?

In production:

- ✔ Keys are stored securely (Key Vault / certificate store)
- ✔ Auth Server uses PRIVATE key
- ✔ API uses PUBLIC key (via metadata/JWKS)

## Option A — Using OpenSSL (common)

**Generate private key**

```bash
openssl genrsa -out private.key 2048
```

**Generate public key**

```bash
openssl rsa -in private.key -pubout -out public.key
```

👉 Good for understanding, NOT ideal for production storage

## Option B — Generate Certificate (.pfx) ⭐ (Recommended)

```bash
openssl req -x509 -newkey rsa:2048 \
  -keyout key.pem \
  -out cert.pem \
  -days 365

openssl pkcs12 -export \
  -out auth-cert.pfx \
  -inkey key.pem \
  -in cert.pem
```

👉 `.pfx` contains:

- Private key ✅
- Public key ✅

- `-keyout key.pem` → saves the private key into `key.pem`.
- `-out cert.pem` → saves the public certificate into `cert.pem`.
- `-days 365` → certificate validity is 365 days.

`pkcs12 -export` → creates a PKCS#12 file (commonly `.pfx`).

- `-out auth-cert.pfx` → output file is `auth-cert.pfx`.
- `-inkey key.pem` → include the private key.
- `-in cert.pem` → include the public certificate.

👉 **Result:**

- `auth-cert.pfx` → a single file containing both the certificate and private key, usually protected with a password.
- This is what you install on your client app for signing or mutual TLS.
- The API/server only needs the public certificate (`cert.pem`) to validate your signatures.

### Code approach

If you want to generate a `.pfx` certificate programmatically, you need to:

- Create a self-signed X.509 certificate using your RSA key.
- Export it as a `.pfx` with a password.

**Example in C#:**

```csharp
using System.Security.Cryptography;
using System.Security.Cryptography.X509Certificates;

void GenerateCertificate()
{
    using (var rsa = RSA.Create(2048))
    {
        var certRequest = new CertificateRequest(
            "CN=MyApp", 
            rsa, 
            HashAlgorithmName.SHA256, 
            RSASignaturePadding.Pkcs1);

        // Self-signed certificate valid for 1 year
        var cert = certRequest.CreateSelfSigned(
            DateTimeOffset.Now, 
            DateTimeOffset.Now.AddYears(1));

        // Export to PFX with password
        var pfxBytes = cert.Export(X509ContentType.Pfx, "mypassword");
        File.WriteAllBytes("mycert.pfx", pfxBytes);

        // Export public cert (no private key)
        var cerBytes = cert.Export(X509ContentType.Cert);
        File.WriteAllBytes("mycert.cer", cerBytes);
    }
}
```

🔑 **Key points**

- `.pfx` = certificate + private key (protected with password).
- `.cer` = public certificate only (safe to share with API).
- Use `CertificateRequest` to generate a proper certificate.
- Don't just dump raw RSA bytes into a `.pfx` file — it won't be valid.

👉 So: generate a proper `.pfx` with `X509Certificate2` and export the public `.cer` to share with the API. Keep the `.pfx` private on your client side for signing.

   - Exposes PUBLIC key via JWKS

   - Fetches PUBLIC key
   - Validates token

5. Client:
   - Uses token
