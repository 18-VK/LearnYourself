# Index

An Index in SQL Server is a data structure (B-Tree) that improves the speed of data retrieval operations on a table.

**Indexing:**

Indexing is a performance optimization technique in SQL Server that improves the speed of data retrieval. There are two main types of indexes:
Clustered and Non-Clustered.

## Clustered Index

A Clustered Index defines the physical order of rows in a table. When you create a clustered index on a column, SQL Server rearranges the actual
data rows to match the index order. This is why a table can have only one clustered index.

A clustered index is created only when both the following conditions are satisfied:

- The data can be stored in a sequential or sorted manner.
- The column used as the key must contain unique values.

**Example of Clustered Index:**

Consider a table called `Student` where the `Roll_No` column is the primary key. This automatically becomes a clustered index. Here, SQL Server
automatically creates a clustered index on the `Roll_No` column. The rows are physically stored in ascending order based on the `Roll_No`.

- A table can have only one clustered index.
- A clustered index can be created on multiple columns → called a composite index.
- In this case, `Roll_No` is the primary key, so it automatically becomes the clustered index.
- Query results are displayed in ascending order of `Roll_No`.

## Non-Clustered Index

A non-clustered index does not change the physical data order. It creates a separate structure with indexed columns and pointers to the actual
rows. Multiple non-clustered indexes can be created, improving performance for searches and joins.

- Stores index data separately from the table.
- Multiple non-clustered indexes can exist on a table.
- Contains a copy of the indexed column(s) and a pointer to the actual data row.

Every non-clustered index stores:

```text
Indexed column + Clustered Key (as row locator)
```

**Example of Non-Clustered Index:**

In the `Student` table, a non-clustered index can be created on the `Name` column. Since `Roll_No` is the primary key, it already has a clustered index.
A non-clustered index creates a separate structure that stores the `Name` values and pointers to the actual rows.

**Query:**

```sql
CREATE NONCLUSTERED INDEX NIX_FTE_Name
ON Student (Name ASC);
```

## Covering Index

> **Note:** May go through this after having idea of execution plan, index seek and index scan.

A covering index contains all columns required by a query, so the database does not need to access the main table.

**Example query:**

```sql
SELECT Name, Salary
FROM Employee
WHERE Name = 'Aman';
```

**Better index:**

```sql
CREATE INDEX IX_Employee_Name
ON Employee(Name)
INCLUDE (Salary);
```

**Usage: Run the Query Normally**

```sql
SELECT Name, Salary
FROM Employee
WHERE Name = 'Aman';
```

That's it.

You don't specify the index manually (unless forcing, which is rarely recommended).

**Verify It Is Being Used (SQL Server)**

Enable execution plan:

```sql
SET STATISTICS IO ON;
```

Or check graphical execution plan.

If it shows:

- ✔ Index Seek on `IX_Employee_Name`
- ❌ No Key Lookup

Then it's working as covering index.

### Composite Non-Clustered Index?

A Composite Non-Clustered Index is:

A non-clustered index created on multiple columns (more than one column).

🧠 **Syntax**

```sql
CREATE NONCLUSTERED INDEX IX_Orders_Cust_Date
ON Orders(CustomerId, OrderDate);
```

Here:

- `CustomerId` → 1st key column
- `OrderDate` → 2nd key column

# Performance comparison (read)

## Equality Search on Primary Key

```sql
SELECT * FROM Orders WHERE OrderId = 100;
```

**1. Clustered Index**

- Direct B-Tree navigation
- Leaf level contains actual data
- Very fast (Index Seek)

**2. Non-Clustered Index**

If searching on non-clustered key:

- Finds row in index
- Then performs Key Lookup (if not covering)
- Slightly slower than clustered

👉 Reading - Winner (PK search): **Clustered**

## Search on Non-Key Column

```sql
SELECT * FROM Orders WHERE CustomerId = 10;
```

**1. Clustered Index**

- Full table scan (if no NCI)
- Slow

**2. Non-Clustered Index**

- Index Seek
- Much faster

👉 Winner: **Non-Clustered**

# WRITE Performance Comparison

Now the important part 🔥

Writes = INSERT, UPDATE, DELETE

Indexes increase write cost.

## INSERT Performance

**1. Clustered Index**

- Data inserted in sorted order
- If key is sequential (`INT IDENTITY`):
- Fast
- Minimal page splits

If key is random (GUID):

- Page splits
- Fragmentation
- Slower

**2. Non-Clustered Index**

Every INSERT:

- Must update clustered index
- AND update every non-clustered index

If table has:

```text
1 clustered index
5 non-clustered indexes
```

Then 6 structures must be updated.

👉 More NC indexes = slower insert

## UPDATE Performance

**1. Updating Clustered Key**

- Very expensive
- Affects:
  - Data row
  - All non-clustered indexes (because they store clustered key as pointer)

Avoid updating clustered key.

**2. Updating Non-Indexed Column**

- Cheap
- No index update

## DELETE Performance

Similar to insert:

Must remove from:

- Clustered index
- All non-clustered indexes

More indexes = slower delete.

### Why updating a clustered key is expensive

**Example:**

```sql
UPDATE Orders
SET OrderId = 5000
WHERE OrderId = 100;
```

Internally SQL Server does NOT simply "edit the value".

Instead it performs:

- 🔥 **Step 1:** DELETE the old row
- 🔥 **Step 2:** INSERT a new row in correct sorted location

Because B-Tree must remain ordered.

# Keys in SQL

## Primary key

- **What:** Uniquely identifies each row. Not nullable.
- **Storage:** In SQL Server a primary key usually creates a clustered index (unless you specify otherwise).
- **When to use:** Every table that represents an entity (Customer, Order, Product).
- **Tip:** Use a small numeric surrogate (`INT IDENTITY`) for high-write OLTP tables; use GUID (`UNIQUEIDENTIFIER`) only when
  you need global uniqueness or offline generation.

**Example:**

```sql
CREATE TABLE Customers (
  CustomerId INT IDENTITY(1,1) PRIMARY KEY,
  Name NVARCHAR(100) NOT NULL
);
```

## Candidate key / Alternate key

- **What:** Candidate keys are columns that could be primary keys. An alternate key is a candidate that is not chosen as PK.
- **When to use:** Enforce business uniqueness (e.g., Email, National ID).
- **Tip:** Implement as a `UNIQUE` constraint/unique index.

**Candidate key** — a column or minimal set of columns that uniquely identify a row (no superfluous columns). A table can have multiple candidate keys.

**Alternate key** — any candidate key that was not chosen as the table's primary key. (Alternate = "the other candidate keys".)

**Example:**

```text
Table: Employee
Columns: EmployeeID (internal id), SSN, Email, FullName, HireDate
```

Candidate keys:

- `{EmployeeID}` — unique internal id (common choice for primary key)
- `{SSN}` — Social Security Number (business natural key)
- `{Email}` — company email (if guaranteed unique)

If you choose `EmployeeID` as the primary key, then `SSN` and `Email` are alternate keys.

**How to implement in SQL:**

```sql
CREATE TABLE Employee (
  EmployeeID   INT PRIMARY KEY,      -- chosen primary key (surrogate)
  SSN          VARCHAR(11) NOT NULL,
  Email        VARCHAR(255) NOT NULL,
  FullName     VARCHAR(200),
  CONSTRAINT UQ_Employee_SSN UNIQUE (SSN),    -- alternate key
  CONSTRAINT UQ_Employee_Email UNIQUE (Email) -- alternate key
);
```

**If table is already there:**

```sql
ALTER TABLE Customers
ADD CONSTRAINT UQ_Customers_Email UNIQUE (Email);
```

## Composite (Concatenated) key

A Composite Key (also called a Concatenated Key) is a primary key made up of two or more columns that together uniquely identify a row.

- **When to use:** Linking tables, many-to-many join tables, natural composite identifiers (e.g., Year+Seq).
- **Tip:** Consider performance — composite keys affect index size and foreign-key references.

**Example:**

```sql
CREATE TABLE OrderItems (
  OrderId INT,
  ProductId INT,
  Quantity INT,
  PRIMARY KEY (OrderId, ProductId)   -- composite PK
);
```

## Surrogate vs Natural key

- **Surrogate:** System-generated (`INT IDENTITY`, GUID).
- **Natural:** Real-world attribute(s) (email, ISBN).
- **Tip:** Surrogates simplify joins and indexing; keep natural keys as unique constraints if they're required by business rules.

## Foreign Key

A Foreign Key (FK) is a column (or set of columns) in one table that refers to the Primary Key (or UNIQUE key) of another table.

- It enforces referential integrity
- It prevents invalid relationships
- It maintains data consistency between tables

**Example (One-to-Many Relationship)**

🎯 **Scenario:** One Department → Many Employees

**Parent Table: Department**

```sql
CREATE TABLE Department (
    DepartmentID INT PRIMARY KEY,
    DepartmentName VARCHAR(100) NOT NULL
);
```

**Child Table: Employee**

```sql
CREATE TABLE Employee (
    EmployeeID INT PRIMARY KEY,
    EmployeeName VARCHAR(100),
    DepartmentID INT,
    CONSTRAINT FK_Employee_Department
        FOREIGN KEY (DepartmentID)
        REFERENCES Department(DepartmentID)
);
```

**What This Means**

- `DepartmentID` in `Employee` must exist in `Department`
- You cannot insert an employee with a non-existing department
- You cannot delete a department if employees are using it (by default)

### Foreign Key with CASCADE Options

By default:

❌ You cannot delete parent if child exists.

But you can control behavior:

**ON DELETE CASCADE**

```sql
FOREIGN KEY (DepartmentID)
REFERENCES Department(DepartmentID)
ON DELETE CASCADE
```

👉 Deleting department automatically deletes its employees.

**ON DELETE SET NULL**

```sql
ON DELETE SET NULL
```

👉 When department is deleted, `Employee.DepartmentID` becomes NULL.

**ON UPDATE CASCADE**

```sql
ON UPDATE CASCADE
```

👉 If primary key changes (rare case), child table updates automatically.

# Constraints (data integrity rules)

## NOT NULL

- **What:** Disallows NULL values.
- **When to use:** Required fields.
- **Tip:** Favor `NOT NULL` + sensible `DEFAULT` for simpler logic.

**Example**

```sql
CREATE TABLE Products (
  ProductId INT PRIMARY KEY,
  Name NVARCHAR(200) NOT NULL,
  Price DECIMAL(10,2) NOT NULL DEFAULT(0)
);
```

## DEFAULT

- **What:** Supplies default value on insert when column is not provided.
- **When to use:** Timestamps, status flags, counters.
- **Tip:** Defaults are applied only when the column is omitted or `DEFAULT` keyword used; explicit NULL overrides.

**Example**

```sql
CREATE TABLE Tickets (
  Id INT PRIMARY KEY IDENTITY,
  CreatedAt DATETIME2 DEFAULT SYSUTCDATETIME(),
  Status NVARCHAR(20) DEFAULT 'Open'
);
```

## UNIQUE

- **What:** Ensures column(s) contain unique values (allows one NULL in SQL Server).
- **When to use:** Candidate keys (email, username), external IDs.
- **Tip:** `UNIQUE` creates a nonclustered index — helps lookups.

**Example:**

```sql
ALTER TABLE Customers ADD CONSTRAINT UQ_Customers_UniqueCode UNIQUE (UniqueCode);
```

## CHECK

**What:** A `CHECK` constraint is used to enforce a condition (rule) on column values in a table.
It ensures that inserted or updated data satisfies a specified logical expression.
If the condition evaluates to FALSE, the operation fails.
If it evaluates to TRUE, it succeeds.

**Basic Syntax:**

**Column Level**

```sql
CREATE TABLE Employee (
    EmployeeID INT PRIMARY KEY,
    Age INT CHECK (Age >= 18)
);
```

**Table Level**

```sql
CREATE TABLE Employee (
    EmployeeID INT PRIMARY KEY,
    Age INT,
    Salary DECIMAL(10,2),
    CONSTRAINT CHK_Employee_Age CHECK (Age >= 18),
    CONSTRAINT CHK_Employee_Salary CHECK (Salary > 0)
);
```

**Example 1: Age Validation**

```sql
INSERT INTO Employee VALUES (1, 25);  -- ✅ Allowed
INSERT INTO Employee VALUES (2, 15);  -- ❌ Error (Age must be >= 18)
```

**Example 2: Gender Validation**

```sql
CREATE TABLE Student (
    StudentID INT PRIMARY KEY,
    Gender CHAR(1),
    CONSTRAINT CHK_Student_Gender
        CHECK (Gender IN ('M', 'F'))
);
```

✔ Restricts values to only allowed options.

# Use-case tips & production best practices

- **Enforce business rules at DB level for critical invariants:**
  Use `CHECK`, `UNIQUE`, `FK` for data integrity that must never be bypassed.
- **Keep constraints simple and fast:**
  Complex validation (heavy string parsing, external calls) belongs to app layer.
- **Indexing implication:**
  `UNIQUE` and `PRIMARY KEY` create indexes. Design to avoid duplicate indexes on same columns.
- **FK and performance:**
  Foreign keys guarantee integrity but may slow DELETE/UPDATE operations; ensure parent lookup/index exists.
- **Cascades carefully:**
  `ON DELETE CASCADE` is powerful but potentially dangerous; use when business expects automatic cleanup.
- **Use surrogate keys for joins, natural keys for business uniqueness:**
  Surrogate PK (`INT`) + `UNIQUE` natural key (email).
- **Column nullability:**
  Prefer `NOT NULL` where possible — NULLs complicate logic and indexes.
- **Schema evolution:**
  Add constraints during maintenance windows for large tables — adding a constraint can scan the table.
- **Transaction & error handling:**
  Be prepared for constraint violations — handle exceptions gracefully in application code.
- **Testing:**
  Test constraint behavior with edge cases (NULLs, duplicates, concurrent inserts).

# Why DELETE / UPDATE Can Become Slower with Foreign keys

When you:

- DELETE a parent row
- UPDATE a parent primary key
- INSERT/UPDATE a child row

The database must check the related table.

That means:

- It searches the child table
- It verifies referential rules
- It may lock rows
- It may cascade changes

If the child table is large and not indexed properly, this becomes expensive.

# Best Practice (Very Important)

Always index foreign key columns.

```sql
CREATE INDEX IX_Employee_DepartmentID
ON Employee(DepartmentID);
```

**Why?**

- Faster parent DELETE checks
- Faster JOINs
- Faster cascades
- Reduced locking

# Quick decision chart (which to use)

- Need unique ID for each row → `PRIMARY KEY`
- Need uniqueness for business column → `UNIQUE`
- Need parent-child referential safety → `FOREIGN KEY`
- Need non-null guarantee → `NOT NULL`
- Need default value for missing inserts → `DEFAULT`
- Need domain validation (e.g., >0, ENUM-like) → `CHECK`
