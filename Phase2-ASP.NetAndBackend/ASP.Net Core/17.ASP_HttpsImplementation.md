# HTTPS Implementation

Here's the complete setup to lock your API down to HTTPS-only with proper authentication and authorization enforced.

# Force HTTPS — reject/redirect plain HTTP

```csharp
// Program.cs
var builder = WebApplication.CreateBuilder(args);

// ... your existing AddIdentityCore, AddJwtBearer, etc. registrations ...

builder.Services.AddHttpsRedirection(options =>
{
    options.RedirectStatusCode = StatusCodes.Status308PermanentRedirect;
    options.HttpsPort = 443;
});

// HSTS - tells browsers to NEVER even try HTTP again for a while
builder.Services.AddHsts(options =>
{
    options.MaxAge = TimeSpan.FromDays(365);
    options.IncludeSubDomains = true;
    options.Preload = true;
});

var app = builder.Build();

if (!app.Environment.IsDevelopment())
{
    app.UseHsts();   // sends Strict-Transport-Security header — only in prod, HSTS + local dev certs don't mix well
}

app.UseHttpsRedirection();   // redirects any http:// request to https://
```

## UseHttpsRedirection — server-side redirect, per request

This runs on every incoming request. If it arrives over plain HTTP, the middleware sends back a redirect response pointing to the HTTPS version of the
same URL.

```csharp
builder.Services.AddHttpsRedirection(options =>
{
    options.RedirectStatusCode = StatusCodes.Status308PermanentRedirect;
    options.HttpsPort = 443;
});

var app = builder.Build();
app.UseHttpsRedirection();
```

**What actually happens on the wire:**

- Request arrives over HTTP

```http
GET http://yourapi.com/api/tasks HTTP/1.1
Host: yourapi.com
```

- Server responds — doesn't process the request, just redirects

```http
HTTP/1.1 308 Permanent Redirect
Location: https://yourapi.com/api/tasks
```

The client then has to make a second request, this time over HTTPS, to actually get data. This means the first request already happened over an insecure
channel — anyone intercepting that initial HTTP request could see the URL path, headers, and (if it's a POST) part of the body, even though the redirect
itself is harmless.

## UseHsts — browser-side instruction, cached ahead of time

This doesn't redirect anything itself. It adds one response header telling the browser: "remember this domain, and never even attempt HTTP for it again
for the next N seconds."

```csharp
builder.Services.AddHsts(options =>
{
    options.MaxAge = TimeSpan.FromDays(365);
    options.IncludeSubDomains = true;
    options.Preload = true;
});

if (!app.Environment.IsDevelopment())
{
    app.UseHsts();
}
```

**What actually happens on the wire:**

Any HTTPS response from your server includes this header:

```http
HTTP/1.1 200 OK
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

Once the browser has seen this header even once, on the next visit, it rewrites `http://yourapi.com` to `https://yourapi.com` internally, before sending
anything over the network at all — no insecure first request, no interception window, nothing to redirect.

**Why you need both, not just one**

```csharp
app.UseHttpsRedirection();   // handles: user typed http://, or an old bookmark/link uses http://
app.UseHsts();               // handles: browser remembers and skips http:// entirely on repeat visits
```

`UseHttpsRedirection` is your safety net for the very first contact — someone typing the bare domain, an old link floating around, a script hardcoded to
`http://`. `UseHsts` is what prevents that insecure first contact from recurring on every future visit once the browser has learned about your HTTPS policy.

### UseHsts options

```csharp
builder.Services.AddHsts(options =>
{
    options.MaxAge = TimeSpan.FromDays(365);
    options.IncludeSubDomains = true;
    options.Preload = true;
});
```

Each of these three options controls exactly what gets written into the `Strict-Transport-Security` header, and each one has a real consequence if set
wrong — HSTS is one of the few settings where misconfiguring it can lock you out of your own domain over HTTP for a long time, so it's worth
understanding precisely.

#### MaxAge

```csharp
options.MaxAge = TimeSpan.FromDays(365);
```

This becomes the `max-age` directive in the header, in seconds:

```http
Strict-Transport-Security: max-age=31536000
```

It tells the browser: "for the next 31,536,000 seconds (365 days) after seeing this header, never attempt a plain HTTP request to this domain — always
upgrade to HTTPS automatically, without asking the server first."

**The critical gotcha:** this is a rolling window. Every time the browser sees the header again (on any HTTPS response), the countdown resets to a full 365
days from that moment. So as long as users keep visiting your site regularly, they effectively stay locked into HTTPS-only indefinitely — not just for
one year total.

**Why this matters practically:** if you ever need to roll back to plain HTTP (e.g. testing, a misconfigured cert, migrating domains), any browser that
already cached this header will simply refuse to make HTTP requests to your domain for up to a year, even if your server itself would now accept HTTP.
There's no way to "un-send" this to browsers that already saw it — you'd have to wait out the `max-age`, or serve a new HSTS header with `max-age=0` to
explicitly clear it.

```csharp
// Emergency "undo" — tells browsers to forget the HSTS policy immediately
options.MaxAge = TimeSpan.Zero;
```

#### IncludeSubDomains

```csharp
options.IncludeSubDomains = true;
```

Adds `includeSubDomains` to the header:

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

Without this, HSTS only applies to the exact domain that sent the header — `yourapi.com`. With it, the policy extends to every subdomain too — `api.yourapi.com`,
`admin.yourapi.com`, `staging.yourapi.com`, all of them, even ones that haven't been created yet.

**Why you'd want this:** prevents an attacker from bypassing your HSTS protection by tricking a user into visiting `http://some-forgotten-subdomain.yourapi.com`
that you never got around to serving HTTPS on.

**The real risk if you set this carelessly:** if you have any subdomain that genuinely can't run HTTPS — an old internal tool, a third-party-hosted
subdomain, a staging environment without a valid cert — turning this on breaks it for every visitor whose browser has cached your main domain's HSTS
header, because the policy now applies there too, whether that subdomain is ready for it or not.

#### Preload

```csharp
options.Preload = true;
```

Adds `preload` to the header:

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

## Avoid HSTS in Development

```csharp
if (!app.Environment.IsDevelopment())
{
    app.UseHsts();            // then set the header on the (now-HTTPS) response, so future visits skip HTTP
}
```

Local development typically uses a self-signed dev certificate (`dotnet dev-certs https`), and HSTS is aggressive — once a browser caches the HSTS policy
for `localhost`, it'll refuse plain HTTP to `localhost` for the `MaxAge` duration, which can break other local projects or tools running on plain HTTP during
development. Keeping it prod-only avoids that friction.

# Enforce it at the hosting level too (defense in depth)

`UseHttpsRedirection` is an app-level redirect — for real production hardening, also configure this outside the app:

"Defense in depth" here means: don't rely on your ASP.NET Core middleware alone to guarantee HTTPS — because in many real deployments, your app code
isn't actually the first thing that receives the request. Something else (a reverse proxy, a load balancer, the OS-level web server) sits in front of it,
and if that layer isn't also configured correctly, your `UseHttpsRedirection`/`UseHsts` code can end up not doing what you think it's doing.

**Why app-level redirect alone isn't enough**

```csharp
app.UseHttpsRedirection();
```

This only works correctly if ASP.NET Core actually knows the original request came in over HTTP. But in most production setups, your app isn't directly
facing the internet:

```text
Internet → Reverse Proxy / Load Balancer (terminates TLS here) → Kestrel (your app, plain HTTP internally)
```

The proxy decrypts HTTPS from the client, then forwards the request to your app over plain HTTP on the internal network. From Kestrel's point of view,
every single request looks like HTTP — even ones that were genuinely HTTPS from the client's perspective. If you don't tell your app about this
arrangement, `UseHttpsRedirection` might think every request needs redirecting (including ones that were already secure), causing an infinite redirect
loop, or it might silently do nothing useful at all.

## The three layers where this needs to be configured

### 1. Kestrel itself — don't even listen on HTTP in production

```json
// appsettings.Production.json
{
  "Kestrel": {
    "Endpoints": {
      "Https": {
        "Url": "https://0.0.0.0:5001",
        "Certificate": {
          "Path": "/etc/certs/yourapi.pfx",
          "Password": "from-env-or-keyvault"
        }
      }
    }
  }
}
```

If Kestrel has no HTTP endpoint configured at all, there's nothing to redirect — a plain HTTP connection attempt fails to even establish, rather than
succeeding and then bouncing to HTTPS. This is the strongest possible guarantee, but it only works if nothing sits between the client and Kestrel (rare
in production — usually there's a proxy).

### 2. Reverse proxy (Nginx/IIS/Azure)

Nginx handles the actual TLS termination and the HTTP→HTTPS redirect entirely on its own — your app never even sees the insecure request. But it forwards
the original scheme via the `X-Forwarded-Proto` header so your app can still correctly answer "was this request secure?" if it needs to (e.g. for building
absolute URLs, or `Request.IsHttps` checks).

**Nginx example**

```nginx
server {
    listen 80;
    server_name yourapi.com;
    return 301 https://$host$request_uri;   # redirect at the proxy, before it even reaches Kestrel
}

server {
    listen 443 ssl;
    server_name yourapi.com;

    ssl_certificate /etc/ssl/certs/yourapi.crt;
    ssl_certificate_key /etc/ssl/private/yourapi.key;

    location / {
        proxy_pass http://localhost:5000;   # internal call to Kestrel is plain HTTP — normal and fine
        proxy_set_header X-Forwarded-Proto https;   # tells your app "this WAS https, even though I'm sending it as http now"
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header Host $host;
    }
}
```

**IIS example (if hosting on Windows Server)**

```xml
<!-- web.config, or via IIS Manager's URL Rewrite module -->
<system.webServer>
  <rewrite>
    <rules>
      <rule name="Force HTTPS" stopProcessing="true">
        <match url="(.*)" />
        <conditions>
          <add input="{HTTPS}" pattern="off" ignoreCase="true" />
        </conditions>
        <action type="Redirect" url="https://{HTTP_HOST}/{R:1}" redirectType="Permanent" />
      </rule>
    </rules>
  </rewrite>
</system.webServer>
```

### 3. Your app must trust and read those forwarded headers

This is the piece that's easy to miss — without it, your app doesn't know the proxy already handled HTTPS, and things like `Request.IsHttps`, `Request.Scheme`, and any redirect logic inside your app will be wrong:

```csharp
builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto;

    // IMPORTANT: by default, ASP.NET Core only trusts forwarded headers from
    // known proxy IPs — if your proxy isn't in that list, headers are ignored
    options.KnownNetworks.Clear();
    options.KnownProxies.Clear();
    // In practice, either add your proxy's actual IP/network here,
    // or (only if the proxy is fully trusted and on a private network) clear both lists to trust any source — be careful with this in shared/cloud environments
});

var app = builder.Build();

app.UseForwardedHeaders();   // MUST come before UseHttpsRedirection/UseAuthentication
app.UseHttpsRedirection();
```

Without `UseForwardedHeaders()`, your app sees every request as arriving over HTTP (since that's genuinely how Nginx forwarded it internally), which can
cause `UseHttpsRedirection` to try redirecting requests that are actually already secure from the client's perspective — leading to a redirect loop between
the proxy and your app.


# TLS Certificate Handling in ASP.NET Core Web API 

**Note : Usually it is handle by reverse proxy in Production system**

TLS has two sides in a Web API: the **server side** (the API presents a certificate and optionally asks callers for one) and the **client side** (the API, or any .NET client, calls another HTTPS service and must decide whether to trust its certificate). Where TLS is terminated (reverse proxy vs Web API) decides which of these you actually have to implement.

---

### 1. Server side: Web API presenting its certificate

#### 1.1 Local development

```bash
dotnet dev-certs https --trust
```

The dev certificate is for `localhost` only. Never ship it.

#### 1.2 Kestrel with a certificate file (appsettings)

```json
{
  "Kestrel": {
    "Endpoints": {
      "Https": {
        "Url": "https://*:5001",
        "Certificate": {
          "Path": "/certs/api.pfx",
          "Password": "from-env-or-secret-store"
        }
      }
    }
  }
}
```

Keep the password out of source control: use environment variables, user-secrets (dev), Azure Key Vault, or Docker/Kubernetes secrets.

Docker equivalent (no appsettings change needed):

```bash
docker run -p 5001:5001 \
  -e ASPNETCORE_URLS=https://+:5001 \
  -e ASPNETCORE_Kestrel__Certificates__Default__Path=/certs/api.pfx \
  -e ASPNETCORE_Kestrel__Certificates__Default__Password=$CERT_PASSWORD \
  -v /host/certs:/certs:ro myapi
```

#### 1.3 Kestrel in code (protocols, store lookup, SNI, rotation)

```csharp
builder.WebHost.ConfigureKestrel(options =>
{
    options.ConfigureHttpsDefaults(https =>
    {
        https.SslProtocols = SslProtocols.Tls12 | SslProtocols.Tls13; // no TLS 1.0/1.1
        https.ClientCertificateMode = ClientCertificateMode.NoCertificate; // see mTLS below
    });

    options.ListenAnyIP(5001, listen =>
    {
        listen.UseHttps(https =>
        {
            // Pick a certificate per request (SNI). Cache it so rotation = swap the cached value.
            https.ServerCertificateSelector = (connectionContext, hostName) =>
                CertificateProvider.GetFor(hostName);
        });
    });
});
```

Notes:
- A certificate loaded once at startup stays in use until restart. For zero-downtime rotation, use `ServerCertificateSelector` backed by a cache you refresh (timer, file watcher, Key Vault), or do a rolling restart.
- Windows: load from the certificate store by thumbprint or subject. Make sure the app identity has read access to the private key.
- Use a certificate from a CA your callers trust (public CA for internet-facing, internal CA for private services). Subject Alternative Names (SAN) must contain the hostname callers use.

#### 1.4 HTTPS redirection and HSTS

```csharp
if (!app.Environment.IsDevelopment())
    app.UseHsts();          // tells browsers "HTTPS only"

app.UseHttpsRedirection();  // only meaningful if the API itself listens on HTTP too
```

Behind a TLS-terminating proxy, the API sees plain HTTP. Without forwarded headers, `UseHttpsRedirection` can cause redirect loops and `Request.Scheme` will be wrong:

```csharp
builder.Services.Configure<ForwardedHeadersOptions>(o =>
{
    o.ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto;
    // Trust only your proxy, not the whole internet:
    o.KnownProxies.Add(IPAddress.Parse("10.0.0.5"));
});

app.UseForwardedHeaders(); // must run first in the pipeline
```

#### 1.5 Mutual TLS (client certificate authentication)

Use when the **callers** must prove who they are with a certificate (B2B APIs, service-to-service, banking/government integrations).

```csharp
// Program.cs  (NuGet: Microsoft.AspNetCore.Authentication.Certificate)
builder.WebHost.ConfigureKestrel(o =>
    o.ConfigureHttpsDefaults(h => h.ClientCertificateMode = ClientCertificateMode.RequireCertificate));

builder.Services
    .AddAuthentication(CertificateAuthenticationDefaults.AuthenticationScheme)
    .AddCertificate(options =>
    {
        options.AllowedCertificateTypes = CertificateTypes.Chained;
        options.RevocationMode = X509RevocationMode.Online;

        // Trust only your own CA instead of the whole OS store:
        options.ChainTrustValidationMode = X509ChainTrustMode.CustomRootTrust;
        options.CustomTrustStore.Add(new X509Certificate2("partner-ca.cer"));

        options.Events = new CertificateAuthenticationEvents
        {
            OnCertificateValidated = ctx =>
            {
                // Authorization decision: is this specific certificate allowed?
                var thumbprint = ctx.ClientCertificate.Thumbprint;
                if (!AllowedPartners.Contains(thumbprint))
                {
                    ctx.Fail("Unknown client certificate");
                    return Task.CompletedTask;
                }

                var claims = new[]
                {
                    new Claim(ClaimTypes.NameIdentifier, ctx.ClientCertificate.Subject),
                    new Claim("cert_thumbprint", thumbprint)
                };
                ctx.Principal = new ClaimsPrincipal(
                    new ClaimsIdentity(claims, ctx.Scheme.Name));
                ctx.Success();
                return Task.CompletedTask;
            },
            OnAuthenticationFailed = ctx =>
            {
                ctx.Fail("Certificate validation failed");
                return Task.CompletedTask;
            }
        };
    });

app.UseAuthentication();
app.UseAuthorization();
```

Use `ClientCertificateMode.AllowCertificate` if only some endpoints need a certificate, and enforce it with `[Authorize]` on those.

**mTLS when a proxy terminates TLS:** the API never sees the real client certificate, so the proxy must validate it and forward it in a header:

```csharp
builder.Services.AddCertificateForwarding(o => o.CertificateHeader = "X-Client-Cert");

app.UseForwardedHeaders();
app.UseCertificateForwarding(); // before UseAuthentication
app.UseAuthentication();
```

Critical: the proxy must **strip any incoming `X-Client-Cert` header from external requests** and set it only from its own validated certificate. Also make sure the API is reachable only from the proxy (network rules or mTLS between proxy and API). Otherwise anyone can forge the header.

---

### 2. Client side: validating the server's certificate

By default, `HttpClient` validates against the OS trust store: chain to a trusted root, not expired, hostname matches SAN, not revoked (if revocation checking is on). For public CAs, do nothing extra.

#### 2.1 Never do this in production

```csharp
// WRONG: accepts any certificate, enables man-in-the-middle attacks
handler.ServerCertificateCustomValidationCallback = (_, _, _, _) => true;
```

If you need to bypass validation for a local dev certificate, guard it:

```csharp
if (env.IsDevelopment())
    handler.ServerCertificateCustomValidationCallback =
        HttpClientHandler.DangerousAcceptAnyServerCertificateValidator;
```

#### 2.2 Trust a private/internal CA without installing it on the machine

```csharp
public static class TlsHandlerFactory
{
    public static SocketsHttpHandler Create(X509Certificate2 internalCa,
                                            X509Certificate2? clientCert = null)
    {
        var ssl = new SslClientAuthenticationOptions
        {
            EnabledSslProtocols = SslProtocols.Tls12 | SslProtocols.Tls13,
            RemoteCertificateValidationCallback = (sender, cert, chain, errors) =>
            {
                if (errors == SslPolicyErrors.None) return true;
                if (cert is null) return false;

                // Only forgive chain errors (unknown CA). Name mismatch or missing cert = reject.
                if ((errors & ~SslPolicyErrors.RemoteCertificateChainErrors) != 0)
                    return false;

                using var customChain = new X509Chain();
                customChain.ChainPolicy.TrustMode = X509ChainTrustMode.CustomRootTrust;
                customChain.ChainPolicy.CustomTrustStore.Add(internalCa);
                customChain.ChainPolicy.RevocationMode = X509RevocationMode.Online;
                return customChain.Build(new X509Certificate2(cert));
            }
        };

        if (clientCert is not null)
            ssl.ClientCertificates = new X509CertificateCollection { clientCert }; // for mTLS

        return new SocketsHttpHandler
        {
            SslOptions = ssl,
            PooledConnectionLifetime = TimeSpan.FromMinutes(15) // picks up rotated certs/DNS
        };
    }
}
```

Register with `IHttpClientFactory`:

```csharp
builder.Services.AddHttpClient("PartnerApi", c => c.BaseAddress = new Uri("https://partner.internal"))
    .ConfigurePrimaryHttpMessageHandler(() =>
        TlsHandlerFactory.Create(
            internalCa: new X509Certificate2("internal-ca.cer"),
            clientCert: new X509Certificate2("api-client.pfx", clientCertPassword)));
```

#### 2.3 Certificate pinning (optional, high-security)

Pin the expected certificate (or public key) hash, so even a valid certificate from another CA is rejected:

```csharp
const string PinnedSha256 = "ABCDEF..."; // thumbprint of expected cert

RemoteCertificateValidationCallback = (_, cert, _, errors) =>
    errors == SslPolicyErrors.None &&
    cert!.GetCertHashString(HashAlgorithmName.SHA256)
        .Equals(PinnedSha256, StringComparison.OrdinalIgnoreCase);
```

Trade-off: when the server rotates its certificate, clients break unless you pin the public key or CA, or ship the new pin first. Use sparingly.

#### 2.4 Common client-side failures

| Error | Likely cause |
|---|---|
| `The remote certificate is invalid ... UntrustedRoot` | Server cert issued by a CA not in the trust store (internal CA, self-signed) |
| `RemoteCertificateNameMismatch` | URL host not in the certificate's SAN |
| `NotTimeValid` / expired | Certificate expired or machine clock wrong |
| `RevocationStatusUnknown` / `OfflineRevocation` | No access to CRL/OCSP endpoints (firewall) |
| `The SSL connection could not be established ... handshake` | TLS version/cipher mismatch, or server requires a client certificate you didn't send |

---

### 3. TLS validation: reverse proxy vs Web API

Reverse proxy here means nginx, IIS/ARR, YARP, Azure App Gateway, AWS ALB, Traefik, Envoy, etc.

#### 3.1 Termination models

| Model | Flow | Who holds the certificate | Typical use |
|---|---|---|---|
| **Offload (terminate at proxy)** | Client ⇄ HTTPS ⇄ Proxy ⇄ HTTP ⇄ API | Proxy only | Most common. Private network between proxy and API. |
| **Re-encrypt (TLS bridging)** | Client ⇄ HTTPS ⇄ Proxy ⇄ HTTPS ⇄ API | Proxy and API (separate certs) | Compliance (PCI, HIPAA), shared or untrusted network, zero-trust. |
| **Passthrough** | Client ⇄ HTTPS ⇄ Proxy (TCP only) ⇄ HTTPS ⇄ API | API only | API must see the real client certificate; proxy needs no L7 features. |

#### 3.2 What each side validates

| Concern | Reverse proxy (terminating) | Web API (Kestrel) |
|---|---|---|
| Server certificate (public-facing) | Presents it, renews it (Let's Encrypt/ACM/Key Vault) | Presents it only in passthrough or re-encrypt hop |
| TLS versions and cipher suites | Enforces for internet clients | Enforces only on its own listener |
| Client certificate (mTLS) validation | Validates chain/revocation, then forwards cert or identity in a header | Validates directly in passthrough; in offload mode, trusts the forwarded header |
| Upstream (proxy to API) certificate | Verifies API's cert (`proxy_ssl_verify on` in nginx) in re-encrypt mode | Presents its cert |
| Hostname/SNI routing, HSTS, HTTP to HTTPS redirect | Usually here | Only if the API is exposed directly |
| App-level authorization of the cert (which partner is this?) | No | Yes: thumbprint/subject/claims checks in `OnCertificateValidated` |

Rule of thumb: **the proxy validates the transport; the API validates identity and authorization.**

#### 3.3 When do you need TLS in the Web API itself?

Handle TLS in the API when:
- The API is exposed directly (no proxy), e.g. an internal service, a gRPC service, or a small deployment.
- You need end-to-end encryption inside the cluster or VNet (compliance, zero-trust, service mesh not available).
- You need the real client certificate in the app (passthrough) and don't want to trust forwarded headers.
- The proxy to API hop crosses a network you don't fully control.
- HTTP/2 or gRPC end to end requires HTTPS on that hop (when ALPN negotiation is needed).

Leave TLS to the proxy when:
- The proxy and API sit on the same host or a locked-down private network.
- You want one place for certificate issuance and renewal instead of one per service.
- You need WAF, rate limiting, caching, or routing decisions based on decrypted traffic.
- Services run in Kubernetes behind an ingress controller or service mesh (the mesh can provide mTLS automatically).

#### 3.4 Example: nginx re-encrypting with upstream verification and mTLS

```nginx
server {
    listen 443 ssl;
    server_name api.example.com;

    ssl_certificate     /etc/ssl/api.example.com.crt;
    ssl_certificate_key /etc/ssl/api.example.com.key;
    ssl_protocols       TLSv1.2 TLSv1.3;

    # Validate client certs at the proxy (mTLS)
    ssl_client_certificate /etc/ssl/partner-ca.crt;
    ssl_verify_client      on;

    location / {
        proxy_pass https://api-internal:5001;

        # Verify the API's certificate (re-encrypt hop)
        proxy_ssl_verify              on;
        proxy_ssl_trusted_certificate /etc/ssl/internal-ca.crt;
        proxy_ssl_name                api-internal;

        # Forward validated client cert; overwrite anything the client sent
        proxy_set_header X-Client-Cert $ssl_client_escaped_cert;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    }
}
```

The matching API side is the `AddCertificateForwarding` and `AddCertificate` setup from section 1.5.

#### 3.5 Decision checklist

1. Internet-facing browser or mobile clients, simple setup: terminate at the proxy, plain HTTP behind it, enable forwarded headers.
2. Compliance or untrusted internal network: re-encrypt, with the proxy verifying the API certificate and the API using an internal-CA certificate.
3. Partner mTLS: validate at the proxy and forward the certificate (lock down the header), or use passthrough if you want the API to do the full validation.
4. Service to service inside a mesh: let the mesh handle mTLS; the API stays on HTTP, plus authorization based on identity headers.
5. Outgoing calls from the API: always validate the remote certificate; trust a private CA via `CustomRootTrust`, never via "accept all".

#### 3.6 Operational checklist

- Monitor certificate expiry (alert at 30/14/7 days); automate renewal.
- Keep private keys out of images and repos; mount them as secrets.
- Disable TLS 1.0/1.1; prefer TLS 1.2+ and let the OS pick ciphers.
- Test with `openssl s_client -connect host:443 -servername host` and `curl -v --cert client.pem --key client.key https://host`.
- Log certificate failures (thumbprint, subject, reason), never the private key or password.
