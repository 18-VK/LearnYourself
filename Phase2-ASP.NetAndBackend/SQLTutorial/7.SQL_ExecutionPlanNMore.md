# What is an execution plan?

An execution plan is SQL Server's recipe for running your query — the steps the query optimizer chooses (joins, scans, seeks, sorts, etc.),
plus estimated costs for each step.

There are two kinds:

- **Estimated Execution Plan** — what the optimizer thinks it will do (no runtime stats).
- **Actual Execution Plan** — what actually happened (with row counts, runtime, actual operator costs).

**How to get them:**

In SSMS: click *Display Estimated Execution Plan* or *Include Actual Execution Plan* (or `Ctrl+M` before running).

Or commands:

```sql
SET STATISTICS TIME ON;
SET STATISTICS IO ON;
-- run query
```

These show CPU/elapsed time and logical reads (IO) alongside the plan.

An execution plan shows how SQL Server executes your query.

It tells you:

- Which index is used
- Whether it scans or seeks
- Join type (Nested Loop / Hash / Merge)
- Estimated cost
- Number of rows processed

## 🔹 How to View Execution Plan

In SSMS:

- Click "Include Actual Execution Plan"
- Or press `Ctrl + M`
- Then execute query

## How to Read Execution Plan (Step-by-Step)

**Example Query**

```sql
SELECT Name, Salary
FROM Employee
WHERE Name = 'Aman';
```

### 1️⃣ Read From Right to Left

Execution flows:

```text
➡ Right → Left
➡ Top → Bottom
```

Rightmost operator runs first.

### 2️⃣ Important Operators

#### 🔹 Index Seek (GOOD)

- ✔ Uses index efficiently
- ✔ Small number of rows
- ✔ Fast lookup

Best case scenario.

#### 🔹 Index Scan

- ⚠ Reads entire index
- Better than table scan
- But still expensive for large data

#### 🔹 Table Scan (BAD for large tables)

- ❌ Reads entire table
- ❌ High IO
- ❌ Slow for large data

#### 🔹 Key Lookup (Important!)

Happens when:

- Non-clustered index used
- But missing columns
- SQL goes back to clustered index
- If many rows → expensive.

**Solution** → Covering index

> **E.g.:** Looking for rows using non-clustered index, and going back to clustered index for accessing other columns
> makes it expensive. To solve this issue, we can use a covering index by adding other columns into the index.

#### 🔹 Join Types

| Join Type   | When Used     | Performance  |
| ----------- | ------------- | ------------ |
| Nested Loop | Small dataset | Fast         |
| Merge Join  | Sorted data   | Efficient    |
| Hash Match  | Large data    | Memory heavy |

### 3️⃣ Estimated vs Actual Rows (Very Important)

Hover over operator.

Compare:

- Estimated Rows
- Actual Rows

If huge difference:

- 👉 Bad statistics
- 👉 Parameter sniffing
- 👉 Poor cardinality estimate

This causes wrong plan selection.

### 📊 4️⃣ Cost Percentage

You'll see:

```text
Hash Match (80%)
Index Seek (5%)
```

- This is relative cost within that plan only
- Not actual execution time.

Do NOT rely only on cost %.

### ✅ 5️⃣ Using SET STATISTICS IO

Enable:

```sql
SET STATISTICS IO ON;
```

Then run query.

**Output example:**

```text
Table 'Employee'.
Scan count 1,
logical reads 150,
physical reads 0
```

🔹 **How to Interpret**

| Metric         | Meaning                |
| -------------- | ---------------------- |
| Logical reads  | Pages read from memory |
| Physical reads | Pages read from disk   |
| Scan count     | Number of scans/seeks  |

Lower logical reads = better.

### ✅ 6️⃣ Using SET STATISTICS TIME

```sql
SET STATISTICS TIME ON;
```

**Output:**

```text
CPU time = 15 ms
Elapsed time = 20 ms
```

| Metric       | Meaning                    |
| ------------ | -------------------------- |
| CPU time     | Processing time            |
| Elapsed time | Total time including waits |

# Index Seek vs Index Scan

## Index Seek

- Uses index to jump directly to matching rows via key lookup (range or single value).
- Efficient when small subset of rows is needed.
- Appears as **Index Seek** in the plan and shows Seek Predicate.

## Index Scan

- Reads many (or all) pages of an index; essentially a full traversal.
- Efficient when you need a large portion of rows (e.g., >30–40% of table) or no useful index exists.
- Appears as **Index Scan** (or **Table Scan** for heap).

**When seek is better:**

Highly selective predicates (e.g., `WHERE CustomerId = 123` with index on `CustomerId`).

**When scan may be better:**

Query needs most rows or when reading a large portion; building a plan with seeks+lookups could be more expensive.

**Example:**

```sql
-- Good: seek (assumes index on CustomerId)
SELECT * FROM Orders WHERE CustomerId = 123;

-- Likely scan (no useful predicate)
SELECT * FROM Orders WHERE Amount > 0;
```

**Tip:** a seek plus lookup can be expensive if many rows match. A covering index (include columns used in SELECT) can avoid lookups.

**Example:**

```sql
-- Good: seek (assumes index on CustomerId)
```

# Costly operators (what to watch for)

Operators that commonly add time/IO/cpu — understand and mitigate them:

**1. Table Scan / Index Scan**

- **Cause:** no useful index or query requests most rows.
- **Mitigation:** add selective index, or accept scan for analytics.

**2. Key / RID / Bookmark Lookup (Lookup by RowID)**

- **Cause:** non-covering index requires fetching remaining columns from clustered index.
- **Mitigation:** create a covering index with `INCLUDE` for those columns.

**3. Sort**

- **Cause:** `ORDER BY`, `DISTINCT`, `GROUP BY` without usable index.
- **Mitigation:** add aligned index (matching `ORDER BY`), use `TOP` with proper indexing, avoid unnecessary sorts.

> **Note:** Need to go through Aligned Index.

# SARGABLE Queries

SARGABLE = **S**earch **ARG**ument **ABLE**

A query is SARGABLE when SQL Server can use an index seek to filter rows efficiently.
If a query is non-SARGABLE, the optimizer cannot use the index properly → leads to index scan or table scan.

## Why It Matters

On large tables:

- SARGABLE → milliseconds
- Non-SARGABLE → seconds or minutes

This is a core performance tuning concept.

## ✅ Example Table

```sql
CREATE TABLE Employee (
    EmployeeID INT PRIMARY KEY,
    Name VARCHAR(100),
    Salary DECIMAL(10,2),
    JoinDate DATE
);

CREATE INDEX IX_Employee_JoinDate
ON Employee(JoinDate);
```

### 1️⃣ SARGABLE Example (GOOD)

```sql
SELECT *
FROM Employee
WHERE JoinDate = '2026-01-01';
```

- ✔ Uses index seek
- ✔ Efficient lookup
- ✔ Reads only matching rows

### ❌ Non-SARGABLE Example (BAD)

```sql
SELECT *
FROM Employee
WHERE YEAR(JoinDate) = 2026;
```

**Why bad?**

- Function applied on indexed column
- SQL Server must compute `YEAR()` for every row
- Index cannot be used properly
- Causes index scan

### 🔥 Fix It (Make It SARGABLE)

Instead of:

```sql
WHERE YEAR(JoinDate) = 2026
```

Use:

```sql
WHERE JoinDate >= '2026-01-01'
AND JoinDate < '2027-01-01';
```

- ✔ Now index seek works
- ✔ Much faster

## Common Non-SARGABLE Patterns

### 1️⃣ Functions on Columns

❌

```sql
WHERE UPPER(Name) = 'AMAN';
```

✔ **Fix:**

```sql
WHERE Name = 'AMAN';
```

(Use case-insensitive collation instead)

### 2️⃣ Calculations on Column

❌

```sql
WHERE Salary * 1.1 > 50000;
```

✔ **Fix:**

```sql
WHERE Salary > 50000 / 1.1;
```

Move calculation to constant side.

### 3️⃣ Leading Wildcard LIKE

❌

```sql
WHERE Name LIKE '%man';
```

- ✔ Cannot use index efficiently
- ✔ Causes scan

✔ **Better:**

```sql
WHERE Name LIKE 'Aman%';
```

Leading characters known → index usable.

### 4️⃣ Implicit Conversions

❌

```sql
WHERE JoinDate = '01-01-2026';
```

If datatype mismatch occurs → conversion on column → scan.
Always match correct datatype.

## SARGABLE vs Non-SARGABLE Comparison

| Pattern            | Uses Index Seek? |
| ------------------ | ---------------- |
| Column = Value     | ✅ Yes            |
| Column > Value     | ✅ Yes            |
| BETWEEN            | ✅ Yes            |
| Column LIKE 'abc%' | ✅ Yes            |
| Function(Column)   | ❌ No             |
| Column + 1 = 10    | ❌ No             |
| LIKE '%abc'        | ❌ No             |

## 🔥 Real Production Use Case

Table: `Orders` (50 million rows)

**Bad query:**

```sql
WHERE MONTH(OrderDate) = 5;
```

→ 50M row scan

**Good query:**

```sql
WHERE OrderDate >= '2026-05-01'
AND OrderDate < '2026-06-01';
```

→ Reads only May partition/index range

Huge performance difference 🚀

## 🔎 How to Detect Non-SARGABLE Query

In execution plan:

- ❌ Index Scan
- ❌ Predicate shows function on column
- ❌ High logical reads

Use:

```sql
SET STATISTICS IO ON;
```

Compare logical reads before and after rewrite.

## Interview-Ready Definition

A SARGABLE query is one that allows the database engine to use an index seek by avoiding functions or calculations on indexed columns. Writing
SARGABLE predicates significantly improves query performance.

## 🎯 Golden Rule

👉 Never apply a function or calculation on indexed columns in `WHERE` or `JOIN` conditions.

👉 Rewrite condition so column remains untouched.

## Examples: query rewrites & fixes

**1. Non-sargable → Sargable**

```sql
-- BAD: will scan
SELECT * FROM Sales WHERE CONVERT(VARCHAR(4), SaleDate, 112) = '202501';

-- BETTER: range seek (sargable)
SELECT * FROM Sales WHERE SaleDate >= '2025-01-01' AND SaleDate < '2025-02-01';
```

**2. Function on indexed column**

```sql
-- BAD: index on Username unused
SELECT * FROM Users WHERE LOWER(Username) = 'aman';

-- FIX A (normalize data): store username lower-case and index
-- FIX B (computed persisted): create persisted computed col LOWER(Username) and index it
```

**3. Covering index to avoid lookups**

```sql
-- Query
SELECT OrderId, Amount FROM Orders WHERE CustomerId = 123;

-- Create covering index
CREATE INDEX IX_Orders_CustomerId ON Orders(CustomerId) INCLUDE(Amount);
```

**4. Replace correlated subquery with join + grouping**

```sql
-- BAD (correlated, possible many executions)
SELECT c.Id,
       (SELECT COUNT(*) FROM Orders o WHERE o.CustomerId = c.Id) AS OrderCount
FROM Customers c;

-- GOOD (set-based)
SELECT c.Id, COUNT(o.Id) AS OrderCount
FROM Customers c
LEFT JOIN Orders o ON o.CustomerId = c.Id
GROUP BY c.Id;
```

# Take one of your slow queries and rewrite it with SARGABLE predicates and index suggestions, showing estimated vs actual IO improvements

## Step 1 — Sample Table (Large Data)

```sql
CREATE TABLE Orders (
    OrderId INT IDENTITY PRIMARY KEY,
    CustomerId INT,
    OrderDate DATETIME2,
    Amount DECIMAL(10,2)
);
```

Create index:

```sql
CREATE INDEX IX_Orders_OrderDate
ON Orders(OrderDate);
```

Assume:

- 5 million rows
- Orders across multiple years

## 🚨 Slow Query (Non-SARGABLE)

**Goal:** Get all 2025 orders.

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT *
FROM Orders
WHERE YEAR(OrderDate) = 2025;
```

🔎 **Execution Plan**

You will see:

- ❌ Index Scan
- Predicate: `YEAR(OrderDate) = 2025`
- Function applied to indexed column

📊 **Example Output (Typical Large Table)**

```text
Table 'Orders'. Scan count 1, logical reads 120,000
CPU time = 850 ms
Elapsed time = 920 ms
```

**Why?**

Because SQL Server must:

- Apply `YEAR()` to every row
- Cannot seek into index
- Must scan entire index

## ✅ Optimized Version (SARGABLE)

Rewrite using range predicate:

```sql
SELECT *
FROM Orders
WHERE OrderDate >= '2025-01-01'
AND OrderDate <  '2026-01-01';
```

🔎 **Execution Plan**

Now you'll see:

- ✅ Index Seek
- Seek Predicate on `OrderDate`
- Much fewer pages read

📊 **Example Output**

```text
Table 'Orders'. Scan count 1, logical reads 3,200
CPU time = 45 ms
Elapsed time = 60 ms
```
