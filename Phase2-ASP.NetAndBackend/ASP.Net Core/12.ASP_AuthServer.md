# Approach for creating Auth Server

## Approach 1 — Fully custom, build-it-yourself (what we've been building)

You write `IdentityService`, `TokenService`, RS256 signing, refresh rotation — everything — using ASP.NET Core Identity as the user store, but rolling your own
token issuance logic.

**When this fits:** Single API, single frontend, you fully control both. No need for multiple client apps, no SSO across products, no third-party developers
consuming your auth.

**Tradeoffs:** Full control over every claim, every flow, every edge case — nothing hidden behind a framework's opinions. But you own every security decision
yourself: token revocation edge cases, replay detection, key rotation, rate limiting — all of it is your bug to find. This is exactly what your Task
Management API auth module is right now, and it's the right call for that scope.

## Approach 2 — Off-the-shelf identity server: Duende IdentityServer / OpenIddict

Instead of writing `TokenService` yourself, you install a framework that implements the full OAuth2/OIDC spec — authorization code flow, PKCE, client
credentials, discovery endpoint, JWKS rotation, consent screens — all of it, out of the box.

**When this fits:** You need real OAuth2/OIDC compliance — multiple client apps (web, mobile, third-party integrations) all needing SSO against one identity provider, or you plan to let external developers register OAuth clients against your API like a real platform.

**Tradeoffs:** You get spec-compliant, battle-tested flows (PKCE, consent, discovery, JWKS rotation) without writing them yourself — huge time save and fewer
security bugs. Duende IdentityServer is commercial-licensed above certain usage; OpenIddict is free and open source and increasingly the more common pick
for exactly that reason. The cost is a steeper learning curve and less flexibility for quirky custom logic (a custom `RefreshTokens` table with your own
reuse-detection semantics, for instance, is more natural to hand-roll than to bend a framework's own model around).

## Approach 3 — Managed identity provider (don't run your own server at all)

You don't build an auth server — you outsource it entirely to Auth0, Azure Entra ID (formerly Azure AD B2C), AWS Cognito, or Firebase Auth. Your API only
validates tokens; user management, MFA, social logins, password policies, breach detection — all handled by the vendor.

```csharp
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.Authority = "https://your-tenant.auth0.com/";
        options.Audience = "https://api.taskmanagement.yourcompany.com";
    });
```

**When this fits:** Startups/small teams who'd rather not maintain auth infrastructure at all, or enterprise contexts where the company already standardizes on
Azure Entra for all internal apps.

**Tradeoffs:** Zero auth code to maintain, professional security team behind it, MFA/social login for free. But you're paying per monthly active user past free
tiers, you're vendor-locked, and any customization (custom claims, unusual token lifetimes, non-standard flows) goes through their extensibility mechanisms
rather than your own code.

# Before choosing any one of them, let's go through some terminologies

> **Note:** This is the general understanding of OAuth 2.0 and OIDC — don't confuse it with how to use it in your scenario.

## OAuth2.0

OAuth 2.0 is an industry-standard authorization framework that allows third-party applications to access your data or perform actions on another service
without giving them your username and password. It uses secure, temporary digital keys called access tokens instead of credentials.

**What it solves**

Before OAuth, if you wanted "Sign in with Google" you'd ask users for their Google password directly — terrible idea. OAuth lets Google issue a temporary,
scoped access token to your app on the user's behalf, without ever giving you the password.

**The four roles**

The **Resource Owner** is the user who owns the data. The **Client** is your app. The **Authorization Server** issues tokens (Google's OAuth server, Auth0, Duende).
The **Resource Server** is the API being protected (your Task Management API, or Google Calendar API, etc.).

### Authorization Code Flow — step by step

This is the flow you use for any web or server-side app. Here's what each step actually does:

**Step 1 — User clicks "Login with Google"**

Your app redirects the browser to Google's authorization endpoint with these query parameters:

```http
GET https://accounts.google.com/o/oauth2/v2/auth
  ?client_id=YOUR_CLIENT_ID
  &redirect_uri=https://yourapp.com/callback
  &response_type=code
  &scope=openid email profile
  &state=random_csrf_token_abc123
```

The `state` is critical — it's a random value your app generates, stores in session, and later verifies. Without it, a malicious site could trick a user into
connecting their Google account to the attacker's app (CSRF on the OAuth flow).

**Step 2 — Google authenticates the user and asks for consent**

Google shows its own login page. The user enters their Google credentials (your app never sees them). Google then shows a consent screen listing what
permissions your app is requesting (the `scope`).

**Step 3 — Google redirects back with an auth code**

After consent, Google redirects to your `redirect_uri` with a short-lived auth code:

```http
GET https://yourapp.com/callback
  ?code=4/P7q7W91a-oMsCeLvIaQm6bTrgtp7
  &state=random_csrf_token_abc123
```

This code is one-time use, expires in minutes, and useless on its own — it has to be exchanged for a real token. It travels through the browser (front
channel) deliberately because the next step (exchanging it) happens server-to-server and is never visible to the browser.

**Step 4 — Your server exchanges the code for tokens (back channel)**

This is the critical security step. Your server makes a direct HTTPS request to Google — NOT through the browser:

```http
POST https://oauth2.googleapis.com/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=4/P7q7W91a-oMsCeLvIaQm6bTrgtp7
&redirect_uri=https://yourapp.com/callback
&client_id=YOUR_CLIENT_ID
&client_secret=YOUR_CLIENT_SECRET   ← never exposed to browser
```

Google responds with:

```json
{
  "access_token": "ya29.A0ARrdaM...",
  "expires_in": 3600,
  "refresh_token": "1//0eXx...",
  "token_type": "Bearer",
  "scope": "openid email profile"
}
```

**Step 5 — Use the access token to call APIs**

```http
GET https://www.googleapis.com/calendar/v3/calendars/primary/events
Authorization: Bearer ya29.A0ARrdaM...
```

The reason this two-step (code → token exchange) exists instead of just returning the token directly from step 3: the auth code can travel through the
browser URL bar, browser history, referrer headers, and server logs. If it leaks, it's useless without the `client_secret`, which never leaves your server.
The access token never touches the browser at all. That's the security guarantee.

## OpenID Connect (OIDC)

OpenID Connect (OIDC) is an identity authentication layer built on top of the OAuth 2.0 framework. It allows an application (Relying Party) to verify a
user's identity based on the authentication performed by an Identity Provider (like Google or Microsoft), securely passing user profile details.

**The "Sign in with Google" Example**

Imagine you are using a new recipe website (the application) and want to create an account. Instead of filling out a form and remembering a new password,
you click "Sign in with Google."

Here is how OIDC handles this interaction behind the scenes:

1. **The Request:**
   The recipe website redirects your browser to Google with an OIDC request, asking for your basic profile (using the scope).
2. **The Authentication:**
   Google prompts you to log in (if you aren't already) and asks for your consent to share your details.
3. **The Token Exchange:**
   Once you approve, Google redirects you back to the recipe website and provides two things: an Access Token (permitting the site to
   fetch your data) and an ID Token (a cryptographically signed JSON Web Token that contains verifiable user details like your name, email, and a unique
   Google user ID).
4. **The Verification:**
   The recipe website verifies Google's signature on the ID Token, recognizes who you are, and logs you in.

**What it adds**

OAuth 2.0 gives you authorization (access to resources) but deliberately says nothing about identity. After the flow above, you know "this user authorized
access to their Google Calendar" — but you don't know who they are. OIDC adds that.

OIDC makes one specific change to step 4 (of OAuth): include `openid` in the scope, and the token response now includes an `id_token` alongside the access token.
The same flow, but the response looks like this:

```json
{
  "access_token": "ya29.A0ARrdaM...",
  "expires_in": 3600,
  "refresh_token": "1//0eXx...",
  "token_type": "Bearer",
  "scope": "openid email profile",
  "id_token": "eyJhbGciOiJSUzI1NiIsImtpZCI6..."
}
```

(`id_token` ← OIDC addition)

**What's inside the id_token**

The `id_token` is a signed JWT. Decode the payload and you get standardized identity claims:

```json
{
  "iss": "https://accounts.google.com",
  "sub": "110248495921238986420",
  "aud": "YOUR_CLIENT_ID",
  "exp": 1737000000,
  "iat": 1736999100,
  "email": "aman@example.com",
  "email_verified": true,
  "name": "Aman Kumar",
  "picture": "https://lh3.googleusercontent.com/..."
}
```

- `iss` — who issued this token
- `sub` — unique user ID; stable, never changes
- `aud` — which app this token is for
- `exp` — when it expires
- `iat` — when it was issued

The `sub` claim is the user's permanent, unique ID at that provider. You persist this in your database alongside whatever local user record you create. Never
use email as a primary key — users can change their email, but `sub` is immutable.

**Three things OIDC standardizes that OAuth doesn't**

The `id_token` is the proof of identity — signed by the auth server using RS256, verifiable by your app without calling the auth server at all (just the
public key from the JWKS endpoint). The **UserInfo endpoint** (`GET /userinfo` with the access token) lets you fetch additional claims if you didn't request
everything in the scope. The **Discovery endpoint** (`/.well-known/openid-configuration`) is a machine-readable JSON document listing the provider's endpoints,
supported scopes, signing algorithms, and JWKS URI — your .NET middleware fetches this once on startup and configures itself automatically.

### code and client_secret

#### Where each one comes from

**`client_secret` — created once, at app registration time, long before any user ever logs in**

This happens when you (the developer) register your app with Google, one time, in the Google Cloud Console:

```text
You → Google Cloud Console: "I'm registering an app called TaskFlow"

Google → You (once, shown only one time in the dashboard):
    client_id     = 847592-abc123.apps.googleusercontent.com
    client_secret = GOCSPX-8f3kL9pQ2rT5vN1xW7yZ
```

This pair identifies your application itself — not any particular user. It's created once and reused for every single login, by every single user, forever
(until you manually rotate it). You copy `client_secret` into your backend's configuration (`appsettings.json`, Key Vault, environment variable) and it just
sits there.

**`code` — generated fresh, by Google, for every single login attempt, at the very end of the user's consent step**

This doesn't exist until a real user actually goes through the login flow:

```text
User clicks "Sign in with Google"
  → User authenticates on Google's page
  → User clicks "Allow"
  → Google generates a brand new code, right now, tied to THIS specific login event:

    code = 4/0AVGzR1AbCdEfGhIjKlMnOpQrStUvWxYz1234567890
```

This code is one-time-use, expires in a few minutes, and represents "this specific user, at this specific moment, approved this specific request." A
different user logging in five minutes later gets a completely different code. The same user logging in again tomorrow gets yet another different code.

#### How they're related — why BOTH are required together

This is the actual mechanism worth understanding. In step 4, your backend sends both, in the same request:

```http
POST https://oauth2.googleapis.com/token
grant_type=authorization_code
&code=4/0AVGzR1AbCdEfGhIjKlMnOpQrStUvWxYz1234567890   ← proves: a user consented
&client_id=847592-abc123.apps.googleusercontent.com
&client_secret=GOCSPX-8f3kL9pQ2rT5vN1xW7yZ             ← proves: this is really TaskFlow asking
&redirect_uri=https://taskflow.yourcompany.com/auth/callback
```

**Google's token endpoint checks two independent things before issuing tokens:**

**Check 1** — Is this `code` valid? Does it exist, is it unexpired, was it issued for this exact `client_id` and `redirect_uri`?

**Check 2** — Is whoever's asking actually TaskFlow? Does the `client_secret` sent match the one on file for `client_id = 847592-abc123...`?

Both have to pass. Neither alone is sufficient — and that's the entire design reasoning:

**Why the code alone isn't enough:**

The code briefly travels through the front channel (the browser's redirect URL, potentially browser history, referrer headers, proxy logs — as we covered
earlier). If Google trusted the code alone, anyone who happened to see that URL could steal the code and redeem it for tokens, impersonating the real user.
Requiring the `client_secret` too means a stolen code is useless to anyone who isn't also in possession of TaskFlow's actual backend.

**Why the client_secret alone isn't enough:**

The secret only proves "this is genuinely the TaskFlow app talking." It says nothing about whether any specific user actually logged in and consented right
now. Without the code, your backend could just call Google's token endpoint at any time and get... nothing, actually — because there'd be no user consent
event to redeem. The code is what ties the exchange to one real, specific, just-happened authentication event.

## What is a JWK (JSON Web Key)?

A JWK is a JSON object that represents a cryptographic key. Instead of sending raw binary keys (which are hard to parse), the industry uses this standard
JSON format to share public keys.

**Example of a JWK (Public Key for RSA):**

```json
{
  "kty": "RSA",
  "e": "AQAB",
  "use": "sig",
  "kid": "unique-key-id-123",
  "n": "v5aP-Q...[long-string]...x4Q"
}
```

- `kty`: Key Type (RSA).
- `kid`: Key ID (used so the API knows which key to use if you have multiple).
- `n` & `e`: The actual mathematical components of the public key.

## JWKS

A JSON Web Key Set (JWKS) is a JSON document containing a set of public cryptographic keys. Identity providers and servers host this on a public endpoint
(like `https://example.com/.well-known/jwks.json`) so clients and backend APIs can fetch them to verify the digital signatures of JSON Web Tokens (JWTs).

**Example of a JWKS Document** — this example contains a single RSA public key used to verify tokens:

```json
{
  "keys": [
    {
      "kty": "RSA",
      "alg": "RS256",
      "use": "sig",
      "kid": "k1e9c8a",
      "n": "oQ9x...Yw==" ,
      "e": "AQAB"
    }
  ]
}
```

**`kid`:** stored in JWT's header part

```json
{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "key-id-12345"
}
```

**How it is used in practice:**

1. When a user logs in, the authorization server (e.g., Auth0 or Keycloak) signs the JWT with its private key.
2. The authorization server includes the `kid` in the JWT header so the client knows which key signed it.
3. The client or backend API retrieves the public keys from the server's JWKS endpoint.
4. The client finds the key in the JWKS array with the matching `kid` and uses it to safely verify the JWT signature.

## PKCE

PKCE (Proof Key for Code Exchange) is an OAuth 2.0 security extension used by public clients like mobile and Single-Page Applications (SPAs). It prevents authorization code interception attacks by requiring the app to prove its identity using a dynamically generated, one-time secret called the Code Verifier.

**How the Flow Works (With Example)**

Imagine your application, "MyApp," needs to securely log a user into an authorization server (like Google or Auth0).

**1. Generate the Code Verifier**

Your app generates a cryptographically random string (e.g., 43 to 128 characters long).

- Example Verifier: `dBjftJeZ4CVK-mJ92_zFhN0UeZ6H8sGZ_yK9N8tC_uI`

**2. Generate the Code Challenge**

Your app then hashes this verifier using SHA-256 and base64url-encodes it.

- Example Challenge: `E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM`

**3. The Authorization Request**

MyApp sends the challenge along with the authorization request to the server. The server safely records it.

```http
GET https://authorization-server.com?
  response_type=code&
  client_id=myapp_id&
  redirect_uri=https://myapp.com&
  code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM&
  code_challenge_method=S256
```

**4. The Authorization Code**

The server authenticates the user, generates a temporary code, and returns it to your app.

- Example Code: `spl-a0a2b3`

**5. Exchanging the Code for Tokens**

This is where PKCE shines. MyApp now requests an access token. Even though a malicious app might have intercepted the code,
it cannot proceed without the original verifier. MyApp sends the code and the original verifier:

```http
POST https://authorization-server.com
  grant_type=authorization_code&
  client_id=myapp_id&
  code=spl-a0a2b3&
  redirect_uri=https://myapp.com&
  code_verifier=dBjftJeZ4CVK-mJ92_zFhN0UeZ6H8sGZ_yK9N8tC_uI
```

**6. Verification**

The authorization server hashes the received verifier and compares it to the challenge it stored in step 3. If they match, the server knows the request
originated from the exact same app that initiated it, and issues the Access Token.

## client_secret vs PKCE code_verifier

Side-by-side against the `client_secret` flow, since you already know that one.

Both `client_secret` and `code_verifier` help prove that a token
exchange is legitimate, but they solve different problems.

- **client_secret** authenticates the client application.
- **code_verifier** proves that the same client instance that started
  the login is the one exchanging the authorization code.

### client_secret

- Authenticates a confidential client (typically a backend application).
- Generated once during client registration.
- Long-lived until rotated manually.

**Stored**

- Key Vault
- Environment variables
- Secret manager
- Server configuration

**Sent During Token Request**

The actual `client_secret`.

**Used By**

Confidential clients such as server-side web applications and backend
services.

Never store it in a browser.

### code_verifier (PKCE)

- Proves that the same application instance which initiated the login is
  exchanging the authorization code.
- Generate as new random value is created for every login attempt.
- Valid only for a single authorization flow.

**Stored**

Temporarily in browser memory or `sessionStorage` (or application memory
on mobile/desktop).

**Sent During Authorization Request**

Only the `code_challenge` (a hash of the verifier) is sent.

**Sent During Token Request**

The actual `code_verifier`.

**Used By**

Public clients (SPA, mobile, desktop) and commonly confidential clients
as well.

**Browser Storage**

Safe because it is temporary and single-use.

**Key Differences**

- `client_secret` is a permanent application credential.
- `code_verifier` is a temporary per-login credential.
- `client_secret` authenticates the client application.
- `code_verifier` protects against authorization code interception.
- `client_secret` must never be exposed to browsers.
- `code_verifier` can safely exist in browser memory because it is
  short-lived and single-use.

## PKCE vs client_secret — when to use what?

Comes down to one question: can the client keep a secret confidential?

### Client secret — for confidential clients

A client secret only works if the client can store it somewhere a user (or attacker with browser devtools) can't read it. That means:

- Backend services (your ASP.NET Core API calling another service, a server-side web app rendering HTML)
- Machine-to-machine flows (Client Credentials grant — no user involved at all)

If the code runs on a server you control, and the secret lives in an env var / secrets manager rather than shipped to the browser, a client secret is fine
and simpler than PKCE.

### PKCE — for public clients

PKCE exists because these clients cannot hold a secret — anything you embed is extractable:

- **SPAs (Angular, React)** — the JS bundle is fully visible in devtools
- **Mobile apps** — the app binary can be decompiled
- **Desktop apps** — same problem

Here, instead of proving identity with a fixed secret, the client proves it's the same app that started the flow: it generates a random `code_verifier`,
sends its hash (`code_challenge`) up front, then reveals the raw `code_verifier` at token exchange. An attacker who intercepts the authorization code can't
redeem it without that verifier, which never touches the browser URL/history.

| Client type      | Can hide a secret? | Use |
| ---              | ---                | --- |
| Angular frontend | No                 | PKCE, `ClientType` = `Public` |
| Backend API → another backend | Yes   | Client secret, Client Credentials grant |
| Mobile app       | No                 | PKCE |
| Server-rendered MVC app | Yes         | Client secret + PKCE (belt-and-suspenders — OpenIddict allows both) |

**The nuance people miss**

PKCE and client secrets solve different problems, so they're not mutually exclusive:

- **Client secret** = authenticates who the client is
- **PKCE** = proves the token redeemer is the same party that initiated the auth request (protects against authorization code interception)

A confidential client (has a secret) can still benefit from PKCE if the redirect could be intercepted (e.g. a native app using a custom URI scheme
redirect, even if it also has an embedded secret). OpenIddict's `RequireProofKeyForCodeExchange()` can be applied server-wide, so plenty of real setups just
require PKCE on every client, confidential or not, since it costs nothing and closes one more attack path. The public/confidential split only tells you
whether you also need a secret — it doesn't tell you PKCE is optional for confidential clients.

## Refresh Token

A refresh token is a secure, long-lived credential used in frameworks like OAuth 2.0 to obtain new access tokens without requiring users to repeatedly
re-enter their login credentials. It acts as a master key for continuous, automated access to protected resources.

**The Lifecycle of a Refresh Token**

The lifecycle balances security with user convenience:

1. **Issuance:** User logs in with username and password. Server grants a short-lived Access Token (e.g., 15 minutes) and a Refresh Token (e.g., 30-90 days).
2. **Access & Depletion:** The client app uses the Access Token to make API requests until it expires.
3. **Refreshing:** When the Access Token expires, the client sends the Refresh Token to the authorization server to seamlessly issue a brand new Access Token.
4. **Rotation (Security Best Practice):** During the refresh step, the server often issues a new Refresh Token and invalidates the old one.

**When is it Created?**

A refresh token is created only once during the initial login or authorization process. When a user successfully authenticates using their credentials (e.g.,
via OAuth 2.0 flows) and grants permission to the client app, the authorization server generates the refresh token alongside the initial access
token.

**When is it Deleted (or Revoked)?**

A refresh token is discarded or marked as invalid in a few specific scenarios:

- **Explicit User Action:** When the user clicks Log Out or revokes the app's access from their connected app settings.
- **Token Rotation (Invalidation):** If your system uses Refresh Token Rotation, the old token is immediately deleted or disabled the moment it is used to
  request a new one.
- **Maximum Expiration Limits:** Refresh tokens are configured with lifetime limits (e.g., 30, 60, or 90 days). Once this time passes, the token naturally
  expires.
- **Security Incidents:** If the token is stolen, servers can invalidate it. Furthermore, if a user changes their account password, or if the server detects
  token reuse (two clients attempting to use the same refresh token), all associated tokens are deleted to prevent fraud.
- **Exceeding Quotas:** Many systems (like Auth0) set limits on active refresh tokens per user. Generating a new token when the limit is hit will cause the
  oldest token to be deleted.

### Why refresh tokens exist in the first place

Access tokens are short-lived on purpose — 15 minutes in your setup — so that if one leaks, the exposure window is small. But asking a user to type their
password every 15 minutes would be unusable. The refresh token is a separate, longer-lived credential (14 days in your `JwtSettings`) whose only job is:
prove you were legitimately logged in recently, so we'll issue you a fresh access token without asking for a password again.

> **Note:** Taking example of custom Auth server, created without any framework like OpenIddict.
> Check this project for more understanding: `Examples/CustomAuthServerWithNoFramework_TaskManagementApi.Auth`

**Step 1 — Initial login, both tokens issued together**

```http
POST /api/auth/login
{ "email": "aman.kumar@example.com", "password": "correct-password" }
```

**Response:**

```json
{
  "accessToken": "eyJhbGciOiJSUzI1NiIsImtpZCI6ImExYjJj...",
  "refreshToken": "Xk92mQp7RtL4vBnW8yZaC3dEfGhIjKlMnOpQrStUvWxYzAbCdEf==",
  "accessTokenExpiresAtUtc": "2026-07-18T10:15:00Z"
}
```

What actually happened server-side, using the `TokenService`/`IdentityService` we already wrote:

```csharp
var tokenFamilyId = Guid.NewGuid();  // "Family A" - born here
var (rawRefreshToken, refreshTokenEntity) = _tokenService.GenerateRefreshToken(
    user.Id, tokenFamilyId, ipAddress, userAgent);

_dbContext.RefreshTokens.Add(refreshTokenEntity);
await _dbContext.SaveChangesAsync();
```

And the actual row that lands in your `RefreshTokens` table:

| Id     | UserId    | TokenHash                         | TokenFamilyId | ExpiresAtUtc | RevokedAtUtc | ReplacedByTokenId |
| ---    | ---       | ---                               | ---      | ---        | ---  | ---  |
| rt-001 | user-aman | SHA256("Xk92mQp7...") = 4f8a2c... | family-A | 2026-08-01 | null | null |

**Notice:** the raw `Xk92mQp7...` string is only ever in the HTTP response and the client's storage — the database only ever stores its hash. Same principle as
passwords.

The access token, decoded, contains what your API actually checks on every request:

```json
{ "sub": "user-aman", "role": "Member", "exp": 1737190500, "iat": 1737189600 }
```

**Step 2 — 15 minutes pass, access token expires**

The client calls `GET /api/tasks` with the now-expired access token. Your `AddJwtBearer` middleware checks `exp` against current time, fails validation, returns:

```http
HTTP/1.1 401 Unauthorized
```

This is expected and routine — not an error condition, just the signal for the client to refresh.

**Step 3 — Client calls refresh, using the stored refresh token**

```http
POST /api/auth/refresh
{ "refreshToken": "Xk92mQp7RtL4vBnW8yZaC3dEfGhIjKlMnOpQrStUvWxYzAbCdEf==" }
```

Inside `RefreshTokenAsync` (code we already wrote):

```csharp
var hash = _tokenService.HashToken(refreshToken);   // recompute the hash, same as verification pattern

var existing = await _dbContext.RefreshTokens
    .Include(rt => rt.User)
    .FirstOrDefaultAsync(rt => rt.TokenHash == hash);   // finds rt-001

// existing.RevokedAtUtc is null, existing.ExpiresAtUtc is in the future → valid
```

Since it's valid, your server does two things at once — revokes the old token and mints a new one, in the same family:

```csharp
existing.RevokedAtUtc = DateTime.UtcNow;   // rt-001 dies right now

var (rawToken, newEntity) = _tokenService.GenerateRefreshToken(
    existing.UserId, existing.TokenFamilyId, ipAddress, userAgent);   // SAME family-A

existing.ReplacedByTokenId = newEntity.Id;
_dbContext.RefreshTokens.Add(newEntity);
```

The table now looks like this:

| Id     | TokenHash | TokenFamilyId | RevokedAtUtc | ReplacedByTokenId |
| ---    | ---       | ---      | --- | --- |
| rt-001 | 4f8a2c... | family-A | 2026-07-18 10:15:03 | rt-002 |
| rt-002 | 9b3e71... | family-A | null | null |

**Response to the client:**

```json
{
  "accessToken": "eyJhbGciOiJSUzI1NiIsImtpZCI6ImExYjJj... (new, fresh 15-min token)",
  "refreshToken": "Qm5vLpR8tXy2wZaBcDeFgHiJkLmNoPqRsTuVwXy==",
  "accessTokenExpiresAtUtc": "2026-07-18T10:30:00Z"
}
```

This is the "rotation" part — the client's old refresh token (`Xk92mQp7...`) is now dead, permanently, even though it hadn't expired yet. The client silently
swaps its stored refresh token for the new one (`Qm5vLpR8...`) and keeps going. From the user's perspective, nothing happened — they're just still logged in.

**Step 4 — This repeats every ~15 minutes, silently, for the whole 14-day window**

Each refresh call revokes the current token and issues a new one, always in family-A. After a day of normal use, the family might have a chain: rt-001 →
rt-002 → rt-003 → rt-004 → ..., each one the "replacement" of the last, only the newest one ever active.

**Step 5 — What happens if the refresh token is actually stolen (the reuse-detection payoff)**

Say an attacker manages to steal rt-002's raw value (`Qm5vLpR8...`) — from an XSS attack, a compromised proxy, whatever. Two parties now hold what they each
believe is "the current valid refresh token": the real user (who has since refreshed again and is now on rt-004) and the attacker (stuck holding the older,
already-revoked rt-002).

The attacker tries to use it:

```http
POST /api/auth/refresh
{ "refreshToken": "Qm5vLpR8tXy2wZaBcDeFgHiJkLmNoPqRsTuVwXy==" }
```

Your server's check:

```csharp
var existing = await _dbContext.RefreshTokens...FirstOrDefaultAsync(rt => rt.TokenHash == hash);
// finds rt-002

if (existing.RevokedAtUtc is not null)
{
    // rt-002 was already revoked (back in step 3, when the REAL user refreshed past it)
    // A revoked token being presented again = someone is replaying a stolen token
    await RevokeFamilyAsync(existing.TokenFamilyId);   // kills rt-002, rt-003, rt-004 - EVERYTHING in family-A
    return new AuthResult { Succeeded = false, Errors = new[] { "Refresh token reuse detected; all sessions revoked." } };
}
```

**The critical insight:** rt-002 being revoked already (because the real user moved past it to rt-003 at some point) is itself the signal. A legitimate client
would never present an already-revoked token — it always has the latest one. Only a stolen, stale copy would ever hit this branch.

**Result:** your server nukes the entire family — rt-002, rt-003, rt-004, everything descended from the original login — in one shot:

| Id | RevokedAtUtc | Notes |
| --- | --- | --- |
| rt-001 | 2026-07-18 10:15:03 | From normal rotation |
| rt-002 | 2026-07-18 10:15:03 | Still shows this, was already revoked |
| rt-003 | 2026-07-18 14:22:07 | Revoked **now**, by the reuse-detection response |
| rt-004 | 2026-07-18 14:22:07 | Revoked **now** too, even though it was the real user's current token |

Even the real, legitimate user gets logged out here — their currently-active rt-004 gets killed too. That's an intentional tradeoff: you can't tell from
the server side who's the "real" user and who's the attacker, so the safe move is to burn the whole family and force a fresh login (password re-entry),
rather than let a suspected-stolen chain keep silently minting tokens.

**Why rotation + reuse detection together matter, not just one alone**

If you only had rotation (new refresh token each time) but no reuse detection, a stolen token would just let the attacker start their own silent refresh
chain in parallel — indistinguishable from the real user's chain, both working forever, neither ever expiring since each refresh resets the clock.

If you only had reuse detection but no rotation (same refresh token reused every time, just checked against a revoke-list), you'd have no way to ever
detect theft in the first place — there'd be no "this token was already used" moment to catch, since nothing changes between calls.

### But if user and attacker have same refresh token at the same time, attacker can use it to get new refresh token before user

**The scenario you're describing**

Both the real user and the attacker are holding the exact same refresh token at the exact same moment — say rt-002 — because the attacker stole it via XSS
or similar, but hasn't used it yet; the real user also still has it in their browser, not yet expired, sitting there before their next natural refresh
cycle kicks in. Whoever calls `/api/auth/refresh` first with rt-002 wins that race — their call revokes rt-002 and gets rt-003 back as the new active token.
The second one to call (whether that's the real user or the attacker) gets the "reuse detected" response, since by the time their request lands, rt-002 is
already revoked.

**The uncomfortable truth: if the attacker wins the race, they get valid tokens**

You're right that in this specific race, whoever calls first — attacker or user — successfully gets a fresh, completely legitimate rt-003 and its
accompanying access token. The server has no way to distinguish "the real user refreshing normally" from "the attacker refreshing with a stolen copy" at
that exact moment, because the token itself is identical bytes in both hands. Reuse detection catches the theft after it's already happened — specifically,
at the moment the loser of that race (whoever calls second) gets rejected and triggers the family-wide revocation.

So the actual sequence, if the attacker wins:

1. Attacker uses stolen rt-002 → gets rt-003 + valid access token (attacker now has API access)
2. Real user's app also tries to use rt-002 (it doesn't know it's already been spent)
3. Server sees rt-002 already revoked → REUSE DETECTED → kills entire family (rt-003 included)
4. Real user gets logged out, forced to re-authenticate
5. Attacker's rt-003 and access token: also just got revoked in step 3's family-wide kill

#### What does a refresh token contain?

It generally contains either an opaque string (a random identifier that the authorization server looks up in its database) or a JSON Web Token (JWT), which
includes metadata like user IDs, authorized permissions (scopes), and expiration times.

But by default, OpenIddict refresh tokens are neither a bare random string (like our hand-rolled design) nor a readable signed JWT (like our access
tokens).
They're a self-contained token that genuinely does carry claims and metadata — but encrypted using ASP.NET Core's Data Protection API, so it's opaque to
anyone without your server's encryption keys.

**What's actually inside, before encryption**

```json
{
  "sub": "user-aman-guid",
  "oi_au_id": "a3f7c912-...",
  "oi_tkn_id": "8f2a91b3-...",
  "client_id": "taskflow-spa",
  "scope": "openid profile tasks.read tasks.write",
  "iat": 1737189600,
  "exp": 1738399200,
  "token_usage": "refresh_token",
  "token_type": "Bearer"
}
```

- `oi_au_id` — authorization ID; links back to the consent grant
- `oi_tkn_id` — this token's own unique ID
- `exp` — 14-day refresh token lifetime

**Then it gets encrypted, not just signed**

```text
raw_payload (JSON above)
    ↓
ASP.NET Core Data Protection: Protect(payload)
    ↓
opaque_token = base64("CfDJ8Kx9pL2vQm3nR7wZmH4jK9pL2vQm3nR7wZmH4jK9pL2vQm3nR7wZmH4jK9pL2v...")
```

This is a meaningfully different guarantee from your hand-built access token JWT. A JWT is signed but not encrypted — anyone holding it can decode the
payload and read the claims in plaintext, they just can't forge a new valid signature. This OpenIddict refresh token is encrypted — you cannot read the
claims at all without the server's Data Protection keys, which never leave the server. So even if this token leaked and someone decoded the base64, they'd
get ciphertext, not JSON.

**Why encrypted-and-self-contained instead of a signed JWT for refresh tokens**

Refresh tokens are longer-lived and more sensitive than access tokens — a leaked access token exposes 15 minutes of access; a leaked refresh token, if it
were readable, would expose `sub`, `client_id`, and `scope` information to anyone who intercepted it, even without being able to actually redeem it. Encryption
closes that observation channel entirely.

#### Note : Below is the in-depth understanding of refresh token encryption, you may skip it

**What do you mean by "encrypted using ASP.NET Core's Data Protection API"? How does it encrypt the refresh token?**

**First — where this sits relative to what we've already covered**

You now know three different cryptographic operations in this whole system: **SHA-256 hashing** (one-way, used for your refresh token storage — can verify but
never recover the original), **RSA signing** (two-way but asymmetric — private key signs, public key only verifies, never decrypts anything back to plaintext),
and now **symmetric encryption** — which is genuinely reversible in both directions, using the same key to encrypt and decrypt. Data Protection is built on
this third kind.

**What "encrypted" actually means here — concretely**

Take the OpenIddict refresh token payload from before:

```json
{
  "sub": "user-aman-guid",
  "client_id": "taskflow-spa",
  "scope": "tasks.read tasks.write",
  "exp": 1738399200
}
```

Encryption transforms this into unreadable ciphertext using a symmetric key (typically AES):

```text
plaintext_bytes = UTF8.GetBytes(jsonPayload)
ciphertext_bytes = AES_ENCRYPT(plaintext_bytes, key)   ← same key used both ways
refresh_token = base64(ciphertext_bytes)
```

The critical difference from RSA signing: this same key can also decrypt it back:

```text
plaintext_bytes = AES_DECRYPT(ciphertext_bytes, key)   ← same key, reverses it completely
```

With RSA signature verification, you never got the original data back out of the signature — you only confirmed a hash matched. With this, the server can
fully recover the original JSON — `sub`, `client_id`, `scope`, everything — because encryption is designed to be reversible by whoever holds the key. That's
fundamentally different from a hash (one-way, never reversible) or a signature (verifiable, but not reversible into the signed content — the content
travels separately, in plaintext, alongside the signature).

**Why this matters for a refresh token specifically**

If OpenIddict just base64-encoded the JSON (like your raw refresh token bytes, no cryptography at all), anyone who intercepted the token could simply
base64-decode it and read `sub`, `client_id`, `scope` directly — no key needed, since base64 isn't a cipher, just a text encoding. Encrypting it means only
someone holding the correct key can turn that ciphertext back into readable JSON. An attacker who steals the token gets meaningless bytes; the server, and
only the server, can decrypt it back to something usable.

**What Data Protection specifically adds on top of "just use AES"**

Data Protection is ASP.NET Core's built-in system for doing exactly this kind of encrypt/decrypt-by-the-server operation, and it handles a few things you'd
otherwise have to build yourself:

```csharp
var protector = dataProtectionProvider.CreateProtector("OpenIddict.RefreshTokens");

string encrypted = protector.Protect(jsonPayload);    // AES-encrypt + authenticate
string decrypted = protector.Unprotect(encrypted);    // decrypt + verify integrity
```

**Key management** — Data Protection generates, stores, and automatically rotates the actual AES keys for you, typically storing them encrypted-at-rest on disk
(or in a shared location like Redis/Azure Blob Storage for multi-server deployments) rather than you hand-managing a raw AES key in config.

**Purpose isolation** — the `"OpenIddict.RefreshTokens"` string above is a "purpose" — a key derived specifically for this use case, so even if the same Data Protection key ring is used elsewhere in your app (e.g. for anti-forgery tokens, or cookie encryption), a key derived for one purpose can't decrypt data encrypted for another purpose, even though they share the same root key material.

**Tamper detection built in** — Data Protection doesn't just encrypt; it also adds an authentication tag (this is "authenticated encryption," AES-GCM or
similar under the hood), so if even one byte of the ciphertext is altered, `Unprotect()` throws rather than silently returning corrupted or attacker-modified
data. This is conceptually similar to what RSA signature verification gives you for JWTs, but built into the encryption step itself rather than being a
separate signature.

**Key rotation without breaking old tokens** — Data Protection keeps a key ring (multiple keys, each with an ID and expiry), so tokens encrypted last week with
key A can still be decrypted today even after key B becomes the new default for encrypting fresh tokens — it tries the right key from the ring based on
metadata embedded in the encrypted payload itself.

**Why this matters operationally — the failure case that trips people up**

Data Protection keys are typically stored per-machine by default (on disk, tied to that machine's identity). If you deploy your auth server across multiple
instances behind a load balancer without explicitly configuring a shared key ring (Redis, a shared file share, Azure Key Vault, etc.), then a refresh token
encrypted by instance A can fail to decrypt when the next refresh request happens to land on instance B — because instance B has a different,
independently-generated key ring. This is the single most common real-world bug with Data Protection in scaled-out deployments, and it's exactly why I
flagged it earlier as the reason some teams prefer OpenIddict's reference token mode instead — a reference token is just a random ID looked up in a shared
database, so it has no dependency on key-ring synchronization across servers at all.
