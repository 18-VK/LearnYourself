# How to communicate between different parts of an application?

How real production applications handle coordination between panes / modules.

There is no single pattern used everywhere.

But almost all serious apps follow this rule:

- ViewModels do not talk directly.
- Communication goes through orchestration or shared state.

## What your scenario is

```text
Main Window
 ├── Left Pane  (projects)
 └── Right Pane (tasks)
```

Left selects project → Right updates.

Very common in:

- IDEs
- Email clients
- task managers
- admin panels

## ✅ What production apps usually choose

- 🥇 #1 → Shared State / Store (VERY common today)
- 🥈 #2 → Parent orchestrator
- 🥉 #3 → Event/Messenger (for large modular systems)

Let's see each with real-world reasoning.

## 🥇 Shared State / Store (MOST POPULAR)

Used heavily in:

- enterprise WPF
- WinUI
- web apps (Redux, Flux)
- modern MVVM

Instead of:

```text
Left → Right
```

You have:

```text
Left → State ← Right
```

Both react to the same truth.

**Example:**

```csharp
public class ApplicationState : INotifyPropertyChanged
{
    public Project? SelectedProject { get; set; }
}
```

**Left pane**

```csharp
_state.SelectedProject = project;
```

**Right pane**

```csharp
if (_state.SelectedProject != null)
    LoadTasks(_state.SelectedProject.Id);
```

**Why companies love this**

- ✔ Very scalable
- ✔ Easy to debug
- ✔ Central truth
- ✔ Time-travel debugging possible
- ✔ Logging becomes easy
- ✔ Works across many modules
- ✔ UI auto refresh

**Real products using this idea**

- Microsoft Teams
- Visual Studio Code
- Jira

They all maintain global UI/application state.

## 🧪 Interview answer (very strong)

If asked:

> "How do you coordinate multiple ViewModels?"

**Answer:**

> In production systems we typically avoid direct ViewModel references and instead use either a shared application state

> testability, and makes UI behavior predictable.

### 🏗 Combine them into AppState

```csharp
public class AppState
{
    public SelectionState Selection { get; }
    public FilterState Filters { get; }
    public NavigationState Navigation { get; }

    public AppState(
        SelectionState selection,
        FilterState filters,
        NavigationState navigation)
    {
        Selection = selection;
        Filters = filters;
        Navigation = navigation;
    }
}
```

### ✅ DI registration (important)

```csharp
services.AddSingleton<SelectionState>();
services.AddSingleton<FilterState>();
services.AddSingleton<NavigationState>();
services.AddSingleton<AppState>();
```

Singleton = shared truth across the app.

### 🧠 How ViewModels use it

**Left VM (project list):**

```csharp
public class LeftViewModel
{
    private readonly AppState _state;

    public LeftViewModel(AppState state)
    {
        _state = state;
    }

    public void SelectProject(Project project)
    {
        _state.Selection.SelectedProject = project;
    }
}
```

Left does not know Right exists.

**Right VM (task list):**

```csharp
public class RightViewModel
{
    private readonly AppState _state;

    public RightViewModel(AppState state)
    {
        _state = state;

        _state.Selection.PropertyChanged += (_, e) =>
        {
            if (e.PropertyName == nameof(SelectionState.SelectedProject))
            {
                LoadTasks();
            }
        };
    }
}
```

Right reacts automatically.

**Search bar VM**

```csharp
public string? SearchText
{
    get => _state.Filters.SearchText;
    set => _state.Filters.SearchText = value;
}
```

Done. Shared instantly.

# 🧠 Core rule for async + AppState

Async work happens in ViewModels or Services.
AppState only stores results & flags.

So:

- ❌ AppState does NOT await
- ❌ AppState does NOT call repositories
- ✅ AppState exposes observable state that async code updates

## Example

### 1️⃣ Extend AppState to support async UI states

You almost always need these three things:

- Loading flags
- Error info
- The actual data

**Example: TaskListState**

```csharp
public class TaskListState : ObservableObject
{
    private bool _isLoading;
    public bool IsLoading
    {
        get => _isLoading;
        set => SetProperty(ref _isLoading, value);
    }

    private string? _error;
    public string? Error
    {
        get => _error;
        set => SetProperty(ref _error, value);
    }

    private IReadOnlyList<TaskItem> _tasks = [];
    public IReadOnlyList<TaskItem> Tasks
    {
        get => _tasks;
        set => SetProperty(ref _tasks, value);
    }
}
```

This is pure UI state. No async here.

### 2️⃣ Async logic lives in the ViewModel

**Right pane VM (loads tasks when project changes)**

```csharp
public class RightTaskListViewModel
{
    private readonly AppState _state;
    private readonly TaskService _taskService;

    private CancellationTokenSource? _cts;

    public RightTaskListViewModel(
        AppState state,
        TaskService taskService)
    {
        _state = state;
        _taskService = taskService;

        _state.Selection.PropertyChanged += OnSelectionChanged;
    }

    private void OnSelectionChanged(object? sender, PropertyChangedEventArgs e)
    {
        if (e.PropertyName == nameof(SelectionState.SelectedProject))
        {
            _ = LoadTasksAsync();
        }
    }
```

### 3️⃣ Correct async loading pattern (important)

```csharp
private async Task LoadTasksAsync()
{
    _cts?.Cancel();
    _cts = new CancellationTokenSource();

    _state.Tasks.IsLoading = true;
    _state.Tasks.Error = null;

    try
    {
        var project = _state.Selection.SelectedProject;
        if (project == null) return;

        var tasks = await _taskService
            .GetTasksAsync(project.Id, _cts.Token);

        _state.Tasks.Tasks = tasks;
    }
    catch (OperationCanceledException)
    {
        // Expected – ignore
    }
    catch (Exception ex)
    {
        _state.Tasks.Error = ex.Message;
    }
    finally
    {
        _state.Tasks.IsLoading = false;
    }
}
```

# How does selection actually flow from the View to AppState?

**Key idea (read this twice)**

The View binds to a ViewModel property.
That property is a thin proxy to AppState.

The View never binds to AppState directly.

## 1️⃣ AppState (already done)

```csharp
public class SelectionState : ObservableObject
{
    private Project? _selectedProject;
    public Project? SelectedProject
    {
        get => _selectedProject;
        set => SetProperty(ref _selectedProject, value);
    }
}
```

## 2️⃣ Left pane ViewModel exposes SelectedProject

This is the bridge.

```csharp
public class ProjectListViewModel : ObservableObject
{
    private readonly AppState _state;

    public ProjectListViewModel(AppState state)
    {
        _state = state;
    }

    public ObservableCollection<Project> Projects { get; } = [];

    public Project? SelectedProject
    {
        get => _state.Selection.SelectedProject;
        set => _state.Selection.SelectedProject = value;
    }
}
```

- 👉 No extra backing field
- 👉 No duplication
- 👉 One source of truth

## 3️⃣ View binds normally (this is the magic)

```xml
<ListBox ItemsSource="{Binding Projects}"
         SelectedItem="{Binding SelectedProject, Mode=TwoWay}"
         DisplayMemberPath="Name" />
```

That's it.

## 4️⃣ What actually happens at runtime

User clicks a project:

```text
ListBox.SelectedItem changes
↓
ProjectListViewModel.SelectedProject setter
↓
AppState.Selection.SelectedProject updated
↓
PropertyChanged fired
↓
Right ViewModel sees change
↓
Async task reloads
```
