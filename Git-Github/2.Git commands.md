# Git Command Reference

This file is a practical command guide for day-to-day Git usage.

---

## 1. Repository setup

### `git init`

Purpose: initialize a new Git repository.

```bash
git init
```

Use when:
- starting a new project locally
- turning an existing folder into a repo

### `git clone`

Purpose: copy an existing repository from a remote server.

```bash
git clone https://github.com/user/repo.git
```

Use when:
- getting a project from GitHub or GitLab
- starting work on an existing codebase

### `git config`

Purpose: set user information and Git behavior.

```bash
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global core.editor "code --wait"
```

Use when:
- setting identity for commits
- configuring editor and aliases

## 2. Remote repository commands

### `git remote -v`

Purpose: list all configured remotes.

```bash
git remote -v
```

### `git remote add origin <url>`

Purpose: connect your local repo to a remote.

```bash
git remote add origin https://github.com/user/repo.git
```

### `git remote rename origin upstream`

Purpose: rename a remote reference.

```bash
git remote rename origin upstream
```

### `git remote remove origin`

Purpose: remove a remote.

```bash
git remote remove origin
```

### `git fetch`

Purpose: download remote changes without altering your working files.

```bash
git fetch origin
git fetch upstream
```

### `git pull`

Purpose: fetch plus merge/rebase into your current branch.

```bash
git pull origin main
git pull --rebase
```
git pull --rebase : 
Fetches changes from the tracked remote branch and places your local commits on top of them.

Equivalent to:

git fetch
git rebase

### `git push`

Purpose: upload local commits to a remote branch.

```bash
git push origin main
git push -u origin feature/login
```

## 3. Multiple remotes

### Why use multiple remotes?

A repository can have more than one remote. This is common in fork-based workflows.

Typical setup:

```bash
origin    -> your fork
upstream  -> original repository
```

### Example

```bash
git remote -v
```

```bash
origin    https://github.com/yourname/project.git (fetch)
origin    https://github.com/yourname/project.git (push)
upstream  https://github.com/company/project.git (fetch)
upstream  https://github.com/company/project.git (push)
```

### Common workflow

```bash
git fetch upstream
git diff main upstream/main
git merge upstream/main
git push origin feature/login
```

### Meaning

- `main` = your local branch
- `origin/main` = your fork main branch
- `upstream/main` = official repo main branch

## 4. Status and diff commands

### `git status`

Purpose: show repo status.

```bash
git status
```

### `git diff`

Purpose: show unstaged changes.

```bash
git diff
```

### `git diff --staged`

Purpose: show staged changes.

```bash
git diff --staged
```

### `git diff HEAD`

Purpose: compare working tree + staging area against the last commit.

```bash
git diff HEAD
```

### `git diff branch1 branch2`

Purpose: compare two branches.

```bash
git diff main feature/login
```

### `git diff --stat`

Purpose: show a summary of changed files.

```bash
git diff --stat
```

```bash
git log

git log -5
```

### `git show`

Purpose: show the content or patch of a specific commit.


### `git blame`

Purpose: see which commit last changed each line.


## 6. Staging and commits

### `git add`

Purpose: stage changes.

```bash
git add file.txt
git add .
git add -A
git add -p
```

### `git commit`

Purpose: save the current staged state.

```bash
git commit -m "Fix login issue"
```

### `git commit --amend`

Purpose: modify the most recent commit.

```bash
git commit --amend -m "Corrected message"
```

### `git commit -am`

Purpose: stage modified tracked files and commit them in one step.

```bash
git commit -am "Update styles"
```

> Note: This does not include newly created untracked files.

## 7. Undo and recovery

### `git restore`

Purpose: discard changes in the working tree.

```bash
git restore file.txt
git restore --staged file.txt
```

### `git reset`

Purpose: move the current branch or index backward.

```bash
git reset HEAD file.txt
git reset --soft HEAD~1
git reset --mixed HEAD~1
git reset --hard HEAD~1
```

`git reset` is used to undo changes by moving the current branch pointer or resetting the index/working tree.

#### `git reset HEAD file.txt`

Purpose: unstage a file but keep the changes in the working directory.

```bash
git add file.txt
git reset HEAD file.txt
```

Now the file is unstaged, but its content remains modified.

#### `git reset --soft HEAD~1`

Purpose: move the branch back one commit while keeping changes staged.

```bash
git reset --soft HEAD~1
```

This is useful when you want to undo the last commit but keep the changes ready to recommit.

#### `git reset --mixed HEAD~1`

Purpose: move back one commit and unstage changes.

```bash
git reset --mixed HEAD~1
```

This is the default behavior of `git reset`.

It moves HEAD backward but leaves your changes in the working directory, unstaged.

#### `git reset --hard HEAD~1`

Purpose: move back one commit and discard all changes in the working tree and index.

```bash
git reset --hard HEAD~1
```

This is destructive and should be used carefully.

Example:

```bash
git status
git reset --hard HEAD~1
```

After this, the current branch points to the previous commit, and your local changes are lost.

#### When to use `git reset`

- use `--soft` when you want to undo a commit but keep edits staged
- use `--mixed` when you want to undo commit and unstage changes
- use `--hard` when you want to completely remove the last commit and all related changes

> `git reset` changes history locally. Use it carefully on branches that others may also be using.

### `git revert`

Purpose: create a new commit that undoes an older commit safely.

```bash
git revert <commit-hash>
```

### `git reflog`

Purpose: show recent history of branch movement and recovery paths.

```bash
git reflog
```

### `git log` vs `git reflog`

Purpose:
- `git log` shows the commit history of the current branch.
- `git reflog` shows recent Git actions like checkout, commit, merge, reset, and branch movement.

Examples:

```bash
git log --oneline
```

```bash
git reflog
```

Difference:
- Use `git log` to inspect what commits exist.
- Use `git reflog` to recover from recent mistakes or find where a branch was before it was deleted.

Example:

```bash
git reflog
# HEAD@{0}: checkout: moving from feature/login to main
# HEAD@{1}: commit: Add login page
```

> `git log` is for commit history. `git reflog` is for recent recovery history.

## 8. Branching and switching

### `git branch`

Purpose: list branches.

```bash
git branch
git branch -a
```

### `git branch <branch-name>`

Purpose: create a new branch without switching to it.

```bash
git branch feature/login
```

### `git switch -c <branch-name>`

Purpose: create a new branch and switch to it immediately.

```bash
git switch -c feature/login
```

### `git checkout -b <branch-name>`

Purpose: older alternative to create and switch to a new branch.

```bash
git checkout -b feature/login
```

### `git switch`

Purpose: move between branches.

```bash
git switch main
git switch feature/login
```

### `git checkout`

Older alternative to switch.

```bash
git checkout main
git checkout -b feature/login
```

### `git branch -m`

Purpose: rename current branch.

```bash
git branch -m feature/new-name
```

### `git branch -d`

Purpose: delete a branch only if it is merged.

```bash
git branch -d feature/login
```

### `git branch -D`

Purpose: force delete a branch.

```bash
git branch -D feature/login
```

### `git branch -d` / delete not possible

Purpose: if Git refuses to delete a branch because it is not merged, you must merge or keep it.

```bash
git branch -d feature/login
```

> If Git says the branch is not fully merged, use `git merge` or `git switch` to another branch before deleting.

### Recovering a deleted or mistaken branch

Purpose: if you accidentally deleted a branch or want to restore a branch you just removed, use `git reflog` to find the last commit and recreate the branch.

Example:

```bash
git reflog
# Output example:
# a1b2c3d HEAD@{0}: checkout: moving from feature/login to main
# d4e5f6a HEAD@{1}: commit: Add login page

# Recreate the deleted branch at the last known commit
git switch -c feature/login d4e5f6a
```

You can also restore it by commit hash:

```bash
git branch feature/login d4e5f6a
```

> There is no special `abort delete` command for branch deletion. The usual recovery is to use `git reflog` or a commit hash to recreate the branch.

## 9. Merge and rebase

### `git merge`

Purpose: combine branch changes into the current branch.

```bash
git switch main
git merge feature/login
```

What happens:
- Creates a merge commit unless fast-forward is possible.
- Keeps the full history of both branches.
- Good when you want to preserve branch context and commit history.

Example:

```bash
# main branch
A---B---C
         \
          D---E   feature/login

# after git merge feature/login into main
A---B---C---M
         \
          D---E
```

This creates a new merge commit `M`.

### `git rebase`

Purpose: move your branch onto a new base commit.

```bash
git switch feature/login
git rebase main
```

What happens:
- Replays your branch commits on top of the target branch.
- Produces a cleaner linear history.
- Good for keeping a feature branch up to date before merging.

Example:

```bash
# before rebase
A---B---C---D   main
     \
      E---F     feature/login

# after rebase
A---B---C---D---E'---F'   feature/login
```

This rewrites commit history, so use it carefully on shared branches.

### `git merge` vs `git rebase`

Use `git merge` when:
- you want to preserve branch history
- you are working on shared branches
- you want a non-destructive commit flow

Use `git rebase` when:
- you want a cleaner linear history
- your branch is private or not yet shared
- you want to update your branch with the latest main before merging

Example comparison:

```bash
# merge example
git switch main
git merge feature/login
```

```bash
# rebase example
git switch feature/login
git rebase main
```

### Conflict commands

```bash
git merge --abort
git rebase --continue
git rebase --abort
```

If conflicts happen:
- `git merge --abort` cancels the merge
- `git rebase --continue` continues after fixing conflicts
- `git rebase --abort` stops the rebase and restores the original branch state

### `git cherry-pick`

Purpose: apply a specific commit onto the current branch.

```bash
git cherry-pick a1b2c3d
git cherry-pick a1b2c3d f4e5d6c
```

## 10. Force push and safety

### `git push --force-with-lease`

Purpose: safely overwrite the remote branch only if it has not changed since your last fetch.

```bash
git push --force-with-lease
```

Use when:
- you rebased your branch
- you changed commit history locally
- you need to update the remote branch without deleting someone else's newer work

Why it is safer:
- Git checks whether the remote branch still matches the version you last saw.
- If someone pushed new commits in the meantime, the push is rejected.
- This prevents accidentally overwriting remote changes.

Example:

```bash
git fetch origin
git rebase origin/main
git push --force-with-lease
```

This is the preferred option for updating a branch after rewriting history.

### `git push --force`

Purpose: force-push and overwrite the remote branch regardless of recent changes.

```bash
git push --force
```

Use when:
- you are sure no one else has pushed to the same branch
- you intentionally want to overwrite remote history
- you are working alone or you already verified the remote state

Risk:
- It can delete other people's work on the same branch.
- It is dangerous on shared branches.

Example:

```bash
git rebase main
git push --force
```

> Prefer `--force-with-lease` over `--force` in team workflows. It is much safer because it checks for remote changes before overwriting them.

### Quick rule

- `git push --force-with-lease` = safer, recommended
- `git push --force` = risky, use only when you know exactly what you are doing

### When do you usually use force push?

- after `git rebase`
- after `git reset --hard` and needing to update the remote
- when you intentionally rewrite commit history on your own branch
