# SQL Server Instance Setup Guide

A complete walkthrough: what you get after installing SQL Server, how server logins work, how to create one, and how to connect via SSMS.

---

## 1. What You Get When You Install SQL Server

When you install **SQL Server Express** (or any edition), here's what gets set up on your machine:

### Installed components
- **Database Engine service** — runs in the background as a Windows service (e.g. `SQL Server (SQLEXPRESS)`)
- **An instance name** — either:
  - A **named instance** like `SQLEXPRESS` (default for the free Express installer) → accessed as `.\SQLEXPRESS`
  - Or the **default instance** `MSSQLSERVER` (no instance name needed) → accessed as `.` or `localhost`
- **System databases** created automatically:
  - `master` — tracks server-wide config, logins, and metadata
  - `model` — template for any new database you create
  - `msdb` — used by SQL Server Agent for jobs/scheduling
  - `tempdb` — scratch space for temporary objects, rebuilt on every restart
- **Windows Authentication enabled by default**, with your current Windows account automatically added as a `sysadmin`
- **SQL Server Browser service** (helps resolve named instances over the network — may need to be started manually)
- Optionally, **SQL Server Management Studio (SSMS)** — this is a *separate* download, not always bundled with the Express installer

### Example — checking what instance was installed
Open **Command Prompt** and run:
```
sqlcmd -L
```
Example output:
```
DESKTOP-ABC123\SQLEXPRESS
```
This tells you the instance name is `SQLEXPRESS`, running on machine `DESKTOP-ABC123`.

## 2. Server-Level Logins: Default vs. Ones You Create

### Default login you get out of the box

| Login | Type | Enabled by default? | Notes |
|---|---|---|---|
| `BUILTIN\Administrators` or `YourMachine\YourWindowsUser` | Windows Authentication | ✅ Yes | Auto-created during install, mapped to `sysadmin` |
| `sa` (system administrator) | SQL Authentication | ❌ Usually disabled | Only active if you chose "Mixed Mode" during install and set a password |

**Key point:** Fresh installs default to **Windows Authentication only**. There is no default SQL username/password combo waiting for you — `sa` exists as an account name, but it's disabled until you explicitly enable Mixed Mode and set its password.

### Logins you can create

| Login type | Use case | Example |
|---|---|---|
| **SQL Server Authentication** | App connection strings, cross-platform tools, non-domain scenarios | `AppUser` with password `StrongP@ss1!` |
| **Windows Authentication** | Trusted internal tools, domain-joined machines | `DOMAIN\jdoe` |

### Example — checking existing logins
Run this in SSMS or `sqlcmd` once connected:
```sql
SELECT name, type_desc, is_disabled
FROM sys.server_principals
WHERE type IN ('S','U','G')
ORDER BY name;
```
Example output:
```
name                        type_desc              is_disabled
--------------------------  ---------------------  -----------
sa                          SQL_LOGIN               1
DESKTOP-ABC123\Aman         WINDOWS_LOGIN            0
```

## 3. How to Create a Server Login to Use

### Step 1 — Enable Mixed Mode authentication (only needed for SQL logins)
1. In SSMS, right-click the server in **Object Explorer** → **Properties**
2. Go to the **Security** page
3. Under "Server authentication," choose **SQL Server and Windows Authentication mode**
4. Click **OK**
5. **Restart the SQL Server service** (via `services.msc`) — this step is required for the change to apply

### Step 2 — Create the login
**Example: creating a dedicated login for your Task Management API**
```sql
CREATE LOGIN AppUser
WITH PASSWORD = 'StrongP@ssw0rd!',
     DEFAULT_DATABASE = master,
     CHECK_POLICY = ON,
     CHECK_EXPIRATION = OFF;
```

### Step 3 — Map the login to a database as a user
A server login by itself can't touch any database — you need a matching database **user**:
```sql
USE TaskManagementDb;
GO
CREATE USER AppUser FOR LOGIN AppUser;
GO
ALTER ROLE db_datareader ADD MEMBER AppUser;
ALTER ROLE db_datawriter ADD MEMBER AppUser;
```

### Step 4 — (Optional) Grant broader server-level permissions
Only if the login genuinely needs it — avoid for app service accounts:
```sql
ALTER SERVER ROLE dbcreator ADD MEMBER AppUser; -- can create new databases
-- ALTER SERVER ROLE sysadmin ADD MEMBER AppUser; -- full control, use sparingly
```

### Step 5 — Test the new login
Disconnect in SSMS, then reconnect using:
- **Authentication**: SQL Server Authentication
- **Login**: `AppUser`
- **Password**: `StrongP@ssw0rd!`

## 4. How to Set Up / Connect to a SQL Server Instance with SSMS

### Step 1 — Open SSMS and find the "Connect to Server" dialog
Launches automatically when SSMS opens, or via **Object Explorer → Connect → Database Engine**.

### Step 2 — Enter the Server name
Try these in order until one connects:
```
.\SQLEXPRESS
(local)\SQLEXPRESS
localhost\SQLEXPRESS
DESKTOP-ABC123\SQLEXPRESS   (your actual computer name + instance)
```
If it installed as a default (unnamed) instance instead, just use:
```
.
```
or
```
(local)
```

### Step 3 — Choose Authentication
- **Windows Authentication** — no username/password needed, uses your logged-in account (works immediately after install)
- **SQL Server Authentication** — enter the login/password you created in Section 3

**Example (Windows Auth):**
```
Server name: DESKTOP-ABC123\SQLEXPRESS
Authentication: Windows Authentication
```

**Example (SQL Auth):**
```
Server name: DESKTOP-ABC123\SQLEXPRESS
Authentication: SQL Server Authentication
Login: AppUser
Password: StrongP@ssw0rd!
```

### Step 4 — If connection fails, check these services
Open `services.msc` and confirm these are **running**:
- `SQL Server (SQLEXPRESS)` — the engine itself
- `SQL Server Browser` — needed for named-instance resolution

### Step 5 — Verify TCP/IP is enabled (needed for app connections, not just SSMS)
1. Open **SQL Server Configuration Manager**
2. **SQL Server Network Configuration** → **Protocols for SQLEXPRESS**
3. Enable **TCP/IP** if disabled
4. Restart the SQL Server service afterward

### Step 6 — Create your database
Once connected, right-click **Databases** → **New Database**, or run:
```sql
CREATE DATABASE TaskManagementDb;
```

## if i can access.. server instance with windows authentication... why should i create a login?

Fair question — if Windows Auth already gets you in, why bother? A few real reasons this actually matters, especially 
given what you're building:

>> Your app doesn't "log in" the way you do

When you open SSMS, you are a person with a Windows session. But your ASP.NET Core API is a background process — it 
doesn't have "you" logged in when it runs. It needs its own identity to authenticate to SQL Server every time it 
starts up or opens a connection.

Windows Auth can work here too — the app process would run under a Windows/service account, and SQL Server trusts that 
account. This works fine as long as the app and SQL Server are on the same Windows domain/machine.
But the moment your app moves somewhere that Windows Auth doesn't reach, you need a SQL login instead.

## Final Connection String Examples

**Windows Authentication (good for local dev):**
```
Server=DESKTOP-ABC123\SQLEXPRESS;Database=TaskManagementDb;Trusted_Connection=True;TrustServerCertificate=True;
```

**SQL Server Authentication (good for app service accounts / non-Windows environments):**
```
Server=DESKTOP-ABC123\SQLEXPRESS;Database=TaskManagementDb;User Id=AppUser;Password=StrongP@ssw0rd!;TrustServerCertificate=True;
```

### Quick Reference Checklist
- [ ] Confirm instance name with `sqlcmd -L`
- [ ] Ensure `SQL Server` and `SQL Server Browser` services are running
- [ ] Connect once via Windows Auth to verify access
- [ ] Enable Mixed Mode if you need SQL logins
- [ ] Create a dedicated login (not `sa`) for your application
- [ ] Map that login to a database user with least-privilege roles
- [ ] Enable TCP/IP if your app will connect over the network
