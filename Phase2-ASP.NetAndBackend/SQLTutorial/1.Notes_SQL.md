# Server → Database → Schema

## High-level logical tree (big picture)

```text
SQL Server Instance
│
├── Logins (Server-level security)
│
├── Database A
│   ├── Users (Database-level security)
│   ├── Schemas
│   │   ├── dbo
│   │   │   ├── Tables
│   │   │   ├── Views
│   │   │   └── Stored Procedures
│   │   ├── sales
│   │   └── hr
│   │
│   └── Roles
│
├── Database B
│   ├── Users
│   ├── Schemas
│   └── Roles
```

## Explained

### 1. Server (top level)

#### What is a server?

- SQL Server instance
- Physical or virtual machine where SQL Server runs
- Controls authentication and connections

#### What belongs to a server?

- Logins
- Server roles
- Linked servers
- Tables, schemas, and users do not belong here (these are not server-level objects)

### 2. Login (server level)

#### What is a login?

- Used to connect to the SQL Server
- Authentication happens here
- Exists at server level

#### Types of logins

- Windows Login (`DOMAIN\User`)
- SQL Login (username + password)
- Azure AD Login

> 📌 A login does not automatically give access to a database.

### 3. Database

#### What is a database?

- Logical container for application data
- Each database is isolated
- The same login can access multiple databases if mapped

#### What belongs to a database?

- ✅ Users
- ✅ Schemas
- ✅ Tables, views, procedures
- ✅ Database roles

### 4. User (database level)

#### What is a user?

- A database-specific identity
- Maps to a login
- Controls what you can do inside that database

```text
Login (Server)
   ↓ mapped to
User (Database)
```

> **Note:** One login can map to many users, one per database.

### 5. Schema (inside database)

#### What is a schema?

- Logical container inside a database
- Used to group objects
- Also used for security

#### Common schemas

- `dbo` → default
- `sales`
- `hr`
- `reporting`

#### What belongs to a schema?

- ✅ Tables
- ✅ Views
- ✅ Stored procedures
- ✅ Functions

```text
Database
 └── Schema
     └── Table
```

## SQL Server vs SQL Server Management Studio (SSMS)

SQL Server and SQL Server Management Studio (SSMS) are two different things that are often confused because they are used together.

### SQL Server

- This is the actual database engine — the software that stores your data, runs your queries, enforces constraints, handles transactions, manages indexes, and so on.
- It runs as a background service (for example, `MSSQLSERVER` or a named instance) on a machine.
- Your application connects to it using a connection string (for example, through EF Core or ADO.NET) — no GUI is involved at that layer.
- Editions include Express (free, limited), Developer (free, full features for dev/test), Standard, and Enterprise.

### SQL Server Management Studio (SSMS)

- This is a free GUI tool used to connect to, manage, and query a SQL Server instance.
- You use it to write and run T-SQL, design tables, manage users and permissions, view execution plans, back up/restore databases, and monitor performance.
- It does not store data itself; it is just a client that talks to the SQL Server engine.
- A simple analogy: SQL Server is the actual database service, and SSMS is the remote control/dashboard for it.

> You could uninstall SSMS and SQL Server would still run normally; you would just lose the convenient GUI to manage it manually.

## Security relationship (very important)

### 🔐 Authentication vs authorization

| Level | What happens |
| --- | --- |
| Server | Login authenticates |
| Database | User authorizes |
| Schema | Permissions applied |
| Object | Read / Write / Execute |

## Complete security flow (end-to-end)

```text
Client
  ↓
Login (Server authentication)
  ↓
User (Database mapping)
  ↓
Schema (Permission boundary)
  ↓
Object (Table / View / Proc)
```

## Real example

### Step 1: Create login (server)

```sql
CREATE LOGIN app_login WITH PASSWORD = 'Strong@123';
```

### Step 2: Create database

```sql
CREATE DATABASE AppDB;
```

### Step 3: Create user (inside AppDB)

```sql
USE AppDB;
CREATE USER app_user FOR LOGIN app_login;
```

### Step 4: Create schema

```sql
CREATE SCHEMA sales;
```

### Step 5: Grant permission

```sql
GRANT SELECT, INSERT ON SCHEMA::sales TO app_user;
```

📌 Result:

- `app_login` can connect to the server.
- `app_user` can access `AppDB`.
- It can only work with objects in the `sales` schema.

> **Note:** One database can have only one user mapped to a specific login, but one login can map to many database users.

## Questions

### 1. Is it mandatory to create a database user under a login?

Yes, practically it is mandatory if you want a login to access a database.
However, a user can exist without a login in some cases.

**Is there an exception?**

#### ✔ Exception 1: `sysadmin` role

If the login is in the `sysadmin` server role:

- SQL Server automatically maps it to `dbo`
- No explicit user is needed
- It has full access to all databases

> ⚠️ Not recommended for applications because it is a major security risk.

#### Exception 2: Contained database user (no login)

You can create a user without a login:

```sql
USE MyDatabase;

CREATE USER ContainedUser
WITH PASSWORD = 'StrongPwd@123';
```

- No server login
- Authentication happens at the database level
- Used in Azure SQL and modern setups

👉 This is the reverse case: a user without a login.

### 2. If a database has a user without a login and I want to connect using a connection string, what happens?

👉 You cannot connect using a user without a login unless the database is a contained database.

👉 The connection string must explicitly specify the database.

#### What is a "user without login"?

```sql
CREATE USER AppUser
WITH PASSWORD = 'Strong@123';
```

- ✔ Database-level authentication
- ❌ No server-level login
- ✔ Works only in a contained database

#### Enable contained database (mandatory)

**Server level**

```sql
EXEC sys.sp_configure 'contained database authentication', 1;
RECONFIGURE;
```

**Database level**

```sql
ALTER DATABASE MyDB
SET CONTAINMENT = PARTIAL;
```

Without this, the connection will fail.

#### Connection string (this is the key part)

✅ Correct connection string:

```text
Server=MyServer;
Database=MyDB;
User Id=AppUser;
Password=Strong@123;
```

- ✔ Authentication happens inside `MyDB`
- ✔ No SQL Server login is required

❌ Wrong connection strings:

```text
Server=MyServer;
User Id=AppUser;
Password=Strong@123;
```

- ❌ Fails because SQL Server does not know this user
- ❌ The database must be specified

> **Note:** With a server login, it is not mandatory to provide a database name in the connection string.

# Basics: databases vs schemas

## Database

A database is a structured collection of related data that serves as a container for storing and managing information. It includes all the data, tables, records, constraints, and schema itself.

A database contains:

- Schemas
- Tables
- Views
- Stored procedures
- Functions
- Indexes
- Users and roles
- Configuration and metadata

## Schema

A schema is the blueprint or structural design of a database. It defines how the data is organized, including tables, fields, relationships, and constraints. In short, it provides the logical framework for storing and managing data within a database.

Think of it as:

> 📂 Folders inside a building

A schema contains:

- Tables
- Views
- Stored procedures
- Functions

---

## `dbo` vs custom schema

### `dbo` = database owner

- Default schema in SQL Server
- Owned by the database owner
- Exists automatically in every database
- If you do not specify a schema, SQL Server uses `dbo`

```sql
CREATE TABLE Employees
(
    Id INT,
    Name NVARCHAR(100)
);
```

👉 This is actually created as:

```text
dbo.Employees
```

Think of `dbo` as:

> 📂 The default folder where everything goes if you do not organize it

### What is a custom schema?

A custom schema is a user-defined logical container created to organize objects.

```sql
CREATE SCHEMA Sales;
CREATE SCHEMA HR;
```

Objects inside custom schemas:

```text
Sales.Orders
Sales.Customers
HR.Employees
HR.Payroll
```

| Aspect | `dbo` | Custom schema |
| --- | --- | --- |
| Created by default | ✅ Yes | ❌ No (manual) |
| Owner                      | Database owner        | Any user/role      |
| Purpose                    | Default container     | Logical separation |
| Security control           | Broad                 | Fine-grained       |
| Organization               | Poor (gets cluttered) | Excellent          |
| Recommended for production | ❌ No (alone)          | ✅ Yes              |

### Security Difference (Very Important ⭐)

❌ **Using only dbo**

If user has access to `dbo`, they often get access to everything.

✅ **Using Custom Schemas**

You can restrict access cleanly.

```sql
GRANT SELECT, INSERT ON SCHEMA::Sales TO SalesUser;
DENY SELECT ON SCHEMA::HR TO SalesUser;
```

👉 This is a major interview talking point

### Performance Aspect (Hidden but Important)

Schema-qualified names improve performance.

```sql
SELECT * FROM Orders;       -- slower (schema resolution)
SELECT * FROM Sales.Orders; -- faster
```

**Why?**

- SQL Server doesn't need to search default schemas
- Execution plan reuse improves

👉 `dbo.ObjectName` is faster only if user's default schema is `dbo`

### Entity Framework Example

```csharp
[Table("Orders", Schema = "Sales")]
public class Order
{
    public int Id { get; set; }
}
```

EF generates:

```sql
SELECT * FROM Sales.Orders;
```

### Common Interview Traps

**Q: Is `dbo` a user?**

👉 ❌ No, it's a schema

**Q: Can two schemas have tables with same name?**

👉 ✅ Yes

```text
Sales.Users
HR.Users
```

**Q: Is schema physical storage?**

👉 ❌ No, logical only

### Create Table Under a Specific Schema ✅

Example:

```sql
CREATE TABLE Sales.Orders
(
    OrderId INT PRIMARY KEY,
    OrderDate DATETIME,
    Amount DECIMAL(10,2)
);
```

### Set Default Schema for a User (Optional)

So objects go to a schema automatically:

```sql
CREATE USER AppUser FOR LOGIN AppLogin;
ALTER USER AppUser WITH DEFAULT_SCHEMA = Sales;
```

Now:

```sql
CREATE TABLE Orders (...);
```

➡️ Created as:

```text
Sales.Orders

# dbo user vs dbo schema

`dbo user` ≠ `dbo schema`

| Item           | What it is                               |
| -------------- | ---------------------------------------- |
| **dbo user**   | A **database user** (security principal) |
| **dbo schema** | A **schema** (object container)          |

They are related by default, but not the same thing.

## 1. dbo User

### 🔹 What is dbo user?

- A special database user
- Stands for Database Owner
- Exists in every database
- Has full permissions inside the database

### 🔹 Who maps to dbo user?

- Any login that is a member of `sysadmin` server role
- Or the database owner (`owner_sid`)

> 📌 `dbo` user bypasses permission checks

### Key Properties of dbo user

- ✔ Cannot be dropped
- ✔ Cannot be renamed
- ✔ Always exists
- ✔ Has implicit access to everything

### Example

If a sysadmin connects:

```sql
SELECT USER_NAME();
```

Result:

```text
dbo
```

Even if login name is `Aman`, inside DB you are `dbo`.

## 2. dbo Schema

### 🔹 What is dbo schema?

A schema:

- Logical container for database objects
- Default schema for new objects

### 🔹 What lives inside dbo schema?

- ✔ Tables
- ✔ Views
- ✔ Stored procedures
- ✔ Functions

### Example

```text
dbo.Customers
dbo.Orders
dbo.GetReport
```

# Connection string if want to connect all dbs under server login

No database system lets you connect to “all databases at once” in a single connection string. A connection string always
targets one database (or service/schema) at a time.

## 🔑 SQL Server

- **Server login:** Defined at the SQL Server instance level.
- **Database user:** A mapping of that login inside each database.
- **Connection string:** Always uses the server login (`User Id=...;Password=...`).
- Once connected, if that login is mapped to users in multiple databases, you can:
  - Run `USE <DatabaseName>;` to switch context, or
  - Query cross-database directly (`SELECT * FROM HRDB.dbo.Employees;`).
- So in SQL Server, you use the server login in the connection string, not the per-database user.

In SQL Server, you can switch databases within the same session if your server login (e.g. `appuser`) has
been granted access to more than one database.

## ✅ Summary

- **SQL Server / MySQL / Postgres** → Use the server login (user at instance level) in the connection string. That login must be
  mapped/privileged in each database you want to access.
- **Oracle** → Use the database user (schema) in the connection string, because Oracle doesn't support multiple databases under
  one instance.

# Should I use diff databases or schemas?

Use different databases when you need complete isolation (separate backups, security, performance tuning), and use schemas
when you want logical separation but still share infrastructure. In practice, schemas are lighter and easier to manage,
while multiple databases give stronger boundaries.

## 📌 When to Use Different Databases

- **Multi-tenant SaaS:** Each customer gets their own DB for isolation.
- **Different Applications:** Separate lifecycle, backups, and performance needs.
- **Compliance:** Legal or regulatory requirements for strict separation.
- **Disaster Recovery:** Easier to restore one DB without affecting others.

## 📌 When to Use Schemas

- **Single Application, Multiple Modules:** e.g., HR, Finance, Sales in one DB.
- **Logical Separation:** Organize tables/views without overhead of multiple DBs.
- **Shared Infrastructure:** Easier to query across schemas.
- **Development Environments:** Keep dev/test/prod schemas in one DB for convenience.

## ✅ Recommendation

- If you're building one application with related modules, use schemas.
- If you're building separate applications or need strict isolation, use different databases.

# Server login vs database user login

Great question — the choice between using a server login or a database user login depends on your environment and security needs. Let's break it down:

## 1. Server Login (SQL Server Authentication)

- Created at the server level.
- Can access multiple databases if permissions are granted.
- Requires a username and password stored in SQL Server.

**Useful when:**

- You need cross-database access.
- You want a single login for multiple apps.
- Windows Authentication isn't available.

## 2. Database User Login

- Created at the database level.
- Tied to a specific database only.
- Can be mapped to a server login or created as a contained user (independent of the server).

**Useful when:**

- You want tighter security (limit access to one database).
- You're working in a contained database environment.
- You want easier migration of databases without worrying about server-level logins.

## Best Practice

- For enterprise setups, use server logins with proper role-based permissions.
- For contained databases or when you want isolation, use database users.
- Always follow the principle of least privilege: give only the access needed, nothing more.

👉 **In short:**

- Use server login if you need access across multiple databases or centralized management.
- Use database user login if you want to restrict access to just one database or simplify migrations.
