# Remote Work: Fetch, Pull, Push

This section explains the commands used to sync your local repository with a remote repository.

---

## 1. `git fetch`

### Purpose
Download remote changes without changing your current branch or working files.

### Syntax
```
>> Common fetch usages
> Fetch from default remote
git fetch origin

> Fetch a specific branch
git fetch origin main

> Fetch all remotes
```
### Why it matters
- safe way to review upstream changes
- does not modify your working files
- often used before merging

### Example

```bash
git fetch origin
git log main..origin/main
git diff main origin/main
```

### Important note
`git fetch` does not update your local branch automatically.

---

## 2. `git pull`

### Purpose
Fetch remote changes and merge or rebase them into your current branch.

### Syntax

```bash
git pull origin main
git pull --rebase
```

### Under the hood
`git pull = git fetch + merge` or `git fetch + rebase` depending on config.

### Example

```bash
git pull origin main
```

### Danger
`git pull` can create merge conflicts if your local work overlaps with remote changes.

---

## 3. `git push`

### Purpose
Send your local commits to the remote repository.

### Syntax

```bash
git push origin main
git push -u origin feature/login
git push
```

### Example

```bash
git push -u origin feature/login
```

### What `-u` means
`-u` = `--set-upstream`

It tells Git to remember the remote branch mapping between your local and remote branch.

### Common scenarios

```bash
git push origin develop
git push --all
```

---

## 4. `git push --force-with-lease` vs `git push --force`

### Why force push exists

A force push is needed when:
- you rebased a branch
- you rewrote commit history
- the remote history no longer matches your local history

### `git push --force`

```bash
git push --force
```

This overwrites remote history without checking whether others changed the branch.
What it does

- Overwrites the remote branch
- Deletes any commits on remote that you don’t have locally
- Does not care if someone else pushed meanwhile

Example (data loss)

You:        A─B─C'
Teammate:   A─B─D   (pushed)

git push --force

Result:

Remote: A─B─C'
❌ Teammate’s commit D is gone

### `git push --force-with-lease`

```bash
git push --force-with-lease
```

This is safer because Git refuses to push if the remote branch changed after your last fetch.

### Best practice

Use `--force-with-lease` whenever you are rewriting branch history.

---

## 5. Safe recovery flow after a rejected push

When Git rejects a force push or a push due to non-fast-forward issues, use this approach:

```bash
git fetch origin
git log --oneline --graph --decorate HEAD..origin/your-branch
git diff HEAD origin/your-branch
git rebase origin/your-branch
git add <fixed-files>
git rebase --continue
git push --force-with-lease
```

### If things go wrong

```bash
git rebase --abort
git merge --abort
```

## 9. `git revert` vs `git reset` vs `git restore`

These three commands look similar, but they do different things.

### 1. `git restore`

Purpose: undo file changes or unstage files without affecting commit history.

Use cases:
- discard changes in a file
- unstage a file from the index
- restore a file from an earlier commit

Examples:

```bash
git restore file.txt
```

This resets the file in the working directory to the last committed version.

```bash
git restore --staged file.txt
```

This unstages the file but keeps local edits.

```bash
git restore --source=HEAD~1 file.txt
```

This restores the file from the previous commit.

Important:
- does not move HEAD
- does not rewrite commit history
- best for local file-level undo

### 2. `git reset`

Purpose: move the current branch backward in history.

Use cases:
- undo one or more commits
- unstage changes
- completely remove recent changes from the branch pointer

Examples:

```bash
git reset --soft HEAD~1
```

This moves HEAD back one commit and keeps changes staged.

```bash
git reset --mixed HEAD~1
```

This moves HEAD back one commit and unstages changes.

```bash
git reset --hard HEAD~1
```

This moves HEAD back one commit and permanently removes all changes from working directory and index.

Important:
- rewrites branch history
- risky on shared branches
- use carefully when the branch is already pushed

### 3. `git revert`

Purpose: create a new commit that undoes an older commit, without rewriting history.

Use cases:
- undo a commit safely on a shared branch
- keep history intact while reversing a change

Example:

```bash
git revert HEAD
```

This creates a new commit that reverses the latest commit.

```bash
git revert a1b2c3d
```

This creates a new commit that undoes the specific commit `a1b2c3d`.

Important:
- safe for shared branches
- does not delete history
- creates a new commit instead of rewriting existing ones

### Quick comparison

| Command | Changes history | Touches working tree | Best for |
| --- | --- | --- | --- |
| `git restore` | No | Yes | undo file edits / unstage |
| `git reset` | Yes | Yes | move branch back / remove commits |
| `git revert` | No (new commit created) | Yes | undo a commit safely |

### Example scenario

Suppose you made 3 commits and want to undo the latest one safely:

```bash
git revert HEAD
```

If you want to completely remove the latest commit and keep the changes for editing again:

```bash
git reset --soft HEAD~1
```

If you want to completely discard the last commit and all changes:

```bash
git reset --hard HEAD~1
```

If you only want to throw away file changes without affecting history:

```bash
git restore file.txt
```

## 10. `git reset` vs `git restore`

### `git restore` (file-focused, safer)

Use it when you want to undo file changes or unstage files, without touching commit history.

Examples:

```bash
git restore Program.cs
```

```bash
git restore --staged Program.cs
```

```bash
git restore --source=HEAD~1 Program.cs
```

Rule: `git restore` never moves `HEAD`.

### `git reset` (history-focused, powerful)

Use it when you want to move the branch pointer backward, rewrite history, or undo commits.

Examples:

```bash
git reset --soft HEAD~1
git reset --mixed HEAD~1
git reset --hard HEAD~1
```

Rule: `git reset` changes the current branch state and can modify commit history.

---

## 11. Final cheat sheet

```bash
git restore file.txt
git restore --staged file.txt
git restore --source=HEAD~1 file.txt
git reset --soft HEAD~1
git reset --mixed HEAD~1
git reset --hard HEAD~1
git revert HEAD
```

Use these commands carefully depending on whether you want to undo a file, unstage, rewrite history, or make a safe reversal commit.

Use it when you want to move HEAD to another commit. Depending on the mode, it can also affect staging and files.

### Three reset modes (VERY important)

1️⃣ --soft (history only)

git reset --soft HEAD~1

- Moves HEAD back
- Keeps changes staged
- Use to edit last commit message/content

2️⃣ --mixed (default)

git reset HEAD~1

- Moves HEAD back
- Unstages changes
- Keeps file edits

Most common reset.

3️⃣ --hard (danger ?)

git reset --hard HEAD~1

- Moves HEAD back
- Clears staging
- Deletes file changes

Use only if you’re sure.

### When to use which (decision guide)
Use git restore when:

- You staged the wrong file
- You want to discard file changes
- You don’t want to touch commits
        
        git restore --staged .

Use git reset when:

- You want to undo a commit
- You want to rewrite local history
- You understand HEAD/staging well

## git revert 

git revert undoes a commit by creating a new commit that reverses its changes.
? “Don’t change history—add a new commit that cancels an old one.”

### Why you should use git revert

- Safe for shared branches (main, develop)
- No history rewriting
- Teammate-friendly
- Ideal for production hotfixes

If a bad commit is already pushed → revert, don’t reset.

### Basic usage

1. Revert a single commit
git revert <commit-hash>

Example:
git revert a1b2c3d

What happens:

- Git opens an editor with a default message
- A new commit is created
- Changes from a1b2c3d are reversed

2. Revert the last commit

git revert HEAD

3. Revert multiple commits
Revert a range (oldest → newest)

git revert a1b2c3d..f4e5d6c

⚠️ Note: This reverts commits after a1b2c3d up to f4e5d6c.

### Conflicts during revert

Yes, reverts can conflict (same rules as merge).

Fix flow : 

// resolve conflicts
git add <files>
git revert --continue

Abort if needed:

git revert --abort

### ? Rule of thumb
cherr
- Public/shared branch → revert
- Local/private branch → reset

## git reflog

git reflog records every move of HEAD in your local repo.
? “Even if a commit looks deleted, Git remembers where you were.”

This is how you recover from:

- git reset --hard
- bad rebase
- accidental branch delete
- lost commits

### Why git reflog is powerful

Git normally shows reachable history (git log).
Reflog shows where you’ve been, even if those commits aren’t reachable anymore.

If you did it locally, reflog knows about it.

### Basic usage
git reflog

Example output:

a1b2c3d HEAD@{0}: reset: moving to HEAD~1
d4e5f6a HEAD@{1}: commit: Add validation
9f3a12c HEAD@{2}: commit: Initial login logic

How to read this

HEAD@{0} → current state
HEAD@{1} → previous position
Each line = a HEAD movement

### Common recovery scenarios (REAL LIFE)

1️⃣ Recover from git reset --hard
Oops moment ?
git reset --hard HEAD~1

Save yourself :
git reflog

Find the commit before reset, then:

git reset --hard HEAD@{1}

? Commit restored.

2️⃣ Recover a deleted branch

git branch -D feature/login

Recover:
git reflog

Find last commit on that branch:

git checkout -b feature/login a1b2c3d

Branch is back.

3️⃣ Undo a bad rebase
git rebase main   # went wrong

Recover:

git reflog
git reset --hard HEAD@{3}

Back to safety.

# Stash & clean

## git stash 

Git stash is a Git command that allows you to temporarily save uncommitted changes in 
your working directory and index, so you can switch branches, fix urgent issues, or 
work on something else without committing incomplete work

Key Uses of git stash :

- Switch branches safely: Save changes without committing, then switch to another branch. 
- Handle emergencies: Stash work to fix a critical bug, then return to your original task. 
- Keep work-in-progress safe: Avoid messy commits or losing unfinished changes

Basic Commands
- git stash – Saves current changes and reverts your working directory to match the HEAD commit.
- git stash list – Shows all saved stashes (e.g., stash@{0}, stash@{1}).
- git stash pop – Applies the most recent stash and removes it from the list. 
- git stash apply – Applies a stash but keeps it in the list for later use. 
- git stash save "message" – (Deprecated) Adds a descriptive message to the stash (use git stash push -m "message" instead).
- git stash push -m "WIP: feature name" – Stash with a custom message for better tracking.

>> Stash including untracked files
git stash -u

>> See stash list
git stash list

Example:
stash@{0}: WIP on feature/login

>> Drop stash
git stash drop stash@{0}

## Git Clean

git clean deletes untracked files/folders.
⚠️ Permanent. No undo.

>> Always preview first (VERY IMPORTANT)
git clean -n

Shows what will be deleted.

>> Delete untracked files
git clean -f

>> Delete untracked files + directories
git clean -fd

### Senior developer habit 🧠

>> Before risky operations:
git stash -u

>> When workspace messy:
git clean -fd

>> Always preview clean with -n

# Tags & releases

## git tag
Git tags are used to label specific, important points in a project's history, such as release versions (e.g., v1.0, v2.0). 
They are like a permanent bookmark to a specific commit and, unlike branches, do not move. 

A tag is like a branch that doesn’t change. Unlike branches, tags, after being created, have no further history of commits. 

- Tags label fixed points in Git history.
- Unlike branches, tags do not move.
- Commonly used for version releases.
- Help easily identify and revisit important commits.

Example:

v1.0  → commit abc123

Even if branches move forward,
the tag always stays there.

Why tags matter

Used for:

- Releases
- Rollbacks
- Production deployments
- Customer builds
- CI/CD triggers

Without tags → version tracking becomes chaos.

>> Types of Tags

- Lightweight tags: These are simple pointers or bookmarks to a specific commit, with no extra information.
- Annotated tags: These are stored as full objects in the Git database and contain metadata such as the tagger's name,      
                  email, date, and a message. Annotated tags are generally recommended for public releases.    

1️⃣ Lightweight tag
    Just a name → to current commit.
    e.g : 
    git tag v1.0

Fast, simple, minimal.

2️⃣ Annotated tag (recommended)

Includes: author, date, message

e.g : 
git tag -a v1.0 -m "First production release"

This is what teams normally use.

>> commands 

- git tag  
  Lists all existing tags.  
  Example: git tag

- git tag <tagname>  
  Creates a lightweight tag at the current commit.  
  Example: git tag v1.0

- git tag -a <tagname> -m "message"  
  Creates an annotated tag with a message.  
  Example: git tag -a v1.1 -m "First stable release"

- git tag <tagname> <commit-hash>  
  Tags a specific past commit.  
  Example: git tag v1.2 9fceb02

- git show <tagname>  
  Shows tag details and commit info.  
  Example: git show v1.1

- git push origin <tagname>  
  Pushes a single tag to the remote repository.  
  Example: git push origin v1.1

- git push origin --tags  
  Pushes all local tags to the remote repository.  
  Example: git push origin --tags

- git tag -d <tagname>  
  Deletes a tag from the local repository.  
  Example: git tag -d v1.0

- git push origin --delete <tagname>  
  Deletes a tag from the remote repository.  
  Example: git push origin --delete v1.0

- git checkout -b <branchname> <tagname>  
  Creates a new branch from a tag, avoiding detached HEAD.  
  Example: git checkout -b version2 v2.0.0

A detached HEAD in Git occurs when the HEAD pointer references a specific commit hash directly instead of a branch name. 
While you can explore or test code in this state, new commits are not associated with any branch and may be lost.

It is typically fixed by creating a new branch via git checkout -b <new-branch-name>. and further merge it to the

# git submodule
must watch : https://youtu.be/JESI498HSMA

A submodule lets your project include another Git repository as a dependency inside a folder.

Why teams use submodules

Common in real systems:

✅ Shared libraries
✅ SDKs
✅ vendor code
✅ large components maintained by another team
✅ infrastructure templates

What Git actually stores

Your repo does not copy the submodule files.
Instead, it stores:

- the repo URL
- the exact commit to use
- So builds are repeatable.

>> Add a submodule
git submodule add https://github.com/company/auth-lib.git libs/auth

What happens:

your-repo/
  libs/auth/   ← separate git repo
  .gitmodules

Commit this:
git commit -m "Add auth submodule"

>> Clone a repo WITH submodules

Normal clone is not enough ❌

git clone <repo>

Submodule folders will be empty.

Correct way ✅
git clone --recurse-submodules <repo>

If you already cloned
git submodule update --init --recursive
