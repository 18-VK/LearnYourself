# Default editor 
Why Git needs an editor

Git opens an editor when:

- You run git commit (without -m)
- You resolve a merge
- You rebase interactively

If not configured, Git may open:

vi (confusing for beginners 😅)

## Set editor (choose ONE)

1. VS Code (recommended)
git config --global core.editor "code --wait"

2. Notepad++ (Windows)
git config --global core.editor "'C:/Program Files/Notepad++/notepad++.exe' -multiInst -nosession -wait"

Verify : 

git config --global core.editor
📌 --wait is mandatory, or Git won’t know when you finished editing.

# Line Endings (CRLF vs LF) — VERY IMPORTANT 🔥

This is where many devs suffer without knowing why.

>> What is the problem?

Different OS use different line endings:

| OS            | Line ending   |
| ------------- | ------------- |
| Windows       | CRLF (`\r\n`) |
| Linux / macOS | LF (`\n`)     |

Git sees this as file changes, even when code is identical.

>> What Git is trying to solve

Git stores files internally as:
LF only

Then converts on checkout / commit based on config.

## Correct settings (DO THIS)

1. If you are on Windows (most likely)
git config --global core.autocrlf true

Meaning:

Checkout → CRLF
Commit → convert to LF

✅ Best for Windows users
✅ Avoids constant diff noise

2. If you are on Linux / macOS
git config --global core.autocrlf input

Meaning:

Checkout → LF
Commit → convert CRLF → LF

## NEVER use this (unless you know why)

git config --global core.autocrlf false

This causes:

- Inconsistent line endings
- Random diffs
- Team conflicts

## Verify your setting
git config --global core.autocrlf

output - true means git config --global core.autocrlf true

# Common mistakes to avoid 🚨

❌ Forgetting --wait with VS Code
❌ Mixing CRLF/LF in same repo
❌ Changing autocrlf mid-project without re-normalizing
❌ Using different emails unknowingly

# .git folder — PURPOSE (very important)
What is .git?

.git is a database + configuration store that Git uses to manage the repository.

📌 If you delete .git → your repo is destroyed (history gone)

What’s inside .git (high-level)

.git/
├── config        ← repo-specific config
├── HEAD          ← current branch reference
├── objects/      ← all commits, trees, blobs
├── refs/         ← branches & tags
├── index         ← staging area
└── logs/         ← reflog (history safety net)

# Working tree vs staging area vs repository

1️⃣ Working Tree (your actual files)
What it is

- The files you see in your project folder
- Where you write and edit code
- Not tracked yet (until you tell Git)

2️⃣ Staging Area (aka Index)
What it is

- A pre-commit buffer
- Lets you choose exactly what goes into the next commit
- Lives inside .git/index

📌 Think of it as:

“Files I approve for the next snapshot”

Add files to staging

git add Program.cs

Now Git says:

Changes to be committed

3️⃣ Repository (committed history)
What it is

- The permanent, immutable history
- Stored in .git/objects
- Each commit is a snapshot

📌 Once committed:

- It’s part of history
- Can be pushed to GitHub
- Can be checked out later

Commit staged changes
git commit -m "Add initial logic"

# Undoing changes at each Git level

Each level has its own undo command.

1️⃣ Working Tree — git restore <file>
Situation

- You edited a file
- You have NOT staged it yet
- You want to discard those edits

Command :
git restore file.txt

What it does

- Replaces the file with the last committed version
- Discards all uncommitted changes in that file

📌 Think:

“Throw away my local edits”

Example :

git status
//modified: app.cs

git restore app.cs

2️⃣ Staging Area — git restore --staged <file>
Situation

- You ran git add
- File is staged
- You want to unstage, not delete changes

Command :
git restore --staged file.txt

What it does

- Removes the file from the staging area
- Keeps changes in the working tree

📌 Think:

“I staged too early — unstage it”

Example
git add app.cs
git status

//Changes to be committed

git restore --staged app.cs

After this:

- File is modified
- Not staged
