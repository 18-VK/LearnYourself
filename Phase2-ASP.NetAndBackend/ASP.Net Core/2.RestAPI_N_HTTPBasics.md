# REST API / RESTful API

A REST API (Representational State Transfer Application Programming Interface) is an architectural style for designing networked applications that uses
standard HTTP methods to enable communication between different software systems. It is a widely adopted, lightweight, and scalable approach for building web
services, especially for web and mobile applications.

## Key Concepts

- **Resources & URIs:**
  Data is managed as resources, uniquely identified by URLs.
- **HTTP Methods:**
  Standard verbs define actions, mapping to CRUD operations: `GET` (read), `POST` (create), `PUT` (update), `DELETE` (remove), and `PATCH` (partial update).
- **Representations:**
  Clients interact with resource states, commonly formatted in JSON or XML.
- **Statelessness:**
  Requests contain all necessary information, as the server stores no client context between calls, improving scalability.

# HTTP Basics - Methods and status codes

**Idempotent** means calling the operation multiple times has the same effect as once (e.g., `DELETE /resource` twice = resource removed).

## Http Methods

### GET

**Meaning:** Read a resource. Must not change server state.

**Safe?** Yes. **Idempotent?** Yes.

**Request (fetch product):**

```bash
curl -i "https://api.example.com/products/5" \
  -H "Accept: application/json"
```

### POST

**Meaning:** Create a new resource or trigger a non-idempotent action.

**Safe?** No. **Idempotent?** No (unless server implements idempotency keys).

**Request (create order):**

```bash
curl -i -X POST "https://api.example.com/orders" \
  -H "Content-Type: application/json" \
  -d '{"customerId":42,"items":[{"productId":7,"quantity":2}]}'
```

**Tip:** Use an `Idempotency-Key` header for payment/order endpoints to avoid duplicates.

### PUT

**Meaning:** Replace a resource entirely (send full representation).

**Safe?** No. **Idempotent?** Yes.

**Request (replace user):**

```bash
curl -i -X PUT "https://api.example.com/users/10" \
  -H "Content-Type: application/json" \
  -d '{"id":10,"name":"Aman Kumar","email":"aman@example.com"}'
```

**Response (204 No Content)** — replacement succeeded, no body:

```http
HTTP/1.1 204 No Content
```

Or server may return `200 OK` with the updated resource.

### PATCH

**Meaning:** Partial update of a resource (only changed fields).

**Safe?** No. **Idempotent?** Usually not guaranteed, but often implemented to be idempotent.

**Request (partial update email):**

```bash
curl -i -X PATCH "https://api.example.com/users/10" \
  -H "Content-Type: application/json" \
  -d '{"email":"new@example.com"}'
```

**Response (200 OK):**

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "id":10, "name":"Aman Kumar", "email":"new@example.com" }
```

### DELETE

**Meaning:** Remove a resource.

**Safe?** No. **Idempotent?** Yes (deleting twice has same result).

**Request:**

```bash
curl -i -X DELETE "https://api.example.com/orders/834"
```

**Response (204 No Content):**

```http
HTTP/1.1 204 No Content
```

If resource not exist → `404 Not Found`.

### HEAD

**Meaning:** Same as GET but only return headers (no body). Useful to check existence or metadata.

**Idempotent?** Yes.

**Request:**

```bash
curl -I "https://api.example.com/products/5"
```

**Response:**

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 234
ETag: "v3"
```

### OPTIONS

**Meaning:** Discover supported HTTP methods on a resource (CORS preflight uses this).

**Response:**

```http
HTTP/1.1 204 No Content
Allow: GET, POST, PUT, DELETE, OPTIONS
```

| Method | Operation              | Example      |
| ------ | ---------------------- | ------------ |
| GET    | Retrieve data          | Get user     |
| POST   | Create resource        | Create order |
| PUT    | Update entire resource | Update user  |
| PATCH  | Partial update         | Update email |
| DELETE | Delete resource        | Delete order |

## Common status codes (grouped) — meaning + example usage

### 2xx — Success

**200 OK** — successful GET/PUT/PATCH returning body.
Example: `GET /products/5` returned product (see above).

**201 Created** — POST created a resource; include `Location` header.
Example: `POST /orders` → `201 Created` + `Location: /orders/834`.

**204 No Content** — success, no body (common for DELETE or successful PUT when server doesn't return body).

### 3xx — Redirection / caching

**301 Moved Permanently / 302 Found** — redirection (web pages).

**304 Not Modified** — used with `If-None-Match` / `If-Modified-Since` for caching (see conditional GET).

### 4xx — Client errors

**400 Bad Request** — malformed JSON, invalid params.

Example response body:

```json
{"type":"https://example.com/probs/invalid-request","title":"Bad Request","status":400,"detail":"Invalid JSON"}
```

**401 Unauthorized** — missing/invalid authentication.
Header: `WWW-Authenticate: Bearer`

**403 Forbidden** — authenticated but not permitted.

**404 Not Found** — resource does not exist.

**409 Conflict** — conflicting state (duplicate unique constraint).
Example: trying to create user with existing email.

**422 Unprocessable Entity** — semantic validation failed (e.g., field validation).

Example:

```json
{"status":422,"errors":{"email":["Invalid email format"]}}
```

**429 Too Many Requests** — rate-limiting; include `Retry-After` header.

### 5xx — Server errors

**500 Internal Server Error** — unexpected server failure (log details server-side; don't leak stack traces).

**503 Service Unavailable** — maintenance or overloaded. Use `Retry-After` header to indicate when to retry.

## Quick cheat sheet (one-liners)

- `GET` → 200 or 304
- `POST` → 201 (Location) or 400/422
- `PUT` → 200/204 or 404
- `PATCH` → 200/204 or 404
- `DELETE` → 204 or 404
- `HEAD` → headers only (200)
- `OPTIONS` → 204 + Allow
