# Cookie Authentication & Authorization in ASP.NET Core

A complete step-by-step guide in two parts:

- **Part 1:** Manual cookie authentication (full control, no Identity)
- **Part 2:** Cookie authentication with ASP.NET Core Identity

---

## The Big Picture

```
Register -> hash password -> store user
Login    -> validate credentials -> SignInAsync -> browser gets encrypted cookie
Request  -> cookie sent automatically -> middleware decrypts + validates -> User populated -> [Authorize] checks
Logout   -> SignOutAsync -> cookie deleted
```

The framework encrypts and signs the principal into the cookie using the Data Protection API, so there is no server-side session by default.

---

# Part 1: Manual Cookie Authentication

## Step 1: User entity and DbContext

```csharp
public class AppUser
{
    public int Id { get; set; }
    public string Email { get; set; } = default!;
    public string PasswordHash { get; set; } = default!;
    public string Role { get; set; } = "User";
    public bool IsActive { get; set; } = true;
    public string SecurityStamp { get; set; } = Guid.NewGuid().ToString("N");
    public DateTime CreatedUtc { get; set; } = DateTime.UtcNow;
}

public class AppDbContext : DbContext
{
    public AppDbContext(DbContextOptions<AppDbContext> options) : base(options) { }
    public DbSet<AppUser> Users => Set<AppUser>();

    protected override void OnModelCreating(ModelBuilder b)
    {
        b.Entity<AppUser>().HasIndex(u => u.Email).IsUnique(); // DB-level duplicate protection
    }
}
```

`SecurityStamp` is a random value you change whenever credentials or roles change. It lets you invalidate old cookies (Step 7).

## Step 3: How validation works (three layers)

| Layer | When | What it checks | Who does it |
|---|---|---|---|
| **1. Input validation** | Before your action runs | Required fields, email format, length, password match | DataAnnotations + `[ApiController]` (auto-returns `400` when `ModelState` is invalid) |
| **2. Credential validation** | Inside login | User exists, account active, password hash matches | Your service + `PasswordHasher<T>` |
| **3. Cookie validation** | Every later request | Cookie authentic, unexpired, user still valid | Cookie middleware + `OnValidatePrincipal` |

Layer 1 is free with `[ApiController]`. For MVC views, check `if (!ModelState.IsValid) return View(dto);` yourself. For stricter password rules, add `[RegularExpression]` or check in the service.

## Step 4: User service (register + credential validation)

```csharp
public class UserService
{
    private readonly AppDbContext _db;
    private readonly IPasswordHasher<AppUser> _hasher;

    public UserService(AppDbContext db, IPasswordHasher<AppUser> hasher)
    {
        _db = db;
        _hasher = hasher;
    }

    // ---------- REGISTER ----------
    public async Task<AppUser?> RegisterAsync(RegisterDto dto)
    {
        var email = dto.Email.Trim().ToLowerInvariant();   // normalise

        if (await _db.Users.AnyAsync(u => u.Email == email))
            return null;                                   // duplicate

        var user = new AppUser { Email = email, Role = "User" };
        user.PasswordHash = _hasher.HashPassword(user, dto.Password);  // salted + slow hash

        _db.Users.Add(user);
        await _db.SaveChangesAsync();
        return user;
    }

    // ---------- CREDENTIAL VALIDATION ----------
    public async Task<AppUser?> ValidateAsync(string emailInput, string password)
    {
        var email = emailInput.Trim().ToLowerInvariant();
        var user = await _db.Users.SingleOrDefaultAsync(u => u.Email == email && u.IsActive);
        if (user is null) return null;

        var result = _hasher.VerifyHashedPassword(user, user.PasswordHash, password);

        if (result == PasswordVerificationResult.Failed) return null;

        if (result == PasswordVerificationResult.SuccessRehashNeeded)
        {   // hashing algorithm/iterations were upgraded; transparently re-hash
            user.PasswordHash = _hasher.HashPassword(user, password);
            await _db.SaveChangesAsync();
        }
        return user;
    }
}
```

**How registration works**

1. Model validation passes (layer 1).
2. Normalise the email so `A@x.com` and `a@x.com` are the same account.
3. Reject duplicates. The unique index is the final safety net against race conditions.
4. `HashPassword` generates a random salt and runs PBKDF2 with many iterations. The result is one string containing algorithm version, salt, and hash. Never store or log the plain password.
5. Save the user. Registration does not need to touch cookies; redirect to login, or call `SignInAsync` right after.

**How credential validation works:** `VerifyHashedPassword` extracts the salt from the stored hash, hashes the supplied password the same way, and compares in constant time. Return the same generic error for "no such user" and "wrong password" so attackers can't discover which emails are registered.

## Step 5: Auth controller

```csharp
[ApiController]
[Route("api/auth")]
public class AuthController : ControllerBase
{
    private readonly UserService _users;
    public AuthController(UserService users) => _users = users;

    [HttpPost("register")]
    [AllowAnonymous]
    public async Task<IActionResult> Register(RegisterDto dto)
    {
        var user = await _users.RegisterAsync(dto);
        if (user is null)
            return Conflict(new { message = "Email is already registered." });

        return CreatedAtAction(nameof(Me), new { }, new { user.Id, user.Email });
    }

    [HttpPost("login")]
    [AllowAnonymous]
    public async Task<IActionResult> Login(LoginDto dto)
    {
        var user = await _users.ValidateAsync(dto.Email, dto.Password);
        if (user is null)
            return Unauthorized(new { message = "Invalid email or password." });

        var claims = new List<Claim>
        {
            new(ClaimTypes.NameIdentifier, user.Id.ToString()),
            new(ClaimTypes.Name, user.Email),
            new(ClaimTypes.Role, user.Role),
            new("security_stamp", user.SecurityStamp)
        };

        var identity  = new ClaimsIdentity(claims, CookieAuthenticationDefaults.AuthenticationScheme);
        var principal = new ClaimsPrincipal(identity);

        var props = new AuthenticationProperties
        {
            IsPersistent = dto.RememberMe,
            ExpiresUtc   = dto.RememberMe
                ? DateTimeOffset.UtcNow.AddDays(14)
                : DateTimeOffset.UtcNow.AddMinutes(30),
            AllowRefresh = true
        };

        await HttpContext.SignInAsync(
            CookieAuthenticationDefaults.AuthenticationScheme,
            principal,
            props);

        return Ok(new { user.Email, user.Role });
    }

    [HttpPost("logout")]
    [Authorize]
    public async Task<IActionResult> Logout()
    {
        await HttpContext.SignOutAsync(CookieAuthenticationDefaults.AuthenticationScheme);
        return NoContent();
    }

    [HttpGet("me")]
    [Authorize]
    public IActionResult Me() => Ok(new
    {
        Id    = User.FindFirstValue(ClaimTypes.NameIdentifier),
        Email = User.Identity!.Name,
        Role  = User.FindFirstValue(ClaimTypes.Role)
    });
}
```

## Step 6: `SignInAsync` explained, argument by argument

```csharp
await HttpContext.SignInAsync(
    CookieAuthenticationDefaults.AuthenticationScheme,   // (1)
    principal,                                           // (2)
    props);                                              // (3)
```

**(1) Scheme (`"Cookies"`).** Tells ASP.NET Core which registered authentication handler issues the sign-in. It must match the scheme in `AddAuthentication(...).AddCookie(...)`. With several schemes (cookie + JWT), this picks the right one.

**(2) `ClaimsPrincipal`.** The user's identity: a principal holds one or more `ClaimsIdentity` objects, each holding claims (name, role, id, etc.).

- **Gotcha:** the authentication type passed to `new ClaimsIdentity(claims, "Cookies")` must be non-empty. Without it, `User.Identity.IsAuthenticated` is `false` and `[Authorize]` rejects the user.
- Keep claims small. Everything is stored in the cookie, and cookies over about 4 KB get chunked.

**(3) `AuthenticationProperties`**

| Property | Meaning |
|---|---|
| `IsPersistent = false` | **Session cookie.** No `Expires` attribute; the browser deletes it when closed. |
| `IsPersistent = true` | **Persistent cookie.** Written with an `Expires` date; survives browser restarts ("Remember me"). |
| `ExpiresUtc` | Absolute expiry stored in the encrypted ticket. Overrides the global `ExpireTimeSpan` for this login. The server rejects the cookie after this time even if the browser still sends it. |
| `AllowRefresh = true` | Permits sliding expiration for this login. |

**Sliding expiration.** With `options.SlidingExpiration = true`, when a request arrives after more than half of the lifetime has passed, the middleware issues a new cookie with the lifetime window restarted. A 30-minute login stays alive while the user is active, and expires after 30 idle minutes.

**What happens inside `SignInAsync`**

1. Wraps your principal and properties in an `AuthenticationTicket`.
2. Serialises it, then encrypts and signs it with Data Protection (the key ring).
3. Adds `Set-Cookie: MyApp.Auth=<encrypted blob>; HttpOnly; Secure; SameSite=Lax` to the response.
4. Sets `HttpContext.User` for the rest of that request.

The user can't read or tamper with the cookie because they don't have the Data Protection keys.

## Step 7: How the cookie is validated on every later request

```
Browser sends Cookie: MyApp.Auth=...
        |
UseAuthentication() -> CookieAuthenticationHandler
        |  decrypt + verify signature       (fails -> anonymous user)
        |  check ticket ExpiresUtc          (expired -> anonymous user)
        |  run Events.OnValidatePrincipal   (your custom check)
        |  maybe renew cookie (sliding)
        |
HttpContext.User = principal from the cookie
        |
UseAuthorization() -> [Authorize] / roles / policies -> 200, 401 or 403
```

Without extra code, a cookie stays valid until expiry even if the user is deleted, disabled, or their password or role changes. `OnValidatePrincipal` closes that gap:

```csharp
options.Events.OnValidatePrincipal = async ctx =>
{
    var idClaim = ctx.Principal?.FindFirstValue(ClaimTypes.NameIdentifier);
    var stamp   = ctx.Principal?.FindFirstValue("security_stamp");

    if (!int.TryParse(idClaim, out var userId))
    {
        ctx.RejectPrincipal();
        await ctx.HttpContext.SignOutAsync(CookieAuthenticationDefaults.AuthenticationScheme);
        return;
    }

    var db   = ctx.HttpContext.RequestServices.GetRequiredService<AppDbContext>();
    var user = await db.Users.AsNoTracking().SingleOrDefaultAsync(u => u.Id == userId);

    if (user is null || !user.IsActive || user.SecurityStamp != stamp)
    {
        ctx.RejectPrincipal();   // treat the request as anonymous
        await ctx.HttpContext.SignOutAsync(CookieAuthenticationDefaults.AuthenticationScheme);
    }
};
```

When you change a password or role, or disable an account, set `user.SecurityStamp = Guid.NewGuid().ToString("N")`. Every existing cookie for that user dies on its next request. This costs a database hit per request; cache the lookup for a minute or so if that matters.

## Step 8: `SignOutAsync` explained

```csharp
[HttpPost("logout")]
[Authorize]
public async Task<IActionResult> Logout()
{
    await HttpContext.SignOutAsync(CookieAuthenticationDefaults.AuthenticationScheme);
    return NoContent();
}
```

- **`[HttpPost]`**: logout changes state, so it must not be a GET. A GET could be triggered by an `<img>` tag on another site ("logout CSRF"). Pair it with antiforgery validation for browser forms.
- **`[Authorize]`**: only logged-in users reach this action. For an idempotent logout that always succeeds, use `[AllowAnonymous]`; `SignOutAsync` is harmless without a cookie.
- **`SignOutAsync(scheme)`**: the cookie handler sends a `Set-Cookie` header for the same cookie name with an expired date, so the browser deletes it. It also fires `OnSigningOut`, a good place for audit logging.
- **`NoContent()`**: returns `204`. For MVC apps use `RedirectToAction("Login")`.

**Limitation:** cookie auth is stateless. Logout only deletes the browser's copy. If someone copied the cookie earlier, it stays valid until it expires. To truly revoke sessions, rotate the `SecurityStamp` on logout (logs the user out of all devices), or use a server-side `ITicketStore` for per-session revocation.

## Step 9: Complete `Program.cs` (manual approach)

```csharp
using System.Security.Claims;
using Microsoft.AspNetCore.Authentication;
using Microsoft.AspNetCore.Authentication.Cookies;
using Microsoft.AspNetCore.Identity;
using Microsoft.EntityFrameworkCore;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddDbContext<AppDbContext>(o =>
    o.UseSqlServer(builder.Configuration.GetConnectionString("Default")));

builder.Services.AddScoped<IPasswordHasher<AppUser>, PasswordHasher<AppUser>>();
builder.Services.AddScoped<UserService>();
builder.Services.AddControllers();

builder.Services.AddDataProtection()
    .PersistKeysToFileSystem(new DirectoryInfo("/keys"))
    .SetApplicationName("MyApp");

builder.Services
    .AddAuthentication(CookieAuthenticationDefaults.AuthenticationScheme)
    .AddCookie(options =>
    {
        options.Cookie.Name = "MyApp.Auth";
        options.Cookie.HttpOnly = true;
        options.Cookie.SecurePolicy = CookieSecurePolicy.Always;
        options.Cookie.SameSite = SameSiteMode.Lax;
        options.ExpireTimeSpan = TimeSpan.FromMinutes(30);
        options.SlidingExpiration = true;

        // API-friendly: 401/403 instead of redirects
        options.Events.OnRedirectToLogin = ctx =>
        {
            ctx.Response.StatusCode = StatusCodes.Status401Unauthorized;
            return Task.CompletedTask;
        };
        options.Events.OnRedirectToAccessDenied = ctx =>
        {
            ctx.Response.StatusCode = StatusCodes.Status403Forbidden;
            return Task.CompletedTask;
        };

        options.Events.OnValidatePrincipal = async ctx => { /* Step 7 code */ };
    });

builder.Services.AddAuthorization(o =>
{
    o.AddPolicy("AdminOnly", p => p.RequireRole("Admin"));
});

var app = builder.Build();

app.UseHttpsRedirection();
app.UseAuthentication();   // before UseAuthorization
app.UseAuthorization();
app.MapControllers();
app.Run();
```

### Authorizing endpoints

```csharp
[Authorize]                                  // any authenticated user
public class OrdersController : ControllerBase
{
    [HttpGet]
    public IActionResult List() => Ok();

    [Authorize(Roles = "Admin,Manager")]     // role-based
    [HttpDelete("{id}")]
    public IActionResult Delete(int id) => NoContent();

    [Authorize(Policy = "CanManageOrders")]  // policy-based (preferred)
    [HttpPut("{id}")]
    public IActionResult Update(int id) => NoContent();

    [AllowAnonymous]
    [HttpGet("public")]
    public IActionResult Public() => Ok();
}
```

Minimal API equivalent: `app.MapGet("/admin", () => "ok").RequireAuthorization("AdminOnly");`

Read the user in code with `User.FindFirstValue(ClaimTypes.NameIdentifier)` and `User.IsInRole("Admin")`.

### Redirect vs 401/403 for APIs and SPAs

By default, unauthenticated requests get a 302 redirect to the login page, which breaks `fetch`/Axios clients. Override `OnRedirectToLogin` and `OnRedirectToAccessDenied` as shown above. For apps that mix MVC pages and an API, only return status codes when `ctx.Request.Path.StartsWithSegments("/api")`.

# Part 2: Cookie Authentication with ASP.NET Core Identity

Identity replaces most of the hand-written code above. It provides user and role stores, password hashing, lockout, email confirmation, password reset, 2FA, and security-stamp validation. It still uses cookie authentication underneath.

## What Identity replaces

| Manual approach | With Identity |
|---|---|
| `AppUser` + `PasswordHash` + `SecurityStamp` | `IdentityUser` has these built in |
| `IPasswordHasher` + `UserService` | `UserManager<AppUser>` |
| `HttpContext.SignInAsync(principal)` | `SignInManager<AppUser>` |
| `OnValidatePrincipal` stamp check | Built in (`SecurityStampValidator`) |
| Manual duplicate-email check | `RequireUniqueEmail` + `CreateAsync` |
| Manual password rules | `options.Password` settings |
| No lockout | `lockoutOnFailure: true` |

## Step 3: Configure Identity in `Program.cs`

```csharp
using Microsoft.AspNetCore.Identity;
using Microsoft.EntityFrameworkCore;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddDbContext<AppDbContext>(o =>
    o.UseSqlServer(builder.Configuration.GetConnectionString("Default")));

builder.Services
    .AddIdentity<AppUser, IdentityRole>(options =>
    {
        // ---- Password rules (validation layer) ----
        options.Password.RequiredLength = 8;
        options.Password.RequireDigit = true;
        options.Password.RequireLowercase = true;
        options.Password.RequireUppercase = true;
        options.Password.RequireNonAlphanumeric = true;

        // ---- User rules ----
        options.User.RequireUniqueEmail = true;

        // ---- Lockout ----
        options.Lockout.MaxFailedAccessAttempts = 5;
        options.Lockout.DefaultLockoutTimeSpan = TimeSpan.FromMinutes(15);
        options.Lockout.AllowedForNewUsers = true;

        // ---- Sign-in ----
        options.SignIn.RequireConfirmedEmail = false;   // set true once email sending works
    })
    .AddEntityFrameworkStores<AppDbContext>()
    .AddDefaultTokenProviders();   // tokens for email confirmation, password reset, 2FA

// Configure the cookie that Identity creates ("Identity.Application")
builder.Services.ConfigureApplicationCookie(options =>
{
    options.Cookie.Name = "MyApp.Auth";
    options.Cookie.HttpOnly = true;
    options.Cookie.SecurePolicy = CookieSecurePolicy.Always;
    options.Cookie.SameSite = SameSiteMode.Lax;

    options.ExpireTimeSpan = TimeSpan.FromMinutes(30);
    options.SlidingExpiration = true;

    // API style: return status codes instead of redirects
    options.Events.OnRedirectToLogin = ctx =>
    {
        ctx.Response.StatusCode = StatusCodes.Status401Unauthorized;
        return Task.CompletedTask;
    };
    options.Events.OnRedirectToAccessDenied = ctx =>
    {
        ctx.Response.StatusCode = StatusCodes.Status403Forbidden;
        return Task.CompletedTask;
    };
});

// How often the security stamp is re-checked against the database
builder.Services.Configure<SecurityStampValidatorOptions>(o =>
    o.ValidationInterval = TimeSpan.FromMinutes(1));   // default is 30 minutes

builder.Services.AddAuthorization(o =>
{
    o.AddPolicy("AdminOnly", p => p.RequireRole("Admin"));
});

builder.Services.AddDataProtection()
    .PersistKeysToFileSystem(new DirectoryInfo("/keys"))
    .SetApplicationName("MyApp");

builder.Services.AddControllers();

var app = builder.Build();

// Seed roles once at startup
using (var scope = app.Services.CreateScope())
{
    var roles = scope.ServiceProvider.GetRequiredService<RoleManager<IdentityRole>>();
    foreach (var r in new[] { "Admin", "User" })
        if (!await roles.RoleExistsAsync(r))
            await roles.CreateAsync(new IdentityRole(r));
}

app.UseHttpsRedirection();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();
app.Run();
```

> **Important:** `AddIdentity` registers the cookie scheme itself. Do **not** also call `AddAuthentication().AddCookie(...)`, or you end up with two competing cookie setups. Customise the cookie only through `ConfigureApplicationCookie`.

## Step 6: Register, login, logout

```csharp
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Identity;
using Microsoft.AspNetCore.Mvc;

[ApiController]
[Route("api/auth")]
public class AuthController : ControllerBase
{
    private readonly UserManager<AppUser> _userManager;
    private readonly SignInManager<AppUser> _signInManager;

    public AuthController(UserManager<AppUser> userManager, SignInManager<AppUser> signInManager)
    {
        _userManager = userManager;
        _signInManager = signInManager;
    }

    // ---------------- REGISTER ----------------
    [HttpPost("register")]
    [AllowAnonymous]
    public async Task<IActionResult> Register(RegisterDto dto)
    {
        var user = new AppUser { UserName = dto.Email, Email = dto.Email };

        var result = await _userManager.CreateAsync(user, dto.Password);
        if (!result.Succeeded)
        {
            foreach (var e in result.Errors)
                ModelState.AddModelError(e.Code, e.Description);
            return ValidationProblem(ModelState);   // 400 with all Identity errors
        }

        await _userManager.AddToRoleAsync(user, "User");

        return Created(string.Empty, new { user.Id, user.Email });
    }

    // ---------------- LOGIN ----------------
    [HttpPost("login")]
    [AllowAnonymous]
    public async Task<IActionResult> Login(LoginDto dto)
    {
        var user = await _userManager.FindByEmailAsync(dto.Email);
        if (user is null)
            return Unauthorized(new { message = "Invalid email or password." });

        var result = await _signInManager.PasswordSignInAsync(
            user,
            dto.Password,
            isPersistent: dto.RememberMe,
            lockoutOnFailure: true);

        if (result.Succeeded)
            return Ok(new { user.Email });

        if (result.IsLockedOut)
            return StatusCode(StatusCodes.Status423Locked,
                new { message = "Account locked. Try again later." });

        if (result.IsNotAllowed)   // e.g. email not confirmed
            return StatusCode(StatusCodes.Status403Forbidden,
                new { message = "Please confirm your email first." });

        if (result.RequiresTwoFactor)
            return Ok(new { requiresTwoFactor = true });

        return Unauthorized(new { message = "Invalid email or password." });
    }

    // ---------------- LOGOUT ----------------
    [HttpPost("logout")]
    [Authorize]
    public async Task<IActionResult> Logout()
    {
        await _signInManager.SignOutAsync();
        return NoContent();
    }

    // ---------------- WHO AM I ----------------
    [HttpGet("me")]
    [Authorize]
    public async Task<IActionResult> Me()
    {
        var user = await _userManager.GetUserAsync(User);
        if (user is null) return Unauthorized();

        var roles = await _userManager.GetRolesAsync(user);
        return Ok(new { user.Id, user.Email, roles });
    }
}
```

## Step 7: What each piece does internally

### Registration: `UserManager.CreateAsync(user, password)`

1. Runs **user validation**: valid username and email, unique email if `RequireUniqueEmail` is set.
2. Runs **password validation** against `options.Password`. It collects all errors (too short, no digit, etc.) into `result.Errors` rather than failing on the first.
3. Normalises username and email into `NormalizedUserName` and `NormalizedEmail` (uppercase), which is why `A@x.com` and `a@x.com` collide.
4. Hashes the password with a random salt using PBKDF2 and stores it in `PasswordHash`.
5. Generates the initial `SecurityStamp` and saves the user.

It returns an `IdentityResult` and does not throw for validation failures, so always check `result.Succeeded`.

### Login: `SignInManager.PasswordSignInAsync(...)`

1. Checks whether the user is **locked out** (`LockoutEnd` in the future). If so, returns `IsLockedOut` without checking the password.
2. Checks whether sign-in is **allowed** (confirmed email or phone, if required).
3. Verifies the password hash.
4. On failure with `lockoutOnFailure: true`, increments `AccessFailedCount`; after `MaxFailedAccessAttempts` it sets `LockoutEnd`. Without this flag there is no brute-force protection.
5. On success, resets `AccessFailedCount`. If 2FA is enabled it returns `RequiresTwoFactor`. Otherwise it builds the `ClaimsPrincipal` (user id, name, roles, security stamp, stored claims) and issues the cookie.

`isPersistent` is the same "Remember me" concept as before: `false` gives a session cookie, `true` a persistent cookie.

For a per-login lifetime (such as 14 days for Remember me), sign in with custom properties after verifying the password yourself (for example with `CheckPasswordSignInAsync`):

```csharp
await _signInManager.SignInAsync(user, new AuthenticationProperties
{
    IsPersistent = true,
    ExpiresUtc = DateTimeOffset.UtcNow.AddDays(14)
});
```

### Logout: `SignInManager.SignOutAsync()`

Deletes the Identity application cookie and also clears the external-login and 2FA cookies, which raw `HttpContext.SignOutAsync` does not. To invalidate the session everywhere:

```csharp
var user = await _userManager.GetUserAsync(User);
await _userManager.UpdateSecurityStampAsync(user!);   // all existing cookies die
await _signInManager.SignOutAsync();
```

### Cookie validation on every request (built in)

Identity registers a `SecurityStampValidator`. Once `ValidationInterval` has passed (default 30 minutes), it loads the user and compares the stamp inside the cookie to the one in the database. If they differ, the cookie is rejected.

Identity changes the stamp automatically when the password changes, roles change, an external login is added or removed, or 2FA is toggled. A shorter interval means faster revocation but more database hits.

## Step 8: Authorization (roles, claims, policies)

```csharp
// Roles
await _userManager.AddToRoleAsync(user, "Admin");

// Claims (these end up inside the cookie at next sign-in)
await _userManager.AddClaimAsync(user, new Claim("permission", "orders.manage"));
```

```csharp
builder.Services.AddAuthorization(o =>
{
    o.AddPolicy("AdminOnly", p => p.RequireRole("Admin"));
    o.AddPolicy("CanManageOrders", p => p.RequireClaim("permission", "orders.manage"));
});
```

```csharp
[Authorize(Policy = "CanManageOrders")]
[HttpPut("orders/{id}")]
public IActionResult Update(int id) => NoContent();

[Authorize(Roles = "Admin")]
[HttpGet("admin/users")]
public IActionResult Users() => Ok(_userManager.Users.Select(u => u.Email));
```

Role and claim changes are baked into the cookie at sign-in. Existing sessions keep the old values until the stamp validator rejects them (after `UpdateSecurityStampAsync` and the validation interval) or the user signs in again.

## Step 9: Common extras

### Change password (keep the current session alive)

```csharp
[HttpPost("change-password")]
[Authorize]
public async Task<IActionResult> ChangePassword(ChangePasswordDto dto)
{
    var user = await _userManager.GetUserAsync(User);
    var result = await _userManager.ChangePasswordAsync(user!, dto.CurrentPassword, dto.NewPassword);
    if (!result.Succeeded) return BadRequest(result.Errors);

    await _signInManager.RefreshSignInAsync(user!);   // new cookie with the new stamp
    return NoContent();                               // other devices are signed out
}
```

Without `RefreshSignInAsync`, the user would be logged out on their own device too, because the stamp changed.

### Email confirmation

```csharp
// After CreateAsync in Register:
var token = await _userManager.GenerateEmailConfirmationTokenAsync(user);
var encoded = WebEncoders.Base64UrlEncode(Encoding.UTF8.GetBytes(token));
var link = $"https://yourapp.com/confirm-email?userId={user.Id}&token={encoded}";
// send `link` via your email service

[HttpGet("confirm-email")]
[AllowAnonymous]
public async Task<IActionResult> ConfirmEmail(string userId, string token)
{
    var user = await _userManager.FindByIdAsync(userId);
    if (user is null) return BadRequest();

    var decoded = Encoding.UTF8.GetString(WebEncoders.Base64UrlDecode(token));
    var result = await _userManager.ConfirmEmailAsync(user, decoded);
    return result.Succeeded ? Ok("Email confirmed.") : BadRequest(result.Errors);
}
```

Then set `options.SignIn.RequireConfirmedEmail = true`. Tokens are time-limited and tied to the security stamp. Password reset works the same way with `GeneratePasswordResetTokenAsync` and `ResetPasswordAsync`. In production, never return "user not found" from the forgot-password endpoint.

## Alternative: built-in Identity API endpoints (.NET 8+)

```csharp
builder.Services.AddIdentityApiEndpoints<AppUser>()
    .AddEntityFrameworkStores<AppDbContext>();

```

Call `/login?useCookies=true&useSessionCookies=false` to get a cookie. Without `useCookies=true` it returns bearer tokens, which are Identity's own opaque tokens, not JWTs. This is the fastest route for a simple app; a custom controller gives full control over responses and flow.

# Security Checklist

- **CSRF:** cookies are sent automatically by the browser, so protect state-changing requests. MVC/Razor Pages: `[AutoValidateAntiforgeryToken]`. Minimal APIs: `app.UseAntiforgery()` plus `.DisableAntiforgery()` only where intentional. `SameSite=Lax` or `Strict` helps but is not a full substitute.
- **Cookie flags:** keep `HttpOnly`, `Secure`, and `SameSite` set.
- **Data Protection keys:** in Docker or multi-instance deployments, persist and share the keys, otherwise cookies become invalid on every restart or across replicas. Use a shared store (Redis, Azure Blob, database) for multiple nodes.
- **Revocation:** a cookie stays valid until it expires. Use the security stamp (`OnValidatePrincipal` or Identity's validator) to invalidate stale sessions.
- **Passwords:** hash with `PasswordHasher<T>` or Identity. Never store plaintext.
- **Generic login errors:** don't reveal whether an email exists.
- **Rate limiting:** rate-limit login endpoints (`AddRateLimiter`) to slow brute-force attacks.

# Common Pitfalls

- `UseAuthentication()` placed after `UseAuthorization()` means `User` is always anonymous.
- A `ClaimsIdentity` without an authentication type is never "authenticated".
- Data Protection keys not persisted means everyone is logged out on every restart or deploy.
- Adding `AddCookie` on top of `AddIdentity`: use `ConfigureApplicationCookie` instead.
- Forgetting `lockoutOnFailure: true` leaves no brute-force protection.
- Ignoring `IdentityResult`: `CreateAsync`, `AddToRoleAsync`, and similar don't throw on failure.
- Role changes not applying immediately because roles live in the cookie. Call `UpdateSecurityStampAsync` after changing them.
- A SPA on a different origin needs `SameSite=None; Secure`, CORS with `AllowCredentials()`, and `credentials: "include"` on fetch. Antiforgery tokens become essential there.

# Cookies vs JWT

Cookies suit browser apps on the same site (MVC, Razor Pages, or a SPA served from the same domain or a BFF). They are simple, and `HttpOnly` keeps tokens away from JavaScript. JWT bearer tokens are better for mobile clients, third-party API consumers, and service-to-service calls.
