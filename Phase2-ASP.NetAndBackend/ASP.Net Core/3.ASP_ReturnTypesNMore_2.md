# IActionResult / ActionResult, ActionResult&lt;T&gt;

## IActionResult

**What it is:**

- An interface
- Represents any HTTP response

**When to use:**

- When your API can return multiple response types
  Example: 200, 400, 404, 500

**Example**

```csharp
[HttpGet("{id}")]
public IActionResult GetUser(int id)
{
    if (id <= 0)
        return BadRequest("Invalid ID");

    var user = GetFromDb(id);

    if (user == null)
        return NotFound();

    return Ok(user);
}
```

**Returns:**

- `BadRequest()` → 400
- `NotFound()` → 404
- `Ok()` → 200

👉 You can return anything implementing `IActionResult`

> **Note:**
>
> - Can return any result type (`OkResult`, `NotFoundResult`, `RedirectResult`, etc.)
> - No compile-time knowledge of the response body type
> - Swagger/OpenAPI can't infer the success response schema without `[ProducesResponseType]`

## ActionResult (Concrete Base Class)

**What it is:**

- A class that implements `IActionResult`
- Enables implicit casting so a specific type `T` can be returned directly (e.g., `return data` instead of
  `return Ok(data)`)

**When to use:**

- Rarely used directly in modern APIs
- Mostly internal base class

## ActionResult&lt;T&gt; (BEST PRACTICE 🔥)

**What it is:**

- A generic wrapper
- Combines:
  - Strongly typed response (`T`)
  - HTTP responses (`BadRequest`, `NotFound`, etc.)

**Why it's best:**

- Strong typing
- Better Swagger/OpenAPI docs
- Cleaner code
- Supports both:
  - `return T`
  - `return IActionResult`

✅ **Example**

```csharp
[HttpGet("{id}")]
public ActionResult<UserDto> GetUser(int id)
{
    if (id <= 0)
        return BadRequest("Invalid ID");

    var user = GetFromDb(id);

    if (user == null)
        return NotFound();

    return user; // automatically 200 OK
}
```

🔥 **Magic Behind It**

```csharp
return user;
```

👉 Internally becomes:

```http
200 OK
{
  "id": 1,
  "name": "Aman"
}
```

🔹 **When Returning Explicit Status**

```csharp
return Ok(user);        // 200
return Created(...);    // 201
return NoContent();     // 204
return BadRequest();    // 400
return NotFound();      // 404
```

## Example:

```csharp
[HttpPost]
public IActionResult CreateUser(CreateUserRequest request)
{
    if (!ModelState.IsValid)
        return BadRequest(ModelState);   // 400

    if (_repo.EmailExists(request.Email))
        return Conflict("Email already exists"); // 409

    var user = _repo.Create(request);

    return CreatedAtAction(nameof(GetUser), new { id = user.Id }, user); // 201
}
```

# Rule of Thumb

- Single return type, always 200? → Return `T` directly (plain method return)
- Mix of success + error responses? → Use `ActionResult<T>`
- Multiple unrelated result types? → Fall back to `IActionResult`

# [ProducesResponseType]

The `ProducesResponseType` attribute in ASP.NET Core is used to explicitly declare the HTTP status codes and
response types that a controller action can return, primarily to generate accurate OpenAPI/Swagger
documentation. It defines the contract between the API and its consumers by specifying which types (e.g.,
`typeof(Product)`) correspond to which status codes (e.g., `StatusCodes.Status200OK` or `StatusCodes.Status404NotFound`).

**Basic Usage**

```csharp
[HttpGet("{id}")]
[ProducesResponseType(typeof(Product), StatusCodes.Status200OK)]
[ProducesResponseType(StatusCodes.Status404NotFound)]
public IActionResult Get(int id)
{
    var item = _repo.Find(id);
    if (item == null) return NotFound();
    return Ok(item);
}
```

**Overloads**

```csharp
// Type + status code
[ProducesResponseType(typeof(Product), 200)]

// Status code only (no body, or body type inferred)
[ProducesResponseType(404)]

// Using StatusCodes constants (preferred — avoids magic numbers)
[ProducesResponseType(typeof(ValidationProblemDetails), StatusCodes.Status400BadRequest)]
```

## With ActionResult&lt;T&gt; — Less Boilerplate

When you use `ActionResult<T>`, the 200 response type is inferred automatically — you only need to annotate
the error codes:

```csharp
[HttpGet("{id}")]
[ProducesResponseType(StatusCodes.Status404NotFound)]   // only errors needed
public ActionResult<Product> Get(int id)               // 200 + Product inferred
{
    var item = _repo.Find(id);
    if (item == null) return NotFound();
    return item;
}
```

## Generic Version (ASP.NET Core 6+)

Avoids `typeof()` — cleaner syntax:

```csharp
[ProducesResponseType<Product>(StatusCodes.Status200OK)]
[ProducesResponseType<ValidationProblemDetails>(StatusCodes.Status400BadRequest)]
```

# Type of return value : Controller

## Ok() / Ok(object) → 200 OK

Use this when the request succeeded. `Ok()` returns an empty 200 OK, and `Ok(object)` returns 200 OK with a body.

```csharp
[HttpGet("{id}")]
public IActionResult GetUser(int id)
{
    var user = _repo.GetById(id);

    if (user == null)
        return NotFound();

    return Ok(user); // 200 OK
}
```

## Created(), CreatedAtAction(), and CreatedAtRoute()

`Created()`, `CreatedAtAction()`, and `CreatedAtRoute()` are ASP.NET Core methods used to return a 201 Created HTTP status code with a `Location` header
pointing to the newly created resource. While all three produce similar responses, they differ in how the URI for the `Location` header is generated.

### Created()

The `Created()` method gives you full control over the URI by accepting a string or `Uri` directly. This is useful when you need to craft the URL
manually, such as when behind a load balancer where headers like `X-Forwarded-For` influence the final address. However, you are responsible for
ensuring the URI is correct and exists on the server.

```csharp
// Example: Using a custom URI string
var uri = $"https://api.example.com/items/{newId}";
return Created(uri, newResource);

// Example: Using a Uri object
var uri = new Uri($"https://api.example.com/items/{newId}");
return Created(uri, newResource);
```

### CreatedAtAction()

`CreatedAtAction()` generates the URI based on the name of an action method (e.g., `GetItem`) within the same or a different controller. It is
generally preferred for its safety, as the framework automatically generates the URL based on existing route configurations, reducing the risk of
typos. You can specify the action name, controller name, and route values (like an ID).

```csharp
// Example: Referencing the action by name within the same controller
return CreatedAtAction(nameof(GetItem), new { id = newId }, newResource);

// Example: Referencing an action in a different controller
return CreatedAtAction("GetItem", "Items", new { id = newId }, newResource);
```

### CreatedAtRoute()

`CreatedAtRoute()` generates the URI based on a named route defined in the application's routing configuration. This requires the target GET action
to have a `Name` attribute (e.g., `[HttpGet("{id}", Name = "GetItem")]`). It is particularly useful when routes are defined centrally or when the
action method name differs from the route name.

```csharp
// Example: Referencing a named route
// Assumes [HttpGet("{id}", Name = "GetItem")] exists on the GET action
return CreatedAtRoute("GetItem", new { id = newId }, newResource);
```

## Accepted() / AcceptedAtAction() / AcceptedAtRoute() → 202 Accepted

Use these when the request is accepted but processing will finish later, such as a background job or queue-based workflow.

The 202 HTTP Status Code is known as "Accepted". It is a success response code indicates that the request has been accepted for processing, but the
processing has not been completed. It is a way to acknowledge the client that the request has been accepted for processing, but the outcome is not
immediately available.

- **Request Accepted:**
  The server has received the request and will process it, but the processing may not be completed immediately.

- **Not a Guarantee of Success:**
  A 202 status code does not indicate that the final processing of the request will be successful; it states that the initial request was valid
  and has been accepted for processing. The final outcome of the request should be checked once the processing has been completed.

- **Asynchronous Operations:**
  Often used for asynchronous operations where the server will process the request in the background, and the client does not need to wait for the operation to complete.

- **Response Payload:**
  The response to a 202 status code typically includes information on how to monitor the progress of the request. This could be in the form of a
  URL pointing to a status endpoint where the client can obtain information about the ongoing processing or details on how long the client should
  wait before checking the status.

**Example:**

```csharp
[HttpPost]
public async Task<IActionResult> CreateJobAsyncWithoutData()
{
    // Start the asynchronous processing without blocking the thread.
    // The LongRunningTask will take 120 seconds to complete.
    // The main thread will not be blocked until the LongRunningTask is completed.
    LongRunningTask();

    // Return 202 Accepted status code without any data.
    return Accepted();
}

private async Task LongRunningTask()
{
    // Simulate a long-running task with a 120 seconds delay.
    await Task.Delay(TimeSpan.FromSeconds(120));
    // Task logic goes here (not implemented in this example).
}
```

## NoContent() → 204 No Content

Use this when the operation succeeded and there is nothing to return, which is common for update and delete endpoints. `NoContent()` returns an empty
204 No Content response.

```csharp
[HttpDelete("{id}")]
public IActionResult DeleteUser(int id)
{
    var deleted = _repo.Delete(id);

    if (!deleted)
        return NotFound();

    return NoContent(); // 204 No Content
}
```

## BadRequest() → 400 Bad Request

Use this for invalid input, failed model validation, or request data that does not meet your API rules. `BadRequest()` and `BadRequest(object)` both
produce 400 Bad Request.

```csharp
[HttpPost]
public IActionResult CreateUser(CreateUserDto dto)
{
    if (string.IsNullOrWhiteSpace(dto.Email))
        return BadRequest("Email is required"); // 400

    return Ok();
}
```

A very common pattern is `return BadRequest(ModelState);` when model binding or validation fails.

## Unauthorized() → 401 Unauthorized

Use this when the caller is not authenticated, for example when the token is missing, invalid, or expired. `Unauthorized()` produces 401 Unauthorized.

```csharp
[HttpGet("profile")]
public IActionResult GetProfile()
{
    if (User?.Identity?.IsAuthenticated != true)
        return Unauthorized(); // 401

    return Ok();
}
```

## Forbid() → 403 Forbidden

Use this when the user is authenticated but does not have permission. Microsoft documents `Forbid()` as producing 403 Forbidden by default.

```csharp
[HttpDelete("{id}")]
public IActionResult DeleteUser(int id)
{
    if (!User.IsInRole("Admin"))
        return Forbid(); // 403

    return NoContent();
}
```

## NotFound() → 404 Not Found

Use this when the requested resource does not exist. `NotFound()` returns 404 Not Found, and `NotFound(object)` can include an error body.

```csharp
[HttpGet("{id}")]
public IActionResult GetUser(int id)
{
    var user = _repo.GetById(id);

    if (user == null)
        return NotFound($"User {id} not found"); // 404

    return Ok(user);
}
```

## Conflict() → 409 Conflict

Use this when the request cannot be completed because of a conflict with the current state, such as duplicate email, duplicate order number, or
concurrency conflict. `Conflict()` produces 409 Conflict.

```csharp
[HttpPost]
public IActionResult CreateUser(CreateUserDto dto)
{
    if (_repo.EmailExists(dto.Email))
        return Conflict("Email already exists"); // 409

    var user = _repo.Create(dto);
    return CreatedAtAction(nameof(GetUser), new { id = user.Id }, user);
}
```

## UnprocessableEntity() → 422 Unprocessable Entity

Use this when the request format is valid, but the business rule fails. Microsoft documents `UnprocessableEntity()` as producing 422
UnprocessableEntity, and the overloads can also return a body.

```csharp
[HttpPost("orders")]
public IActionResult PlaceOrder(CreateOrderDto dto)
{
    if (dto.Quantity <= 0)
        return UnprocessableEntity("Quantity must be greater than zero"); // 422

    return Ok();
}
```

A useful mental model is: 400 for malformed/invalid request data, 422 for valid data that breaks business rules. That distinction is a design
choice you make in your API.

## Problem() → Problem Details response

Use `Problem()` for standardized error responses based on `ProblemDetails`. Microsoft documents `Problem(...)` as creating an `ObjectResult` that produces a `ProblemDetails` response.

```csharp
[HttpGet("boom")]
public IActionResult Boom()
{
    return Problem(
        title: "Unexpected error",
        detail: "Something failed while processing the request",
        statusCode: 500);
}
```

## ValidationProblem() → validation error response

Use `ValidationProblem()` when model validation fails and you want a structured validation response. Microsoft documents that `ValidationProblem()` produces a 400 Bad Request response with validation errors from `ModelState`.

```csharp
[HttpPost]
public IActionResult CreateUser(CreateUserDto dto)
{
    if (!ModelState.IsValid)
        return ValidationProblem(ModelState); // 400 with validation details

    return Ok();
}
```

**What is ValidationProblem in ASP.NET Core**

`ValidationProblem` is a standardized way to return validation errors (HTTP 400 Bad Request) in Web APIs.
It returns a `ProblemDetails` response (RFC 7807 format) with structured error info.

🔹 **When it is used**

- Model validation fails (`[ApiController]` auto-handles this)
- Manual validation in controller/service
- Returning consistent API error responses

If invalid input is sent, ASP.NET Core automatically returns:

```json
{
  "type": "https://tools.ietf.org/html/rfc7231#section-6.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": {
    "Name": ["The Name field is required."],
    "Email": ["The Email field is not a valid e-mail address."]
  }
}
```

### Manual ValidationProblem

Use when you want custom validation logic.

```csharp
[HttpPost]
public IActionResult Create(CreateUserRequest request)
{
    if (string.IsNullOrEmpty(request.Name))
    {
        ModelState.AddModelError("Name", "Name is required");
    }

    if (!ModelState.IsValid)
    {
        return ValidationProblem(ModelState);
    }

    return Ok("User created");
}
```

**Important: [ApiController] behavior**

When you use `[ApiController]`:

- Automatically checks `ModelState`
- Automatically returns `ValidationProblem`
- You don't need:

  ```csharp
  if (!ModelState.IsValid)
  ```

## StatusCode(int, object) → custom status code

Use this when none of the built-in helpers fit exactly. `StatusCode(int, object)` creates an `ObjectResult` with the status code you specify, and
`StatusCode(int)` returns a plain status code result.

```csharp
[HttpGet("maintenance")]
public IActionResult Maintenance()
{
    return StatusCode(503, "Service is temporarily unavailable"); // custom code
}
```

# How to remember this in interviews

- 200 = success with data,
- 201 = created, 202 = accepted for later work,
- 204 = success with nothing to return,
- 400 = bad request, 401 = not authenticated,
- 403 = authenticated but not allowed,
- 404 = missing resource,
- 409 = conflict,
- 422 = business rule failure, and `Problem()` /
  `ValidationProblem()` give you standardized error payloads.

# Accessing request headers

In ASP.NET Core Web API, you can access request headers through the `Request.Headers` property, which is available inside controllers, minimal APIs, or middleware. It's an `IHeaderDictionary`, so you can query it like a dictionary.

✅ **Examples**

**1. Inside a Controller**

```csharp
[HttpGet]
public IActionResult GetData()
{
    // Access by header name
    var userAgent = Request.Headers["User-Agent"].ToString();
    var customHeader = Request.Headers["X-Custom-Header"].ToString();

    return Ok(new { userAgent, customHeader });
}
```
